Enable SSH on Steam Deck: Secure Remote Access

By Brittany Coleman • Published March 10, 2026

You want SSH on Steam Deck to allow remote access without drama. This walkthrough assumes Desktop Mode with Konsole available, and it guides you from setting a password to enabling the OpenSSH service. You will hear the subtle fan ramp as the device wakes its network, feel the small pause after Enter, and notice a satisfying status line confirming success. We will focus on safe defaults, explain why each choice matters, and point out reversible changes when filesystem protections are involved. By the end, your Steam Deck will accept SSH connections reliably, and you will know exactly how to verify, harden, and troubleshoot the setup with minimal guesswork.

Key takeaways

  • Set a strong password for the deck user before starting SSH.
  • Start and enable sshd with systemctl to persist across reboots.
  • Prefer key-based login and disable password authentication when feasible.
  • Reapply SteamOS read-only protection after editing sshd_config settings.
  • Verify connectivity with local ssh and a remote client test.

Plan the work

The first decision is scope, because SSH access can be local network only or exposed through port forwarding. Start with LAN-only access while you learn the basics, then reconsider exposure after you layer keys and firewall rules. For example, a home router with no forwarding keeps sshd reachable only from your Wi-Fi, which reduces unsolicited scans. The tradeoff is that off-site administration stays unavailable until you configure a secure tunnel or reverse proxy. Choosing a narrow initial scope reduces risk while you validate connections and confirms that your Steam Deck responds as expected within a controlled environment.

The next choice is authentication, which affects both convenience and safety. Password login works quickly once you set a strong deck user password, yet it is easier to brute-force if an external port is opened. Key-based authentication replaces repeated passwords with a private key, improving resilience when combined with a passphrase and limiting options like PubkeyAuthentication only. The constraint is managing keys across laptops and desktops, which adds setup time. Decide early which method you will support, then align your sshd_config settings to allow only the method you intend to maintain over time.

Finally, plan your rollback steps, since SteamOS uses a read-only root by default that protects system files. Editing /etc/ssh/sshd_config requires temporarily disabling that protection, then enabling it again to preserve integrity. A simple rule is to batch related changes, test them, and restore read-only mode in the same session. For instance, apply PermitRootLogin no and PasswordAuthentication no together after confirming key-based access works. The benefit is predictable state and fewer surprises during updates. This approach keeps your Steam Deck secure and tidy while minimizing the window where system files are writable.

Prepare environment

Preparation begins with Desktop Mode and Konsole, because you need a terminal to configure OpenSSH reliably. Confirm network connectivity with a quick ping to your router or an IP you trust, which ensures DNS and routing behave before you blame sshd. Set or update the deck user password with passwd, selecting at least twelve characters and a mix of types. A strong password shores up security if you keep PasswordAuthentication enabled during setup. The tradeoff is memorability versus entropy, so consider a passphrase you can type steadily on the Steam Deck’s keyboard without introducing repetitive patterns that weaken protection.

Understand filesystem protections next, since SteamOS mounts the root filesystem read-only by default. You can start and enable sshd without modifying config files, but any change to /etc/ssh/sshd_config needs write access. Use steamos-readonly disable with caution, make your edits, then run steamos-readonly enable. This rhythm keeps changes explicit and short-lived, limiting accidental tweaks. The limitation is that package updates may overwrite files in future releases, so keep a brief note of your edits. A simple rule is to prefer drop-in files under /etc/ssh/sshd_config.d when available to avoid merging conflicts later.

Gather your client-side tools as a final preflight, because testing from both ends catches subtle issues early. On the Steam Deck, confirm ssh is installed with pacman -Qi openssh or simply check ssh -V. On your laptop, prepare an SSH client, then decide whether to generate an ed25519 key with ssh-keygen for key-based access. If you plan to transfer files later, have scp or an SFTP client ready. Execute steps

Execution starts with service control, because sshd must be started and enabled to persist across reboots. The minimal path is to set a password for the deck user, start the service, and ensure it is enabled now and on boot. The why is straightforward: systemd manages services, and OpenSSH integrates with it on SteamOS. You should feel a calm pace here, with each command yielding a simple status line and no error noise. After these actions, sshd listens on port 22 by default. If a firewall blocks the port on your network, resolve that before altering OpenSSH settings that are correct by default.

Before hardening, verify access using a local test on the Steam Deck and a second test from another machine. A loopback ssh to localhost confirms the daemon accepts credentials and that PAM integration functions. Then a remote ssh from your laptop ensures routing and keys work as expected. Only after you have proof of working authentication should you modify sshd_config options like PasswordAuthentication or PermitRootLogin. This pattern avoids locking yourself out. If your threat model expects external exposure, plan to disable password logins and use ed25519 keys with a passphrase while keeping a recovery console or USB keyboard nearby.

When editing configuration, apply changes in one small batch, restart sshd, and test immediately. If you need to allow key-only access, set PasswordAuthentication no after confirming keys are in place. If you target a nonstandard port, update the Port directive and document it to prevent confusion with other tools. The constraint is that some routers and corporate networks block arbitrary ports, so do not assume obscurity equals safety. Always combine key-based authentication with clear audit steps like reading journalctl -u sshd for warnings. A clean log and a successful test connection tell you the service behaves as intended.

  1. Set the user password: run passwd for deck and store it securely.
  2. Start sshd now: use systemctl start sshd to launch the service.
  3. Enable on boot: run systemctl enable sshd or systemctl enable --now.
  4. Test locally: use ssh deck@localhost and exit after a prompt appears.
  5. Test remotely: connect from another device using the Deck’s IP address.

Validate results

Validation begins on the device to isolate problems before they reach the network. Use systemctl is-active sshd to confirm the service reports active, then run ss -tlnp | grep 22 to check that port 22 is listening. A quick ssh deck@localhost ensures PAM prompts appear correctly and that the shell opens. The benefit of this order is fast feedback with minimal variables. If localhost login fails, the issue is authentication or sshd_config, not routing. Correct locally first, and you will avoid chasing phantom network issues that hide the true configuration problem on the Steam Deck itself.

Next, validate addressing and names, because reachability depends on accurate IP information. On the Steam Deck, run ip addr show and note the IPv4 address for your Wi-Fi interface. From your laptop, connect using ssh deck@that.ip.address to bypass DNS. If this works, you can later add a hosts entry or configure mDNS for convenience. If it fails, check for a firewall on your laptop or router that blocks port 22. The tradeoff when using hostnames is convenience versus occasional name resolution hiccups that produce delays, so favor the raw IP on first attempts to reduce ambiguity.

Finally, confirm your chosen authentication path with a realistic workflow. If using keys, ensure your public key lives in ~/.ssh/authorized_keys on the Steam Deck with permissions set to 600 for the file and 700 for the .ssh directory. Test an ssh connection that leverages the key and expects no password. If using passwords, attempt two successful logins in a row to confirm no intermittent PAM issues appear. Review journalctl -u sshd for warnings about permissions, methods refused, or syntax errors. Clean logs and reliable connections indicate your setup is production-ready for everyday remote administration tasks.

Troubleshoot and optimize

When SSH fails, start by reading error text closely, because messages usually point to the layer at fault. A refused connection points to a stopped daemon or blocked port, while a prompt without acceptance indicates authentication trouble. Use systemctl status sshd and journalctl -u sshd to narrow scope. If the log mentions bad ownership or mode, fix permissions on ~/.ssh and authorized_keys. A measured rhythm helps here: make one change, test, and then proceed. This cadence prevents compounding mistakes and makes it easier to undo a single misstep rather than rolling back a pile of guesses.

Once working, reduce attack surface with a few principled changes. Disable PermitRootLogin by setting it to no, prefer PubkeyAuthentication yes, and consider PasswordAuthentication no after validating your keys. If you must keep passwords, pick a long passphrase and set MaxAuthTries to a modest value like three. The tradeoff is lockout risk, which you mitigate by ensuring a local console or recovery input is available. After each edit, restart sshd and retest. This cycle preserves usability while raising the bar for brute-force attempts and keeps your Steam Deck’s remote access aligned with sensible security practices.

Frequently asked questions

Do I need to disable SteamOS read-only to start sshd?

No. Starting and enabling the service does not require filesystem changes. Disable read-only only when editing sshd_config and restore protection after restarting the service.

What is the default SSH username on Steam Deck?

The default user is deck. Ensure deck has a strong password or that your public key is in ~/.ssh/authorized_keys with correct permissions before disabling password authentication.

How do I find the Steam Deck’s IP address?

Run ip addr show and look for the IPv4 address on your active interface. Alternatively, check the connection details in KDE’s network applet while connected to your Wi-Fi.

Why does my SSH key fail with permission denied?

Incorrect permissions usually cause key rejection. Set ~/.ssh to 700 and ~/.ssh/authorized_keys to 600 on the Steam Deck, then retry and review journalctl -u sshd for hints.

Should I change the SSH port for security?

Changing the port reduces noise from scans but is not a substitute for proper authentication. Use key-based login and disable root access regardless of which port you select.
