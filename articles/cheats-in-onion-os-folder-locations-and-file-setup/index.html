Cheats in Onion OS: Folder Locations and File Setup

By Jordan Kelly • Published February 1, 2026

Cheats in Onion OS ride on emulator behavior, so folder placement and file naming determine whether codes appear in menus. Most setups rely on RetroArch cores that look for .cht or compatible lists, while some standalone cores read their own formats. Treat cheats like configs rather than ROM content, because they follow cores and regions more than file system labels. A good baseline is to mirror the core’s expectations for files and directories, then adjust naming to match the exact ROM label or content hash. That approach avoids confusion when switching handhelds or updating cores, and it prevents silently missing entries during play. In this guide, we define expected locations, formats, and naming rules, then show practical choices and tradeoffs that keep everything tidy.

Key takeaways

  • Match cheat filenames to the ROM name the core recognizes.
  • Prefer per core folders so updates do not collide files.
  • Use core native formats first, then convert only if needed.
  • Verify region and revision tags to avoid mismatched addresses.
  • Test with clean states because cheats can poison saves.

Concepts and definitions

Cheat systems inside Onion OS generally follow the emulator core, which is why folder location and file formats matter. RetroArch-based cores look for .cht files by default, while some standalones accept plaintext lists or proprietary structures. A useful mental model is that cheats attach to the content identity the core sees, not the visible folder where a ROM lives. For example, a file named after the ROM’s base label loads more reliably than a nickname, because the core matches the filename it indexed. This is also why region tags like USA or Europe change address maps, making a universal list risky. When uncertain, start with a per core cheats directory and one file per game, then confirm in the core’s menu that entries populate and toggle correctly.

Folder placement usually sits under the emulator’s configuration path, not under ROMs, which keeps lists portable when you move content. In many builds, RetroArch expects a cheats directory alongside its config, with subfolders for each system or core to reduce collisions. That separation helps when multiple cores can run the same platform, because each core may parse options differently. If a handheld build exposes a different layout, check the core’s directory settings and align to its reported cheats path rather than improvising a custom tree. Consistency reduces subtle failures when you update Onion OS or swap SD cards. For organization, mirror system names and ensure filenames mirror the ROM label visible in the playlist, including region tags and revision if the list shows one.

File formats affect what options appear and how safely they toggle during play. RetroArch .cht files store entries with names, types, and default states, while simple TXT lists from legacy devices may need conversion. Built in database packs often exist, but they may not match patched or fan translated builds. Treat them as a starting point and layer a custom per game file that matches your exact ROM. Keep entries minimal to avoid cluttered menus and to reduce the chance of overlapping addresses that break physics or progression. When a cheat depends on frame timing, expect occasional instability and keep a clean savestate ready. That habit preserves progress if an experimental code locks the core or corrupts memory temporarily.

Frameworks and decision lenses

Choose format by starting with what the core supports natively, then convert only when a code is unavailable in that syntax. RetroArch .cht is a safe default for its cores because it preserves toggle states and descriptions. Next, decide folder scope by mapping cheats per core rather than per platform, which avoids cross parser conflicts. For naming, match the ROM filename the playlist shows, not the dump’s internal title, and include region or revision if present. This framework reduces ambiguity when a series has many versions. Lastly, consider maintainability: one file per game is easier to audit than giant lists. The tradeoff is more files, but search is faster and entries remain coherent, preventing accidental toggles applied to the wrong release.

When you build your structure, align it with broader content hygiene so cheats and ROMs stay discoverable together without cohabiting folders. A clean library benefits from accurate folders and naming across ROMs, BIOS, and artwork, which keeps playlists predictable. As a follow up, ensure the ROM is not a patched variant with shifted addresses. Pitfalls, limitations, and edge cases

Mismatched filenames are the most common reason a cheats menu appears empty, since many cores compare the visible ROM label to the cheat filename. Another frequent issue is region or revision drift, where a code written for a Japanese release fails on a US build due to different memory maps. To mitigate, add region tags consistently and verify the exact build in your playlist. A second category involves parser differences between cores, which can silently ignore certain fields. Separating per core directories reduces this risk. For broader library hygiene that supports cheats and artwork together, learn how to keep folder structures clean with accurate ROMs, BIOS, saves, and art: keep the structure tidy.

Save states can hold altered values from enabled cheats, which complicates testing. If you disable a code but load an old state that preserved the effect, you may misdiagnose behavior. The simple remedy is to maintain one clean state per game specifically for testing and to save over it only when confirmed stable. Another limitation is performance impact. Some codes write frequently and can increase CPU work on modest handhelds, causing stutter. If you notice hitching, disable high frequency toggles or prefer static patches that do not run every frame. Lastly, expect that some anti cheat routines exist in certain games and may react unpredictably to injected values, so proceed incrementally and watch for signs like corrupted HUD elements.

Multi disc titles and patched translations introduce harder edges where content hashes diverge from databases. In these cases, bundled cheat packs will rarely match perfectly. Build a minimalist .cht with only essential entries and label it clearly with region and disc indicator if applicable. When you change cores for better compatibility, do not reuse the same cheat file until you confirm the new core’s parser. If your setup also includes renamed ROMs for cleanliness, ensure your artwork scraper and cheat files both track the same naming rule to avoid drift. For more naming discipline across your library that supports cheats and scraping together, check guidance on regional tagging and conventions in related resources when needed.

Frequently asked questions

Do cheat files belong in ROM folders?

No. Store cheats under the emulator’s cheats directory so updates and cores can find them consistently without mixing with content.

Why do cheats not show up in the core menu?

Most often the cheat filename does not match the playlist label, the region differs, or the core’s cheats path points to another directory.

Can I share one cheat file across multiple cores?

It is safer to keep separate files per core because parsers and features vary. Shared files can be misread or silently ignored.

Do cheats affect save states?

Yes. Save states can preserve altered values, so test with a clean state and disable codes before saving long term progress.

Is converting text codes to .cht reliable?

Often yes if addresses are correct. Keep entries minimal, verify in game, and avoid frame intensive writes on lower power devices.
