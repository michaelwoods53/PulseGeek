Throughput vs Airtime Graphs for 320 MHz

By Rachel Morgan • Published February 24, 2026

Throughput and airtime are tightly coupled on ultra wide 320 MHz channels, and small misreads can trigger poor tuning choices. This piece explains how to interpret graphs that plot delivered throughput against consumed airtime, so you can separate useful load from waste. We focus on practical signals like retry rate, modulation stability, and latency dispersion, because those reveal whether the airtime curve is efficient or noisy. The guidance applies to greenfield 6 GHz as well as mixed environments where legacy devices and DFS events reshape behavior. The target reader is a network engineer or architect tasked with capacity planning and post‑deployment validation for high density or high throughput areas.

Key takeaways

  • Saturation appears as a knee where airtime rises faster than throughput.
  • Retry spikes flatten graphs by consuming airtime without useful delivery.
  • Use fixed load baselines to compare 160 and 320 MHz fairly.
  • Plot median latency bands to reveal scheduling or queuing stress.
  • Normalize by client count to avoid misleading per‑AP interpretations.

Concepts and definitions

The core idea is that an airtime axis measures medium occupancy while throughput measures useful payload delivered, and their relationship changes with channel width. On 320 MHz, the same packetized load should require less airtime than on 160 MHz when signal quality and scheduling remain stable, because more resource units are available for parallelization. A clean graph shows a near linear region at modest loads, then a knee where contention, aggregation limits, or modulation fallback begin. A practical example is a lab test pushing 400 Mbps increments while recording retries and MCS distribution. If retries rise above a threshold and MCS spreads downward, airtime increases faster than throughput. The limitation is that some controllers approximate airtime using sampled duty cycles, so confirm whether your platform measures PHY occupancy or infers it from counters.

Definitions matter before comparing plots, because different tools label similar fields differently. Airtime can mean transmitter airtime, total medium busy time, or scheduler time per BSS, and each variant changes interpretation. Throughput can be MAC throughput, TCP goodput, or application payload after TLS, which affects how stark the knee appears. A reliable approach is to align definitions with test goals, like using MAC throughput when evaluating frame aggregation and using TCP goodput when modeling real user sessions. For example, if you trend TCP throughput against medium busy time, encryption overhead and MSS tuning will shift the curve’s shape. The tradeoff is precision versus portability, since highly specific metrics may not be available across vendors, but comparability across sites often outweighs theoretical purity.

Reading order also shapes decisions, so establish a consistent workflow for graphs. Start by scanning the low load region for near proportional growth, which indicates clean spectrum and stable modulation. Next, locate the knee where additional airtime yields diminishing throughput gains, often coinciding with rising retries or buffer buildup. Finally, inspect tail behavior at peak offered load, since a flat throughput plateau with climbing airtime signals contention rather than RF impairment. As an example, if you see latency variance widen while throughput stalls, look for queue depth and EDCA contention ratios. An edge case occurs when multi link operation balances load across links, masking knees on a per link view. In that case, a combined plot prevents optimistic readings on individual links.

Frameworks and decision lenses

A strong decision lens starts with axis choice, because the wrong pairing obscures causality. Plot delivered throughput on the Y axis and total medium busy time or scheduler airtime on the X axis, then color by retry rate or MCS median to expose efficiency. For 320 MHz, add separate panels for 160 MHz using the same offered load to ensure apples to apples comparison. In practice, run fixed step loads like 25, 50, 75, and 100 percent of a defined baseline while holding packet mix constant. The advantage is clear knees and consistent curves that expose when width helps. The limitation is that real networks experience burstiness, so supplement with percentile bands for latency to see how queues behave during spikes without overfitting to lab smoothness.

Normalization prevents misleading optimism on ultra wide channels, so adjust for client count and flow type. Divide throughput by active clients to reveal per user experience, then map airtime per client to check fairness. As an example, a site with ten laptops might show stellar aggregate throughput while two voice handsets suffer if WMM configuration starves voice queues. Include an annotation for voice airtime share and packet loss to surface this mismatch. A tradeoff exists when per client data is sampled sparsely by certain controllers, which can jitter the curve. When sampling limits apply, use a moving median or bucket by one minute intervals to smooth noise, and document that limitation in your analysis notes to avoid false confidence.

Baselines make comparisons defensible, so define a reference mix and RF floor before charting. Set transmit power, guard interval, and minimum MCS policies, and record noise floor and channel occupancy with neighboring APs idle. For 320 MHz, write down puncturing state because it changes usable bandwidth. Then specify a packet size distribution, like 70 percent large frames and 30 percent small, to model typical flows. The benefit is reproducibility across venues and time. The downside is reduced spontaneity when unexpected client behavior appears. Use a secondary exploratory run that varies aggregation and pacing to test sensitivity. Examples and short scenarios

A clean deployment example helps anchor expectations. Consider a quiet 6 GHz floor with 320 MHz enabled, strong SNR above 35 dB, and laptops capable of high modulation. As offered load climbs from 200 to 1.5 Gbps, the graph shows near linear throughput growth with modest airtime increases. The knee appears around 1.7 Gbps where retries nudge above typical levels and median MCS dips slightly, yet latency percentiles remain tight. The interpretation is that the width is paying off and the environment remains orderly. If the same baseline on 160 MHz requires 30 to 40 percent more airtime to deliver similar throughput, the choice to stay wide is justified. Limitations include potential DFS reactions and client roaming that can disrupt this calm picture during business hours.

A noisy scenario shows why airtime can lie when read alone. Imagine intermittent interference from a neighboring lab causing bursts of energy on part of the band. Throughput flattens while airtime rises because frames are retried and aggregation becomes less effective. The graph’s color by retry rate deepens, and latency bands widen significantly during spikes. In this case, trimming width to 160 MHz or using puncturing to avoid the dirtiest subchannels may reclaim efficiency. The tradeoff is reduced peak capacity at quiet times. A dashboard scenario highlights ongoing operations. Suppose a weekly report plots throughput versus medium busy time and annotates DFS events and controller queue depth. Weeks without alarms show stable slopes and consistent latency medians, while weeks with elevated contention show flatter curves and voice airtime squeezed below a defined threshold. The action is to tweak EDCA or enforce minimum MCS on problem SSIDs, then track the next report for a steeper slope at the same offered load. An edge case occurs when per link views in multi link operation look fine, but the combined BSS view reveals saturation. Looking ahead

The next step is to formalize a repeatable validation plan that codifies how throughput and airtime are tested during commissioning and after changes. Write a short playbook that sets baselines, packet mixes, and logging fields, and embed it in change management so graphs are captured before and after adjustments. Include explicit thresholds for retry rate and latency spread at each load step, because decisions to keep 320 MHz or trim to 160 MHz hinge on those limits. A rule of thumb is to revisit the plan quarterly or after firmware changes that affect scheduling. The tradeoff is the effort to run controlled tests amid production traffic, so use maintenance windows and synthetic traffic tagged for easy filtering.

Operationally, bring dashboards closer to daily work so graph patterns are visible without digging. Add a panel that overlays throughput against medium busy time with a seven day trend, annotate DFS events, and publish a weekly summary that comments on slope changes. Pair this with alerts that trigger when slopes flatten beyond a tolerated margin under similar offered load, which suggests rising contention or interference. As your tooling matures, compare controllers that surface true 320 MHz utilization and actionable telemetry to reduce guesswork. If you need help choosing platforms that read the signals well, explore materials describing how to monitor utilization dashboards to spot contention early without drowning in noise.

Finally, round out comparisons by expanding tests across client profiles. Include modern laptops, tablets, and at least one latency sensitive device so the graphs reflect diverse behavior under the same channel width. Normalize results per device class and document any minimum MCS settings required for fairness. This protects against decisions that prioritize peak throughput while hiding poor experience for chatty or voice endpoints. The limitation is that some clients change behavior with power states or roaming, so mark those conditions when recording. Over time, this discipline turns throughput versus airtime from a one off chart into a durable metric that guides width, scheduling, and placement choices with confidence.

Frequently asked questions

What does a healthy throughput versus airtime curve look like?

A healthy curve rises nearly linearly at low to moderate load, shows a gentle knee near peak efficiency, and avoids large retry spikes or widening latency bands as offered load increases.

How do retries affect airtime readings on 320 MHz?

Retries consume medium time without delivering new payload, so throughput flattens while airtime continues rising. Color coding by retry rate helps reveal this inefficiency on the plot.

Should I reduce width when airtime rises faster than throughput?

Consider trimming to 160 MHz or applying puncturing if noise or contention is confirmed. Verify by correlating retries, MCS drift, and latency variance before changing width.

Which baseline helps compare 160 and 320 MHz fairly?

Use identical offered load steps, packet size mix, and fixed RF parameters. Record puncturing state and noise floor so differences reflect width rather than setup drift.
