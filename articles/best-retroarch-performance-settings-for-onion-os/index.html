Best RetroArch Performance Settings for Onion OS

By Sarah Carter • Published February 2, 2026

These recommendations focus on RetroArch performance and practical settings that hold up on Onion OS. Each item was selected for measurable impact, repeatability across devices, and a clear tradeoff you can evaluate. I prioritized options available in stock RetroArch menus and per-core overrides so you can reproduce results without custom forks or risky tweaks.

Key takeaways

  • Per-core profiles beat one-size settings across mixed emulator workloads.
  • Threaded video and the right driver stabilize frame delivery.
  • Audio latency buffers prevent crackle without hurting input feel.
  • Use per-game overrides to rescue outliers without global penalties.
  • Thermal and power profiles cap throttle and preserve stability.

1. Per-core presets over global toggles

Use per-core settings because emulator workloads differ by system generation and renderer. For example, an 8-bit core can run with light shaders and lower audio latency, while a PlayStation core benefits from higher audio buffer and more conservative video sync to avoid stutter. In RetroArch on Onion OS, save a core override after tuning one system so it does not penalize others. The tradeoff is management overhead, since profiles multiply. However, the why is simple. Global choices force your fastest cores to adopt heavyweight guardrails meant for demanding systems, wasting headroom. Per-core presets localize cost where needed and let simpler cores stay snappy.

Start with light baselines and grow options only where a core drops frames. For instance, leave video smoothing and heavy shaders off globally, then enable a mild preset only in a core that maintains full speed. On Onion OS devices, extra GPU work can tip thermals into throttling, so isolation matters. A concrete flow is to tune NES with minimal latency and zero shaders, then save override. Next, set higher audio latency and strict sync on PlayStation and save again. The tradeoff is potential drift if you forget what changed, so keep a short note or use consistent filenames when exporting overrides for backup.

Section highlights

  • Per-core overrides prevent heavy settings from slowing simple systems.
  • Save tuned profiles and document changes to avoid configuration drift.

2. Video driver and threaded video

Choose a stable video driver and enable threaded video to smooth frame delivery. On many Onion OS handhelds, the gl or vulkan driver may exist, but a simpler driver like sdl2 can reduce overhead and frame pacing variance. As an example, switch to sdl2, enable threaded video, and set maximum swap interval to 1, then test run-ahead later. The tradeoff is latency. Threading decouples rendering from emulation which can add a few milliseconds. Still, consistent pacing helps performance and avoids visible stutter. The mechanism is straightforward. Threading keeps the UI and renderer responsive during emulation spikes, preventing big frame drops from propagating through the pipeline.

If you prefer a configuration file approach, you can set the video driver and threading flags in RetroArch’s config so per-core overrides inherit sane defaults. This keeps global stability while letting demanding cores tighten sync later. In practice, switching drivers sometimes requires a restart before it takes effect. Edge cases include cores that crash under one driver while stable under another, so always test your most demanding core when changing drivers. The tradeoff is potential incompatibility with certain shaders. If a favorite shader requires a different backend, keep the driver simple for speed and use milder visual tweaks instead.

Section highlights

  • Threaded video improves frame pacing with a small latency cost.
  • Test demanding cores after driver changes to avoid compatibility surprises.

3. Audio latency and sync tuning

Increase audio latency in small steps to eliminate crackle during load spikes while keeping input feel acceptable. A practical range is raising the audio buffer size until stutter disappears during busy scenes, then backing off one notch. For example, start around 64 ms, test a boss fight or a 3D scene, and adjust until audio is clean. Keep audio_sync on to maintain alignment with video. The tradeoff is added delay that affects rhythm games or tight platformers. The reasoning is that audio underruns are a canary for CPU spikes. A larger buffer buys resilience when emulation briefly stalls, preserving perceived smoothness even when frames are tight.

When a single core remains noisy despite a higher buffer, save a core override rather than raising the global default. As a concrete example, enable a moderate buffer only for PlayStation or SNES cores with heavy effects and keep handheld-friendly cores like NES lean. On Onion OS, this avoids global penalties across menus and simple games. An edge case occurs when run-ahead is enabled. Run-ahead reduces latency but can starve the audio thread if the CPU budget is small. If audio returns to crackle with run-ahead on, disable it for that core and keep the higher buffer, favoring stability over theoretical latency wins.

Section highlights

  • Raise audio buffers gradually until crackle stops, then back off slightly.
  • Use core overrides when run-ahead conflicts with audio stability.

4. Display latency settings

Favor stable vsync with a single buffering scheme before chasing ultra-low latency. On many Onion OS setups, keeping vsync on and limiting swapchain images to 2 produces smoother motion than forcing no sync. For instance, set video_vsync to true and use a swap interval of 1, then evaluate run-ahead. The tradeoff is slightly higher latency than unsynced rendering, yet fewer frames are dropped and tearing is eliminated. The underlying reason is that handheld panels and drivers often expect synchronized updates. When you disable sync, micro stutters accumulate and feel worse than a few extra milliseconds of delay.

Run-ahead can still help when the CPU has headroom, but treat it as per-core. Test with one frame of run-ahead first and watch for hitching in 3D titles. If a core shows intermittent stutter, disable run-ahead for that core rather than sacrificing global smoothness. A helpful example is enabling run-ahead for NES and SNES while leaving it off for PlayStation. Onion OS devices vary, so consider screen refresh constraints. If your panel runs at a fixed 60 Hz and a core cannot reliably maintain 60 frames, prioritize consistency using vsync and threading. That combination usually keeps timebase drift under control while preserving battery life.

Section highlights

  • Keep vsync on and limit buffering to stabilize frame pacing.
  • Apply run-ahead only to cores with confirmed headroom.

5. Core options for demanding systems

Turn off heavy features like high-accuracy renderers, high-resolution upscaling, and texture enhancement for demanding cores before adjusting global settings. For example, in a PlayStation core, disable internal resolution upscaling and texture filtering, then confirm full-speed gameplay. Only after reaching stable 60 frames should you add subtle enhancements. The tradeoff is visual fidelity. Disabling enhancement features reduces crispness but maintains consistent speed, which is more important on limited hardware. The mechanism is resource budgeting. Accuracy and enhancement options consume CPU and GPU cycles that your device may not have, triggering throttling or dips that feel worse than jagged edges.

When you need a visual boost, pick one light feature at a time and save the result as a core override. As a concrete example, enable a very mild shader preset or a 1.5x internal resolution only if your device holds 60 frames in busy scenes. Onion OS devices vary in thermal ceilings, and long play sessions can erode headroom. By testing heavy scenes first, you avoid surprises in later levels. Edge cases include cores that expose options with confusing names. If uncertain, choose the default or consult a stability-focused resource with clean configs and core choices that reduce crash risk. That prevents accidental slowdowns while you learn the option set.

Section highlights

  • Disable costly enhancements first to recover consistent frame rate.
  • Add one light visual feature only after stress testing.

6. Per-game overrides for hot titles

Use per-game overrides to isolate outliers without burdening an entire core. Some titles push emulation harder with effects or streaming, so give them slightly higher audio buffers or turn off run-ahead only for those games. A concrete example is disabling run-ahead and increasing audio latency for a demanding 3D title while keeping run-ahead on for 2D games in the same core. The tradeoff is time spent testing and saving overrides, but the payoff is strong. You keep the core’s general feel while rescuing the few troublemakers. This respects how Onion OS devices handle bursts and leaves lighter games fast and responsive.

Save the override after confirming a stable session of at least ten minutes in a heavy scene. If the title still hitches after adjustments, check whether a different core for that system is more forgiving on your device. Some cores aim for accuracy, others for speed. The risk is forgetting to remove an override if a future core update changes performance. Keep a short list of your per-game tweaks so you can revisit them after updates. When repeated instability appears, step back to a clean configuration approach that reduces crash risk before adding new layers of settings.

  • Revisit overrides after core updates to avoid stale settings.

7. Thermal and power profiles

Tune within your device’s thermal and power envelope or stability will slip during long sessions. On Onion OS handhelds, sustained high clocks can trigger thermal throttling that looks like inconsistent frame pacing or random slowdowns. Practical steps include using moderate power profiles, keeping threaded video on, and avoiding heavy shaders that spike GPU load. For example, run stress scenes for fifteen minutes to let temperatures stabilize, then decide if a mild enhancement is viable. The tradeoff is absolute performance. Capping clocks or features may limit peak numbers, but it preserves smoothness over time. The why is that thermal headroom is a finite budget that evaporates when effects stack up.

Add simple monitoring into your routine. If your device exposes temperature readouts or logs, watch them while playing demanding cores. When you see temperatures approach the throttling threshold, back off features until readings fall to a safe margin.
