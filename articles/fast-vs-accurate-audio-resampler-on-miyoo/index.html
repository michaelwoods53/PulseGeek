Fast vs Accurate Audio Resampler on Miyoo

By Austin Price • Published January 7, 2026

Choosing between fast and accurate audio resampler modes on Miyoo shapes perceived latency, stability, and smoothness. The fast path aims for lower processing cost, which can feel snappier during action games, while the accurate path prioritizes fidelity and clock tolerance that reduces crackle. The decision sits inside a broader performance stack that includes frame pacing, vsync, and buffering choices. We will compare these options using practical criteria like artifact risk under load, input feel with runahead or frame delay, and battery draw in long sessions. By anchoring each point to how RetroArch schedules audio and video, you can set a default that works across most cores, then override only when a title demands it.

Key takeaways

  • Fast resampler lowers CPU cost and can reduce input latency.
  • Accurate resampler resists drift and prevents intermittent audio crackle.
  • Pick a default, then override per core for edge behaviors.
  • Test with fixed FPS and vsync to isolate resampler impact.
  • Tune audio buffer size before blaming the resampler choice.

Evaluation criteria and how to weigh them

Start with an objective: minimize crackle without inflating latency. The fast resampler reduces CPU cycles, which can help cores that flirt with full speed stay stable at the display refresh, but it may tolerate less clock drift between the emulated system and the hardware. The accurate option usually tracks drift better, keeping audio consistent when frame pacing wobbles. A good rule of thumb is to test during worst case scenes for 3 to 5 minutes while watching for underruns and listening for pops. If you hear periodic ticks only under load, accurate often masks them. If performance dips disappear with fast enabled, the CPU headroom benefits likely dominate your choice.

Input feel matters, especially if you use runahead or frame delay. Because fast resampling consumes fewer cycles, it leaves room for modest frame delay or lower audio buffers, sometimes shaving meaningful milliseconds of end to end latency. Accurate can add overhead that narrows timing margins, and if paired with aggressive runahead, you may trade smooth audio for inconsistent frame times. The mechanism is simple: tighter CPU budgets reduce jitter tolerance, which surfaces as either crackle or dropped frames depending on which queue underflows first. This is why you should tune one variable at a time, starting with a conservative buffer and stable vsync before chasing the last bit of responsiveness.

Battery life is a secondary but real factor on small handhelds. The fast resampler typically draws less power since it executes fewer operations per sample block, which accumulates over long sessions. Accurate processing can increase CPU wake time just enough to matter during portable play. That said, if accurate avoids retriggered buffers from frequent underruns, it may paradoxically save power by preventing recovery work. Weigh this by watching a simple indicator like remaining percentage over a fixed 30 minute test. Deep dives per attribute with tradeoffs and examples

On CPU load, the mechanism is straightforward. Audio resampling interpolates between sample rates to align emulated audio with the output device. Fast methods choose simpler math that completes quickly per buffer, leaving more cycles for video and input processing. Accurate methods perform costlier interpolation and drift handling, improving continuity when clocks are not perfectly aligned. For example, a core that averages 58 to 60 frames under stress may avoid audio stutter with accurate, since it can adapt smoothly, whereas fast could expose minor underruns as ticks. The tradeoff appears if you also push frame delay toward the frame boundary, where the extra cost from accurate compresses timing margins and makes missed vblank more likely.

For crackle resistance, think in terms of underrun probability rather than always-on quality. Accurate resampling can stretch or shrink buffers more gracefully, which prevents hard underruns when frame times fluctuate. An edge case is a game with streaming audio cutscenes that spike CPU use. Accurate often smooths those transitions. However, if your base frame pacing is unstable, accurate may only mask symptoms. Fix root causes like vsync and FPS limits first using guidance such as how to choose the right vsync option, then pick a resampler. This ordering ensures you do not mistake an audio workaround for a lasting performance solution.

Latency tuning interacts with buffer size and resampler choice. Fast resampling plus a modest audio buffer, for instance 80 to 120 ms depending on core, often yields a responsive feel without audible artifacts. Accurate with the same buffer may still feel fine, but if you add runahead or raise frame delay, the compounded cost can push the system over the edge during heavy scenes. A safe approach is to establish stability with conservative buffers, then reduce stepwise while listening for artifacts and watching input consistency. If audible crackle appears before input starts to feel sluggish, favor accurate and restore a slightly larger buffer.

Fit by scenario with short, explicit recommendations

If you prioritize responsiveness and mostly play 8 or 16 bit titles at full speed, start with fast resampling as your default. Pair it with a moderate audio buffer and confirm that frame pacing is clean. A good validation path is to pick a level with constant music, enable your FPS limiter, and listen for ticks while performing inputs. If crackle surfaces during effects heavy scenes, try accurate on that core only and retest. When planning your overall setup, revisit advice on setting audio buffer size so you can strike a balance without overcompensating.

If your library spans cores with varied timing, or if you often use rewind or overlays, favor accurate as the global default. These features create periodic load that can amplify small timing mismatches, and accurate tends to absorb that variance with fewer audible issues. Verify that this choice does not constrain your chosen level of frame delay by conducting an A or B test at the same buffer size. If accurate blocks your target frame delay, consider reducing delay slightly while maintaining accurate to preserve stable audio, or selectively switching to fast on the most consistent cores.

If you chase the lowest possible input lag and use runahead, be methodical. Start with accurate and a safe buffer, then enable one runahead frame. If input feels stable and audio is clean, test fast and lower the buffer stepwise to see if the feel improves without artifacts. Keep vsync behavior consistent during tests to avoid confounding variables. For players who also struggle with occasional tearing or pacing dips, review this guidance on picking the right vsync option so resampler decisions build on a solid timing base rather than compensate for it.

Frequently asked questions

Will changing the resampler affect battery life on Miyoo?

Yes, though the difference is usually modest. Fast resampling often reduces CPU work and can save some power over long sessions. Accurate may draw slightly more, but if it prevents audio underruns it can avoid extra recovery work that also costs energy.

Where do I change the resampler in RetroArch on Miyoo?

Change it in RetroArch settings under audio, then set audio resampler to your preferred option. Apply the change, restart content, and test. You can also create per core overrides so the global default stays stable while exceptions are isolated.

How do I know if fast is too aggressive for my setup?

Listen for periodic ticks or crackle during heavy scenes and watch for audio dropping out during transitions. If these issues appear only with fast and vanish with accurate at the same buffer size, the fast path is too tight for that core or game.

Should I tune the audio buffer before choosing a default?

Yes. Establish a conservative buffer that eliminates underruns first, then compare resamplers. Once you pick a default, reduce the buffer in small steps and retest. This sequence separates buffer stability from resampler behavior and prevents false positives.

Can I combine fast resampling with runahead safely?

Often, but test carefully. Fast may free enough CPU to support one runahead frame and modest frame delay, yet tight budgets can still cause crackle. Add features incrementally and keep vsync consistent so you can spot the point where stability breaks.

Looking ahead

The right default holds up across libraries and still leaves room for selective tuning. After you settle on fast or accurate, document per core overrides and keep buffer changes small so you maintain repeatable tests. If you continue to chase smoother pacing or fewer artifacts, pair this choice with measured tweaks to vsync and limits. When new cores or firmware arrive, rerun a short stress scene and validate that your baseline still behaves. This habit converts isolated fixes into a coherent setup that feels consistent week to week.
