GPU Culling: Occlusion, Frustum, and Smart Skips

By Ethan Palmer • Published January 8, 2026

Good GPU culling turns invisible work into free time for visible pixels. We will examine frustum tests, occlusion methods, and smart skips that reduce overdraw without hurting quality. Each technique includes a concrete example and tradeoff so you can decide when to use occlusion or frustum checks, or combine both. Selection criteria focused on approaches that ship in mainstream engines, map to modern hardware features, and show measurable impact under profiler scrutiny. Along the way, we connect these skips to frame pacing and batching, not just raw throughput. The result is a toolkit for practical decisions rather than a single recipe.

Key takeaways

  • Use frustum culling first to remove obviously offscreen objects cheaply.
  • Adopt Hi-Z occlusion where overdraw dominates and occluders are stable.
  • Drive draws indirectly so culling and rendering remain on the GPU.
  • Combine tiled or clustered light culling to limit per-pixel lighting work.
  • Validate with debug overlays to avoid aggressive or flickering culls.

1) GPU frustum culling as the cheapest first pass

Start with frustum culling on the GPU because it is the fastest broad-phase skip and scales across thousands of instances. The claim is that per-instance bounding volume checks in a compute pass prune most offscreen objects before any draw setup. For example, pack sphere bounds and model matrices in structured buffers and mark survivors into a compacted list for indirect drawing. In a third-person level with long corridors, this removes entire rooms outside the camera frustum with negligible ALU cost. The tradeoff is precision versus overhead. Spheres are quick but can be conservative, while oriented boxes tighten coverage but require matrix transforms. The why is simple. The frustum test is branch-light, coherent, and amortized by the GPU’s parallel lanes, so it decongests later stages with predictable cost.

Section highlights

  • GPU frustum checks cheaply remove offscreen instances at scale.
  • Prefer spheres for speed, boxes for tighter acceptance when needed.

2) Hierarchical occlusion using Hi-Z depth pyramids

Use hierarchical Z occlusion to skip objects hidden by solid occluders, because it leverages a downsampled depth pyramid that answers visibility queries quickly. The claim is that a two step test, coarse then refined, rejects many interior meshes in dense city blocks. For example, generate a mip chain of the main depth buffer and test object bounds against progressively higher levels until either visible or fully occluded. In a street canyon, small props behind a building face fail at coarse mips, saving vertex and pixel work. The tradeoff is stability and latency. Pyramids are usually one frame behind, so rapid camera cuts can temporarily mispredict. The why is that depth hierarchies compress visibility structure, letting a few texture fetches approximate many pixels worth of hidden surface decisions, at a cost dominated by bandwidth rather than ALU.

Section highlights

  • Depth pyramids quickly reject objects hidden by large occluders.
  • Expect one frame latency and tune mip levels for stability.

3) Hardware occlusion queries with temporal coherency

Hardware occlusion queries can validate or correct predictions, but they shine when guided by temporal coherency. The claim is that you can issue queries for borderline objects and reuse last-frame results to avoid stalls. For example, tag low-confidence instances and let their draws run with an any-sample-passed query, then use the result next frame to promote or demote them in the culling list. In a foliage-dense forest, this prevents flicker on swaying branches that intermittently peek out. The tradeoff is pipeline bubbles if you read results too soon, which can serialize the GPU. The why is that deferring decisions by one frame exploits the fact that visibility rarely changes drastically frame-to-frame, and the small temporal lag costs less than forcing immediate synchronization.

Section highlights

  • Use queries sparingly for borderline visibility with frame delay.
  • Avoid stalls by reading results after later passes complete.

4) Clustered and tiled culling for lights

Switch to tiled or clustered lighting so light evaluation scales with visible space, not total lights. The claim is that binning lights into screen tiles or 3D clusters drastically reduces per-pixel loops. For example, a 16x16 tile pass builds light lists using min-max depth, then shading reads only the local subset, cutting branchy if tests in the main lighting stage. In a scene with 500 small point lights, tiled bins constrain the average to single digits per tile. The tradeoff is memory for lists and extra passes to build them, which can hurt very simple scenes. The why is that visibility and proximity are the real determinants of light cost, so mapping lights to tiles or clusters aligns compute with what the camera actually sees. For broader engine context, see this guide to rendering pipelines, stages, and buffers.

Section highlights

  • Tiled or clustered bins limit per-pixel work to relevant lights.
  • Account for list memory and bin building cost in simple scenes.

5) Conservative raster with simplified occluder meshes

Conservative rasterization paired with simplified occluder meshes yields robust occlusion at coarse cost. The claim is that inflating triangle coverage slightly ensures depth writes cover true geometry, making tests reliable even with approximate blockers. For example, author low-poly walls and terrain shells and render them into a depth prepass using conservative raster, then query the Hi-Z for object bounds. In fortress courtyards, this blocks far interiors without per-object draws. The tradeoff is over-occlusion if the shells deviate too much, causing aggressive culls at silhouettes. The why is that small conservative bias flips errors toward safe hiding rather than sporadic see-through, and because the meshes are simplified, the pass stays cache friendly. For a system-wide backdrop, review this tour of rendering, physics, and optimization.

Section highlights

  • Conservative raster plus shells delivers stable occlusion coverage.
  • Keep occluder proxies close to silhouettes to prevent over-culls.

6) Software raster occlusion in a compute pass

A software raster occlusion pass in compute gives maximal control over precision and ordering when hardware features are limited. The claim is that rasterizing bounding triangles or quads into a screen-space depth tile buffer lets you schedule work exactly when needed. For example, generate a 2x downscaled depth for major occluders inside compute, write min depth per tile, and test object bounds before issuing any graphics draws. In an engine targeting multiple APIs, this avoids reliance on conservative raster extensions while achieving similar rejection. The tradeoff is implementation complexity and cache behavior, since tile buffers must be carefully laid out to avoid thrashing. The why is that compute gives you a programmable path to occlusion that can be tuned per platform, matching tile size and wave width for better occupancy.

Section highlights

  • Compute-based occlusion offers portability and scheduling control.
  • Balance tile size, memory layout, and wave width for efficiency.

7) GPU-driven indirect draws with compacted instance lists

Drive rendering with indirect draws so culling and submission stay on the GPU. The claim is that compacting visible instances into a single buffer, then issuing DrawIndexedInstancedIndirect or similar, removes CPU bottlenecks. For example, a compute pass writes counts and argument buffers per mesh, and the graphics queue consumes them directly, enabling thousands of instances to render without per-draw CPU calls. In a forest scene with heavy foliage, this pairs well with frustum and Hi-Z culling earlier in the frame. The tradeoff is debugging complexity and the need for robust synchronization, since counters and arguments must be reset correctly. The why is that eliminating CPU submission overhead reveals the true benefit of culling by aligning the skip decisions with execution and freeing the main thread for gameplay. Consider also these concrete methods to reduce draw calls.

Section highlights

  • Indirect draws let culling results feed rendering without CPU work.
  • Reset counters and sync argument buffers to avoid races.

8) Screen size thresholds and LOD-aware culling

Screen size thresholds remove objects that contribute nothing, while LOD-aware culling trades geometry for texture detail where it matters. The claim is that computing projected radius or bounding rectangle area and comparing against a small pixel threshold eliminates noise. For example, anything under four to eight pixels wide can be culled or replaced with a billboard, depending on motion speed. In a mountaintop vista, distant pebbles disappear, and small shrubs swap smoothly to impostors. The tradeoff is popping and temporal shimmer during camera acceleration, which you can soften with hysteresis and motion vectors. The why is that perception is not linear with distance, and tiny features do not survive post processing, so culling them creates headroom for materials and shadows that players actually notice.

Section highlights

  • Cull or replace tiny features using projected size thresholds.
  • Add hysteresis to prevent popping during fast camera motion.

9) Portals and cells as a hybrid with GPU tests

In structured interiors, combine classic cells and portals with GPU occlusion to narrow candidates aggressively. The claim is that topological pruning beats purely geometric tests when doorways and halls constrain visibility. For example, traverse a room graph to generate a small set of potentially visible cells, then let a Hi-Z pass confirm or reject objects within them. In a museum layout, this prunes entire wings before screen-space checks run, keeping the GPU focused. The tradeoff is authoring or baking connectivity data, which adds pipeline steps and can drift when levels change. The why is that visibility is both spatial and structural, and when the world’s layout cooperates, a graph cut before compute reduces worst-case overdraw spikes and avoids per-object tests that would otherwise flood caches.

Section highlights

  • Use room graphs to limit candidates before GPU occlusion tests.
  • Maintain connectivity data to avoid drift during level edits.

10) Asynchronous compute to overlap culling and shading

Run culling on an asynchronous compute queue to hide its cost behind raster work. The claim is that visibility passes overlap well with graphics when resource hazards are managed. For example, kick frustum and Hi-Z tests as soon as previous depth is available, then signal a fence that the graphics queue waits on only when it needs the compacted lists. On a GPU with spare compute, this turns culling into near-free latency. The tradeoff is scheduling complexity and contention for memory bandwidth, which can reduce benefit on fill-limited scenes. The why is that modern architectures can dual-issue compute and graphics under light stalls, and culling is coherent, low-divergence work that fits the overlap window. For foundational context on GPU flow, this primer on rasterization and lighting helps frame expectations.

Section highlights

  • Overlap culling with rendering using async compute and fences.
  • Watch bandwidth contention that can erase expected wins.

11) Debugging overlays and validation loops

Build robust debug overlays to trust your culling, because correctness beats theoretical speedups. The claim is that visualizing accepted versus rejected instances and showing occluder coverage exposes aggressive thresholds and latency issues. For example, color objects by cull reason, draw bounds over the depth pyramid, and include a hotkey to disable specific tests in live builds. In a user report about flickering props, a toggle quickly reveals a too-coarse mip level causing temporal holes. The tradeoff is maintenance overhead and the temptation to ship debug code that affects performance. The why is that visibility bugs are slippery, and immediate feedback turns “what-if” speculation into targeted fixes. Frequently asked questions

Should frustum or occlusion culling run first?

Run frustum culling first because it is extremely cheap and removes offscreen objects before depth work. Then apply occlusion to the survivors to eliminate hidden geometry efficiently.

How many Hi-Z mip levels should I sample?

Start coarse and refine as needed. One to two samples at higher mips can catch obvious occlusion, then drop to finer levels only for borderline cases where false positives are common.

Do indirect draws help if my scene is CPU bound?

Yes. Indirect draws reduce per-draw CPU submission and let the GPU consume compacted lists directly. You still need profiling to confirm the main thread bottleneck moves meaningfully.

Will culling cause popping or flicker?

It can. Use hysteresis, fade transitions, and temporal stability tricks like rechecking borderline objects less aggressively. Debug overlays help tune thresholds for motion and camera cuts.

Looking ahead

Compose your culling stack deliberately. Lead with frustum, add Hi-Z where occluders are strong, and reserve queries for uncertainties. In outdoor vistas, prioritize screen size heuristics and indirect draws; in interiors, combine portals with depth tests. Profile changes under varied camera paths to ensure frame pacing improves, not just averages. Then revisit lighting costs and fold in clustered bins so shading scales with what is visible. When the results align, your engine can trade invisible complexity for visible quality without surprises.
