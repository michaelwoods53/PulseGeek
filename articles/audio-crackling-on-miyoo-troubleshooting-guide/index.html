Audio Crackling on Miyoo: Troubleshooting Guide

By Austin Price • Published March 4, 2026

Audio crackling on Miyoo often comes from timing drift, overloaded cores, or storage hiccups rather than a single broken setting. This stepwise how-to shows how to stabilize sound by testing audio sync, rate control, and I/O in isolation. You will make small, reversible changes and validate with repeatable listening loops so you can attribute improvement to a specific tweak, not luck.

Key takeaways

  • Reproduce crackling consistently before changing settings to avoid false positives.
  • Prefer audio sync with 44100 Hz output and modest timing skew limits.
  • Fix storage contention first when crackles appear during loads or saves.
  • Use frameskip sparingly and only after verifying frame pacing stability.
  • Validate by looping the same scene and listening with wired headphones.

Plan the work

Start by defining the crackling pattern so you can reproduce it on demand and test changes reliably. Note whether artifacts appear during busy scenes, when loading save states, or even at menu idle. A thirty to sixty second loop that reliably triggers the issue, like a voiced intro or a dense action scene, is ideal for A/B tests. Record your baseline settings and firmware so you can roll back if a tweak makes things worse. The tradeoff here is time up front versus certainty later, but without a consistent trigger you will chase ghosts and stack changes you cannot attribute. Clear reproduction anchors each experiment and keeps this process disciplined.

Segment likely causes into timing, CPU load, and storage, then test one category at a time. Timing faults show up as crackles that correlate with frame pacing or vsync, while CPU limits cause bursts during heavy effects or simultaneous sprites. Storage contention usually crackles during savestates, shader loads, or content scanning. Creating hypotheses helps you choose the first actions, like enabling audio sync when drift is suspected or checking SD health if loads spike the issue. The limitation is that multiple factors may interact, so expect a few passes where you disable previous changes to confirm which variable mattered most.

Define success criteria before editing anything so you know when to stop. A practical goal is zero audible crackles in your loop across three consecutive passes plus no regression in input feel. If audio improves but input becomes mushy, you solved the wrong problem. Use wired headphones to remove external latency variables and listen for subtle ticks that speakers can mask. Document each change and outcome in a small note so you can undo side effects cleanly. This prevents configuration drift where multiple small adjustments accumulate and obscure the original fault, a common pitfall when tuning RetroArch on handhelds.

Prepare environment

Back up your SD card and configs first so every change is reversible. Copy RetroArch’s configuration directory and your core overrides to a safe folder on a PC before you start. If you recently migrated systems, confirm you are on a stable build of OnionOS or MinUI without experimental modules enabled. A quick integrity check of the SD with a desktop tool can reveal corruption that mimics audio issues. The tradeoff is a small setup delay, yet it prevents chasing symptoms caused by storage faults. Prepare two test ROMs and one save state that trigger the crackle, and keep a spare SD if you suspect aging flash that stalls under load.

Prepare a clean baseline by resetting only audio-related options rather than wiping everything. In RetroArch, note the current audio driver, output rate, audio sync, and maximum timing skew. Set input latency features like runahead to off for initial tests so audio timing is not complicated by speculative frames. This narrowed scope prevents false interactions that mask whether audio sync corrected drift. If your baseline is messy, consider restoring defaults for RetroArch audio and video timing while leaving controls, playlists, and paths untouched. The practical limit is time spent reapplying personalization, but you will gain a known-good reference for each change.

Execute steps

Execute changes in a strict order so you do not mask causality between fixes. Start with audio timing because it is fast to change and low risk, then move to frame pacing and finally storage. After each step, replay your crackle loop and note audible changes plus any input feel differences. This cadence prevents over-tuning while building confidence that a single edit delivered the improvement. When drift was the cause, audio sync and correct output rate typically yield immediate silence. If bursts persist during I/O, you will pivot to storage checks and file layout. Keeping changes atomic forms a breadcrumb trail so you can revert with certainty.

Before listing the steps, understand how a few settings interact. Audio sync keeps the sound buffer aligned with frame delivery, while rate control gently adjusts playback to absorb micro drift. Output rate at 44100 Hz matches most classic content, minimizing resampling artifacts. On the video side, vsync one and no hard sync produces stable pacing without starving audio on these handhelds. The tradeoff emerges when a core runs near its performance limit, where strict sync can cause stutter. In that case, you will prefer stability by reducing latency features and avoiding shaders that add load during sound-critical moments.

Use this checklist to change only one variable at a time. Stop when your loop plays clean for three passes and input feel remains consistent. If a step regresses feel or does nothing, revert it and continue. The priority remains stable, crackle-free sound with minimal side effects. Where a core offers an internal audio rate, set it to match RetroArch. If your crackle only appears during savestates or asset loads, skip ahead to the storage hygiene actions to prevent unnecessary timing edits.

Validate results

Validate by replaying your trigger loop three times and listening with wired headphones. Wired removes wireless latency variables and exposes small ticks that device speakers can hide. Note whether the first seconds are quiet and whether crackles return during scene changes. A correct timing fix usually creates uniform silence across the loop and leaves input feel unchanged. If isolated single ticks remain after rate control, reduce rate control delta slightly, but avoid chasing the last one percent if gameplay remains smooth. The point is to confirm stable audio without trading away responsiveness that matters during actual play.

Cross-check your fix under a different emulator core to ensure it generalizes. Some cores resample independently, so aligning their internal rate to RetroArch avoids double processing. If the second core crackles again, your earlier fix may have been core specific, which is acceptable when you lock it behind a core override. When both are clean, you can promote the changes into the global config with confidence. This pattern prevents polluting global timing with a tweak needed only by a single core, a common source of surprising regressions on other systems later.

Run a short storage stress test if your crackle appeared during I/O. Save state repeatedly while audio plays, enter and exit menus, or quickly switch small shaders to simulate load spikes. If sound stays clean, your earlier SD hygiene steps worked. If ticks correlate with those actions, plan a deeper card check or try a known good SD and repeat the loop. Spread changes out to keep attribution strong.

Troubleshoot and optimize

If audio still crackles after timing fixes, focus on CPU headroom. Disable heavy shaders, per-game overlays, and any high-latency input features that might starve the audio thread under load. In borderline cases, lowering interpolation quality in the core can ease pressure with minimal audible change. Avoid frameskip for sound quality unless the core cannot maintain pace even after reductions, because it can mask timing faults while degrading motion feel. When crackling spikes only during savestates, your root cause is still storage, not timing. Addressing compute and I/O headroom preserves audio integrity without risky overclocking or irreversible changes.

Watch for signals that indicate timing versus storage. If ticks coincide with every vsync or disappear when pausing video while audio plays, timing remains the issue. If they appear during content scanning, saving, or shader compilation, storage is the culprit. In those cases, reorganize ROMs into fewer directories, avoid massive playlists, and keep thumbnails modest to reduce metadata churn. Consider testing with a fresh, high-quality SD card and copying content anew to reflow file layout. For structured guidance on stutter that often accompanies audio issues, use the playbook on stopping stutter through sync and storage checks as a complementary path.

When a core offers internal audio rates or resamplers, match 44100 Hz and select a low-latency method. If a particular core still crackles, store your fix as a core override to contain side effects. Periodically compare your config to defaults after system updates, because new builds can introduce slightly different timing behaviors. Keep a dated backup of your working audio configuration to restore quickly if changes regress. This lightweight configuration management is often faster than hunting a single toggled field and ensures you can return to known-good behavior within minutes.

Frequently asked questions

Should I use frameskip to stop audio crackling?

Use frameskip only after confirming stable audio timing and adequate CPU headroom. Frameskip can hide timing faults but often harms motion feel. Prefer audio sync, correct rates, and reduced visual load before considering frameskip.

Why does audio crackle only during savestates?

Crackling during save or load usually points to storage contention. The audio thread is starved while I/O peaks. Rebuild the SD layout on a fresh card, reduce content scanning overhead, and retest with the same loop to confirm the cause.

Which output rate should I pick for classic systems?

Choose 44100 Hz for broad compatibility and minimal resampling artifacts. Matching core internal rate to 44100 helps avoid double resampling. Deviating rarely helps unless a core documents a different native rate and provides a clean conversion.

Do I need to change the audio driver in RetroArch?

Most Miyoo builds use ALSA reliably. Changing drivers is rarely necessary for crackling. Focus on audio sync, rate control, and video pacing first. If problems persist, test another driver briefly and revert if no improvement appears.

How do I safely revert if a change makes things worse?

Restore the backup of your RetroArch configuration or remove the core override file you created. Keeping dated copies lets you roll back in minutes. Reproduce your test loop again to verify the revert restored prior behavior.
