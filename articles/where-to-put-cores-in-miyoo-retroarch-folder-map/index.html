Where to Put Cores in Miyoo RetroArch

By Jared Butler • Published February 26, 2026

Miyoo owners often ask where cores belong in RetroArch, since placement determines whether content loads and saves behave as expected. This article maps the core folders, explains how RetroArch resolves paths, and shows tradeoffs when firmware like OnionOS or MinUI shifts defaults. You will leave with a reliable folder map, simple checks to confirm the cores path, and practical advice for updating without breaking playlists or BIOS detection.

Key takeaways

  • Place core files in the RetroArch cores folder for consistent detection.
  • Confirm system BIOS location, since many cores depend on it.
  • Keep cores and core info versions aligned to prevent incompatibilities.
  • Use firmware presets but verify paths after updates or SD swaps.
  • Test a few ROMs per system to validate the folder map quickly.

Concepts and definitions

The core idea is simple: RetroArch loads emulator modules called cores from a defined directory, and Miyoo builds usually point that directory to a folder named cores under the main RetroArch path. On a typical SD layout, you will see RetroArch alongside content and saves, with cores inside RetroArch. Many builds also include a system directory for BIOS files that some cores require to boot. A quick rule is to keep cores and their core info files together so metadata like supported extensions remains accurate. An edge case appears when firmware presets override paths through configuration files, which can move cores to a custom location. Verifying that the configured cores path matches your SD structure prevents silent load failures and confusing black screens.

Definitions help orient the folder map. The cores directory stores shared objects ending in .so, each representing a specific emulator. The core info directory holds .info metadata used by RetroArch to label features and associate valid file extensions. The system directory houses BIOS files that some cores read synchronously at startup, and saves or states paths determine where game progress lands. These terms matter because misplacing any of these folders creates mismatches that look like broken ROMs. A useful practice is to confirm the absolute paths in settings, then drop a single known good core and test one ROM. If load succeeds, add more cores incrementally to avoid debugging a large batch.

Default paths on Miyoo distributions are usually sane, yet they vary across OnionOS and MinUI releases. You can treat the expected map as RetroArch/cores for modules, RetroArch/core_info for metadata, RetroArch/system for BIOS, and RetroArch/saves or RetroArch/states for progress. Differences typically arise when a vendor wants writable directories segregated by user or app partitioning. The practical implication is that updates may rewrite config files and reset paths, moving the expected cores directory. To reduce surprises, capture a backup of your RetroArch config before changing firmware. Frameworks and decision lenses

A simple decision lens is permanence over convenience. If you want dependable behavior across updates, store cores in the default RetroArch cores directory and keep the path unchanged. This choice simplifies backups and makes support guidance predictable, since most instructions assume defaults. The tradeoff is less flexibility when running multiple firmware variants on one card. Another lens is write frequency, where you place cores on a partition that receives fewer writes to reduce wear. On tiny cards, the difference is small, yet moving cores rarely saves meaningful space because .so files are compact. Path stability and clarity usually matter more than minor storage gains.

Firmware coupling is the second lens. OnionOS may ship with presets that point to curated cores, while MinUI distributions sometimes favor minimal footprints, and both can reshape default directory names. Aligning with those presets reduces friction when the OS updates paths during version upgrades. The downside is lock in if you later switch firmware, as path assumptions change and RetroArch might not find cores. To mitigate, keep a short record of your paths and verify them after upgrades. The second pass decides whether to override cores directory in settings only if a firmware-specific reason exists, such as read only partitions or sandboxed apps. The final pass checks that your content scanner or manual playlist creation reflects the chosen path. These steps reduce bugs where ROMs seem undetected because path variables changed. Examples and short scenarios

Consider a typical layout on a single card. You place .so files in RetroArch/cores, .info files in RetroArch/core_info, BIOS in RetroArch/system, and saves in RetroArch/saves. To verify, open RetroArch settings and confirm the Paths entries for Cores, Core Info, and System point to these directories. A quick diagnostic is to run one ROM per console and check whether the core loads, then ensure the correct BIOS is detected where required. If you changed directories previously, RetroArch may still point to the old location, producing a failed load. The sample map below highlights a stable baseline you can mirror. A second scenario is updating cores while preserving settings. Download vetted builds compatible with your Miyoo architecture, replace .so files in the cores directory, and update matching .info files to keep metadata aligned. Before upgrading, copy your RetroArch folder or at least the config file so you can revert quickly if a core regresses. After the swap, test two games known to be stable and verify that saves still appear in the expected directory. If performance or compatibility changes, roll back only the affected core and leave the rest untouched. A third scenario involves a firmware that relocates paths through presets. You might see cores redirected to a custom directory while BIOS moves to a firmware controlled system folder. The best approach is to accept the preset and mirror the expected structure, then confirm that playlists and thumbnails still resolve correctly. When presets conflict with your existing library, correct them in settings or restore the defaults and migrate files once. Avoid repeatedly moving cores back and forth because that invites confusion and stale paths in configuration. If you later switch to another firmware, document old paths and validate the new ones by testing a few representative ROMs. This routine limits downtime and helps you isolate issues to either paths or files.

Pitfalls, limitations, and edge cases

The most common pitfall is version drift between .so cores and .info metadata. When they fall out of sync, RetroArch may mislabel supported extensions or fail to launch content. Always update both together, and keep a backup of the previous pair for quick rollback. A limitation on some Miyoo builds is a read only area that hosts defaults while user writable folders live elsewhere. Confusing these can cause writes to silently fail or paths to revert. If ROMs do not appear during scans, verify that the core in use recognizes the file extension listed in its .info. For troubleshooting scanning quirks and naming, learn proven do and do not tips for the content scanner on Miyoo devices.

Wrong architecture is another edge case. A core compiled for the wrong CPU will not load, even if placed in the correct folder. Validate compatibility at the source and favor known stable builds. On older cards, fragmentation or file system errors can corrupt cores during copy, so reformatting and recopying from verified archives may fix intermittent crashes. A simple test is to swap in a second SD with the same structure to see if the issue follows the card or the install. When ROMs appear but fail to load, double check BIOS placement, since many cores require a specific directory under system. If ROM detection fails entirely, a focused guide on resolving detection problems can save significant time on path checks.

Path resets after updates deserve special attention. Some firmware updates rewrite config files and reset directories to their preferred defaults. If your cores live elsewhere, RetroArch will look in the wrong place, and games stop launching. The fix is to compare current settings against your documented map and either restore defaults or update the config to your custom location. Consider keeping a small checklist for post update verification, including paths, hotkeys, and latency settings. Spreading out verification reduces the chance that a single missed toggle cascades into a bigger problem. Looking ahead

Maintaining a clean map is lighter than repeatedly fixing surprises. Keep cores in the default folder when possible, pair updates with matching .info files, and verify Paths after firmware changes. Build a small smoke test with two ROMs per system and a short note of where saves land. Over time, this routine becomes a quick ritual that protects your library from mismatches and broken launches. If you want to extend the baseline with better menus and storage hygiene, explore configuration patterns geared toward reliable play on Miyoo hardware, then adapt just enough to fit your habits without overcomplicating paths and folders.

Think of portability as a goal. If you migrate to a new SD card or firmware, a predictable structure and a written map reduce downtime. Back up your RetroArch directory before core updates, and copy it again after successful tests to set a restore point. If you prefer richer library browsing, playlists and thumbnails can be layered on once the core locations are stable. That way, cosmetic upgrades never interfere with core detection. Finally, keep learning from small experiments. Try a new core for a system you know well, measure how it behaves with your BIOS set, and compare saves and states between versions. Only promote the core to your main card once it passes your quick checks. This practice avoids chasing regressions after a full install. If something breaks, roll back the single core and move forward with a known stable set. Documenting one or two lessons per update will pay off during future migrations. It keeps your Miyoo RetroArch folder map understandable and resilient when firmware or cards inevitably change.

Frequently asked questions

What folder should RetroArch cores use on Miyoo?

Use the RetroArch cores directory unless your firmware specifies a different path. Keep core info in the matching core_info folder and verify both paths in settings.

Do I need to update core info files with cores?

Yes. Update .info files alongside .so cores to keep metadata aligned. This prevents mislabeling of extensions and reduces launch issues after updates.

Where do BIOS files belong for cores that need them?

Place BIOS in the RetroArch system directory, often with subfolders per console. Many cores will not boot content if BIOS files are missing or in the wrong place.

Why do ROMs stop launching after a firmware update?

Updates can reset path settings. Recheck the paths for Cores, Core Info, and System in RetroArch. Restore your documented map or adjust to the firmware’s defaults.

Can I store cores on a separate SD card partition?

You can, but it adds maintenance. Keep documentation and update paths in settings. The default cores folder is simpler and avoids drift during updates.
