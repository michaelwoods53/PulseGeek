Onion OS Saves and Save States: Paths and Backups

By Jordan Kelly • Published February 10, 2026

Save files and save states in Onion OS are distinct, and knowing their locations prevents lost progress after updates or SD swaps. Most handhelds route saves and states through per-core directories, so path behavior depends on the emulator core in use. This guide explains practical ways to find current paths, set consistent directories, and build backups that restore cleanly across devices without guesswork.

Key takeaways

  • Saves and save states live in different folders with separate lifecycles.
  • Per-core settings determine default paths, not Onion OS alone.
  • Confirm paths inside RetroArch before changing directories.
  • Back up both saves and states to preserve complete progress.
  • Use one root archive and dated increments for fast restores.

Concepts and definitions

Saves represent in-game writes to a cartridge or memory card abstraction, while save states are emulator snapshots of RAM, CPU, and device state. The distinction matters because saves are portable across cores that emulate the same system format, but save states usually work only with the exact core and version that created them. For example, a Game Boy save created in-game typically loads fine in other compatible cores, whereas a state from a particular Gambatte build may fail elsewhere. This separation explains why backups must include both directories, yet restores should prioritize saves for cross-core resilience. If you switch cores to fix performance or audio quirks, saves often migrate successfully, but states can break, so treat states as convenience rather than canonical progress.

Paths for saves and states are often core-defined, which means default locations can vary across systems even within Onion OS. RetroArch cores typically expose two settings: a save file directory and a state directory, each resolving relative to the active storage. As a rule of thumb, in-game saves appear inside a folder named for the system or core, while states land in a parallel or dedicated directory. When users update Onion OS or swap SD cards, these references may point to new mount points or fall back to defaults. That is why verifying the configured directories inside RetroArch’s settings is safer than assuming one global path, especially after firmware changes or card migrations.

Backups exist to restore expected behavior across devices and updates, so structure matters. A reliable approach is to mirror the active save and state directories into a human-readable archive with system, core, and date metadata. For instance, use a folder naming pattern like System_Core_Save and System_Core_State under a top-level Backups directory, then create dated subfolders for increments. This pattern discourages mixing files from incompatible cores, which can cause silent failures when loading states. The cost is a small amount of added storage and ceremony during backup, but the payoff is clarity during recovery when you want predictable load behavior. Consistency and labeling prevent confusion caused by different core defaults on similar devices.

Frameworks and decision lenses

A simple decision lens starts with discovery, then standardization, and finally backup. Discovery means checking each core’s configured save and state directories before making changes. Standardization means choosing target folders that you can replicate on other cards without manual edits, such as predictable subdirectories under a common root. Backup means capturing both saves and states on a schedule you can maintain. For example, confirm current paths, set unified directories for key cores, and back up weekly or after major sessions. The tradeoff is effort upfront to set and test directories, but this reduces recovery time later. The why here is repeatability. When paths follow a rule and backups follow a cadence, you can restore with minimal troubleshooting.

Verification steps catch misconfigured or drifting paths, particularly after core updates. A dependable check is to save in-game, then immediately create a save state, and finally locate the newest files by modified time. If both files appear where expected, your configuration matches your plan. If they land in different or legacy folders, update the core settings to align them with your standard. An edge case is when a core ignores a custom directory due to permissions or mount differences. In that scenario, keep the default but place a note in your backup routine to include that location. The emphasis is to validate actual behavior with test files rather than trust menu labels.

Backup strategy should balance redundancy and simplicity. A compact plan uses one master archive plus dated increments that include only changed files since the last run. For handheld owners, that could mean copying the Saves and States directories to a desktop, then zipping the increment with the date in the filename. The main tradeoff is choosing between full copies every time, which are slower but easy to reason about, and incremental copies, which are faster but rely on careful tracking. If you rarely change cores, incremental is efficient. If you experiment often, occasional full copies avoid mismatch between state versions and saves. The goal is a restore path that your future self can execute in minutes.

Examples and short scenarios

Consider a player moving from one SD card to another after expanding storage. The saves load but save states fail for a few systems. The likely cause is core version drift or a different state directory on the new card. A quick diagnostic is to create a fresh state and compare its location and file extension to the migrated ones. If paths differ, copy the old states into the live directory and test again. If core versions changed, try loading only the in-game saves and recreate states after confirming stable gameplay. This approach keeps progress intact while minimizing time lost to incompatible snapshots. The tradeoff is rebuilding convenience features, not progress itself.

Another scenario involves switching cores for a system to improve performance or accuracy. Suppose you move from a fast core to a more precise one for a difficult title. In-game saves often transfer, but states almost always fail. The safe sequence is to back up both folders, set unified directories for the new core, then load from the in-game save to confirm continuity. After that, generate fresh states during key checkpoints. If the new core accepts your directory settings, your backup routine remains consistent across both cores. If not, add a note to include the new core’s default state path in your backup plan. This preserves momentum while absorbing the cost of core specificity.

For users curating tidy libraries, naming and placement influence automated artwork and collections. Clean folder names for systems and consistent directories reduce metadata mismatches when scraping art. When paths are scattered, scrapers can attach covers to the wrong entries or miss items entirely. A useful pairing is to confirm paths first, then run your art scraper to avoid rework. Looking ahead

The next layer is to connect path hygiene with your broader Onion OS workflow. After you standardize directories and confirm behavior with fresh files, schedule backups that match your play habits. Weekly increments work for frequent sessions, while a post-marathon copy suits sporadic play. Export a tiny checklist that reminds you to verify at least one save and one state after changes. The habit reduces anxiety when updating cores or moving cards. The why is simple. Small, predictable steps prevent surprises and keep effort proportional to the risk of data loss.

It also helps to align saves and states management with other maintenance tasks. When you reorganize ROM folders or adjust BIOS placements, add a quick verification pass to ensure paths remain intact. If your device supports profiles or per-core overrides, document where they live and include them in your backup plan. A light record such as a text file in the backup root listing core versions and key settings pays dividends during recovery. This extra context narrows troubleshooting when a state refuses to load or a save appears missing after updates.

Finally, keep learning resources close for adjacent tasks that interact with saves and presentation. If you are preparing a clean drive or planning a full setup refresher, pair your backup work with a methodical setup walkthrough that reinforces folder conventions and safe practices. When placing ROMs for new systems or re-scraping art, cross-check directories to maintain consistency. Over time, these small alignments create a stable environment where saves load predictably and states provide fast checkpoints without surprises. A little structure up front yields smoother sessions and reliable restoration later.

Frequently asked questions

Do saves and save states use the same folder?

Usually not. Most cores separate in-game saves and emulator states into different directories. Verify both locations before backing up.

Why did my save states stop loading after an update?

Core versions or directory paths likely changed. Confirm the current state directory and test with a new state created after the update.

Can I move saves between cores for the same system?

Often yes for in-game saves, but formats may differ. Test on a copy, then standardize directories to keep backups consistent.

How often should I back up saves and states?

Match the schedule to your play habits. Weekly for frequent sessions, or after long play times if you game sporadically.

Do I need to back up BIOS with my saves?

Not for save integrity, but including BIOS can simplify restores. If storage allows, keep BIOS copies with your main archive.
