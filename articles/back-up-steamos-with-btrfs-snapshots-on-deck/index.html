Back Up SteamOS with Btrfs Snapshots on Deck

By Brittany Coleman • Updated January 4, 2026

Backing up SteamOS with Btrfs snapshots gives you fast, consistent restore points that feel predictable. This guide focuses on user data and configuration because SteamOS uses a protected system partition, and Btrfs excels at capturing subvolumes like home and config. You will plan subvolumes, run snapshot and send operations, and verify results before updates so your Deck feels quiet and safe during changes.

Key takeaways

  • Btrfs snapshots capture state quickly and restore user data reliably.
  • Snapshot home and config; SteamOS root stays read only by design.
  • Use send and receive to copy snapshots to another Btrfs filesystem.
  • Verify with mount checks, diff comparisons, and hash sampling.
  • Keep two rotating snapshots and one off device backup copy.

Plan the work

Start by scoping the backup to where Btrfs snapshots bring value. On Steam Deck, the system partition is read only, so focus on /home, Flatpak data under ~/.var, and any app configuration in /etc that you manage. A reliable baseline is to snapshot a @home subvolume and a lightweight @etc subvolume. This targets data that changes often and affects daily play. The tradeoff is that packages installed outside Flatpak may not be captured if they live in system areas. That is acceptable, because reimaging restores the base system while snapshots bring back personal state efficiently.

Choose a destination that preserves Btrfs features. If you snapshot locally, you can keep short term copies on the internal drive for quick rollbacks. For resilience, add a second destination on a Btrfs formatted microSD or external SSD and use btrfs send to replicate. Sending preserves subvolume metadata and makes incremental updates efficient when parent snapshots are retained. The tradeoff is that the destination must be Btrfs. If you require exFAT for cross device use, mirror with a file archive as a secondary export, accepting the loss of instant rollback semantics.

Define retention in simple, repeatable numbers. A practical pattern is two rotating local snapshots per subvolume and one off device snapshot per week. That keeps storage predictable while giving you three fallbacks. Storage cost varies by change rate. Games stored outside the snapshotted subvolumes do not impact size. If you install mods inside home, expect snapshots to grow after heavy sessions. Check free space before creating snapshots and avoid running below a safe threshold, such as leaving several gigabytes free, to prevent balance operations from stalling at inconvenient times.

Section highlights

  • Target home and lightweight etc to capture meaningful, changing state.
  • Plan local rotation and off device copies for resilient recoveries.
  • Ensure destinations use Btrfs to preserve metadata and efficiency.

Prepare environment

Confirm where Btrfs is available before proceeding. Many Decks ship with ext4 on internal storage, so consider using a Btrfs formatted microSD or external SSD to host subvolumes for data and snapshots. Create a labeled partition and mount point that you can recognize in Desktop Mode. This separation reduces risk and lets you move snapshots between devices. The limitation is that applications writing to internal ext4 cannot be snapshotted at the filesystem level. Mitigate by pointing large content libraries to the Btrfs device and keeping configs centralized under home, which you plan to snapshot and replicate.

Verify Desktop Mode access and basic Linux tools. You will use Konsole for commands and need sudo privileges to manage mounts and subvolumes. If you prefer a graphical helper, Timeshift can operate on Btrfs for user level captures, but command line gives tighter control and fewer surprises. Make sure the target drive is mounted with noatime to reduce churn during play. If your workflow includes file moves, consider reviewing a guide on microSD file systems and storage tuning to keep I/O smooth in games, as covered in microSD file systems and storage tuning.

Create predictable mount points. Use directories like /mnt/btrfs-data for active subvolumes and /mnt/btrfs-backups for the destination. Consistent paths make scripts and notes easier to share across sessions. Before trusting the path, unplug and remount once to ensure the label and fstab or autostart mechanism works. Listen for the faint click of the cable and feel for the drive spin or LED to confirm power. If KDE shows a prompt to mount, pick the same options each time. The tradeoff with automounting is potential race conditions at boot. Favor manual mounts before snapshot operations for maximum control.

Execute steps

You will create subvolumes, snapshot them, and replicate to an external Btrfs destination. The flow ensures you can roll back locally and also restore from another device. We use plain btrfs subcommands to keep behavior transparent. The approach assumes your data lives on Btrfs at the source and that the destination is mounted and writable. If your source is ext4, relocate change heavy folders, such as game profiles and saves, to the Btrfs volume and bind mount them back. This indirection requires care, but it enables snapshot semantics without reinstalling SteamOS or reformatting the internal drive.

This snippet creates read only snapshots with a timestamp and streams them to a second Btrfs filesystem so metadata remains intact. Expect nearly silent activity and a brief LED blink pattern while the copy proceeds. If you intend to run frequent backups, keep the last snapshot on both sides and switch to incremental sends using btrfs send -p with the previous snapshot as the parent. Incremental sends are faster and reduce wear. The limitation is that you must retain parent snapshots on both source and destination or the chain breaks. If that happens, fall back to a full send and re establish the new base snapshot.

Validate results

Confirm snapshots exist and mount cleanly before trusting them. Use btrfs subvolume list to see the new entries and mount a snapshot read only under a temporary path to inspect files. Browse for game saves, controller profiles, and config directories that should be present, listening for the reassuring soft whirr of the drive without grinding. Sample a few file hashes with sha256sum locally and on the destination to confirm equality. This spot check is not exhaustive, but it catches path mistakes early. If you see permission issues, review mount options and ownership, especially if Steam ran during the snapshot window.

Practice a non destructive rollback on a small subvolume. Create a temporary copy of a snapshot by sending it to a scratch location, then bind mount it over a test directory to simulate a restore. Open a game and confirm settings appear as expected. This dry run helps you feel the rhythm of a recovery without touching production paths. The tradeoff is time. Even a short simulation takes minutes, but the payoff is confidence when a real update lands. Keep a simple log noting which snapshot you tested and what visual or audio cues confirmed success.

Record essential metadata for each run. Capture the snapshot names, parent relations if using incremental sends, and free space before and after. A tiny table taped into your notes reduces guesswork during cleanups. For example, when removing old snapshots, ensure no incremental chains depend on them. Better situational awareness reduces mistakes during late night maintenance.

Troubleshoot and optimize

When btrfs send fails with an unsupported parent error, it usually means the destination lacks the specified base snapshot. Switch to a full send without the -p flag, or recreate the missing parent by transferring it first. If you encounter read only filesystem messages mid send, recheck the destination mount and remount read write. Under low space conditions, snapshot creation can fail quietly. Keep a buffer of free space and consider running a balance operation during maintenance windows, accepting temporary I/O impact while the filesystem reclaims and redistributes extents.

Slow replication often traces to a cable or hub bottleneck. Test with a direct USB connection and feel the firmer click when the plug seats properly, then watch throughput improve. If performance remains uneven, review mount options and confirm the drive is using a fast port. For higher reliability, avoid large queue depths during active gaming sessions and schedule backups when fans are calm and the room is quiet. That sensory checkpoint helps you notice spikes that suggest other workloads or background downloads interfering with sustained streaming.

Choose tools based on comfort and scope. Native commands are predictable and scriptable. Timeshift favors ease for desktop style restores, while Snapper offers snapshot policies and cleanup. On Deck, the simplest stack wins. Start with the native path and add tooling only when rotation policy or scheduling becomes tedious. The tradeoff is that GUI tools can obscure what gets snapshotted. Confirm their include paths match your plan for home and lightweight etc. When in doubt, run a manual snapshot after a GUI driven run and compare lists to ensure parity.

Quick start checklist

  1. Confirm Btrfs availability: verify source and destination filesystems support snapshots.
  2. Create subvolumes: set up @home and @etc under a consistent mount path.
  3. Run read only snapshots: use timestamped names to simplify rotation and logs.
  4. Replicate off device: stream snapshots with btrfs send and receive to Btrfs media.
  5. Mount and inspect: read only mount a snapshot and check expected files and hashes.
  6. Practice rollback: restore to a scratch path to confirm reversibility before updates.

Frequently asked questions

Can I snapshot the SteamOS root partition?

SteamOS uses a protected system partition. Focus snapshots on user data and configs. Restore the base system with the recovery image if needed, then reapply user snapshots for settings and saves.

Do I need Btrfs on the backup drive?

Yes for send and receive to preserve snapshot metadata. You can also export archives to non Btrfs storage, but you lose instant rollback and efficient incremental replication.

What if my internal drive is ext4?

Place change heavy folders on a Btrfs formatted microSD or SSD and bind mount them back. Then snapshot those Btrfs subvolumes and replicate to another Btrfs device.

How many snapshots should I keep?

A practical baseline is two local snapshots per subvolume and one off device copy weekly. Adjust based on change rate and available space.

Are snapshots enough for disaster recovery?

Snapshots help with quick restores but do not replace reinstall media. Keep one off device backup and the official recovery image for full system rebuilds.
