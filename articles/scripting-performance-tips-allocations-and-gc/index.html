Scripting Performance Tips: Allocations and GC

By Ethan Palmer • Published January 28, 2026

Performance work in scripting starts with seeing where allocations arise and how garbage collection interrupts frames. This guide curates repeatable techniques that reduce allocations, shape GC behavior, and stabilize frame time. Items were selected by how reliably they cut spikes across Unity, Unreal through C++, and Godot with GDScript or C#, with a bias toward patterns that scale in real projects. You will move from profiling to pooling to boxing fixes, while learning when an allocation is acceptable and when it derails a hot path. Expect concrete patterns and tradeoffs that favor predictable updates over theoretical micro-wins.

Key takeaways

  • Target allocations in hot paths first to prevent GC from hitting frames.
  • Use pools where lifetimes repeat, and cap growth to avoid leaks.
  • Eliminate hidden boxing and per-frame string churn in scripts.
  • Reuse buffers and builders to keep transient data off the heap.
  • Batch updates and schedule work so GC runs outside critical windows.
  • Profile regularly and treat GC as a budget with guardrails.

1) Profile allocations in hot paths

Start by claiming that only allocations inside hot paths meaningfully threaten frame time. A hot path is code that runs every frame or many times per frame such as Update loops, animation sampling, or physics callbacks. For example, sampling allocations on a character controller loop often reveals transient vector wrappers, string formatting in logs, or allocations from LINQ enumerators. Focus there before touching cold paths like menu setup. The tradeoff is scope blindness. Over-optimizing a cold scene initializer can waste hours and introduce regressions without changing gameplay responsiveness. Use per-frame allocation samples, flame charts, and diff captures when toggling features to see causality. When in doubt, insert counters or guard probes around suspected code, then correlate allocation deltas with frame spikes to ensure your fix targets the real culprit.

Next, assert that ranking allocations by size alone misses death by a thousand cuts. Ten tiny 64 byte allocations every frame can force a GC after a few seconds in a gameplay loop, whereas one large allocation at level load may be harmless. A concrete example is per-frame creation of small structs boxed as objects, which drip-feed the young generation until GC interrupts combat. The tradeoff is analysis time. Sampling across devices and build types multiplies test runs, but it avoids optimizing for a single editor profile. Build a simple rule of thumb. Fix anything that allocates inside every-frame callbacks, especially in inner loops. Defer low-frequency allocations unless they cascade into stutters during camera pans, weapon fire, or UI updates where cadence matters most.

Section highlights

  • Prioritize allocations inside per-frame loops and inner iterations first.
  • Rank by frequency and spike impact, not just single allocation size.

2) Pool objects with caps and reset rules

Object pooling can remove recurring allocations when lifetimes repeat predictably. Consider projectiles, UI list items, or temporary effect nodes that churn every few seconds. A basic pool hands out preallocated instances, then resets and returns them after use. The example win is a shooter where bullet instances are reused across waves, eliminating per-shot allocations and easing GC. The tradeoff is memory pressure. Unbounded pools hoard unused instances after a spike and mask leaks. Add hard caps, idle trimming, and a reset function that clears references and restores defaults. In engines like Unity or Godot, also guard against double-free by tracking a simple in-use flag. When pooling physics-enabled objects, ensure that velocities, transforms, and event subscriptions are reset to prevent cross-frame ghosts.

It demonstrates a reset callback and timed trimming so the pool does not grow forever after a combat burst. Expect fewer allocations during waves and steady memory after the peak ends, at the cost of a small background maintenance pass.

Section highlights

  • Pool repeatable lifetimes and enforce caps with reset rules.
  • Trim idle items to prevent growth after temporary spikes.

3) Eliminate boxing and LINQ churn

Hidden allocations often stem from boxing value types and convenient LINQ calls in C# gameplay scripts. Boxing turns a struct like Vector3 into an object, placing it on the heap and feeding GC. Similarly, LINQ Select or Where in per-frame loops allocates enumerators and closures. For instance, filtering enemies with a LINQ chain each Update can allocate enough to trigger GC during combat. Replace with cached lists, for loops, or preallocated scratch buffers. The tradeoff is clarity. Hand-written loops can reduce readability and introduce subtle bugs when predicates change. Keep a tested helper that mirrors the intent without allocations, and use it only in hot code. Outside hot paths, keep expressive LINQ to speed iteration velocity and avoid premature complexity.

A practical rule is to scan for interface-typed collections and logging that embeds structs into interpolated strings, which silently box values. Prefer generic overloads and preformatted messages buffered with a shared StringBuilder. For example, converting Debug.Log to a pooled builder that clears between uses prevents per-frame string objects. The downside is an extra discipline step. Builders must be returned or cleared, and accidental cascade into async code can leak data. Set conventions. Builders stay local to a frame, and hot-path lists always come from a reusable pool. This preserves script ergonomics elsewhere while keeping the hottest loops allocation-free where it matters most.

Section highlights

  • Replace boxing and LINQ in hot paths with cached structures.
  • Adopt builder and list reuse conventions to avoid per-frame churn.

4) Reuse buffers and builders

Reusing buffers turns many small allocations into stable memory that you manage explicitly. Allocate scratch arrays, temporary structs, and a per-thread StringBuilder once, then reuse them across frames. A typical example is pathfinding or visibility checks that need short-lived lists. Using a ring buffer or thread-local pool for these lists prevents churn and reduces GC pressure. The tradeoff is potential fragmentation and stale data if reset rules are lax. Always clear or overwrite, and prefer fixed maximum capacities that reflect observed peaks from profiling. When peaks are rare, degrade gracefully by allocating a one-off overflow buffer and logging the event, rather than permanently inflating your steady-state memory footprint.

Another angle is to align buffer sizes with cache behavior and the engine’s update cadence. For instance, a 256 element ring can match typical AI batch sizes, avoiding reallocations and giving predictable latency. On the flip side, oversizing buffers worsens locality and increases copy time during clears. Balance by measuring hit rates and time spent in resets. If 95 percent of frames use under half the capacity, trim the buffer and add a small growth path with a cap. This keeps your buffers tight while preserving headroom for rare spikes that otherwise cause stutter when the allocator steps in at the worst possible moment.

Section highlights

  • Allocate scratch buffers once, then clear and reuse each frame.
  • Size buffers from measured peaks and cap rare overflow growth.

5) Manage lifetimes to shape GC timing

You can influence when garbage collection runs by structuring lifetimes and batching disposals. Group short-lived objects so they die together outside critical windows, like just after a boss spawn cut-in rather than during combat. In engines where you can trigger or configure GC, schedule collection in loading screens or low-intensity moments. The tradeoff is complexity and the risk of trading one spike for another. For example, forcing a collection too aggressively can steal time from a brief quiet period and still push a hitch into the next frame. Aim for amortization. Free a chunk of objects per frame over several frames, and use budgets that adapt to frame time rather than fixed counts.

Another lever is decoupling reference chains to avoid accidental retention. Subscription patterns, static caches, and long-lived singletons often hold references that extend object lifetimes beyond intention. For instance, an event bus without unsubscribe logic keeps dead UI elements alive, bloating young generations and delaying reclamation. The fix is a clear lifecycle policy. Use weak references for listeners that are not critical, or tie subscriptions to explicit scopes that nullify references on exit. The downside is bookkeeping overhead and occasional missed events when weak listeners are collected. In practice, the gain in predictable memory churn outweighs the rare edge case, and your GC has fewer surprises during boss phases where timing must stay consistent.

Section highlights

  • Batch disposal and schedule GC-friendly windows to reduce hitches.
  • Break reference chains so objects die when intended and predictably.

6) Batch updates and jobify hot loops

Batching and job systems reduce both allocation frequency and per-frame pressure by restructuring work. Combine many small updates into larger chunks processed in fixed phases, and push CPU-heavy jobs into parallel workers where appropriate. For example, batching projectile updates into a single system tick reduces repeated iterator allocations and limits points where new objects are created. Jobifying AI queries lets you reuse shared buffers per job and keeps allocations off the main thread. The tradeoff is complexity in synchronization and debugging. You must establish safe ownership of buffers, and handle contention without resorting to per-job allocations. Start with clear ownership rules and small prototype jobs before scaling to whole subsystems.

Reshaping work also improves cache locality and reduces the need for transient data. Data oriented layouts pair well with ECS style systems, where components of the same type are processed together in contiguous memory. Even without a full architecture shift, grouping similar entities and iterating with index-based loops gives many of the benefits. The downside is rigidity. Systems that process batches at fixed moments can impose latency on rare one-off events that used to occur immediately. Address this with small event queues that preallocate space and flush each batch, avoiding heap churn while preserving responsiveness for critical interactions like parry windows or damage resolution during combat.

Section highlights

  • Process similar work in batches and parallel jobs to curb churn.
  • Adopt data oriented layouts to reuse buffers and improve locality.

7) Assets, strings, and serialization without spikes

Asset and data pipelines can cause major allocation bursts that collide with gameplay. Lazy-loading JSON or building long strings for UI every frame allocates heavily and invites GC. Prefer binary formats for hot data, cache parsed results, and pre-slice UI strings into tokens or IDs that map to localized text. For instance, caching deserialized enemy stats at level load avoids per-encounter parsing. The tradeoff is upfront memory and versioning friction. Binary formats require schema discipline and migration steps when fields change. Mitigate by keeping a thin translation layer at load time and storing only the minimal runtime representation that gameplay systems need, leaving the source format for editor tooling.

Streaming also benefits from chunked reads and object reuse. Read assets in fixed-size blocks into a reusable buffer and reuse deserializer instances where safe. For UI, virtualize scrolling lists and recycle item renderers instead of constructing and discarding widgets during rapid scroll. The limitation is more moving parts and careful error handling, especially when network or disk hiccups occur. Build watchdogs that fall back to smaller chunks on transient failures and log allocation counts around streaming events. With this guardrail, string and serialization work no longer competes with frame-critical logic, and GC has fewer opportunities to interrupt the most visible interactions in your game.

Section highlights

  • Cache parsed data and prefer binary formats for hot paths.
  • Stream with reusable buffers and recycle UI elements during scroll.

8) Verify with engine-level perspective

Ground your fixes in how the engine turns inputs and data into frames. Rendering, physics, assets, scripting, and optimization interact, so a scripting change can shift cost elsewhere. For example, moving dynamic string formatting out of Update into a UI binding can reduce allocations in gameplay but increase GC during layout passes. Cross-check with an engine-level tour to see where work lands and whether batching introduces new ordering issues. The tradeoff is more disciplines in the loop. Bringing rendering and physics owners into performance reviews takes time, but it prevents whack‑a‑mole optimizations. Keep a short architecture map that identifies where allocations can seep in and which subsystems own them.

When learning the scripting model, review how components communicate, how loops run, and how data flows. A comprehensive guide to scripting, components, loops, and data flow in engines helps you see patterns that cause churn. Likewise, a complete tour of rendering, physics, assets, scripting, and optimization clarifies how inputs become a responsive world so you can place fixes where they stick. The tradeoff is reading time, yet the perspective saves rework. With shared vocabulary across teams, your allocation budgets align with engine phases, so GC pressure is less likely to surprise you during critical beats or platform certification performance tests.

Section highlights

  • Align fixes with engine phases to avoid shifting spikes elsewhere.
  • Leverage broad engine tours to place durable allocation changes.

9) Looking ahead: plan GC budgets and reviews

Treat GC as a tracked budget with thresholds per scene, not a background detail. Define allowed allocations per frame in hot systems and set alerts for sustained overages. For example, a combat scene might allow near zero GC allocations across successive frames, while a hub area tolerates small bursts during dialogue. The tradeoff is rigidity under changing content. New mechanics or enemy types may push legitimate allocations. Bake periodic reviews into your process. When budgets fail, either adjust targets with evidence or prioritize fixes. This pushes teams to decide deliberately rather than letting allocations drift until a late surprise. Keep the budget visible in dashboards and guard it like draw calls or memory limits.

Institutionalize habits that keep the wins. Add a lightweight checklist for new hot-path code that asks about allocations, boxing, and pooling plans. Encourage engineers to compare composition and data oriented layouts when lifetimes are complex, and point them to ECS patterns when decoupling helps processing. The tradeoff is some up-front ceremony that may feel heavy for prototypes. Balance by limiting the checklist to a few high-signal questions and by revisiting it after milestones. Over time, teams internalize the patterns and can relax the process without losing the performance intuition that protects frame time from GC surprises.

Section highlights

  • Set per-scene allocation budgets and monitor sustained overages.
  • Adopt lightweight reviews so hot-path code avoids GC pitfalls.
