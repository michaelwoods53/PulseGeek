Migrate Saves When Updating Onion OS Safely

By Sarah Carter • Published February 22, 2026

Updating Onion OS is simpler when you plan how to migrate saves. This guide focuses on copying save data reliably while preventing corruption, using verifiable methods and validation steps that match most handheld workflows. You will learn what to back up, which tools to use for file integrity, and how to confirm that games still load. The process works across Windows, macOS, and Linux with SD cards or adapters, and it minimizes risk by verifying checksums and timestamps. If you encounter mismatches, you will know which comparisons to run before booting. The result is a safe handoff of saves during system updates with a clear record of what changed and why it is trustworthy.

Key takeaways

  • Back up entire save directories before changing or updating Onion OS.
  • Use copy tools with verification flags and preserve timestamps and attributes.
  • Validate results by comparing counts, sizes, and hashes of migrated saves.
  • Resolve mismatches before first boot to avoid silent save corruption.
  • Document what you moved and keep one known good, read only backup.

Plan the work

Start by defining scope so you copy only what matters and nothing risky. Identify where Onion OS stores saves, states, and config such as typical subfolders like Saves, BIOS, or RetroArch configs if used by your device. A quick inventory prevents missing edge cases like per-core save directories or SRAM versus save states, which sometimes live in different paths. Create a simple checklist that names each folder and its expected size range so anomalies stand out. This also helps you decide whether to migrate settings or only saves to reduce cross-version conflicts. The tradeoff is convenience versus stability, and choosing saves only cuts compatibility risks when formats change between releases.

Next, choose a migration method that balances speed and verification. File-level copy with tools that preserve attributes is safer than drag and drop because timestamps and permissions can matter to emulators. For example, using rsync with archive mode or a Windows copy utility that keeps metadata reduces re-indexing quirks after an update. Plan for at least one integrity check such as a hash comparison on representative files. While full-image cloning offers simplicity, it can carry over filesystem errors or stale caches, so use it only when you need a byte-for-byte snapshot of the old card.

Establish recovery points before touching data to reduce risk during the update. Create one read only backup on external storage and label it clearly with date and device name. This protects against accidental overwrites or partial copies if power or USB disconnects occur. Capture a small manifest that lists folder counts and total sizes to speed later validation. If your update also changes emulator cores or directory layouts, note expected mapping differences and plan temporary redirects or symlinks after the update. The tradeoff is a few minutes of prep for a major reduction in uncertainty when comparing results after migration.

Prepare environment

Stabilize your environment so copying saves is repeatable and low risk. Use a reliable card reader, avoid USB hubs with flaky power, and keep the SD write lock engaged on the backup media. Ensure disk health looks normal using your OS disk utility and unmount safely before swapping cards. On Windows, verify you can see hidden files. On macOS or Linux, confirm mount points and filesystem support to avoid silent attribute loss. This upfront check catches oddities like exFAT inconsistencies that can derail validation. As a safety measure, disable any background sync apps that could race file timestamps while you copy.

Gather the right tools that preserve metadata and offer verification. On macOS or Linux, rsync with archive mode handles ownership, permissions, and times in one step. On Windows, robocopy with the appropriate flags keeps timestamps and retries on transient errors. Plan a hashing tool such as shasum or certutil to sample-check files after migration. The tradeoff between GUI and CLI is comfort versus control, and CLI options make it easier to script repeatable operations. Keep a small text file ready to log commands and results so future updates reuse the same reliable steps.

Decide on directory mappings if the new Onion OS layout differs. Some builds revise where saves or cores live, which can move subfolders or rename paths. Create a mapping table that pairs old and new locations so you do not scatter files. If needed, schedule a second pass to migrate only the subset that matches the new core versions. When uncertainty exists, keep original structure in the backup and copy into the new layout with intent instead of merging automatically. This avoids conflicts that can surface as missing saves inside emulators that expect specific folders.

Execute steps

Perform the copy with options that preserve metadata and allow validation. Mount both the source SD and the destination updated SD or staging folder. Use a single command that archives attributes and prints a summary so you can log outcomes. Copy saves and states first, then optional configs if you decided to move them. Avoid open files while copying to reduce partial writes. If your OS supports it, enable read-after-write verification or run a separate hash check on a sample set. This controlled copy minimizes mismatches that would surface as missing saves or corrupted states after the update.

For macOS and Linux, archive mode with rsync is both concise and careful, capturing permission bits and timestamps needed by some emulators. A verbose progress view reduces anxiety by making throughput and file counts visible as you move. If you maintain large states, consider using checksums on a few representative files to confirm integrity without spending hours hashing every byte. On Windows, you can apply a similar principle with a robust copy tool that supports retries and logs. Both approaches favor predictability that you can repeat every update with the same command options.

When copying from an older Onion OS layout into a new structure, segment the migration. Copy saves and states to their mapped destinations first, boot once to confirm discovery, then consider migrating configs cautiously. If cores or emulators changed versions, old configuration files might cause behavior differences. In that case, prefer clean configs and only restore controller mappings or hotkeys that have not changed. This staged approach trades speed for confidence and reduces the chance of subtle incompatibilities that waste time later. Keep your original backup untouched until at least one full play session confirms proper saving and loading.

Validate results

Confirm the migration with simple, repeatable checks before booting the updated system. Compare file counts and total sizes for each mapped directory against your manifest. Spot check several save files with hashes to prove that content stayed identical. If you find differences, re-copy only the affected files to avoid disturbing good data. Record results in your log so you can prove the state of the system if future issues arise. This extra minute prevents silent corruption that might only appear after long sessions or multiple save writes, where small mismatches can snowball into lost progress.

After on-disk checks, perform an application-level validation. Boot the updated Onion OS and open two or three games that you know have recent saves. Load and then save again to ensure both read and write paths work as expected. Watch for behaviors like defaulting to a new profile or failing to detect states, which often indicate path changes or permission issues. If discovery fails, verify directory mappings and confirm the emulator’s configured save path. This step ensures you test the real workflow that matters rather than only the filesystem view.

Finally, review timestamps and permissions for suspicious patterns. Saves created years ago that suddenly appear “new” may have been copied without original times, which can confuse sorting or auto-sync tools. If you rely on external sync services, configure them to respect the destination’s state and avoid two-way merges until stability is proven. Keep the read only backup intact until at least one full session confirms stable saves and states. This discipline helps isolate variables and keeps later troubleshooting focused on genuine incompatibilities rather than copy mistakes.

When hash comparisons differ, check for interrupted copies or files locked by the OS. Re-run the copy for affected items with verbose output to confirm replacement. If permissions look off, reapply attributes or recopy with options that preserve timestamps. Frequently asked questions

Do I need to migrate configs or just saves?

Migrate saves and states first. Only copy configs if you know versions are compatible. When in doubt, prefer fresh configs and restore specific controller mappings or hotkeys as needed.

Why do some saves not appear after updating?

Paths or directory names may have changed. Confirm emulator save paths, verify folder mappings, and check permissions. If counts mismatch, recopy affected files and recheck discovery in-game.

Is hashing every file required?

No. Sample several representative saves and all recent files. If any mismatch appears, expand hashing. Full checks are slower and usually unnecessary when counts and sizes already match.

Can I just clone the entire SD card?

You can, but only when the source is known healthy. Cloning copies errors and stale data too. File level migration with verification reduces risk and allows cleaner layout updates.

What if the copy was interrupted?

Re-run the copy command with verification flags. Replace only changed or missing files, then repeat validation checks. Keep the original backup read only until in-game saves load normally.
