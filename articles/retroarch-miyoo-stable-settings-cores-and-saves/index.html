Saves, storage, and integrity

Treat saves as critical data, because recovery is harder than prevention. Separate SRAM, save states, and config backups into clearly labeled directories, and standardize naming to avoid overwrites. Enable autosave cautiously and verify it does not conflict with state usage in quick sessions. For a practical deep dive into save states, SRAM, backups, compression, and SD choices, see guidance on save states, SRAM, backups, and storage organization. The tradeoff with aggressive autosave is potential performance blips at state write, so test on a quiet screen before relying on it during boss fights.

Back up on a schedule, because microSD cards fail unpredictably. A weekly copy of saves and states to a computer takes minutes and protects dozens of hours of progress. Keep two generations so accidental overwrites can be rolled back. If you compress archives, choose formats that favor reliability over maximum reduction to simplify restores. Testing a sample restore monthly verifies your process. Avoid moving files while the device is writing to storage, since that risks partial saves that later refuse to load. Unmount cleanly before removing the card.

Respect performance during save features, because heavy options can cost frames. Rewind and frequent state writes add CPU load and disk access. If a demanding core already sits near the limit, disable rewind and reduce save frequency until frame pacing stabilizes. A safe alternative is manual state use during calm moments. When you need more responsiveness, revisit latency tuning with modest runahead rather than pushing save-related features that stress IO. This strategy preserves the feel of tight controls while keeping data safe from interrupted writes.

Document where things live, because future you will forget. Record the exact paths for states, SRAM, and thumbnails, and include brief notes on how they are rotated or archived. A simple text file in the config folder can prevent confusion months later when you change cores or move to a new card. If you are still refining your core selection and encounter input delays, revisit latency advice at low-latency configuration with cautious sync before assuming storage is the culprit.

Frequently asked questions

Should I enable runahead on every core?

No. Start with one frame on lighter 8 and 16 bit cores, verify stability, and increase only if frame pacing and audio remain steady. Heavier cores may lose performance with aggressive settings.

Are shaders safe to use on Miyoo?

Yes, if they are lightweight and tested. Enable a single preset after confirming stable performance without effects. If scrolling or text clarity degrades, turn the shader off and recheck timing.

What is the safest way to back up saves?

Copy both SRAM and state folders to a computer on a schedule, keep two generations, and test restoring a small sample monthly. Always unmount cleanly before removing the SD card.

Do autosave and rewind affect performance?

They can. Autosave writes and rewind buffers add CPU and IO load. If frame pacing suffers, reduce write frequency, disable rewind, or apply latency improvements instead of heavier save features.

When should I switch to a different core?

Switch when a title shows persistent timing issues, audio artifacts, or crashes after baseline tuning. Choose the next-most-accurate core and document why, so you avoid retesting the same path later.
