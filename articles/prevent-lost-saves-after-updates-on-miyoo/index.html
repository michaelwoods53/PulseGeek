Prevent Lost Saves After Updates on Miyoo

By Logan Ward • Published March 11, 2026

Updates improve stability, but they can also orphan saves if paths shift or databases rebuild unexpectedly. This guide prioritizes saves, updates, and Miyoo reliability by focusing on repeatable habits that survive firmware or core changes. Each item was chosen because it prevents the two most common loss modes: path mismatches and interrupted writes. You will find concrete checks, short examples, and the tradeoffs that matter when time is tight or storage is limited. Use them together as a checklist before changing anything that might affect how your device reads and writes progress.

Key takeaways

  • Back up savefiles and savestates before any Miyoo firmware change.
  • Keep ROM names stable so cores always map the same save paths.
  • Prefer FAT32 with verified integrity to reduce post-update corruption.
  • Test one game restore after updating to confirm save visibility.
  • Avoid power loss during writes by charging and using quality cards.

1) Pre-update backup habit that captures saves reliably

Make a complete backup of savefiles and savestates before every update because a single path change can hide progress until directories are restored. A simple rule of thumb is to copy both the savefiles directory and the savestates directory, plus any per-core config that references save paths. For example, copy a top-level Saves folder and the RetroArch savefiles and savestates folders to a computer before installing new firmware. The clear advantage is fast recovery if an update relocates default directories. The tradeoff is time and storage, especially with large savestates, but you can trim by backing up only recent titles. This habit works because it prevents divergence between expected and actual locations and lets you roll back selectively without reinstalling the entire SD image.

2) Stable save paths and directory structure

Keep save paths consistent so updates do not strand files in obsolete folders. The practical move is to confirm where each core writes savefiles and savestates, then align your SD layout to that expectation. For instance, ensure Saves, savefiles, and savestates folders exist, and check core settings for path overrides after updating. If a new build moves defaults, mirror your old hierarchy or adjust the configuration so it still points to your known locations. When paths drift, you will see games booting fresh profiles despite existing saves. The benefit is predictable restore behavior, but you must track differences between cores that store SRAM and snapshot states separately. To avoid confusion, document your chosen layout and reconcile mismatches after any system upgrade that touches core versions or global directories.

If your games still do not appear or saves seem missing, verify the ROM directory layout and scan behavior. A tidy structure helps the system index titles and locate matching saves tied to ROM names. Follow a clean scheme for ROMs, BIOS, saves, and thumbnails so the database scan behaves consistently after upgrades. When paths are scattered or mislabeled, the device may boot slowly or ignore some entries. 3) File system choice and integrity checks

Choose a compatible file system and verify integrity before updating, because corruption often masquerades as lost saves. FAT32 is widely supported on handhelds and avoids edge cases some firmwares show with exFAT during unclean ejects. A safe workflow is to run a file system check, ensure proper allocation unit size recommended by your formatting tool, and then back up. For example, a card formatted FAT32 with verified sectors will reduce the chance that a sudden power cut produces orphaned directories where saves reside. The advantage is predictable behavior across cores, but the tradeoff is file size limits that may matter for large assets. If you consider exFAT for convenience, test read and write operations plus safe ejection on your specific device before trusting it for saves.

If the device intermittently loses visibility of the SD card, address that before any update that could rewrite configs. Intermittent detection can break writes mid save, producing partial files or zero-byte savestates that resemble path issues. Work through format verification and slot cleanliness so the update process does not occur on a flakey storage foundation. 5) Keep ROM names and cores consistent

Keep ROM filenames and chosen cores consistent so saves map correctly after updates. Many cores derive savefile names from the ROM base name and core identifier, which means renaming a ROM or switching cores can make existing progress appear lost. For example, changing Sonic_2.md to Sonic2.md may fork the save mapping, and moving from one Genesis core to another can produce a separate save path. The advantage of fixed names and stable cores is predictable continuity through upgrades. The tradeoff is that you give up opportunistic core experiments. If you must rename or switch, copy the old savefiles and savestates to the new expected names and paths, then test a single title. When lists look empty, repairing filters and the game database can also restore visibility for renamed files after an update.

6) Test a restore on one title before going wide

Run a single-game smoke test right after any update to confirm saves still attach. Pick a game with both an SRAM save and a savestate, restore your backup if needed, and launch it to verify both load correctly. This test catches path changes early, before you play for hours on a forked directory. For example, launch a familiar platformer, load the in-game save, then load the savestate and note whether both work. The advantage is rapid validation with minimal time. The tradeoff is that a few cores treat save locations differently, so test at least one representative from each system you care about. If either test fails, pause and check path overrides, ROM naming, and whether the update reset configuration directories to defaults that ignore your established save locations.

7) Protect writes with stable power and healthy cards

Protect save writes by charging the device, using a reliable SD card, and avoiding unsafe ejection, because interrupted writes often create zero-byte files that updates later expose. A sensible routine is to update with the battery charged and run a short verification pass that opens and closes a game to trigger a proper flush. If the card shows intermittent read or write delays, consider replacing it and testing with known good media from a reputable brand. The upside is fewer silent corruptions masquerading as path issues. The tradeoff is the cost of better media and time spent verifying. If you recently reformatted or replaced cards, confirm compatibility guidelines for larger capacities and address long filename pitfalls that can interfere with scans and consistent save discovery on some setups.

When saves still go missing after a crash or a frozen boot during an update, focus on safe recovery before resuming normal play. Start with read-only mounting if supported, make a full image backup, and then run file checks. If the card mounts but shows damaged entries, use a clean computer to copy off all intact save directories first. Frequently asked questions

Which folders should I always back up before an update?

Back up the Saves folder, RetroArch savefiles, RetroArch savestates, and the RetroArch config directory if it contains path overrides. These locations typically cover in-game saves, savestates, and settings that map saves.

Why do my saves disappear even though the files are still on the card?

Saves often look missing when the ROM filename or core changed and the system now looks for a different save path. Restoring the old name or copying the save to the new expected name usually fixes visibility.

Is exFAT safe for Miyoo save storage?

ExFAT can work but some setups show issues after unsafe ejects or power loss. FAT32 is widely compatible and more forgiving on many devices. If you use exFAT, test reads and writes and always eject safely.

How do I check if a save file is corrupted?

Look for zero-byte files or timestamps that do not change after saving. Try loading the file on a computer emulator that supports the same core format. If it fails there, restore from your pre-update backup.

What single step prevents most post-update save loss?

A pre-update backup that captures savefiles, savestates, and configs prevents most loss scenarios. It allows fast rollback when paths or defaults change during firmware or core updates.

Looking ahead

Build a lightweight routine you will actually follow during every update: confirm stable paths, run your save backup script, validate one game, and only then expand changes. Over time, consider standardizing card brands and capacities you trust and documenting your preferred directory layout so future migrations are predictable. If you plan to reorganize ROMs, schedule a short pass to rebuild the library and retest mappings before a longer play session. With these habits, updates become routine maintenance rather than risky events, and your progress remains a constant companion rather than a fragile artifact of last week’s configuration.
