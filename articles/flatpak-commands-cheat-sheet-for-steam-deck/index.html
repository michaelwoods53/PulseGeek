Flatpak Commands Cheat Sheet for Steam Deck

By Brittany Coleman • Published January 21, 2026

Here is a concise Flatpak commands cheat sheet tuned for Steam Deck users who want reliable results without surprises. Each item explains when to use a command, shows a short example, and notes tactile or visual cues you might notice while it runs. I focus on commands that reduce friction during installs, updates, remote management, permissions, and troubleshooting, so your deck feels steady in hand while the terminal hums along.

Key takeaways

  • Prefer user scope for apps and system scope only when necessary.
  • Update with awareness of rollbacks to protect working configurations.
  • Keep remotes minimal and trusted to reduce unexpected app behavior.
  • Change Flatpak permissions incrementally and document every tweak.
  • Use verbose flags sparingly to diagnose slow or failing commands.

1) Install and remove apps reliably

Default to user installs for Flatpak apps to keep Steam Deck system updates lightweight and low risk. The claim is simple. Installing to --user avoids mixing app payloads with the system partition, which SteamOS may replace during system updates. For example, install Firefox with flatpak install --user flathub org.mozilla.firefox and you will feel the terminal scroll steadily while the UI remains responsive. Removing is symmetric using flatpak uninstall --user, which cleans the app while leaving unrelated runtimes intact. The tradeoff is shared devices. If multiple accounts need the same app, a system-wide install using --system reduces duplication at the cost of requiring sudo and more careful maintenance across updates.

Use search and explicit IDs to avoid wrong packages when similar names appear across remotes. The guiding rule is to verify the app ID and the remote before installing. Example. Run flatpak search firefox then install using the full identifier and chosen remote. You will notice a short pause as metadata resolves, then a clear prompt listing remotes and permissions. The tradeoff is speed. Searching adds a step, but it saves time later by preventing accidental installs from unofficial sources. If you prefer faster paths, cache the exact app IDs you trust and reuse them, accepting slightly less discovery at install time.

Section highlights

  • Favor user scope for safety and simpler SteamOS updates.
  • Search and install using full IDs to avoid wrong packages.

2) Update, downgrade, and rollback

Update with awareness of what will change and how to retreat if something breaks. Use flatpak update to refresh apps and runtimes, then keep rollbacks reachable with flatpak update --commit=COMMIT or flatpak install --reinstall when an earlier build is still available on the remote. For instance, after an update, you might hear the fan pick up briefly while the disk activity indicator stays steady, signaling runtime downloads. The tradeoff is storage churn. Frequent updates can accumulate old data until deduplication catches up. A practical rhythm is weekly updates unless a security notice suggests sooner action, keeping recovery steps documented so you can reverse a single app without disturbing stable ones.

Selective upgrading limits blast radius when you only need a fix for one tool. Try flatpak update org.mozilla.firefox rather than blanket updates, then verify behavior before touching other apps. On the Steam Deck, this feels gentler. You will notice a shorter progress bar and less UI interruption. The downside is fragmentation. Different apps may rely on different runtime versions, and waiting too long can force larger jumps later. Use a small maintenance window and stabilize one app at a time. If you want deeper guidance on safe refreshes with rollback awareness, see the guide about updating Flatpak applications on Steam Deck safely with rollback awareness in the related reading.

Section highlights

  • Update selectively and keep a rollback path documented.
  • Stagger upgrades to reduce risk and isolate failures.

3) Manage remotes cleanly

Keep remotes minimal and trusted to reduce surprises from unofficial builds. List configured sources with flatpak remotes, add Flathub with flatpak remote-add, and remove anything you do not recognize. For example, if you use only Flathub, your search results become predictable and installs feel consistent, like steady progress messages without permission oddities. The tradeoff is choice. Limiting remotes narrows early access to niche builds or betas. When you do need prerelease software, consider adding a beta remote purposefully and documenting why it exists. If you are setting up Flathub for the first time on the Deck, refer to the step by step walkthrough that shows how to add Flathub safely and unlock a wide catalog.

Verify remote details before trusting app listings to avoid impersonation and signature issues. Run flatpak remote-info flathub org.mozilla.firefox to inspect signatures and metadata, then compare the application ID with what your launcher shows. You will notice a clean chain of information and signature status in the output. The tradeoff is time spent validating. It adds a minute now to save hours later if an app behaves oddly. If you are experimenting with pre-release channels, a short companion guide explains how to add the Flathub Beta remote and manage app channels carefully without losing track of stable builds.

Section highlights

  • Limit remotes to trusted sources for consistent search and installs.
  • Inspect remote info and signatures before relying on an application.

4) Understand permissions and sandboxing

Grant the minimum Flatpak permissions an app needs, then expand only when a real task fails. The sandbox model isolates applications by default, so commands like flatpak override --user --filesystem=xdg-download open specific doors while keeping others closed. A practical example is enabling the Downloads folder for a browser while leaving home directory access untouched. On the Deck, the result is subtle. Apps feel normal, but file pickers show only what you allow. The tradeoff is friction. Too little access frustrates workflows until you fine tune. A reversible approach is to record each override and test one change at a time. If you prefer a GUI, use the guide that explains how to adjust Flatpak app permissions on Steam Deck safely and reverse them later.

Favor granular filesystem and device flags over broad allowances to keep risk contained. Rather than --filesystem=home, try --filesystem=xdg-pictures:ro for read only access to images. This keeps creative tools functional without exposing secrets or configs elsewhere. You will notice predictable file dialogs and fewer editor warnings. The limitation is advanced apps that need system features like DRI, PulseAudio, or portals for printing. In those cases, enable only the required interfaces and retest. Document the reason for each change so future you understands what to keep after an update or a SteamOS refresh.

Section highlights

  • Open the smallest permission needed and record every override.
  • Prefer specific read only paths over broad home directory access.

5) Run, troubleshoot, and clean

Run apps with logs when behavior feels off, then prune leftover data deliberately. Use flatpak run normally, and add --verbose to surface portal or permission errors that are otherwise invisible. For a concrete pass, try flatpak run --verbose org.mozilla.firefox while watching for warnings about sandboxed paths. You will hear a quiet pause before the window appears, and messages scroll with enough detail to guide the next step. The tradeoff is noise. Verbose logging is chatty, and rare warnings can be harmless. After uninstalls, clean residues with flatpak uninstall --unused to remove unneeded runtimes while keeping shared components. This frees space gradually without breaking healthy apps.

Diagnose startup failures with staged resets before heavier measures. Start with flatpak repair to check refs and metadata, then reinstall the app with flatpak install --reinstall if its files look corrupt. The terminal will show steady validation lines, and you will feel the Deck settle as CPU spikes recede. If a specific app refuses to launch, a detailed troubleshooting guide can walk through clear checks and resets that match common Deck symptoms. The tradeoff is time spent isolating issues. Rushing to wipe everything is faster but risks losing custom settings that were not backed up.

Section highlights

  • Use verbose mode to surface portal and permission errors quickly.
  • Clean unused runtimes after removals to recover storage safely.

6) Integrate with Desktop Mode

Use Desktop Mode for navigation and file checks while relying on Flatpak CLI for precise state changes. The combination speeds routine tasks. For example, search menus in KDE to confirm app IDs and verify where launchers live, then apply flatpak override or flatpak update in Konsole to make the actual change. The sensory tell is fluid switching. You click to inspect, then type to enact, avoiding guesswork. The tradeoff is context switching, which can feel scattered if you do not keep notes. A practical approach is to maintain a tiny scratch file on the desktop with the exact commands you run. If you are still learning, a comprehensive Desktop Mode walkthrough explains navigation, app management, files, and networking with reproducible steps that map cleanly to the Deck.

Add Flatpak apps to the Steam library only after validating launch behavior in Desktop Mode. First run the app normally and confirm it opens without permission errors. Then use Add a Non Steam Game and select the Flatpak launcher that appears in the menu. You will notice cleaner controller input mapping when the Desktop Mode launcher matches the Flatpak ID. The limitation is complex apps that spawn helper processes not recognized by Steam Input at first. In those cases, test with a short session and adjust launch options before committing to Big Picture time.

Section highlights

  • Use Desktop Mode to inspect and CLI to apply precise changes.
  • Validate Flatpak launchers before adding entries to the Steam library.

7) Pick known good app examples

Start with widely used Flatpak apps because broad usage reveals issues early and documentation is richer. Install a popular browser, chat client, or editor to verify your environment behaves predictably. For instance, add Google Chrome, Discord, or Visual Studio Code via Flathub and watch for consistent permission prompts and normal first launch times. You will notice familiar UI and predictable updates that make the Deck feel stable. The tradeoff is that well known apps may come with larger runtimes and heavier footprints. If you run lean, consider lighter tools while keeping one mainstream install for comparison during troubleshooting.

When evaluating alternative formats, understand how portability and updates differ from Flatpak. AppImage offers self contained bundles and easy removal, while Flatpak provides sandboxing plus managed updates through remotes. Try one example each to feel the difference in startup, theming, and permissions. You will hear fan behavior change under heavier runtimes and see different dialogs for file access. The tradeoff is maintenance. Mixing formats can complicate updates and support. Keep notes on where each app came from and how it updates so you can triage odd behavior later without reinstallation.

Section highlights

  • Prefer popular Flatpaks first to validate environment and behavior.
  • Document differences when testing formats to speed future fixes.

Frequently asked questions

Should I install Flatpak apps as user or system on Steam Deck?

User scope is safer because SteamOS updates do not overwrite user apps. Use system scope only when multiple Deck accounts need the same app or when a service integration requires system wide availability.

How do I safely update Flatpak apps without breaking everything?

Update one app at a time and verify behavior before moving on. Keep rollback options ready by noting commit IDs or reinstalling a known good build if it remains available on the remote you use.

What is the quickest way to fix a Flatpak that will not launch?

Run the app with verbose logs to surface portal or permission errors. Then try flatpak repair, and if needed reinstall the same app, preserving settings when possible to avoid unnecessary reconfiguration.

When should I add the Flathub Beta remote on Deck?

Add it only when you need a prerelease feature or a fix not yet on stable. Document the reason and remove the beta channel when it is no longer required to keep your environment predictable.

Is it safe to grant Flatpak full home directory access?

Prefer specific paths or read only access when possible. Broad home access increases risk and can expose secrets or configuration files that an app does not need for normal operation.
