Fix Duplicate ROM Entries in Onion OS Libraries

By Sarah Carter • Published January 8, 2026

Duplicate ROM entries can appear in Onion OS when playlists reference the same file, when clones sit in multiple folders, or when scraping creates parallel records. This guide focuses on the exact goal of removing redundant entries while protecting saves and artwork. We assume a microSD-based setup on common handhelds, read and write access to the SD card, and comfort with simple file operations. You will make a backup first, examine playlists, compute hashes to confirm true duplicates, and then clean safely. The steps are reversible, so progress stays visible and low stress. If artwork desynchronizes, we will rebuild thumbnails in a targeted way. By the end, your library will retain unique ROMs, and Onion OS lists should scan cleanly without repeated items.

Key takeaways

  • Create a full backup before any edits to playlists or ROMs.
  • Confirm duplicates by file hash, not just filename or folder path.
  • Fix playlists after removals so Onion OS scanning stays consistent.
  • Rebuild thumbnails selectively to preserve artwork and speed checks.

Plan the work

Start with a clear definition of a duplicate ROM entry and how it differs from a duplicate file. A duplicate entry happens when Onion OS shows the same game twice in a playlist, which might come from multiple paths, copied ROMs, or stale list records. A duplicate file occurs when identical data exists in separate locations, often hidden beneath different names. Plan to treat entries first, then files if needed. As a rule of thumb, fix logical lists before deleting anything on disk, because playlist edits are reversible and low risk. The tradeoff is time spent confirming which entries represent true copies, but this caution prevents accidental loss of rare hacks or different region variants you actually want to keep.

Map the folders you will touch and write a short checklist. Typical Onion OS layouts keep console directories under a ROMs root, with subfolders by system. Plan to back up the entire ROMs directory and any playlist files before changes. Include saves and states to avoid mismatches. The benefit is obvious: if a bad edit breaks detection or artwork, a rollback requires minutes, not hours. The limitation is storage space, so if your card is tight, compress backups or copy playlists and saves first. This planning step sets expectations for time and ensures you will not chase issues caused by missing dependencies later.

Decide why duplicates appeared to choose the right fix. If two dumps share content but differ by filename, hash comparison will confirm sameness. If a scanning pass referenced both a zipped and unzipped copy, a folder policy will resolve it. If lists reference moved files, you probably have ghost entries that need pruning. Document which evidence you will collect: sample filenames, sizes, and computed hashes. The advantage of evidence-driven cleanup is predictable results and fewer rescans. The drawback is initial effort to gather details, yet that cost is smaller than redoing artwork or re-scraping metadata because of rushed deletions.

Prepare environment

Create a restorable snapshot before touching anything. Copy the ROMs root, playlists, and the thumbnails directory to a computer or second card. If space is constrained, at minimum back up playlists and saves. Verify your backup by opening a few files to ensure they are readable. Use a text editor that handles large files for list inspection, such as VS Code or Notepad++. For hashing, macOS ships with shasum and Linux with md5sum or sha1sum. On Windows, CertUtil can compute hashes from the command line. The tradeoff between MD5 and SHA1 here is negligible for collision risk when deduping personal files, so pick what is available and consistent.

Understand path casing and file extensions for your setup. Some handhelds or microSD formats treat case insensitively, yet Onion OS playlists might store paths case sensitively. Mismatches cause ghost entries that look like duplicates but point to nonexisting files. Sample a few entries and confirm that path casing mirrors the actual directory structure. Also note whether ROMs are zipped or extracted, and whether your cores prefer one format over the other. This context avoids false positives when you later compare hashes or remove files. It also helps you prioritize removing redundant archive types to simplify future scans.

Choose a baseline method for spotting duplicates. Playlist inspection is fast for entry-level cleanup. Hash-based comparison is accurate for file-level decisions. A targeted rescan helps rebuild clean lists after edits. Combine these methods to avoid over-deleting. The limitation of playlist-only review is that identical files may remain in different folders. Hash-only review can be slow on large libraries. A hybrid approach, starting with lists, prevents wasted compute and keeps changes narrow. If you expect artwork issues to surface, plan for a selective thumbnails rebuild after you validate results, not before.

Execute steps

Work through a consistent sequence so you never lose track. First, confirm the problem scope by sampling a system with visible repeats. Second, open the matching playlist and identify whether duplicates share identical paths or reference different folders. Third, compute hashes on the suspected files to confirm sameness by content, not name. Fourth, decide whether to prune entries, remove files, or both. Finally, record each change so you can revert or redo cleanly. This approach reduces anxiety because evidence precedes deletion, and each action has an immediate validation point. If you discover broader structure problems, pause and consider a targeted rescan after finishing one system.

Use a simple hash listing to spot content-level duplicates without deleting anything. The pattern groups files with matching hashes so you can compare names and locations. On large cards, limit depth to one system at a time to keep results readable. The main tradeoff is speed, as hashing reads whole files. Start with a smaller sample folder to estimate runtime, then expand. Expect archives to hash differently from extracted ROMs unless decompressed. When hashes match exactly across different directories, you have a strong signal that only one copy is needed for clean lists.

Validate results

Verify that playlists now show unique items and that each entry launches correctly. Reopen the system you cleaned and scroll for repeats. Try launching two or three representative games that had duplicates to ensure paths resolve. If an entry fails, restore from the backup of the playlist and recheck casing or directory names. This step catches path typos or files removed prematurely. The tradeoff is a few minutes per system, but it avoids chaotic rescans later. For large libraries, set a small acceptance rule, such as testing three titles per platform before proceeding. That balances confidence with time spent.

Check saves, states, and artwork after file removals. When you consolidate to a single file, ensure that the remaining path matches what saves expect. If artwork disappears for cleaned items, you likely changed a filename or moved a folder that thumbnails reference. Instead of global scraping, rebuild thumbnails for only the affected system. If the artwork pipeline was unstable previously, consider reading a steady end-to-end guide that addresses assets and updates so you can stabilize before final polish. This preventive step avoids chasing artwork regressions caused by prior inconsistencies.

Rerun a targeted scan or library refresh only where necessary. If your structure is sound and playlists are fixed, a light refresh forces Onion OS to reflect changes without touching unrelated systems. The benefit is speed and minimal risk to already clean lists. The downside is that stale metadata in ignored systems will remain until you schedule their maintenance. Record what you refreshed so you can revisit later. If duplicates reappear immediately, you probably have a second playlist referencing a different folder or a misconfigured scanner pattern that includes old archives alongside extracted ROMs.

Troubleshoot and optimize

When duplicates persist, look for hidden sources like parallel archives and extracted folders scanned together. A common pattern is keeping both ZIP and extracted versions of the same set, which creates two valid entries. Standardize on one format per system and exclude the other folder from scans. Another source is mismatched playlist casing on case sensitive paths. If a path exists but casing does not match, it can scan as a new entry later. Align folder names and playlist entries exactly. This tidy work prevents the recurrence of duplicate ROM entries and reduces future false positives during validation.

If artwork vanishes after cleanup, the cache may be stale or misaligned. Rebuild the thumbnail cache for the impacted system so images reindex against the new paths. Avoid full library rescans unless structure is heavily changed. If your issue involves missing BIOS or general stability problems, work through a broader troubleshooting sequence designed for Onion OS users. That structured flow includes checklists for boot issues, crashes, and asset repairs, and will help you stabilize before returning to library polish. Keeping repairs scoped reduces risk and saves time.

For large sets, optimize by batching and automating safe parts. Run hash listing per system overnight, then review groups the next day. Maintain a small decision table for region variants and hacks you keep even if hashes match, since content can differ through headers or patches. Keep your backup updated after each clean segment, not just at the start. This prevents backsliding if an edit goes wrong. Resist aggressive deletions without verification. Favor playlist pruning and exclusion filters first, then file consolidation, to minimize accidental loss and artwork churn across scans.

  4. Prune redundant entries: edit the playlist to retain a single correct record.
  5. Consolidate files carefully: keep the preferred copy and remove confirmed duplicates.

Frequently asked questions

Do I need to delete files to fix duplicate entries?

No. Start by pruning playlists that reference the same path. Only remove files after confirming true duplicates by hash and after verifying saves and artwork.

Why do duplicates come back after I edit the playlist?

A rescan may include multiple folders or archive formats. Standardize on one source path, exclude redundant directories, and ensure path casing matches actual folders.

Will rebuilding thumbnails erase existing artwork?

Rebuilding for a single system refreshes cache files and should not remove curated images. It realigns artwork to updated paths when filenames or folders change.

Which hash should I use for detecting duplicates?

Use the tool you have. MD5 or SHA1 both work for personal deduping. Consistency matters more than algorithm choice for identifying identical ROM content.

Looking ahead

Set a simple maintenance rhythm to keep Onion OS libraries tidy without heavy rescans. After adding new games, run a quick hash check on the affected system and scan only that folder. Keep a short policy for which region variants you retain and whether archives or extracted files are standard. Update your backup once each batch is validated so you can always revert cleanly. If you continue to see missing assets or recurring list issues, consult a broader troubleshooting path that addresses boot issues, crashes, and asset corrections, then return to library hygiene. A calm, repeatable approach makes expansion predictable and stable over time.
