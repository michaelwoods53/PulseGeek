Screen Tearing on Miyoo: Enable VSync the Right Way

By Logan Ward • Published January 15, 2026

Screen tearing on Miyoo breaks immersion, but a careful VSync setup restores clean motion. This how-to explains when to toggle vertical sync, how to align frame rate with the panel, and what to adjust in RetroArch without adding latency. You will need a Miyoo handheld with RetroArch-based firmware, basic access to configuration menus, and a few minutes to test changes. We assume default Onion OS or stock firmware behavior where video timing and audio timing can drift. By the end, you will understand which settings prevent tearing, which ones create stutter, and how to verify that pacing stays steady during scrolling scenes and cutscenes.

Key takeaways

  • Enable VSync first, then match frame rate to the display refresh.
  • Cap frames one to one with refresh to avoid pacing jitter.
  • Use on-screen stats to confirm no dropped or delayed frames.
  • Prefer core overrides when a single core misbehaves with VSync.
  • Keep frame delay modest to prevent audio crackles and instability.

Plan the work

Start by defining success criteria so you know when VSync is working. The goal is to remove visible screen tearing while keeping input response and audio stability acceptable. Use a scrolling test scene, such as a platformer level or an RPG map scroll, because motion makes pacing faults obvious. Plan to compare three states: VSync off, VSync on with default timing, and VSync on with a frame rate cap matched to the display. This structured comparison reveals whether tearing vanished or if new stutter appeared. A tradeoff exists between strict sync and input latency, so we will keep frame delay modest and avoid aggressive audio sync options that can crackle on weaker cores. Deciding this upfront shortens troubleshooting and guides safe adjustments.

Identify which layer should control timing to prevent conflicting signals. On Miyoo devices, RetroArch typically handles synchronization, while the operating system and panel expose a fixed refresh. Let RetroArch own VSync and frame limit, and avoid stacking external limiters. When multiple layers try to pace frames, micro stutter or double buffering artifacts can occur. An example is enabling a GPU driver limiter alongside RetroArch’s own limiter, which adds jitter because they fight over delivery cadence. The rule of thumb is one authoritative limiter and one sync flag. If a specific core demands its own timing model, configure that via core override, not global settings, to avoid surprising other systems and to keep your baseline behavior predictable.

Map your rollback path before changing settings to recover quickly from errors. Save your current RetroArch configuration to a backup file, then note which options you will change: VSync, maximum swapchain images, frame limit, hard GPU sync, and frame delay. If a toggle causes black screens or audio pops, restoring the prior config avoids compounding mistakes. Edge cases include cores with uneven frame times that look worse with strict sync. In those cases, fallback to VSync on with no frame delay and a conservative limiter. Planning recovery reduces risk while testing. It also lets you gather clean before and after comparisons that reveal which setting actually removed tearing rather than guessing based on feel.

Prepare environment

Create a safe workspace so changes are reversible and testing is clean. Back up retroarch.cfg to a known location and confirm you can restore it. Note access paths on your Miyoo firmware to reach Video and Latency menus quickly, because you will toggle options repeatedly during verification. Choose one test game per system, ideally titles with smooth background scrolling or constant camera pans. Examples include early 16-bit platformers and overhead shooters that expose pacing defects immediately. Avoid changing unrelated video filters or shaders during setup because shaders can complicate timing and heat. The main limitation on these devices is modest GPU bandwidth, so extra effects increase risk of dropped frames. Keep the baseline simple to see whether VSync alone fixes the tearing you observed.

Document baseline measurements to make outcomes objective rather than subjective. In RetroArch, enable on-screen statistics so you can see frame rate, frame time variance, and dropped frames while playing the test scene. If your panel refresh is 60 Hz, expect a stable 60 fps with minimal variance when VSync is correct. If you see 59 to 60 oscillation or occasional dips, note when they happen relative to effects or scene changes. This helps distinguish between fixed pacing faults and occasional load spikes. A limitation of visual inspection is bias, so combine the on-screen stats with a short video clip for later frame-by-frame review. With this record, you can evaluate whether each change improved pacing or introduced a different artifact.

When you must edit files directly, keep the touch minimal and verified. Most VSync behavior is accessible in menus, but some builds honor configuration keys like video_vsync and video_adaptive_vsync in retroarch.cfg. Edit only known flags and restart RetroArch to apply. Do not batch change unrelated options because it hides the source of improvements. If a core requires a specific timing fix, prefer a core override file so the change is scoped. This isolation prevents regressions in other systems that were already stable. The risk of manual edits is typos that disable settings, so validate by reopening the menu and reading the effective state. A short test after each edit ensures you catch issues early rather than after many changes.

Execute steps

Apply settings in a controlled order to isolate each effect and catch regressions. Start with global VSync on, then verify that the frame rate equals the panel refresh during your test scene. Next, set a conservative frame limit matching 60 Hz panels that most Miyoo models use. Only after VSync and the limiter are stable should you consider enabling hard GPU sync or modest frame delay. These additions can reduce latency but risk stutter if the device cannot keep up with tighter deadlines. If a specific core shows uneven pacing, scope adjustments with a core override rather than changing the global profile. This order keeps your baseline stable and makes it obvious which toggle solved tearing or introduced a side effect.

Use a small decision table to pick safe values for pacing options. If you test hard GPU sync, start with it disabled because it sometimes increases micro stutter on slower devices. If input latency feels high, add frame delay in small steps and watch for audio instability. For adaptive VSync, prefer off unless a core exhibits periodic tearing with regular VSync. The reason is predictability. Adaptive modes vary enforcement to avoid drops, which can look like hitching in consistent scroll tests. When two options produce similar results, keep the simpler one. Simpler settings are easier to reproduce and less likely to regress when firmware updates change defaults or rendering paths behind the scenes.

Validate results

Confirm success using both visual inspection and quantitative checks so you do not miss subtle pacing faults. With VSync enabled and the frame cap matched, the stats overlay should show a stable frame rate equal to the refresh with minimal variance. During long horizontal or vertical scrolls, no diagonal tear lines should appear. If short hitches occur during effects, relate them to load spikes rather than timing failures. A quick video recording helps verify that hitching patterns repeat at the same spots, which suggests rendering load rather than sync. The distinction matters because you fix heavy scenes by reducing filters or shaders, not by toggling VSync. Validation keeps you from chasing the wrong fix when the root cause is performance.

Check input and audio after tearing is gone, because a cure that increases lag or crackle is not acceptable. Test a platformer jump or rhythm game input window to gauge feel. If latency seems higher, step frame delay up slightly or test hard GPU sync on, watching for renewed stutter. For audio, listen during long held notes and ambient loops for pops or jitter. If artifacts appear, return frame delay to zero and prefer clean pacing over risky latency tweaks. Remember that some cores enforce their own buffer models. In those cases, separate core audio settings may require adjustment, and it is safer to apply them via core override so they do not affect other systems that were stable.

Repeat the test across two or three representative cores to ensure your approach generalizes. Some cores have unique timing behavior, and a VSync configuration that looks perfect on an 8-bit system may show minor inconsistencies on a more demanding 32-bit core. If the baseline remains clean and only one core struggles, keep your global settings and create a local override. This preserves stability everywhere else while giving the outlier just enough flexibility to behave. If several cores regress, revisit the earlier plan and simplify. Remove optional tweaks, disable adaptive VSync, and return to one limiter. Validation across systems prevents you from overfitting to a single game that happens to align with a fragile configuration.

Troubleshoot and optimize

When tearing persists with VSync on, look for pacing conflicts or overdraw. Conflicts arise when multiple systems try to control timing. Turn off external frame limiting and keep RetroArch as the sole authority. Overdraw appears when heavy shaders or high scaling factors push the device beyond comfortable budgets. Remove post-processing first and retry your scroll test. For stubborn micro tearing that appears only during effects, test adaptive VSync as a targeted compromise. If this reduces artifacts without visible hitching, leave it scoped to that core via override. Otherwise, revert to standard VSync and accept minor effects-related hitches, because predictable timing usually looks better than adaptive fluctuation on handheld panels.

If you see new stutter after toggling hard GPU sync or increasing frame delay, back those out and recheck. These options reduce latency by tightening deadlines, which can starve the pipeline on lower power hardware. A safer optimization is reducing swapchain depth, such as two images, which lowers buffering while staying compatible with VSync. Watch the overlay for frame pacing variance under this change. If variance increases, restore the previous value. Keep a written log of each adjustment, expected benefit, and outcome. This method reveals patterns, such as a specific core disliking hard sync, and it speeds resolution when you revisit the same core months later after a firmware update changes default timing behavior.

When behavior becomes unpredictable across games or resumes after reboots, refresh your baseline. Restore the backed-up configuration, enable only VSync and a matching frame cap, then retest. If issues resolve, reapply optional tweaks one by one. If not, consider broader system causes like unstable storage, overheating, or under-voltage. In those cases, step through a structured approach using the identify and isolate workflow for system stability before returning to video. Artifacts that mimic tearing can also stem from display gamma and color settings that exaggerate transitions. If edges shimmer without true tear lines, consult video calibration guidance rather than timing options to address perceived roughness.

Quick start checklist

  1. Back up retroarch.cfg: save a copy so you can restore quickly.
  2. Enable VSync: toggle vertical sync in Video settings and restart RetroArch.
  3. Match the frame limit: set the cap to the display refresh, typically 60.
  4. Turn on stats: enable fps and frame time overlay to monitor pacing.
  5. Test a scrolling scene: look for diagonal tear lines or dropped frames.
  6. Adjust carefully: try small frame delay increases and avoid hard sync first.

Frequently asked questions

Why do I still see tearing with VSync on?

Another limiter may be conflicting, or the frame rate is not matching the panel refresh. Disable external limiters, set the frame cap to the display rate, and remove heavy shaders that can cause missed deadlines.

Should I use adaptive VSync on Miyoo?

Use adaptive VSync only if regular VSync shows periodic tearing that does not respond to other changes. It can reduce artifacts but sometimes introduces hitching, so keep it scoped per core as an override.

Does hard GPU sync reduce input lag safely?

It can reduce latency but tightens rendering deadlines. On lower power hardware this may produce micro stutter. Try it after achieving stable VSync, test in small increments, and revert if pacing variance increases.

What frame limit should I use?

Match the panel refresh rate. Most Miyoo devices use 60 Hz, so set 60 fps. If your model differs, set the cap to that exact refresh to keep pacing aligned and avoid oscillation around the target.

How do I undo a bad change?

Restore your backup configuration file. If you do not have one, reset RetroArch to defaults, enable only VSync and the frame cap, and retest before reintroducing optional tweaks one at a time.
