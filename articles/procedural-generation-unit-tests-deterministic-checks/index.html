Procedural Generation Unit Tests: Deterministic Checks

By Jacob Reed • Published December 16, 2025

Deterministic unit tests for procedural generation keep results stable while you refactor algorithms. This how-to focuses on seeds, fixtures, and golden outputs so the same input produces the same map or loot table every time. We assume a standard game build environment, a reproducible random number generator, and a unit test framework like pytest, NUnit, or JUnit. You will define invariants, wire seed control, and capture outputs as hashes or structured snapshots. The outcome is a set of fast checks that detect regressions without flaky noise. If your generator runs in Unity, Unreal, or a custom engine, the process still applies because it relies on isolation and deterministic seams rather than engine specifics.

Key takeaways

  • Lock a seed and RNG to make procedural tests deterministic.
  • Assert invariants first, then add golden outputs for regressions.
  • Stabilize hashes by canonicalizing order and normalizing floats.
  • Fail tests fast with minimal fixtures and explicit preconditions.
  • Quarantine nondeterminism with mocks and fixed time sources.

Plan the work

Start by declaring what must never change and what may vary within bounds. Treat these as invariants and tolerances, such as connectivity of a dungeon graph, absence of overlaps, or average enemy count within a narrow range per difficulty tier. Write them down alongside representative seeds that exercise edges like smallest map, largest map, and hallway-heavy patterns. The rule of thumb is to begin with three seeds that map to distinct structural regimes. Overplanning can slow iteration, but underplanning leads to noisy failures. By focusing on structural properties first, you avoid brittle tests that fail on harmless cosmetic differences while still catching regressions that affect gameplay or level fairness.

Define an observation surface that tests can read without rendering. Prefer structured outputs like tile arrays, adjacency lists, or JSON summaries rather than screenshots. This enables fast, headless tests and avoids graphics driver variability. For example, expose a function that returns a grid plus metadata such as spawn points and path lengths. An edge case to consider is floating point drift across platforms. To mitigate, store positions as integers in fixed units or quantize to a small epsilon before hashing. The goal is to make every assertion compare canonical data so minor floating noise does not create flicker in otherwise stable runs.

Choose a minimal yet discriminative set of checks. Start with invariants such as path existence from start to goal, door count within a target interval, and no isolated rooms. Then add golden outputs for one or two seeds by hashing canonicalized data. Golden tests are powerful for regression detection, but they can ossify progress if overused. Balance by keeping few goldens for core seeds and leaving the rest to invariant-based checks. When unsure, prefer an invariant and add a comment explaining intent, because future maintainers need to understand why a failure matters. This discipline keeps tests meaningful rather than decorative.

Section highlights

  • Prioritize structural invariants and pick seeds that probe distinct regimes.
  • Favor canonical structured outputs to avoid platform float drift issues.
  • Use few golden tests for core seeds and rely on invariants elsewhere.

Prepare environment

Stabilize the random backbone before writing tests. Select a reproducible RNG like PCG or Mersenne Twister and pass it explicitly through your generation pipeline rather than relying on global state. Inject a clock abstraction so time-based randomness can be mocked. In engines like Unity, avoid using UnityEngine.Random in tests and instead create a deterministic wrapper. The tradeoff is extra plumbing, but it pays off by removing flakiness from environmental noise. Document the seed space and any known bad seeds for later exclusion. This setup phase is where you also decide how to serialize outputs for hashing and where those artifacts will live in your repository.

Create minimal fixtures that run the generator in isolation. Replace file I/O with in-memory streams, and substitute physics checks with deterministic geometry routines. For instance, use a tile occupancy grid instead of real physics overlap queries. A limitation is that you may miss physics quirks from the runtime, so reserve separate integration tests for that layer. Keep fixture data small so tests run in under a few hundred milliseconds. Fast turnaround encourages frequent runs and tight feedback loops. Small fixtures also make it simpler to bisect failures because the surface area of possible interactions is narrow and easier to reason about.

Decide how you will verify outputs. Two complementary techniques are stable hashing and structured snapshots. Hashes are compact and easy to assert, but offer no clue about where the change occurred. Snapshots are verbose but diffable, especially when fields are sorted and floats normalized. A hybrid approach stores both: a golden hash for quick detection and a human-readable snapshot for diagnosis. Make sure to canonicalize ordering, such as sorting rooms by top-left coordinate and listing neighbors in ascending indices. Without canonicalization, tests can flip-flop even when structure is equivalent. This discipline prevents false positives and keeps test signal clean and trustworthy.

Section highlights

  • Inject deterministic RNG and abstract time to remove environmental noise.
  • Use small isolated fixtures and replace heavy systems with simple surrogates.
  • Combine stable hashes with canonicalized snapshots for detection and diagnosis.

Execute steps

With planning and setup complete, write tests that encode the intended behavior. Each test should set a fixed seed, build the generator with the deterministic RNG, and assert key invariants before asserting any golden hash. Start with a seed trio that exercises different map topologies, then add a single golden for a representative seed. If you work across teams, include a short comment describing the seed’s selection rationale. Validate results

After tests run, evaluate both stability and coverage signal. Stability means rerunning the same suite produces identical pass results across machines and operating systems. If failures appear only on a subset of platforms, suspect float roundoff, different standard library RNGs, or locale-sensitive formatting. Standardize these inputs by pinning RNG implementation and using invariant culture for serialization. For coverage, ask whether the invariants would catch a real design regression. A simple exercise is to deliberately break a rule, like allowing overlapping rooms, and confirm the test fails quickly. This manual perturbation validates that your checks measure what matters.

Golden outputs should be updated intentionally, not automatically. When a legitimate algorithm change creates a new stable state, regenerate the canonical snapshot and hash using a reviewable process. Require a brief note in version control explaining why the golden changed and which behavior improved. A limitation of goldens is their brittleness to benign adjustments, so keep their number small. Favor property tests that measure structural qualities like connectivity, bounds, and degree distributions. When you do update a golden, rerun the suite multiple times to ensure no hidden non-determinism remains, like accidental reliance on iteration order of hash maps.

To check that tests remain informative, track the ratio of invariant failures to golden failures over time. A balanced suite reports invariant violations first, since those encode domain rules and guide fixes. If most failures are golden mismatches, you may be overfitting to a specific snapshot and missing generality. Add or refine invariants to capture the design intent directly, such as minimum corridor width or objective placement rules. Also confirm test runtime stays short to fit into pre-commit hooks. A fast suite encourages developers to run it frequently, which prevents accumulation of subtle issues that are expensive to diagnose later.

  • Update goldens deliberately and prefer strong property-based invariants.
  • Keep suites fast and informative by monitoring failure types and runtime.

Troubleshoot and optimize

When a test flakes, inspect sources of nondeterminism in priority order. First, ensure all randomness flows through your injected RNG and that there are no accidental calls to global random functions. Second, check for iteration order dependence by replacing hash map traversals with sorted enumeration. Third, sanitize float handling with fixed-point or rounding to a small epsilon before serialization. If failures persist, log a minimal snapshot on failure that includes the seed, generator version, and key parameters. This breadcrumb trail accelerates reproduction and isolates the specific subsystem where drift begins. Avoid masking flakiness by widening tolerances without understanding root causes.

Once stability improves, optimize the suite for speed. Cache expensive preprocessing steps like noise field generation when inputs are identical, or shrink fixtures to the smallest grid that still exercises the rule. Batch slow tests behind a build tag so quick invariant checks run on every commit and heavier golden tests run in nightly pipelines. The tradeoff is delayed feedback for some regressions, but overall developer velocity increases. For visibility and faster diagnosis, add lightweight telemetry counters for failure reasons and seed frequency. Simple counts reveal hotspots that justify deeper profiling or more targeted assertions in problematic systems.

Finally, clarify configuration options so intent remains explicit. A small table helps developers choose flags that stabilize and accelerate tests without guessing. For example, expose options for RNG backend, seed source, and snapshot tolerance. Prefer explicit defaults that are deterministic in all environments. Document when to switch a backend or adjust tolerance, and warn about consequences such as changing hash outputs. Keeping these knobs visible reduces accidental drift and aligns the team on shared expectations for deterministic behavior during refactors and engine upgrades.

Quick start checklist

  1. Identify invariants: list structural rules that must hold for every map.
  2. Inject deterministic RNG: pass a seeded generator through all random calls.
  3. Canonicalize outputs: sort collections and normalize floats before hashing.
  4. Add one golden: pick a representative seed and store its stable hash.
  5. Fail fast on invariants: assert reachability and bounds before golden checks.
  6. Quarantine nondeterminism: mock clocks and replace physics with geometry checks.

Looking ahead

Extend coverage by graduating a few integration tests that run the generator inside the engine with the same seeds and fixtures. Keep their number small and focused on cross-system seams like saving, loading, and pathfinding queries. Pair these with metric tracking that summarizes difficulty and flow across a diverse seed set so your suite guards experiential quality, not just structure. As your content grows, revisit invariants to reflect new rules and retire obsolete ones. Treat tests as living documentation for design intent, which makes future changes safer and faster. The north star remains the same: deterministic feedback that developers trust.

Iterate on seed strategy as systems gain complexity. Introduce hierarchical seeds that scope randomness per subsystem and per room so local changes do not ripple unexpectedly. Add telemetry that counts failure categories over time to surface regressions in new features quickly. When you adopt a new RNG backend or serialization format, plan a controlled migration with side-by-side runs to ensure behavior parity. The process you built for deterministic unit tests scales to new content and helps maintain continuity across platforms and releases. With these habits, procedural content stays reliable while you innovate on algorithms.

For teams formalizing standards, write a compact testing charter that lists required invariants, approved RNGs, and snapshot formats. Include guidance on when to create or retire goldens and how to document changes in version control. This keeps expectations clear across contributors and reviewers. Consider adding a pre-commit hook that runs the fastest subset of tests and a scheduled pipeline that exercises heavier seeds and integration checks nightly. Over time, refine the suite by pruning flaky or redundant tests so the signal stays strong. Consistent, deterministic tests shorten feedback loops and build confidence in procedural systems.

Section highlights

  • Evolve seeds, invariants, and integrations as features and rules expand.
  • Document standards and automate fast checks in hooks and nightly runs.
  • Prune brittle tests to keep the suite’s signal strong and actionable.

Frequently asked questions

How do I pick seeds that provide useful coverage?

Choose seeds that trigger distinct structural regimes, like sparse versus dense maps or small versus large layouts. Validate by visualizing snapshots and confirming each seed exercises different rules. Maintain a short list with documented intent.

When should I update a golden hash?

Update only after a deliberate algorithm change that improves behavior and is now stable. Include a note explaining why the new snapshot is preferred. Rerun the suite multiple times to confirm there is no hidden nondeterminism.

Why are tests passing on Windows but failing on Linux?

This often indicates differences in RNG implementations, float rounding, or locale-sensitive serialization. Pin the RNG, quantize or use fixed-point, and serialize with invariant culture settings to eliminate platform-specific drift.

Should I use screenshots for golden tests?

No. Screenshots are brittle and depend on drivers and resolution. Prefer canonical structured data like grids or adjacency lists. If visual confirmation is necessary, keep it for manual review or separate non-blocking checks.

How many golden tests are reasonable?

Keep the count small, commonly one or two per generator. Rely on invariants for broader coverage. Too many goldens create maintenance overhead and fail on benign changes that do not affect gameplay or structural quality.
