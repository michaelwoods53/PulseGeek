Audio Latency and Sync Settings Step by Step

By Logan Pierce • Published December 21, 2025

Our goal is to dial audio latency and sync settings so input feels crisp while timing stays stable. We assume a desktop emulator environment with adjustable audio buffer, sample rate control, and frame synchronization options. If your emulator exposes runahead or GPU sync, plan to evaluate those after baseline. The process uses tight but safe ranges, with a verify step before pushing further. Throughout, we will reference audio latency, synchronization behavior, and rate control as distinct levers. Keep notes as you test, because small changes interact across drivers, devices, and displays. This route avoids guessing by pairing each change with a measurable check and a rollback point.

Key takeaways

  • Set a baseline buffer, then reduce gradually while monitoring underruns.
  • Enable rate control only when video sync needs small drift smoothing.
  • Test with fixed refresh content before enabling variable refresh features.
  • Prefer runahead for input feel, not for audio timing correction.
  • Validate with looped scenes and controller taps to confirm sync.

Plan the work

Start with a clear target: reach responsive audio without introducing drift or stutter. Define acceptable limits such as no audible crackles, no periodic desync, and steady frame pacing during 2 to 5 minute loops. A simple rule is choose a baseline buffer that never underruns on your slowest test scene, then step down in small increments. For example, if 80 ms is stable across games, test 64 ms and 48 ms while watching an underrun counter if available. The tradeoff is smaller buffers lower round trip delay but raise risk of glitches on CPU spikes. Planning these checkpoints keeps you from confusing random hiccups with a bad setting.

Map the levers you will adjust and the order to touch them, because sequencing matters. Begin with audio device buffer, then align video sync, then decide on audio rate control, and only then consider extras like runahead or hard GPU sync. This order avoids masking problems, such as rate control smoothing a jitter source you should fix at its origin. A practical pattern is change one variable, test on two scenes, and log the outcome. If a scene exposes a weakness, fix it before layering more features. The why is simple: controlled isolation gives true cause and effect.

Establish test content and measurements before tuning, so results are comparable. Pick a static menu with constant music, a busy gameplay scene, and a load transition. Use a metronome video or a rhythm stage if available to expose drift. If you can, measure latency with a high frame rate camera, but if not, rely on emulator stats for underruns and frame time variance. As a guardrail, avoid changing multiple drivers at once like switching from WASAPI to ASIO while toggling VSync. Consistent test loops create a reliable baseline you can return to after each change.

Prepare environment

Choose a stable audio backend first, because driver behavior sets your floor. On Windows, WASAPI exclusive often reduces overhead versus shared mode, while macOS typically benefits from the native Core Audio path. Linux users can compare ALSA with PulseAudio or PipeWire, preferring the layer that offers fixed buffer sizes without resampling churn. The tradeoff here is convenience versus determinism. Shared modes simplify desktop mixing but can add hidden buffering. If your emulator lists device latency in frames or milliseconds, record that value as your baseline. Its purpose is to ensure your starting point is known and repeatable.

Set the emulator audio buffer to a conservative value that never underruns on your heavy scene. Many emulators expose this as milliseconds or frames per buffer. A practical starting point is 80 to 120 ms for safety, then reduce after validation. You can also lock the sample rate to a standard value like 48000 Hz if your device prefers it, which avoids resample jitter. An edge case appears when capture software forces different rates and causes resync glitches. If you stream or record, harmonize the sample rates across apps first to prevent unnecessary buffering and drift.

Align display sync before touching audio rate control, because the display dictates pacing. Enable VSync or a variable refresh mode you trust, then test if frame times are stable under your target game. If frame pacing is inconsistent, audio can appear early or late even with correct buffering. In difficult cases, review a broader foundation about emulator timing and performance in an evergreen resource like the complete foundation for emulator concepts and tuning. Fixing shader compilation stalls or GPU queues often removes the need for aggressive audio smoothing later.

Execute steps

Apply settings in a defined sequence so each change has a measurable effect. We begin by reducing the device buffer in small increments while monitoring underruns. Next, we confirm display sync choice and only then consider audio rate control to smooth tiny cadence mismatches. If your emulator provides a runahead feature, enable it after audio timing is stable, since its goal is input feel rather than audio correction. Some emulators expose a hard GPU sync option that can swap latency for potential micro stutter. Use it cautiously and prefer a single frame render queue when possible. A separate, detailed reference on latency sources can help you decide tradeoffs, such as the guide to input lag measurement and practical reductions.

If your emulator uses a config file, you can set representative options directly. The following snippet shows typical keys mirroring UI controls for buffer size, sync, and rate control. Expect lower round trip audio delay when reducing audio_latency, but stop before underruns. Enable video_vsync to fix cadence, then consider audio_rate_control to correct minor drift by resampling. Set runahead_frames only after audio tests pass. If your system struggles during heavy scenes, revert the last change and try a slightly larger buffer. This sequence maintains stability while you approach the responsiveness target without introducing new timing paths.

Use a consistent checklist to execute adjustments and capture outcomes. Change one variable, run your two to five minute loop, and record underruns, average frame time, and any audible artifacts. If everything remains clean, step down the buffer by a small amount, typically 8 to 16 ms, and repeat. Only enable audio rate control if cadence mismatch is small but persistent, indicated by rare desync without frame pacing issues. If runahead is needed for input feel, test one frame first, then two, watching CPU headroom. The tradeoff is higher CPU usage that can indirectly provoke audio glitches. Your notes ensure reversibility when a borderline setting fails later.

Validate results

Prove that your chosen configuration stays solid under expected and stressful moments. Run the busy gameplay loop for several minutes and note if underruns remain at zero or within a rare blip that does not repeat. Then pause and unpause rapidly to test start and stop transitions, which often reveal buffering mismatches. If your emulator shows audio and video timestamps, confirm they move in lockstep within a small bound. A looped rhythm track is helpful to expose periodic drift. When doubts remain, extend the loop duration to catch heat buildup or background tasks that may surface only after minutes of play.

When ambiguity persists, a small decision table can clarify which lever to adjust next. Compare symptoms like crackle, late audio, or visible tearing against probable sources. This reduces guesswork and prevents overusing rate control to hide unrelated issues. For example, crackle under load usually means the buffer is too small or CPU headroom is low. Late audio with clean frame pacing might benefit from a slight increase in buffer or a tiny rate control delta. Visible tearing usually points to VSync settings rather than audio. Troubleshoot and optimize

When problems appear, match the symptom to the narrowest fix before trying global changes. For bursty crackle during heavy scenes, increase the audio buffer one step and re test. If improvement is partial, inspect CPU and GPU usage to see which resource is spiking, then ease features like runahead or shaders. For periodic hiccups, check storage or shader compilation behavior and precompile or warm caches where possible. If your sync is clean but you feel sluggishness, revisit input handling and USB polling rather than touching audio timing. Targeted fixes avoid piling on smoothing and keep the system predictable.

Use audio rate control carefully, since it trades accuracy for steadiness. Small deltas like 0.001 adjust sample rate by a tenth of a percent to catch minor cadence mismatch. That is often inaudible yet effective for slow drift. However, larger deltas can create pitch or timing artifacts over time. If you notice wobble on sustained notes, reduce the delta or disable rate control and fix the underlying pacing path. Some emulators offer maximum timing skew limits that constrain how far resampling can bend. Setting a reasonable cap protects against runaway corrections when the system is under stress.

Finally, optimize for your display mode. If you use variable refresh, confirm that audio remains stable when the frame rate swings between typical gameplay and menus. In fixed refresh scenarios, consider matching the emulator speed to the display using frame pacing tools rather than heavy resampling. Quick start checklist

  1. Select a stable backend: pick WASAPI exclusive, Core Audio, or ALSA.
  2. Set a safe buffer: start around 80 to 120 ms and log underruns.
  3. Stabilize video pacing: enable VSync or known good VRR mode first.
  4. Reduce buffer gradually: step down 8 to 16 ms and re test loops.
  5. Enable gentle rate control: use a tiny delta only for slow drift.
  6. Add runahead sparingly: try one frame and watch CPU headroom.

Frequently asked questions

Should I enable audio rate control by default?

No. Start with clean pacing and only enable it to correct small drift. Use a tiny delta so pitch changes remain inaudible and disable it if artifacts appear.

Why do I get crackles after lowering the buffer?

Crackles indicate underruns or CPU spikes. Raise the buffer one step, reduce runahead, or remove heavy shaders. Confirm background tasks are not stealing time during busy scenes.

Is runahead an audio sync feature?

No. Runahead reduces input latency by predicting frames. It does not correct audio timing and can raise CPU use, which may indirectly cause audio glitches if headroom is low.

How do I know if drift is from video pacing?

If VSync is off or frame times vary, drift often follows. Enable VSync or a reliable VRR mode and retest. If cadence stabilizes but drift persists, consider gentle rate control.

Does higher sample rate reduce latency?

Not directly. Latency is set by buffer duration and processing time. Use device preferred rates to avoid resampling overhead, then reduce buffer size safely to lower delay.
