Onion OS Performance Tips for Smooth Emulation

By Jeremy Crawford • Published January 26, 2026

These Onion OS performance tips prioritize smooth emulation and stable input feel over flashy tweaks. Recommendations are based on predictable RetroArch behavior, conservative settings, and repeatable tests. Each item explains why a change helps, shows a simple example, and notes tradeoffs to consider. If you still need to install Onion OS or set up your Miyoo Mini from scratch, start with a safe, step-by-step setup and core packages so your baseline is stable before tuning.

Key takeaways

  • Pick lighter cores for 8 and 16-bit systems to reduce stutter.
  • Use threaded video and integer scaling to stabilize frame pacing.
  • Adjust audio latency slightly upward to avoid crackle and drift.
  • Avoid heavy shaders and overlays that increase render time.
  • Update cores carefully to keep compatibility and protect save files.

1) Choose cores that match system limits

Use cores that balance accuracy with speed for the Miyoo Mini’s limited hardware. For example, choose a lighter SNES core for smoother frame pacing on Onion OS rather than a feature-heavy alternative that demands more CPU. On Game Boy and Game Boy Color, simple and accurate cores are often faster, improving input response while maintaining correct timing. The tradeoff is fewer advanced options like exotic filters or runahead modes. Start by prioritizing stable full-speed output at the native frame rate, then re-enable features only if headroom remains. This approach prevents stutter during busy scenes where heavy cores drop frames. If you need extra features for a specific title, test per game and save a per-content core override to avoid burdening other systems with unneeded complexity.

Section highlights

  • Pick lighter cores to maintain full-speed output on limited hardware.
  • Use per-game overrides when a title needs extra options or features.

2) Enable threaded video and a stable video driver

Threaded video decouples rendering from emulation, which often smooths frame delivery on Onion OS. In RetroArch, enable threaded video and avoid experimental drivers that add jitter. For example, pairing a proven video driver with threaded video can reduce microstutters during scrolling scenes in 16-bit titles. The tradeoff is slightly higher input latency in some cases, because render and emulation queues are separated. If you are sensitive to input feel, test with and without threading on a demanding scene and compare. Use integer scaling to reduce interpolation costs and eliminate shimmering. Consistency usually beats raw throughput on handhelds, so aim for predictable frame pacing. When switching drivers, back up current config and revert quickly if visuals tear or menus flicker, since driver changes affect both games and Onion’s front end behavior.

Section highlights

  • Threaded video improves frame pacing but can add slight input latency.
  • Stick to stable drivers and test integer scaling for consistent output.

3) Use smart frameskip only when necessary

Frameskip can save performance during brief spikes by dropping render frames while keeping audio close to real time. In practice, turn it on only for games that occasionally dip below full speed, such as late-generation 16-bit titles with heavy parallax. The benefit is reduced audible crackle and less choppy scrolling during momentary load. The drawback is visible frame drops that make motion look uneven, which is distracting in fast action. A safe approach is to set a low frameskip value and disable it per-core if the effect is too noticeable. Test in areas with known stress like Mode 7 scenes and adjust until motion appears tolerable. If frameskip becomes constant rather than occasional, revisit core choice or reduce shaders and overlays instead of masking a broader performance deficit.

Section highlights

  • Apply frameskip sparingly to smooth brief slowdowns without heavy artifacts.
  • Reconsider cores or visuals if frameskip becomes constantly active.

4) Raise audio latency slightly to prevent crackle

A small audio latency increase often stops crackle and desync during tight CPU moments. Increasing the audio buffer gives emulation a margin to deliver consistent samples at the correct cadence. For example, nudging latency up by a modest step can stabilize sound in sprite-heavy scenes without audible delay in handheld speakers. The tradeoff is marginally slower response to rapid sound cues, which most players do not notice at conservative values. Tune per-core if one system needs more headroom. If audio still breaks up despite a higher buffer, the bottleneck is elsewhere, like shaders or an overtaxed core. In that case, lower visuals or switch cores before increasing latency further. Keeping audio steady protects the perception of smoothness because users notice sound glitches more readily than minor frame variance.

Section highlights

  • Increase audio buffer slightly to mask short CPU spikes and crackle.
  • If crackle persists, reduce visuals or switch to a lighter core.

5) Disable runahead on low power hardware

Runahead reduces input lag by simulating frames ahead, but it adds CPU overhead that can hurt performance on the Miyoo Mini. Disabling runahead typically stabilizes frame time for 8-bit and 16-bit systems without a noticeable loss of responsiveness, especially when threaded video and integer scaling are already tuned. For example, a platformer with tight jumps may feel more consistent with runahead off if it avoids periodic slowdowns. The tradeoff is a slight increase in end-to-end latency compared to aggressive runahead settings, which speed-focused players might miss. If you experiment, try a single-frame runahead and measure whether stutter increases. The goal is steady full-speed emulation rather than chasing the lowest possible latency figure, since inconsistent frame time makes timing harder than a small, steady delay.

Section highlights

  • Turning off runahead reduces CPU load and stabilizes frame timing.
  • Test one-frame runahead only if full speed remains consistent.

6) Prefer integer scaling and avoid heavy shaders

Integer scaling preserves pixel clarity and reduces the math required for each frame, which helps Onion OS maintain smooth output. In RetroArch, use integer scale when aspect and viewport allow, then add a simple scanline preset only if there is headroom. For example, ditching multi-pass CRT shaders with reflection and curvature can recover several milliseconds of render time, eliminating hitches in scrolling shooters. The downside is less visual flair compared to complex presets. On a small handheld screen, the gain in readability often outweighs the loss of stylistic effects. If you want minimal texture, choose a single, lightweight pass and avoid blending overlays that stack alpha. Check a busy scene with sprites and parallax to confirm the change improved pacing rather than just boosting average frame rate.

Section highlights

  • Integer scaling reduces render cost and cleans up pixel edges.
  • Use a single lightweight shader pass only if headroom exists.

7) Limit overlays and HUD elements

Every overlay pass and alpha-blended element increases render work, which can tip borderline games into stutter. Streamline layouts by using a minimal bezel or disabling extra HUD features that draw each frame. As an example, a decorative frame plus a semi-transparent control guide can combine to create consistent micro-hitches on scrolling scenes. The tradeoff is less on-screen information and fewer aesthetic touches. Keep what you truly reference while playing and remove everything else. If you need an overlay for one title, configure it per-game so the default stays lean. This targeted approach keeps most content smooth while preserving special layouts where helpful. After trimming, replay the same trouble spot to verify the improvement, because overlays impact both GPU and composition steps, which are sensitive to alpha stacking on small devices.

Section highlights

  • Reduce alpha layers and bezels to prevent composition slowdowns.
  • Apply overlays per-game so defaults remain fast and uncluttered.

8) Close background tasks and use sane governors

Background tasks and aggressive power saving can starve emulation of CPU bursts. In Onion OS, keep background features lean and avoid settings that throttle cores during load spikes. For instance, turning off rarely used services or widgets reduces contention and smooths performance in sprite-heavy scenes. The tradeoff is losing convenience features you might enjoy, like animated elements or frequent background scanning. Prioritize stable gameplay and selectively re-enable items that matter. If you are preparing a fresh setup, follow a start-to-finish walkthrough that covers safe settings and SD prep so you do not inherit slow defaults. A clean baseline makes it easier to isolate cause and effect when tuning. When in doubt, change one variable at a time and test the same scene to confirm the impact.

Section highlights

  • Minimize background features that compete for CPU during spikes.
  • Establish a clean baseline so changes are easy to evaluate.

9) Use fast SD cards and keep free space

Storage speed affects loading, save states, and texture streaming in some cores. Use a reputable SD card with good random read performance and avoid filling it to the brim, since near-full cards fragment and slow down writes. For example, leaving a reasonable margin of free space helps autosaves commit without hiccups when levels end. The tradeoff is slightly less total storage for ROMs and media. Prioritize stability by archiving rarely played sets off-device. If you are setting up Onion OS for the first time, follow a safe install flow with core packages so folder structure and updates remain predictable. This reduces the chance of filesystem quirks that produce stutter during save operations. Periodically check the card’s health and back up save files before making system-level changes or updates.

Section highlights

  • Choose reliable SD media and maintain free space to prevent stalls.
  • Back up saves before system changes to protect progress and settings.

10) Set conservative autosave and savestate options

Frequent autosaves and heavy savestate compression can introduce pauses when the system writes to storage. Use conservative autosave intervals and disable aggressive compression if you notice skips right after level transitions. For example, saving only on quit or at checkpoint screens may eliminate a recurring hitch on some titles. The downside is increased risk of lost progress if the device is powered down unexpectedly. Balance this by performing manual saves at natural breaks and by using a stable power routine. Before you change save behavior broadly, test with one demanding game to see if the hitch disappears. If not, the slowdown likely originates in rendering rather than I/O. Remember that consistent frame pacing improves input feel more than dense save automation on a handheld with limited throughput.

Section highlights

  • Reduce autosave frequency to avoid write-induced frame hitches.
  • Favor manual saves at breaks to balance reliability and smoothness.

11) Update cores safely and stick to proven builds

Updating RetroArch cores can improve performance, but it may also change timing or save compatibility. Update only when release notes promise clear gains for your systems, then test on copies of save files before committing. For example, apply a core update to a single platform and compare performance on a stress scene, keeping a rollback path if input timing or shaders behave differently. The tradeoff is delaying new features, yet you avoid breaking stable setups mid-playthrough. Use a safe method that keeps settings intact during system updates so you do not lose configurations honed for smooth emulation. Also, choose initial packages that are recommended for your device rather than pulling experimental modules that overtax the hardware and degrade frame pacing.

Looking ahead

Once stable frame pacing is achieved, document your per-core and per-game overrides so future changes do not undo good results. Keep a small changelog of settings, core versions, and SD health checks, then test new ideas against the same demanding scenes. Focus on predictable improvements rather than chasing one-off results. When you do update Onion OS or RetroArch cores, back up saves and settings first, apply changes in small increments, and validate after each step. A disciplined approach preserves performance gains while giving room to experiment with lightweight shaders or specific features where headroom exists.

Key terms

  • Emulator Core — The component that emulates a specific system.
  • Frame Pacing — Consistency of frame delivery intervals.
  • Frames Per Second — The number of images shown each second in a game.
  • Input Latency — Delay between pressing a control and seeing the result.
  • Libretro Core — A plugin that emulates a specific system in RetroArch.
  • Network Latency — The time it takes for data to travel between your device and the game server.
  • Per-Core Override — RetroArch settings saved for one core only.
  • Per-Game Settings — Settings that apply only to a specific game.
