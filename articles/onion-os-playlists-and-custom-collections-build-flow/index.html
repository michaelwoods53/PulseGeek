Onion OS Playlists and Custom Collections: Build Flow

By Jordan Kelly • Published February 8, 2026

Playlists and custom collections in Onion OS streamline browsing by grouping games intentionally rather than relying on long alphabetical lists. This guide targets creating portable lists that survive SD card moves and future updates, using predictable folder patterns and simple text formats. You only need a working Onion OS handheld, a card reader, and basic file navigation on a desktop. We will map a sensible structure first, then craft playlist files, and finally validate art and metadata so each collection feels crisp. Along the way, you will learn when to prefer a lightweight playlist and when a curated folder makes more sense, plus how to handle multi disc games without surprises.

Key takeaways

  • Choose stable folder roots before writing any playlist references.
  • Use relative paths so playlists remain portable across SD cards.
  • Keep naming predictable to align with metadata and scraper rules.
  • Test a small sample list before expanding to large collections.
  • Prefer playlists for cross system sets, folders for heavy art sets.

Plan the work

Start by defining the scope of your Onion OS collection because clear boundaries prevent list bloat and scraping mistakes. For example, decide whether your “Platformers 16-bit” set spans only SNES and Genesis or also includes PC Engine. A tight scope simplifies naming and reduces art mismatches since metadata tools map more accurately when systems are distinct. The tradeoff is flexibility, because broader sets are fun but increase false positives during art scraping. Capture the rule of thumb that a themed list should rarely exceed fifty titles on small handhelds, which keeps navigation quick. This planning step matters because every later decision, from folder layout to filename conventions, follows the chosen scope.

Next, choose stable root folders that will not change with future SD card reorganizations, since playlist reliability depends on path predictability. A common approach is anchoring all references relative to the ROMs directory rather than absolute drive letters. For instance, store entries like ../roms/GB/Tetris.gb instead of a device specific path that breaks when the card is reimaged. The upside is portability between devices and backups. The downside is you must keep relative depth consistent across systems. To manage this, sketch a simple map of your ROM roots and note one or two shared patterns you will reuse across lists. Consistency is what keeps playlists functional.

Finally, set filename and region tags that echo your scraping standards, because names drive matching for art and metadata. Use short region tokens like (USA) or (Europe) only when they add clarity, and drop redundant tags that clutter scrolling. A practical test is whether two games would collide in a search without tags. If yes, keep them. If no, simplify. Consider multi disc naming early, using concise Disc 1 and Disc 2 suffixes so any playlist entries remain unambiguous. The main tradeoff is between readability and precision, but balanced naming improves search, sorting, and artwork accuracy inside Onion OS interfaces.

Prepare environment

Establish a predictable directory layout before creating any playlist files, because list entries mirror your storage map. Keep each system’s ROMs in a clearly named folder, and reserve a dedicated area for optional collections or lists if your image supports it. A simple structure reduces confusion when you update cores or migrate cards. The tradeoff is up front effort to rename a few directories that drifted over time, but it pays off the first time you validate paths. This is also the moment to decide whether artwork will live centrally or alongside ROMs, since that affects scraper behavior and thumbnail caching performance.

Gather minimal tools that make edits safe and reversible, such as a plain text editor and a checksum utility for verifying ROM integrity. Text editors preserve the simple line breaks that playlist formats expect, and checksums confirm that two files with identical names are actually the same content. This prevents silent mismatches that confuse metadata or achievements. Keep a small sandbox with three to five games per system to test your approach before scaling. The tradeoff is maintaining duplicates temporarily, but a cordoned sandbox lets you iterate quickly without risking the main library until you are confident.

Use tags sparingly, and only if they reduce collisions or clarify multi disc ordering. Too many tags slow scanning and clutter handheld screens, while too few create scraping errors. This balanced approach aligns readability with technical correctness so your playlists remain understandable months later.

Execute steps

Create small, testable playlists first so you can validate path rules and art behavior before scaling. A playlist can be a plain text file listing relative paths to ROMs, which keeps entries portable across SD cards and future devices. Start with five entries across two systems to confirm cross platform ordering. If your theme or front end supports it, place the file in its recognized playlists directory; otherwise keep it near ROM roots for clarity. The tradeoff is discovery, because some interfaces display lists only from a specific folder, while others index any readable file. Testing a small set uncovers these nuances without risking time.

For multi disc titles, reference the disc files in canonical order and verify that your emulator core handles disc swapping if you intend to switch mid session. A playlist entry can point to an .m3u file that lists multiple disc images, which simplifies user flow. The tradeoff is maintenance, because you must keep both the playlist and the .m3u in sync when files are renamed. Still, this approach keeps game selection clean and prevents accidental booting of disc two. If your device supports quick disc change hotkeys, document them in a small readme so future you remembers the friction free path.

When your test list behaves correctly, expand incrementally and store source files under version control or a dated backup folder. Treat playlists as configuration, not disposable scratch files, because small changes accumulate over time. Export or copy a checkpoint after every major growth, like adding a new system or theme pack. The benefit is rollback if a scraper reassigns art incorrectly or a folder move breaks references. The cost is a few extra minutes per milestone, which is a fair trade for stability. This mindset turns your library into a predictable, maintainable collection rather than a one off experiment that decays.

Validate results

Begin validation by opening the playlist on device and scrolling the full set to detect broken paths, slow thumbnails, or odd sorting. A practical pass includes launching at least three games from different systems to confirm emulator associations are correct. If artwork appears slowly, reduce image size or verify that images are cached in the expected folder. The tradeoff is time spent testing, but light sampling prevents shipping a frustrating experience. Keep notes on any missorted entries, because minor naming tweaks such as removing double spaces or unifying hyphens often resolve inconsistent positions in alphabetical views.

Confirm art and metadata mapping with a targeted scraper run on a copy of your playlist set, avoiding bulk operations until you trust matches. When you encounter ambiguous titles that show multiple candidates, use region tags or serial numbers to raise precision. The limitation is that some rare releases share names across regions, leading to occasional mismatches that require manual selection. Keeping your tags concise yet informative creates a clear signal, which improves match rates and avoids overwriting correct data. After a small batch succeeds, consider applying the same process to the remainder of the collection.

Measure navigational feel on the actual device rather than your desktop, because handheld performance reveals issues like long list lag or slow back button behavior. A common rule is that lists around fifty entries remain snappy on modest hardware, while heavier sets may need subdividing. If scrolling feels sluggish, split by subtheme or era and keep the original monolithic list archived. The why is simple: fewer records reduce UI repaint and disk fetches, improving responsiveness. Balancing convenience with speed ensures a delightful browsing experience that does not sacrifice discoverability or the joy of themed exploration.

Troubleshoot and optimize

Path failures typically trace to changed directory depth or hidden characters, so open the playlist in a plain text editor and reveal whitespace. Look for stray tabs, mismatched case on systems that care about capitalization, or a renamed folder that shifted relative paths by one level. A reliable fix is normalizing paths to a shared root pattern and testing a single entry before batch correcting. The limitation is historical artifacts, since older lists may include absolute paths that are hard to repair. In those cases, recreate the short list from scratch for speed rather than chasing every discrepancy.

Art mismatches often come from ambiguous naming rather than scraper flaws, so refine titles to reflect the edition you own without stuffing labels. Add a minimal region tag or revision only when it distinguishes two similar entries the scraper presents. If your handheld caches thumbnails in a separate directory, clear the cache after adjusting names to force a fresh render. The downside is a temporary delay on first load. Still, it is essential for accurate previews. As you stabilize naming practices, these corrections shrink, and playlists retain the intended look across themes and updates.

Performance bottlenecks respond best to structure, not tweaks. Consolidate giant playlists into smaller, meaningful sets like “Shmups 1990–1994” and link them from a master list that contains only references to sublists if your front end supports it. If not, keep the master list offline as your editor’s index. The benefit is fast navigation and clearer discovery by era or mood. The tradeoff is more lists to maintain, which is manageable with versioned folders. Over time, this modular approach makes your library resilient to hardware limits and easy to extend as new systems or favorites join the rotation.

Frequently asked questions

Why do some playlist entries not launch even though files exist?

Paths often break due to case sensitivity or incorrect relative depth. Confirm folder names exactly match, check for stray spaces or tabs, and ensure the playlist uses the correct number of ../ segments for your current layout.

Should I store playlists with ROMs or in a dedicated folder?

Both work if your front end recognizes them. Keeping playlists near ROM roots improves clarity, while a dedicated folder centralizes management. Choose one approach and stay consistent so paths and indexing remain predictable.

How big can a playlist be before performance suffers?

It depends on hardware and theme, but smaller sets feel faster. If scrolling feels sluggish, split by subtheme or era and keep the original set archived. Fewer entries reduce UI work and improve perceived responsiveness.

What file encoding should I use for reliable playlists?

Save playlists as plain UTF-8 text with Unix line endings. This avoids hidden control characters and improves cross device compatibility, reducing errors when lists are copied between operating systems or editors.

How do I manage multi disc games cleanly?

Create an m3u file listing the discs in order and reference that file from your playlist. This keeps selection tidy and lets compatible cores handle disc changes using menu options or mapped hotkeys.
