Run an iPerf Test Between PC and Steam Deck

By Jacob Reed • Published January 11, 2026

You will run an iPerf3 test between a PC and a Steam Deck to measure real local throughput, then prove results by comparison. The goal is a repeatable baseline that separates device limits from Wi‑Fi or cabling issues. Assumptions include a PC with admin rights, Steam Deck in Desktop Mode, and either a reliable Ethernet path using a USB‑C adapter or a strong Wi‑Fi link. iPerf gives directional bandwidth and jitter context that raw downloads cannot, so it is ideal for diagnosing in‑home bottlenecks. We will cover setup, the exact commands, interpretation, and remediation. Expect to compare wired versus wireless to pinpoint where performance falls off and why.

Key takeaways

  • Use iPerf3 to measure true LAN throughput, not internet speed.
  • Compare wired and Wi‑Fi runs to localize the performance bottleneck.
  • Keep server stationary and change one variable per retest.
  • Run multiple 10 to 20 second tests to average transient noise.
  • Check CPU load and duplex mismatches when numbers look suspicious.

Plan the work

Start by defining the scope so the iPerf test answers a narrow question instead of producing noise. Decide whether you want to benchmark the Steam Deck’s Wi‑Fi path or its wired USB‑C Ethernet path first. For a baseline, keep the server on the PC and the client on the Deck to measure downstream toward the Deck, then reverse later if needed. Choose two or three environments like same room line of sight, one wall away, and wired dock to isolate RF or cable impacts. This plan prevents chasing random variance and ensures each run ties back to a test case with a clear purpose and a comparable setup.

Select roles and freeze them for the first pass to keep directionality constant. iPerf3 measures throughput from client to server, and changing direction can mask issues like receive buffer limits or driver quirks. Keep the PC as server initially because it is likely wired and has a stable IP address, which simplifies client targeting. Document the IP and adapter type you will test, and list adapters you will not change yet. By working one direction at a time, you avoid conflating transmit-side limits with receive-side bottlenecks, which makes root cause analysis faster and cleaner.

Define success thresholds and guardrails before touching commands so decisions do not drift. For example, expect wired gigabit paths to report near 900 Mbps under iPerf3 with default TCP settings, while Wi‑Fi can vary widely with distance and interference. Decide what gap justifies a change, like investigating anything below half the expected rate for the link layer. Also note environmental constraints such as shared 2.4 GHz channels in apartments that can depress throughput. This written target turns subjective impressions into objective outcomes, and it guides whether you need optimization or just acceptance of realistic limits for your setup.

Prepare environment

Stabilize the network path before installing tools to avoid misattributing faults. If possible, connect the PC with Ethernet to remove Wi‑Fi variability on the server side. On the Steam Deck, decide whether to use Desktop Mode with Wi‑Fi or a USB‑C Ethernet adapter to create a wired baseline. Ensure both devices share the same LAN and subnet by confirming their IP ranges match. Disable heavy background transfers and pause game downloads that can interfere with available bandwidth. This preflight step ensures that any low throughput later comes from the path under test rather than background noise, routing ambiguity, or cross traffic.

Install iPerf3 on both endpoints in a way that matches your operating systems. On Windows, use a trusted package like the official iPerf3 binaries or winget for convenience, and on Linux the Deck can install via Discover or a package manager. Confirm the binary is iPerf3 rather than legacy versions to match options and output formats. Record the installation paths if system PATH is not updated. Test that running iperf3 -v yields a version string on both devices. These checks catch mismatched versions early, which can produce confusing errors or missing flags that would derail the execution phase.

Gather the PC’s IP address and preselect a port to prevent firewall surprises. Use a port like 5201, iPerf3’s default, and allow inbound on that port in any host firewall temporarily during tests. If you cannot adjust firewall rules, consider running the server on an allowed user port instead and reflect that choice on the client command. Note that security software may throttle unfamiliar traffic, so plan to disable only what is necessary and reenable after testing. This careful preparation reduces false negatives from blocked ports or shaped flows and keeps your measurement aligned with your test plan’s assumptions on direction and scope.

Execute steps

Use a simple server and client pairing to produce an initial throughput value that you can compare across locations. Start the iPerf3 server on the PC and run the client from the Steam Deck, targeting the server’s IP and using defaults first. Defaults create a 10 second TCP test that is stable for most LAN paths and provides a clear Mbps value. This initial run serves as your baseline. If you are on Wi‑Fi, stand still and avoid antenna shadowing while the test runs. A short baseline makes later tuning meaningful and prevents premature flag tweaking that hides signal quality or driver issues you might need to address.

Introduce one variable at a time to observe its effect without noise from overlapping changes. If you want to explore UDP behavior or longer durations, change only that single parameter and rerun at least twice to catch transient jitter. Avoid changing both duration and parallel streams together on the first pass because their interactions can mislead you about congestion or buffer pressure. Keep a simple log that captures date, location, adapter type, and your iPerf3 command. This structure avoids drift and helps you roll back to the last known good configuration should a later variation produce inconsistent readings that do not align with expectations.

The goal is to collect a small set of comparable outputs instead of a heap of one‑off runs. Watch CPU usage on both endpoints to ensure the tool is not the bottleneck under high throughput. If numbers plateau at a suspicious ceiling like 94 Mbps on a wired link, suspect a Fast Ethernet hop rather than a protocol limit.

  3. Open the server port: allow 5201 inbound on the PC during testing.
  4. Run a 10s baseline: execute default TCP and record the Mbps reported.
  5. Compare wired first: create a wired baseline before testing Wi‑Fi changes.
  6. Log each run: note location, adapter, duration, and parameters for parity.

Validate results

Validate the baseline by repeating the same iPerf3 command at least twice and averaging results. Repeatability within a small margin indicates the path is stable, while large swings suggest contention or interference. For TCP, look at the summary bandwidth and note if retransmissions are high, which can point to Wi‑Fi issues or duplex mismatches on wired links. If the Deck shows much lower numbers than the PC in reversed roles, suspect receive path constraints or CPU overhead. This consistency check ensures you trust the metric before you act on it, reducing the risk of optimizing around a fluke reading or transient condition.

Compare wired versus Wi‑Fi readings to determine where to optimize. If wired approaches gigabit while Wi‑Fi underperforms, focus on channel congestion, band selection, and spatial setup rather than stack tuning. If both wired and wireless are low, check for a 100 Mbps hop, old cables, or switch port negotiation issues. Mapping deltas across transport types narrows the search dramatically.

For example, lengthening duration reduces noise, and restrained parallelism probes headroom without masking single‑flow limits. When UDP is necessary, bound the offered rate to avoid flooding beyond radio capacity and misreading loss. This structured validation approach helps you diagnose whether the bottleneck is radio, cabling, or endpoint resource constraints, and it stops you from overfitting test parameters that produce attractive numbers but do not reflect how your games or downloads actually behave under real usage patterns.

Troubleshoot and optimize

Work from physical to logical so you fix the simplest constraints first. If a wired run caps near 94 Mbps, suspect a Fast Ethernet segment, a bad cable, or a 10/100 port. Replace patch leads with Cat5e or better and verify link negotiation shows 1 Gbps full duplex. On Wi‑Fi, confirm the Deck is using the intended band and that signal strength is strong enough for the expected rate. A single wall or a metal shelf can create multipath that behaves poorly. This hardware first approach removes hidden ceilings that no amount of parameter tuning can overcome within iPerf3 or operating system settings.

Address software and stack factors once the physical checks are clean. Inspect host firewalls and security suites for traffic shaping that could throttle unknown flows. On Linux, verify CPU frequency scaling is not pinning to low states during the test. If the Deck overheats under sustained load, brief pauses can keep clocks stable without changing test parameters. For advanced analysis of packet behavior during the run, packet capture tools can reveal retransmissions or unexpected traffic competing for airtime. These insights avoid blind parameter flips and ensure that any tuning maps to an observed mechanism rather than superstition or coincidence.

When wireless remains inconsistent after fixes, revisit radio basics like band choice, channel width, and interference. Use a nearby 5 GHz channel with low congestion and avoid extremes in channel width that reduce resilience. Also consider scheduling iPerf runs at different times to detect patterns like evening interference. By pairing targeted remediation with repeatable measurement, you will converge on stable performance that matches your environment rather than chasing one‑time spikes.

  • Transmission Control Protocol — A reliable, connection-oriented transport protocol.

Frequently asked questions

Why is my wired iPerf3 result stuck near 94 Mbps?

A 100 Mbps link or bad cable often caps throughput near 94 Mbps after overhead. Check port negotiation, replace the patch cable with Cat5e or better, and confirm the switch and adapter support gigabit full duplex.

Should I use TCP or UDP for Steam Deck testing?

Start with TCP for a conservative, application like measure of throughput. Use UDP only to probe loss sensitivity, and bound the offered rate so you do not overrun the radio and misread congestion as device limitations.

How long should each iPerf3 run be?

Ten seconds is a good default. Use 20 seconds when results fluctuate or when Wi‑Fi conditions are variable. Longer tests average transient noise but increase exposure to background activity that may skew readings.

Do parallel streams give more accurate results?

Parallel streams can show total path capacity, but they can hide single flow limitations that affect many apps. Use one or two streams sparingly to probe headroom, and compare against a single stream baseline for context.

Can iPerf3 numbers replace internet speed tests?

No. iPerf3 measures local network throughput between two endpoints. It is ideal for diagnosing in home links. Internet speed tests measure your ISP path and remote server performance, which are different constraints.

Looking ahead

Extend your workflow by correlating iPerf3 with latency and loss metrics so you understand both capacity and responsiveness. Pair the throughput baseline with periodic pings or jitter logging to detect time‑based degradation. If you want to refine Wi‑Fi behavior further, revisit router band and channel settings and retest in the same locations to maintain comparability. Over time you will build a local profile that guides small, high‑leverage changes that stick, rather than resets or guesswork. This steady approach turns one successful iPerf test into a durable method for keeping the Steam Deck and home network smooth and predictable under varied conditions.
