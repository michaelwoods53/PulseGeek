Input Polling and Frame Delay on Miyoo Explained

By Jared Butler • Published February 7, 2026

Latency tuning on Miyoo starts with two levers that sound similar but act differently: input polling and frame delay. Input polling governs when RetroArch reads controller state during a frame, while frame delay attempts to push that work later to shorten the gap between your press and the next on-screen update. Both affect perceived responsiveness, yet each carries different risks on a small handheld. This article explains how these interact with cores, audio, and video sync, then offers safe ranges and decision criteria. The goal is practical understanding so you can trade small frame delay gains for stability when needed, and know when polling changes are enough to deliver the feel you want.

Key takeaways

  • Input polling sets when controls are read within each frame.
  • Frame delay shortens latency but risks stutter when timing slips.
  • Use conservative ranges first, then test per core and game.
  • Runahead and polling interact; avoid doubling the same benefit.
  • Audio crackle signals timing pressure from aggressive delay.

Concepts and definitions

Input polling is the point in the render loop where controller state is sampled, which determines how quickly a button press can affect the next frame. On Miyoo hardware, RetroArch and the active core coordinate this sampling, usually at a consistent point each frame to keep audio and video stable. For twitch games, earlier polling can lengthen the wait until the next displayed frame, while slightly later polling can reduce the window between input read and scanout. The tradeoff is predictability. Some cores expect polling at a stable phase, so moving it too late can amplify jitter if the system occasionally stalls. The practical approach is to shift in small steps and watch for drift or uneven pacing in scrolling scenes.

Frame delay deliberately postpones nonessential work inside the frame to the last safe moment, aiming to shave a fraction of a frame from button press to visible response. On Miyoo, this is bounded by the handheld’s CPU budget and the core’s timing behavior, which can vary widely between 8 and 16 bit systems. Pushing delay high can look great when the device holds 60 frames per second, but any small hiccup forces a missed vblank and adds a whole frame of lag. That cliff effect makes aggressive values risky on heavier cores. A good rule is to start modestly, advance until you see intermittent stutter or audio ticks, then back off one or two steps to leave a margin.

Runahead tackles a different piece of perceived latency by simulating one or more frames ahead and discarding frames with old input. Unlike input polling or frame delay, which adjust timing within a single frame, runahead rewinds internal game state to present a result that feels earlier than the hardware would normally allow. On Miyoo, that can be transformative in lightweight cores, yet it increases CPU load and can break cores with complex or unstable serialization. Combining modest frame delay with one runahead frame is common, but stacking high delay and multiple runahead frames compounds risk. The guiding idea is overlap: aim to fix one dominant source of lag at a time rather than attack all fronts simultaneously.

Frameworks and decision lenses

A practical framework begins with budget, headroom, and priority. Budget is the time per frame, usually 16.67 milliseconds at 60 hertz. Headroom is the consistent slack the core leaves after rendering and audio processing on Miyoo. Priority is what you will trade: absolute smoothness, or minimum latency. Measure first by playing a scrolling scene for a minute and noting if frame pacing looks even and audio is steady. If the core already rides near full budget, prioritize stability and touch only input polling. If headroom is healthy, you can consider small frame delay increments. This sequence enforces that you never overdraw the frame time before you seek gains.

Next, separate within-frame and across-frame tools. Input polling and frame delay operate within the current frame and can slightly shift the perceived timing of your press. Runahead operates across frames by presenting a simulated result from the future. If you use runahead, assign it the primary role and keep within-frame adjustments light on Miyoo to avoid double counting improvements. The tradeoff is that runahead can stress serialization, so some cores or specific games may lose determinism. In those cases, drop runahead and return to cautious frame delay plus polling changes. Treat each lever as exclusive phases rather than additive layers to keep testing clean and interpretable.

Finally, bake in rollback criteria. Define stop signals such as new audio crackle, dropped frames on status overlays, or inconsistent input feel during rapid taps. When one appears, revert the most recent change and retest for a full minute. Keep a tiny note for each core with acceptable ranges and caveats. This simple log avoids re-learning the same limits and speeds future tuning. Start by nudging input polling later so the press is sampled closer to scanout, then test a mild frame delay increment. A visible improvement feels like smoother ledge grabs or snappier jumps without audio fluctuation. The risk shows when background scrolling grows uneven or a rare frame hitch appears after long plays. If that happens, step the frame delay back one notch and retest. For tighter input feel without added delay pressure, try a single runahead frame after verifying the core supports clean state saves. In that case, revert polling to default and confirm stability. If you crave more responsiveness, attempt runahead one frame, but abort if serialization creates glitches on scene transitions.

Pitfalls, limitations, and edge cases

Chasing aggressive frame delay often triggers the cliff effect where a rare busy frame misses vblank and adds a whole frame of lag plus visible stutter. On Miyoo, that manifests as brief hitching in scenes with many sprites or transparency effects. The fix is counterintuitive: reduce delay to restore headroom and accept slightly higher latency that is stable. Another pitfall is relying on reported frame rate alone. A readout of 60 frames per second does not guarantee even pacing if work bunches near the end of each frame. Use scrolling tests and your ears. If audio starts to tick or drift relative to motion, your settings are beyond a safe operating window.

Combining multiple latency reducers without a plan can double count improvements while multiplying risk. For example, a late input poll, moderate frame delay, hard GPU sync, and one runahead frame may feel great alone, yet together overload the handheld during spikes. The remedy is constraint. Choose a primary and a secondary lever, and keep others at defaults. On Miyoo, hard GPU sync can help consistency in certain cases, but paired with high frame delay it can expose tiny CPU spikes that were previously hidden. If enabling a feature adds clarity in one scene but introduces hitches elsewhere, privilege the setting that behaves consistently across the widest range of loads.

Core specifics matter because emulation timing varies. Some cores serialize state cleanly, making runahead reliable, while others have intermittent desync during rapid effects or special chips. Likewise, input polling shifts may be ignored or quantized differently by individual cores. Do not assume global settings apply uniformly. Instead, confirm changes per core and sometimes per game. Maintain a short note per configuration with rules such as avoid runahead on this core or limit frame delay to a small value during water stages. This discipline prevents tedious backtracking. When audio crackle persists even at modest delay, revisit audio buffering and sync options before touching input timing again to avoid chasing the wrong root cause.

Frequently asked questions

Should I change input polling or frame delay first?

Adjust input polling first when headroom is tight, because it is less risky. Use frame delay only after confirming stable 60 frames per second with a small margin on your target core and game.

Why does audio crackle after increasing frame delay?

Audio crackle often signals timing pressure where work bunches near the end of the frame. Reduce frame delay or restore default polling, then recheck for consistent pacing in a busy scene.

Is runahead better than frame delay on Miyoo?

Neither is universally better. Use runahead when the core saves state cleanly and CPU headroom exists. Prefer small frame delay on light cores and polling changes on heavier ones.

What is a safe starting range for frame delay?

Begin with a very small value and test for a minute in a busy scene. Increase gradually until you notice stutter or audio ticks, then back off one step to leave margin.

Do these settings apply equally across all cores?

No. Cores differ in timing behavior and serialization quality. Validate per core and sometimes per game, and keep short notes with safe ranges and exceptions.
