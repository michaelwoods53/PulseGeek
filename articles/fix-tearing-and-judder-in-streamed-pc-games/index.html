Fix Tearing and Judder in Streamed PC Games

By Jacob Reed • Published March 8, 2026

Goal: fix tearing and judder during streamed games by aligning motion pacing from host to client. We will assume a Windows or Linux host, a Steam Deck or PC client, and a wired LAN where possible. Tearing appears when frames display mid scan, while judder shows uneven motion from irregular frame intervals. Both arise when refresh, vsync, and frame cap logic disagree with network timing. This guide proposes a testable order of operations that isolates variables and preserves headroom. You will set a stable refresh target, choose a sync method, and cap frames cleanly before tuning the encoder. We will also verify results with frame time overlays and adjust only one factor at a time for clarity.

Key takeaways

  • Match client refresh and stream fps to avoid uneven pacing.
  • Use one vsync domain and cap frames slightly below refresh.
  • Prefer wired LAN and stable bitrate to reduce jitter.
  • Validate with frame time graphs, not only perceived smoothness.
  • Adjust encoder buffers last to keep comparisons reliable.

Plan the work

Start with a clear objective: synchronize delivery cadence across host, encoder, network, and client display so frames arrive on time and in order. Define constraints like target refresh and expected frame rate. For a 60 Hz screen, aim for a steady 60 or a clean 30 with integer pacing. If the client supports 90 or 120 Hz, consider 60 capped with VRR off for easier control. Identify where you will measure success, such as a frame time graph in the overlay. Planning reduces false fixes that mask root causes, like enabling two conflicting vsync systems that only appear smooth in simple scenes but break during camera pans.

Set measurement checkpoints before changing anything to avoid chasing placebo improvements. Use the client overlay for fps and frame time deviation, plus a test scene with constant panning like a third person walk through a dense area. A repeatable camera path reveals microstutter that sporadic combat does not. Document the baseline with a short clip and note the mean frame time and worst frame spikes. Establish what acceptable looks like, for example standard deviation below a threshold that feels smooth to you. Without measurement, you might trade tearing for judder or vice versa without noticing until later.

Define your knobs and lock the rest to a neutral baseline to isolate effects. Knobs include refresh rate, vsync method, a game engine frame limiter, and the streaming app’s fps target. Neutral settings might be 60 Hz refresh, game vsync off, driver vsync off, and the streamer locked at 60 fps. From there, introduce one change at a time. A common trap is stacking game vsync with driver vsync and the streamer’s frame queue, which adds latency and can produce periodic hitching. If you plan for predicates like wired network only and stable GPU clocks, later steps become shorter because you eliminate causes early.

Prepare environment

Stability begins with consistent display timing and drivers. Set the client display to a fixed refresh that matches your stream target, such as 60 Hz, and disable VRR while you tune. VRR can hide pacing errors by stretching frames unevenly, which complicates diagnosis. Update GPU drivers to current stable and reset any exotic toggles like low latency modes or frame pre-render limits to defaults. On Linux, verify compositor settings align with fullscreen flipping or direct scanout where supported. The goal is predictable scheduling so that changes in one layer do not ripple unpredictably through another.

Prepare the network to remove jitter that mimics judder. Prefer Ethernet for both host and client. If Wi-Fi is unavoidable, use 5 GHz or Wi‑Fi 6 with a clear channel and disable power saving on the adapter. Start with a moderate bitrate target that leaves headroom, for instance 30 to 40 Mbps for 1080p60, then adjust after pacing is stable. Packet bursts force the client to re-time frames, which can look like cadence issues. Keep background traffic off the LAN and ensure the router QoS does not deprioritize your streaming protocol. Clean transport turns visual tuning into a deterministic exercise.

Align terminology across tools so settings map cleanly. Many launchers and drivers label similar ideas differently, which encourages double-enabling. Use the following quick reference to match common options. Refer to the encoder and game only after a single control point is chosen, which minimizes queuing. If your driver exposes a global vsync override, prefer application controlled unless you explicitly test a driver-locked scenario. Maintain a notepad of changes for each test run so rollbacks are immediate if a result degrades.

Execute steps

Execution benefits from a strict order that aligns display, rendering, and transport. Start by matching the client refresh to the intended stream frame rate, for example 60 Hz for 60 fps. Next, pick a single vsync domain to control frame presentation. I recommend disabling vsync in the game and driver, then letting the streaming client handle pacing, or alternatively turning on game vsync while the streamer simply targets a matching fps with minimal buffering. Cap the game at 59 or 60 depending on your testing to prevent run-ahead frames. This avoids periodic collisions where the game renders faster than the display interval and a frame is sliced mid-scan.

When using Moonlight or Steam Link, combine a clean game-side cap with an encoder fps target. The intent is to keep queues shallow so latency and cadence stay predictable. If your game lacks a native limiter, a driver limiter or RTSS can cap within 0.5 to 1 fps of refresh, such as 59.94 on a 59.94 Hz mode. This slight undershoot helps prevent VSYNC stalls without introducing noticeable slowdowns. Only after the cadence is stable should you try higher bitrates or hevc/av1 to improve quality. Visual clarity is a secondary goal once pacing is correct.

To make the Moonlight case concrete, the CLI can express fps, bitrate, and encoder choices explicitly. The following example sets the stream to 60 fps, a balanced bitrate, and a modest network mtu. Expect a stable cadence if your game is capped to 60 with a single vsync domain. If you still see slicing, review your display mode and ensure VRR remains disabled during tests. After verifying smooth pans, raise bitrate gradually while watching frame time variance.

Validate results

Validation focuses on whether motion remains even during worst-case pans. Use an overlay that shows instantaneous fps and frame time graphs, then run a repeatable camera sweep across dense geometry. Look for a flat frame time line near 16.7 ms for 60 fps. Occasional spikes can be asset loads or shader compilation and are acceptable if rare, while rhythmic spikes often signal a pacing conflict. Record a short clip and replay it in slow motion to check for residual slicing. If the picture holds without diagonal tears, your vsync domain and cap are aligned.

Verify that latency did not balloon while removing tearing. A single vsync system with a near-refresh cap should add minimal delay, but triple buffering or long encoder queues can creep in if left enabled. A good rule is to balance smoothness and responsiveness by monitoring both average latency and variance using a simple input test like menu cursor movement. If menus feel syrupy after your changes, reduce buffering in the streamer and re-test. Latency and pacing must be tuned together, not traded recklessly.

When the stream appears clean, stress it with variable complexity scenes. Try a bright outdoor area with foliage, then a dark interior with particle effects. High-motion content challenges the encoder and can force buffer growth, which introduces tiny cadence errors that mimic judder. If issues return only under heavy load, you may need to increase bitrate or switch codecs after confirming your network can sustain it. Troubleshoot and optimize

If tearing persists, check for dueling sync systems. A typical offender is game vsync on while the streamer also enforces pacing, leading to periodic stalls every few seconds. Disable one and confirm improvement. Another edge case is mismatched fractional refresh like 59.94 Hz against a strict 60 fps cap, which produces a slow beat pattern of hitches. Cap to 59 or 59.94 instead. On Steam Deck, some titles route through a compositor that can re-time frames, so prefer true fullscreen or direct scanout modes when available. Avoid global driver overrides unless you document the effect precisely.

If motion is even but still judders during camera pans, investigate bandwidth and packet loss that force buffer stretching. Use wired LAN or a clean Wi‑Fi channel and monitor router queues. If you suspect loss, run short tests while adjusting the streamer jitter buffer by small increments. Too small and minor jitter creates stutter, too large and latency grows while cadence becomes mushy. For platform-specific quirks, consider GPU driver features that may conflict with streaming. Image sharpening, frame generation, and aggressive low latency modes can alter pacing or collide with encoder scheduling. Reset to defaults and reintroduce one at a time. If you see black frames on start or after alt-tab, that is a different class of failure linked to capture or surface negotiation. Work through known remedies that focus on black screen symptoms to fix capture paths first, then return to cadence tuning once video is stable.

Quick start checklist

  1. Fix refresh: set the client display to 60 Hz and disable VRR.
  2. Choose one vsync: keep only game vsync or streamer pacing active.
  3. Cap cleanly: set an fps limit to 59–60 for 60 Hz displays.
  4. Match stream fps: configure the streaming app to the same fps target.
  5. Stabilize network: use Ethernet and a moderate bitrate before tuning higher.
  6. Validate cadence: check frame time graphs during slow camera pans.

Frequently asked questions

Should I enable both game vsync and streaming client pacing?

No. Use one vsync domain to avoid periodic stalls or added latency. Either enable game vsync with the client targeting the same fps, or disable game vsync and let the client handle pacing. Do not stack them.

Why does 60 fps stutter on a 59.94 Hz mode?

A strict 60 fps cap drifts against 59.94 Hz and produces a repeating hitch as frames desynchronize. Cap to 59 or 59.94 to align cadence with the display’s fractional refresh and eliminate the beat pattern.

Does VRR help or hurt while tuning tearing issues?

VRR can mask pacing problems by stretching frames to fit the refresh window, which complicates diagnosis. Disable VRR while tuning, then re-enable after cadence is stable to reduce residual tearing without hiding issues.

Is triple buffering good for streamed games?

Triple buffering can smooth delivery at the cost of extra latency and periodic queue growth when bandwidth fluctuates. Prefer double buffering with a clean frame cap first, and only add extra buffering if tearing returns.

What bitrate should I start with at 1080p60?

Begin around 30 to 40 Mbps to leave headroom, then increase cautiously after cadence stabilizes. If your network shows loss or spikes, raising bitrate will worsen judder and should wait until transport is stable.
