Audio Latency Buffer Size on Miyoo Mini

By Austin Price • Published January 3, 2026

Audio latency, buffer size, and RetroArch sync choices determine how the Miyoo Mini feels under your thumbs. This guide targets clean sound with minimal delay using settings that hold up across cores. You need a stock firmware or a mainstream custom build with RetroArch available, plus a few consistent test ROMs. We assume no overclock and default audio drivers. The process starts with planning baselines, then preparing the device for repeatable tests, executing a narrow sequence of changes, and finally validating with loops and stressors. Each step explains why a value works, what can break, and how to recover quickly.

Key takeaways

  • Set audio latency conservatively first, then step down while monitoring crackle.
  • Keep audio sync on and rate control enabled to stabilize pacing.
  • Validate with loops and stress tests before saving per core overrides.
  • Use a small table of values to map safe choices by system.
  • Rewind, shaders, and overlays can force larger buffers on Miyoo.

Plan the work

Start with a specific target: reduce audio delay without introducing crackle or jitter while keeping frame pacing stable. Choose one or two games per system that expose issues quickly, such as a title with tight percussion or rapid menu bleeps. Set a baseline by noting current RetroArch values for audio latency and sync so you can revert if needed. Define pass and fail criteria beforehand. A pass means no audible crackle during ten minutes of play and no obvious desync during scene transitions. A fail includes repeated pops or drift. Planning these criteria upfront avoids chasing subjective impressions and makes each change purposeful.

Anchor the plan in safe ranges so experimentation stays controlled. On handheld hardware like the Miyoo Mini, buffers that are too small amplify timing noise from CPU load or storage I/O. A practical rule of thumb is to begin at a moderate buffer and work downward in small steps. Use per core overrides only after a global setting behaves well. That approach prevents inconsistent experiences across systems and speeds up testing. The tradeoff is that a global value might be slightly conservative for one lightweight core, but consistency and simplicity usually beat fine grained micro tuning early on.

Map dependencies that skew results before touching any slider. Features like rewind, heavy shaders, layered overlays, or high frame delay tighten timing margins and can force larger buffers. If you want the fastest feel, evaluate whether those features are essential. For example, disabling rewind often recovers headroom immediately, letting you try smaller latency values safely. Document which extras are active during tests so you can reproduce outcomes later. The limitation is that removing features can change the game’s look or convenience. Decide what you are willing to trade to keep audio steady and inputs responsive.

Prepare environment

Stabilize the test environment so buffer changes reflect actual audio behavior. Charge the device, close other apps, and ensure storage is healthy to avoid I/O stalls that masquerade as crackle. In RetroArch, confirm audio sync is enabled and rate control is on, because both help the mixer adapt safely when the frame time wobbles. These baseline toggles reduce artifacts that small buffers might otherwise reveal prematurely. The tradeoff is a slightly less aggressive latency floor, yet this foundation lets you explore smaller values with fewer false negatives. Capture current settings in a text note to track your path.

Pick representative content for repeatable evaluation. A menu with crisp beeps, a rhythm segment, or a looping intro exposes discontinuities fast. Run each test scene for at least two minutes, then replay after changes. Keep screen brightness and volume consistent to avoid psychoacoustic shifts that could bias judgment. If your build supports it, enable on screen frame time graphs only during diagnosis, then turn them off to remove overhead. This discipline keeps observations comparable across iterations, which matters when deciding between two close latency values that both sound acceptable in casual play.

With that context, your buffer experiments will produce cleaner, more transferable results.

If a value almost works except during streaming scenes, consider backing off by one step rather than flipping new toggles that add complexity. Document each trial with notes on game, core, buffer value, and any crackle moments. This audit trail becomes invaluable when per core overrides later need a quick reference.

Validate results

Validation is proof that your chosen buffer size holds under realistic pressure. Recreate stress conditions: pause menus, rapid scene changes, and streaming levels. Listen for repeating pops, which indicate underruns, and watch for audio falling behind after long loads. Use long loops, at least ten minutes across varied scenes, to catch slow drift. If everything stays clean, mark the value as stable. If rare pops occur only during extreme moments, decide whether a single step increase is acceptable. The goal is dependable behavior, not theoretical minimums that collapse during real play when the handheld’s resources spike.

Cross check related features that often hide timing problems. Turn rewind on and off to understand its cost, then choose based on your priority. Disable heavy shaders or overlays temporarily to isolate whether visuals forced your buffer higher. If changes reveal the sound is only fragile under optional effects, you can keep the lower latency for a minimal setup and accept a higher value when those extras are enabled. This split approach acknowledges tradeoffs without locking you into one compromise. The key is documenting which features require which buffer so switching profiles remains intentional.

Before finalizing, compare your outcome with a broader performance stack so you do not solve a symptom while ignoring a root cause. Troubleshoot and optimize

When crackle appears at aggressive settings, raise the buffer one step and retest. If pops persist, confirm audio sync remains enabled and rate control is on. Consider whether the core is CPU bound during certain scenes that pull headroom away from the mixer. In those cases, a slightly larger buffer prevents underruns without making the system feel sluggish. If drift appears after long loads, increase the buffer modestly or reduce any competing features such as rewind depth. The principle is to change one variable at a time, validate quickly, and keep notes so you can back out unsuccessful moves confidently.

If sound is clean but inputs feel sluggish, explore cautiously reducing the buffer while keeping rate control active. The practical ceiling for responsiveness is where changes produce no perceivable improvement in timing. Do not sacrifice stability for a placebo win. For tight latency beyond buffer tuning, evaluate video sync options and display timing, which can influence perceived input feel more than audio alone. A targeted resource on selecting vsync approaches can help you pick settings that balance smoothness with latency. That path can unlock responsiveness without pressuring audio to live on a knife edge.

For recurring issues tied to specific cores, isolate using per core overrides. Start from your stable global baseline, then try one step lower per core if tests stay clean. If a core needs a higher value consistently, write that override and document the exception. Keep the number of exceptions small to preserve predictability. Recheck after firmware or core updates, since timing behavior can shift. If problems expand rather than shrink, reset to the global baseline and review upstream changes. These resets are not setbacks. They protect your time and keep the device feeling consistent across varied sessions.

Frequently asked questions

What audio latency value should I start with on Miyoo Mini?

Begin with a conservative value near 96 ms with audio sync and rate control enabled. Lower in small steps to 80 ms and 64 ms while replaying the same loop. If crackle appears, step back up one increment and retest.

Why does audio crackle when I lower the buffer size?

Crackle usually means underruns caused by timing spikes from CPU load, storage, or extra features like rewind and heavy shaders. Increase the buffer one step or disable the feature that tightens timing margins and test again.

Should I use per core overrides for audio latency?

Use per core overrides only after a global value is stable. Some cores tolerate smaller buffers or require larger ones. Document exceptions, keep them minimal, and revalidate after core or firmware updates because behavior can shift.

Does changing vsync affect perceived audio latency?

Vsync influences frame timing, which can change how responsive the system feels even with the same audio buffer. Fix display pacing first, then tune audio. This order prevents masking audio issues with unstable video timing.
