Format SD Card for Onion OS: FAT32 the Right Way

By Jordan Kelly • Published January 21, 2026

Our goal is simple and specific. We will format an SD card to FAT32 for Onion OS in a way that is reproducible and safe. This guide assumes a basic desktop environment and a removable SD card reader. You will learn when to choose quick versus full format, how to apply correct allocation unit sizes, and how to confirm the result before first boot. By the end, you will have a FAT32 volume that Onion OS can read on devices like the Miyoo Mini, validated with a couple of quick checks that prevent surprises later.

Key takeaways

  • Use FAT32 with an MBR partition and a single primary volume.
  • Prefer 32 KB clusters for 32 GB to 128 GB SD cards.
  • Run a read and file integrity check before first boot.
  • Avoid Windows GUI limits by using CLI tools when needed.
  • Label the volume clearly to prevent accidental selection mistakes.

Plan the work

Start by defining the target: a clean FAT32 volume the device can read consistently. FAT32 remains the expected format for Onion OS on handhelds because it maximizes compatibility across tools and boot steps. Choose a card that matches your library size and your device’s tested limits. As a rule of thumb, 32 GB to 128 GB works well and formats quickly, while larger capacities may add time and risk during verification. Plan to back up any files first, since formatting erases content. Capture the card’s exact device path before acting to avoid overwriting the wrong disk. Clarity at this stage prevents rushed mistakes later.

Decide on partitioning and cluster size before you connect the card. A single primary partition with MBR partitioning and FAT32 is the simplest approach for Onion OS and keeps boot logic straightforward. Allocation unit size, often called cluster size, influences performance and space overhead. For handheld ROM libraries that include many small files and some larger archives, 32 KB clusters balance directory performance with acceptable slack space. Tiny clusters can bloat directory lookups, while very large clusters waste space. Document your chosen settings, because you will need to reproduce them if you ever reformat or migrate.

Define verification criteria now so validation does not get skipped. Plan to reinsert the card and check the filesystem label, capacity, and allocation unit size after formatting. Add a small integrity test by copying a handful of representative files and verifying open and delete operations. For extra assurance, run a read-only surface test or at least a checksum pass on a small sample. This small investment catches early issues like counterfeit media or silent write errors. Prepare environment

Preparation reduces risk and speeds up the format step. Install or confirm access to platform tools. On Windows, have Disk Management and an administrative shell ready, plus a trusted FAT32 formatter if the GUI blocks large cards. On macOS, Disk Utility and the Terminal provide reliable control via diskutil and newfs_msdos. On Linux, lsblk, fdisk or parted, and mkfs.fat are standard. Before you run anything, insert the SD card and list disks to capture the device identifier and current partitions. Record the card’s size to catch mismatches that can indicate counterfeits. This quick inventory becomes your safety baseline.

Gather values you will reuse during execution. Decide a volume label with no spaces, for example ONIONSD, to make it readable on the device. Note your desired allocation unit size and confirm your OS supports specifying it. If your card is exFAT or NTFS, you may need to delete and recreate the partition before formatting. Execute steps

Execution starts with cleanly removing any existing partitions that could block a FAT32 format. On Linux or macOS, unmount the volumes first, then recreate a single MBR partition that spans the card. On Windows, use Disk Management or diskpart to delete and create a primary partition if the card shows multiple volumes. Once the partition table is correct, perform the FAT32 format with the chosen label and cluster size. Quick format is acceptable for known good cards, but a full format is safer on a first run or when a card’s origin is uncertain. Finish by safely ejecting and reinserting to read fresh metadata.

Validate results

Validation ensures the FAT32 format meets expectations before you copy gigabytes of files. Start by checking the filesystem type, capacity, and allocation unit size reported by your OS. On Linux, use lsblk and fsck.vfat to inspect; on macOS, diskutil info provides details; on Windows, properties or fsutil fsinfo shows cluster size. Create a small test: copy a few directories that mirror your typical Onion OS usage, then open and delete them. Time a simple copy to catch suspicious slowdowns that hint at failing media. Early measurements help you decide whether to continue or replace the card.

Check for silent errors with a quick surface or read test suited to your platform. Tools like f3 on Linux or macOS, or H2testw on Windows, write and read patterns that expose counterfeit or worn media. You do not need a full card scan every time, but running at least a partial test after a first format can prevent surprises later. If the test reveals mismatched capacity or repeated read errors, retire the card rather than trusting intermittent behavior. The goal is not perfect benchmarking but confidence that the media will hold Onion OS files reliably.

Finally, mount and safely eject the card to confirm clean shutdown behavior. Pulling power or removing media during writes risks corruption. Practicing safe removal here builds habits that protect your library during daily use. Troubleshoot and optimize

When formatting fails, start with the device path and permissions. Many errors trace back to attempting writes on a mounted volume or choosing the wrong disk. Unmount and retry, or elevate privileges if your OS requires admin rights for partitioning. If you see messages about unsupported size on Windows, use an administrative shell or a trusted FAT32 formatter for larger cards. For persistent errors on Linux, check dmesg for device I/O warnings that indicate a failing reader. Swapping the USB adapter often resolves odd behavior. The immediate goal is to isolate environment issues before blaming the card.

Performance complaints usually relate to cluster size or fragmented directory structures. If your library contains many tiny files, smaller clusters reduce slack but can slow directory scans. Conversely, larger clusters can speed sequential reads at the cost of wasted space on small items. Reformatting with 16 KB or 32 KB clusters allows you to tune for your library pattern. Keep your layout simple and avoid multiple partitions, which add complexity with little benefit on handhelds. As your collection grows, consider staging ROM copies in batches to keep the filesystem healthy and reduce long write sessions.

If first boot on Onion OS stalls or the card is not detected, validate that the card presents a single MBR FAT32 partition and that files were copied to the correct folders. Corruption often traces back to unsafe removal during a large copy. Frequently asked questions

Can I use exFAT instead of FAT32 for Onion OS?

Use FAT32. Many handheld builds expect FAT32 and may not mount exFAT reliably. FAT32 ensures compatibility with common tools and boot sequences used by Onion OS.

Why does Windows refuse to format larger cards as FAT32?

The Windows GUI restricts FAT32 creation above 32 GB. Use an administrative shell or a trusted formatter for larger cards. Always verify the target disk before running any format.

What cluster size should I choose for performance?

32 KB is a balanced starting point for 32 GB to 128 GB cards. Smaller clusters can reduce slack for tiny files but may slow directory scans. Reformat only if measurements justify it.

Do I need to run a full format every time?

No. Quick format is fine for known good media. Use full format or a write and read test when the card is new, has unknown history, or after repeated filesystem errors.

How do I confirm I picked the correct disk?

List disks and match size, model, and removable status. Double check the device path before running commands. If uncertain, stop and reinsert the card to refresh identifiers.
