Miyoo RetroArch Backup and Restore: Settings Safe

By Jared Butler • Published February 20, 2026

Good backups start with a precise inventory of RetroArch settings, saves, and components on Miyoo. This guide prioritizes the directories and files that matter, then shows how to restore them without breaking paths. Decisions balance backup speed with reliability so you can restore quickly after a card failure or OS change. Throughout, I highlight where version drift can upset a restore, how to test safely, and which folders deserve redundancy when space is tight.

Key takeaways

  • Back up configs, saves, cores, and BIOS to preserve RetroArch behavior.
  • Verify versions and paths before restore to prevent broken references.
  • Use rsync or zip with excludes to keep backups lean and repeatable.
  • Test restores on a spare SD or profile before replacing production.

1) Capture global config and per-core options

Back up the configuration that defines RetroArch behavior because a restore without these files will feel like a different system. On Miyoo, prioritize /RetroArch/retroarch.cfg for global settings, then the /RetroArch/config/ directory for per-core options and input remaps. For example, a tuned latency profile for SNES and a unique overlay for GB will live in core-specific subfolders under config. The gain is continuity after reinstalling or moving to a new SD card. The tradeoff is that old configs can reference paths that change with OS flavors like OnionOS or MinUI, so stale content_directory or overlay paths may fail. Audit path keys after a restore and prefer relative paths where possible to reduce future mismatch risk.

Include supporting assets that configs expect, especially /RetroArch/overlays/, /RetroArch/config/remaps/, and /RetroArch/shaders/ if used. A common example is a Game Boy bezels folder referenced by a core override file. Without the overlay images, RetroArch will load but drop your overlay silently. To reduce bloat, you can exclude large shader packs you do not use and re-download later. A limitation of this lean approach is that community presets might change upstream, so identical visuals are not guaranteed if you restore from a partial set. When unsure, capture a small, curated shader and overlay subset that reflects what you actually use, rather than everything available.

  • Audit restored paths, preferring relative references to reduce breaks.

2) Save files and states without corruption

Preserve progress by copying /RetroArch/saves/ and /RetroArch/states/ with care, because interrupted transfers can corrupt write-active files. A safe pattern is to quit a core to flush buffers, then exit RetroArch before copying, or copy from a powered-down handheld via card reader. As an example, JRPG SRAM in saves and quick states in states can be mirrored to a desktop folder named by date. Compression helps space, but choose lossless zip and avoid recompressing states repeatedly to reduce wear on cards. The tradeoff is restore time and the risk that per-core filename conventions differ after renaming ROMs, leaving orphaned saves. Keep stable ROM names or maintain a mapping note to rename save files when collections evolve.

Spot-check integrity after backing up saves, because silent failures cost hours. Reopen RetroArch with a small test ROM, load a state, and confirm the save slot number and timestamp match expectations. For large libraries, prioritize recent saves and long-form games for verification. When you plan to migrate cards, consider a dry run on a spare microSD where you restore only saves and states first, then boot a few systems to confirm the folder paths are correct. If states fail but SRAM loads, you may have mismatched core versions. In that case, defer states and rely on SRAM until core parity is restored. For broader migration guidance, see the SD card move notes in the related piece on safely moving save files to a new card.

  • Verify a few games and timestamps before trusting the backup.

3) Keep cores and BIOS organized and verifiable

Back up /RetroArch/cores/ and /RetroArch/system/ because they govern compatibility and determinism for states. A concrete example is a state created with a specific Genesis core build that fails with a newer core after a restore. Keeping the exact core binaries preserves behavior and often rescues states. BIOS files in system should be validated by filename and checksum to avoid subtle boot errors. The tradeoff is legal: only keep BIOS you have a right to possess. To minimize ambiguity, store a small text file listing the expected hashes next to sensitive BIOS files. If an OS like OnionOS relocates BIOS, update system_directory in configs after a restore and verify one system boots from a known title screen or BIOS splash.

Reduce confusion by maintaining a simple directory convention and a minimal set of BIOS tailored to the cores you actually load. For instance, if you use one PlayStation core, do not keep redundant BIOS variants. This makes future audits easier and reduces restore size. A limitation is that certain cores accept multiple regional BIOS versions and switch behavior based on region, which can impact save compatibility. Decide on one region and stick with it, or keep a labeled trio with clear notes so you do not mix them inadvertently. 4) Automate backups with rsync or zip safely

Automate backups to avoid stale copies, because manual runs slip during busy weeks. A practical approach is a desktop script that copies only changed files from /RetroArch/ while excluding cache and thumbnails. Expect faster runs, smaller transfers, and fewer write cycles on your microSD. The tradeoff is complexity and the risk of copying while RetroArch is open. Run after ejecting the card or when the device is powered off. If you want a baseline zip snapshot, keep one full archive per month and incremental rsync mirrors weekly. Name folders with a date prefix like YYYY-MM-DD and include a short note file describing OS version and RetroArch build. That small context speeds restores when a mismatch appears months later.

Section highlights

  • Use scripted mirrors to capture changes without bloating backups.
  • Run when RetroArch is closed to prevent partial file copies.

5) Restore cleanly and validate paths and versions

Restore in a controlled order to reduce conflicts. Start with retroarch.cfg, then config/, followed by saves/ and states/, then cores/ and system/. After copying, launch RetroArch and check Settings to confirm the content, system, and shader directories point to valid locations on Miyoo. As an example, test one system per console family and load one state. If any state fails, compare the core name and build date with your backup set to confirm parity. The tradeoff is time spent verifying, but it prevents cascading errors later. Keep a small text checklist in your backup with the expected versions for high-dependency cores like PlayStation, Saturn, and N64 so mismatches are obvious.

Resolve problems with minimal risk by isolating differences. If paths break due to OS differences, edit only the necessary keys in retroarch.cfg or a per-core override rather than resetting everything. For example, update system_directory and retest BIOS-dependent consoles first. If you installed fresh RetroArch on Miyoo Mini Plus and want baseline defaults, compare your restored settings against a stable settings guide to ensure latency and video flags make sense for the handheld’s limits. When playlists appear empty, refresh them from your backup and confirm ROM paths match the new SD layout. If you changed folder names, use consistent renaming so thumbnails, playlists, and saves find their targets without manual rebuilds.

Frequently asked questions

Which RetroArch folders on Miyoo are essential to back up?

Prioritize retroarch.cfg, config, saves, states, cores, and system. Include overlays, remaps, and shaders you actively use. Thumbnails are optional and can be rebuilt later.

Can I restore save states across different core versions?

Sometimes, but it is unreliable. Save states depend on core implementation details. Match the same core build when possible. Regular SRAM saves are more portable across versions.

Do I need to back up thumbnails?

No, thumbnails are noncritical. They take space and can be re-downloaded or regenerated. Back them up only if you have a curated set you cannot easily replace.

How often should I back up RetroArch on Miyoo?

Back up after meaningful configuration changes and after long play sessions. Weekly is reasonable for active use. Automate with scripts to capture only changed files.

Is it safe to zip my RetroArch folder directly?

Yes, if RetroArch is closed and the SD card is not being written to. Quitting RetroArch before zipping reduces the chance of partially written files.

Looking ahead

Once backups are routine, expand testing by rotating one system each week and confirming states, SRAM, and overlays still behave. This small cadence catches drift before it becomes a surprise during a long playthrough. If you switch to a different OS flavor, snapshot the previous card first and record the build numbers in a note inside the backup so future restores can reproduce your environment precisely.
