Miyoo Mini Menu Navigation: A Friendly Walkthrough

By Jeremy Crawford • Published February 10, 2026

Miyoo Mini owners often ask how to move confidently through the menu system, which can feel dense at first. This walkthrough explains navigation patterns, menu structure, and safe defaults so you understand where settings live and why. Whether you use stock firmware or Onion OS, you will learn predictable routes that reduce trial and error and make play sessions smoother.

Key takeaways

  • Main menu handles system-wide options, while in-game menus are per core.
  • Quick controls change brightness or volume without leaving the current game.
  • Save frequently and use safe shutdown to avoid data loss during navigation.
  • Use consistent paths for common tasks to reduce taps and confusion.
  • Document personal defaults so reconfiguration stays fast after updates.

Concepts and definitions

The most useful starting concept is the separation between system menus and in-game options, because navigation differs by context. System menus handle global items like language, time, Wi Fi if present, display theme, and storage. In-game options belong to the emulator core or frontend and include save states, aspect ratio, shader choice, and input mapping. For example, screen brightness often appears in a quick overlay or hardware shortcut, while video scaling may live inside the emulator pause menu. The tradeoff is convenience versus control. Quick overlays are fast but limited, and deep emulator menus unlock precise behavior at the cost of extra steps. Understanding which layer governs a setting prevents frustration, because changing an in-game option will not affect another title unless that core reuses profiles.

A second foundational idea is consistent navigation patterns, which act like muscle memory across menus. Most builds map a pause or function button combination to open an in-game menu, while the main menu uses directional navigation with confirm and back. As a concrete example, holding a designated combo might open save and load, whereas a single press could toggle an on screen overlay. The tradeoff is discoverability. Combos are fast once learned but opaque to newcomers. Good practice is to learn three anchor routes: reach the main settings page, open the game pause overlay, and access quick brightness or volume. With those anchors, you can handle ninety percent of tasks without searching, since everything else stems from these branches.

Third, scopes determine persistence, which affects how changes carry forward. Global settings persist across games and reboots, core settings often apply to any title using the same emulator, and per game overrides stick to one ROM only. For instance, a Game Boy core may keep your integer scaling preference across that library, but a single wide screen tweak might save only for one game if set as an override. The advantage of scoped saves is fine control, but the drawback is accidental overrides that cause surprising differences later. A useful rule is to change defaults at the global level first, then promote core preferences only when a console family needs something different, and reserve per game overrides for edge cases like special aspect ratios.

Frameworks and decision lenses

A practical lens is task frequency versus depth, which guides where to place a setting. Frequent actions like brightness, volume, and save state should sit in quick access or a single combo to minimize friction. Infrequent yet impactful items like time zone or Wi Fi credentials can live deeper because the cost is paid rarely. For example, mapping quick save to a safe button combo reduces risk when you need to capture progress during short sessions. The tradeoff is accidental activation if combos overlap with other functions. Mitigate by choosing nonadjacent buttons or enabling a confirmation prompt. This lens keeps navigation efficient by aligning proximity with usage patterns, so time sensitive actions never require laddering through multiple screens.

Another useful framework is risk containment for data integrity, which prioritizes save workflow and power behavior. Always ensure save or exit actions write to storage before sleep or power off, particularly on retro frontends that buffer writes. A safe pattern is save state, return to the game menu, then exit to the system menu, and finally use a safe shutdown. The tradeoff is extra steps, yet it prevents corruption far more reliably than hard power cuts. As a concrete reference route, treat the in-game pause menu as a checkpoint where writes are flushed. If your build supports auto save on exit, still perform a manual save during important moments to guard against unexpected battery depletion.

A third lens is consistency across consoles, which reduces relearning as you switch systems. Standardize a small set of behaviors such as integer scaling for pixel art systems, a common shader family for 8 bit and 16 bit consoles, and matching hotkeys for save and load. For example, using the same combo for save across GB, GBC, and SNES cores means you never pause to recall controls. The tradeoff appears when one core lacks a feature or interprets a setting differently, creating exceptions that you must document. Keep a short note in your device or a card wallet listing three to five anchors. This minimizes cognitive overhead and shortens navigation time across diverse libraries.

Frequently asked questions

Where do I change global settings versus per game options?

Global settings live in the main system menu, while per game options are inside the in-game pause or core menu. Change global defaults first, then adjust core or per game overrides when a console or title needs exceptions.

How do I safely exit a game without corrupting saves?

Use the in-game menu to save, exit back to the game list or system menu, then choose safe shutdown. Avoid hard power cuts. If autosave on exit exists, still perform a manual save before leaving the game.

What is the fastest way to adjust brightness and volume?

Use the assigned quick shortcuts or overlay controls during gameplay. These actions are designed for frequent changes. If shortcuts do not respond, verify the hotkey configuration in your system or frontend settings.

Should I use integer scaling or full screen for retro systems?

Integer scaling keeps pixel art crisp with clean lines, but adds borders. Full screen fills the display and may introduce shimmering. Choose integer for visual accuracy and switch per game when the border is distracting.

When should I use sleep instead of shutting down?

Use sleep for short breaks when you will return soon, and choose safe shutdown for longer pauses or bag storage. Sleep is faster but carries a small risk if the battery drains unexpectedly during the pause.
