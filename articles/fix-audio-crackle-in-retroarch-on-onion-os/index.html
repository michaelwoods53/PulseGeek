Fix Audio Crackle in RetroArch on Onion OS

By Sarah Carter • Published February 5, 2026

Audio crackle in RetroArch on Onion OS usually points to timing drift between the CPU, audio driver, and emulation core. This guide targets a clean fix by adjusting safe parameters and validating results before locking them in. We assume a stock Onion OS install, RetroArch accessible through the frontend, and SD card access for backups. You will tune latency, sync, and driver choices in small steps to avoid side effects like stutter or input lag. When a setting improves audio, we verify across two different games and a music track so changes generalize. If uncertainty appears, we roll back quickly with backups and check logs to avoid chasing noise.

Key takeaways

  • Start with backups, then change one RetroArch audio setting at once.
  • Prefer consistent sync and modest latency over lowest theoretical delay.
  • Verify improvements using a looping track and two distinct cores.
  • Use logs to spot underruns before overclocking or risky tweaks.
  • Keep per-core overrides when one system needs different audio timing.

Plan the work

Start with scope and safety so progress stays visible and reversible. Define the symptom as brief crackle, continuous hiss, or pops during loading, because each points to different timing issues. For example, short crackle during heavy scenes often means buffer underruns, while constant hiss suggests driver or rate mismatch. Create a plain backup of /roms/BIOS/retroarch.cfg and the config/ directory to allow quick rollbacks. The tradeoff is time spent organizing before tweaking, yet these checkpoints prevent false wins that return later. Write a short baseline: game title, core, device state, and a 30 second observation. Baselines make tiny improvements real, and they help you avoid escalating to overclocking before simpler fixes.

Choose a test track that exposes artifacts predictably. Menu music with sustained tones or an early stage with steady drums works better than chaotic scenes. A stable motif reveals crackle when buffers underrun or when sample rates drift from core output. For instance, a Genesis core running a steady arpeggio will highlight pops if audio latency is too low. The risk is overfitting to one game, so add another system with different timing, like SNES or GBA, for cross-checks. This two-core habit catches driver mismatches sooner and avoids making a setting that helps one emulator harm another.

Decide which settings to prioritize and in what order. A reliable path is driver selection, then latency, then sync features, then resampling or output rates. Driver controls the pipeline, latency sizes the buffer, and sync features determine how audio and video stay aligned. Starting with the driver reduces downstream guesswork because many bugs originate in low level APIs. The tradeoff is that driver changes can shift input responsiveness slightly, so validate control feel alongside audio. Keep a change log with the exact menu path or retroarch.cfg keys and values, noting whether the tweak was global or per-core, so future adjustments remain surgical.

Prepare environment

Enable logging so you can catch underruns and timing hints instead of guessing. In RetroArch, turn on Settings → Logging → Log Level to INFO, then reproduce the crackle to capture messages during playback. Onion OS stores logs where you can read them from the SD card after a test session, making off-device review easy. The upside is faster root cause detection; the limitation is that not every core reports underruns consistently. As a fallback, listen for crackles aligned with frame dips, which often means the audio buffer ran dry. Pair logs with a short video recording so you can correlate sound artifacts with on-screen events later.

Stabilize the SD card and power path to avoid false audio artifacts. A worn or slow microSD can starve assets and increase CPU load, amplifying crackle during heavy scenes. Re-seat the card, run a filesystem check, and avoid mixed speed content folders. Keep the battery comfortably charged and avoid thermal strain during tests. Execute steps

Begin with driver sanity, because the output API shapes timing and compatibility. In RetroArch, open Settings → Drivers → Audio and test the default choice against an alternative available on your build. Some devices expose only a single option, while others allow switching. If an alternate driver reduces pops during your baseline track, keep it and continue. Remember that drivers can influence input feel slightly, so recheck a tight control moment. If your device only offers one driver, proceed to latency. For further driver stability and core choices that influence crashes or thermals, a separate guide covers clean configs, logging, and thermal tuning in detail to stabilize tricky builds without overreaching.

Next, adjust latency conservatively. Set Settings → Audio → Audio Latency to a modest value like 64 ms, then test for one minute. If crackle persists, raise in small steps until artifacts stop, usually within a practical range for handhelds. Dropping too low often sounds great until the scene gets busy, then pops return. If higher latency eliminates crackle but input feels sluggish, you can partially offset that later by enabling a mild rate control or video sync. Record each value in your log so you can compare net results. When different cores diverge, keep a per-core override so a twitchy system does not force lag everywhere.

Finally, tune sync and rates to cement stability. Enable Audio Sync and turn on Audio Rate Control with a conservative pitch tolerance. This lets the emulator nudge timing to match the audio clock, preventing slow drift that ends as crackle. If you hear warble or see jitter, reduce tolerance or disable secondary syncs like Hard GPU Sync for the audio test. When output rate mismatches the core’s native rate, set Audio Output Rate to a standard like 48000 Hz and retest. Avoid large resampler quality changes until basic stability is verified, since heavier resampling can eat CPU and reintroduce underruns on demanding scenes.

Validate results

Assess changes with a repeatable loop and at least two cores. Re-run your baseline track for one minute and note any residual crackle, then try a second emulator with different timing characteristics. For example, test a SNES menu loop after verifying a Genesis tune. If both stay clean, your change generalizes. If only one improves, keep a per-core override and resume testing. The tradeoff is extra time spent listening, but it avoids false success that returns mid-game. Check inputs by executing a short tap dance in a tight platformer to ensure latency remains acceptable. Validation is what turns guesswork into a stable configuration.

Use logs to corroborate what you hear. If crackle vanished but INFO lines still report underruns, your buffer remains marginal and may fail in heavy scenes. In that case, add a small latency increment or relax rate control tolerance slightly and retest. If logs show quiet playback and your ears agree, document the successful values right away. Where logs are sparse, rely on consistent A/B tests and a simple scorecard that flags clean, improved, or no change. The goal is to avoid chasing minor fluctuations and instead confirm durable fixes that survive scene complexity.

Frequently asked questions

Should I lower audio latency as much as possible?

No. Extremely low latency risks buffer underruns and audible pops during busy scenes. Use the lowest value that stays clean across a full minute of playback and two different cores. Prioritize consistent audio over marginal input gains.

Does enabling audio sync add input lag?

A small amount is possible, but moderate sync and gentle rate control usually stabilize timing without noticeable delay. If controls feel sluggish after enabling sync, step latency down slightly or relax rate control tolerance and retest.

Which output rate is safest for handhelds?

48000 Hz is a common, stable choice that pairs well with many cores. If your logs show underruns at this rate, increase latency first. Only explore alternate rates after core stability is verified and other causes are ruled out.

When should I use per-core overrides?

Use them when one emulator needs different timing to stay clean while others work with global settings. Save the override after confirming it fixes crackle without breaking input feel. Keep notes so updates remain reproducible.
