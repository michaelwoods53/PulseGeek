Artwork Thumbnails Not Appearing on Onion OS? Fixes

By Sarah Carter • Published January 5, 2026

When artwork and thumbnails do not appear on Onion OS, the root cause is usually mismatched names, incorrect platform choices, or a stale cache. This guide walks through practical fixes that restore thumbnails with minimal risk and clear checkpoints. You will map ROM filenames to the expected database format, pick the right system during scraping, and rebuild only the pieces that need attention to avoid lengthy rescans. Assumptions are simple: you have read and write access to the SD card, you can navigate Onion OS menus, and you can run basic desktop tasks if needed. The workflow emphasizes reversible steps and quick validation so you can confirm progress after each change without guessing. By the end, thumbnails should render consistently and stay visible after reboots.

Key takeaways

  • Thumbnails depend on correct ROM names and matching platform databases.
  • Rebuild caches only after naming and platform checks pass locally.
  • Validate a small sample before applying changes to the full library.
  • Keep artwork in one location to reduce duplication and confusion.
  • Create a backup before deleting or regenerating thumbnail folders.

Plan the work

Start by framing the problem precisely, because thumbnails fail for different reasons that need different fixes. If names do not match the database, a scraper cannot attach images even when the files exist. If the wrong platform is selected, hashes and names route to a different index and nothing shows. Decide on a small pilot set of 10 to 20 ROMs from one system to test hypotheses quickly. This sampling helps you isolate whether naming conventions or platform choices drive the failure. A narrow test also prevents you from accidentally overwriting a working cache elsewhere. Define a success checkpoint for the pilot, such as five verified images appearing in the system carousel, before scaling to the entire library.

Next, document the current locations of ROMs and images, because scattered assets amplify confusion during debugging. Some setups use a RetroArch thumbnails directory while others keep artwork alongside ROMs. Mixing both often produces partial matches that are hard to reason about. Create a note with the absolute path for ROMs and the folder where artwork is supposed to live for this system. Record the scraper or tool you used last time. This information reduces backtracking later and avoids deleting the wrong directories. The main tradeoff is time spent up front, but these notes prevent risky bulk operations on the SD card without a clear map of what exists today.

Set explicit guardrails for edits so you can revert if a step misfires. Create a timestamped backup of the artwork and any playlist metadata before changes. Keep pilot changes limited to the test ROM set until you confirm improvement. Decide the order of operations to reduce side effects: validate names first, then confirm platform mapping, and lastly rebuild caches. That sequence keeps your manipulations surgical and avoids rescanning failures caused by the same underlying mismatches. The limitation is that some front ends resolve artwork differently across themes, so testing with your current theme is important. Still, most issues trace back to naming or platform alignment, which this plan addresses directly.

Prepare environment

Create a safe workspace that supports repeatable checks, because fragile SD cards and long rescans increase risk. Back up the artwork folders and playlists to your desktop with a timestamped name. Verify the backup by opening a few images to ensure they are readable. Prepare a text editor for quick renames and a checksum utility if you plan to verify file integrity. On your handheld, ensure there is at least several hundred megabytes free to allow cache rebuilds to complete. The tradeoff is time spent copying files, but you avoid data loss and can roll back instantly if a change does not help. This foundation makes every fix less stressful and more reversible.

Gather references that help you pick the right platform and naming style for your target system. Many scrapers rely on community databases where the platform choice determines which naming conventions are matched. If you scraped a PlayStation game under a general console category, for example, the cover may never resolve. Note the exact platform you intend to use for the pilot and stick to it. If you change platforms midstream, caches can contain mixed entries that appear to flicker. The limitation is that databases evolve and sometimes rename entries, so you may need to rescrape a subset to align with updates while keeping your core approach consistent.

Prepare a simple method to compare ROM filenames with their expected names so you can spot mismatches. You can do this by exporting a list of ROM basenames and then comparing against names shown by the scraper’s preview. If your desktop supports command line tools, generating a list lets you automate detection later. Alternatively, work within Onion OS menus to preview match candidates before committing. The benefit of a scripted list is speed when dealing with large libraries, though it requires comfort with a terminal. If you prefer menus, limit changes to small batches and record each run to avoid duplicate attempts that clutter the cache and confuse results.

Execute steps

Start by aligning ROM filenames to the database because thumbnails attach when names match the index for the selected platform. Remove extra tags that confuse scrapers such as region markers, multi disk notes, or scene release metadata. Keep a clean basename with the title and version when applicable. Test a handful of renamed files with the preview feature of your scraper to confirm positive matches. If the preview consistently shows the intended artwork, proceed with the rest of the pilot set. The tradeoff is losing some descriptive tags in filenames, but you can preserve details in a metadata file rather than the filename. Clean names reliably connect to consistent artwork across tools.

Next, verify platform mapping for each pilot ROM, since wrong system selection prevents thumbnails from attaching at all. Ensure your scraper targets the console or handheld the ROM actually belongs to. When in doubt, search the database by title inside the scraper and observe where it resides. If a game appears under two systems, prefer the version that matches your emulator core. This avoids conflicts where a different system uses an incompatible naming scheme. The limitation is that multi region or compilation releases sometimes differ slightly by database, but choosing the emulator matched platform usually yields the most stable artwork behavior in Onion OS interfaces.

Finally, rebuild or refresh thumbnails only after names and platforms are aligned, because regenerating too early bakes errors into the cache. Delete only the specific system’s thumbnail cache to minimize collateral damage. Then run the scraper or refresh function for the pilot set and wait for completion before checking the menu. If images appear, roll the procedure to the larger library in batches. If not, revert from backup and adjust the previous steps. For large libraries, a quick command line check can surface missing artwork candidates before you rescrape. The idea is to compare ROM basenames with image basenames in your chosen artwork folder. When a ROM has no corresponding image file, it likely needs renaming or rescraping. Create two lists and diff them to highlight gaps. This method avoids blindly rebuilding caches and focuses effort where it matters. The tradeoff is that it assumes artwork uses the same base naming as ROMs, which is common in curated setups but not universal. Use this as a heuristic, then confirm with your scraper preview to prevent false positives.

Validate results

Confirm success on the device first, because desktop previews do not guarantee Onion OS behavior. Open the target system menu and scroll through the pilot games to check that images render instantly and persist after navigating away. Reboot the device once to ensure thumbnails survive a fresh start. If everything holds, note the time between scrolling and image display, since long delays can indicate a slow card or oversized art. The tradeoff is spending a few extra minutes testing, but this avoids rolling out changes that look fine on a workstation and then disappear on the handheld due to caching differences or theme expectations in the live environment.

Record where the artwork files ended up so you can repeat the process consistently. If your build uses a dedicated thumbnails path, confirm that new images landed there, not scattered across multiple folders. Keeping art in one place reduces duplication and prevents ghost entries after updates. Capture a screenshot of the menu showing a working thumbnail for your notes. These artifacts help you compare future behavior if an update modifies directory structures. The drawback is documentation overhead, but strong notes transform troubleshooting from guesswork into a quick checklist that scales well when you address additional systems later.

For added certainty, test a second system with three to five ROMs using the same steps. Cross system validation reveals whether your process relies on a quirk of one database or theme. If the second test succeeds, proceed to scale. If it fails, review platform mapping differences and naming rules that may vary by system. To avoid confusion, keep each system’s artwork cache and ROM folder clearly labeled. Troubleshoot and optimize

If thumbnails still fail after alignment, inspect ROM regions and multi disc conventions. Some databases treat regional variants as distinct entries, which breaks matches when a file carries a different region tag than the expected title. Standardize on one region for the pilot and use the same choice in the scraper. For multi disc sets, use a naming pattern that your scraper recognizes as one game. If the tool does not consolidate discs, attach art to the first disc only. The limitation is that not all scrapers handle compilations uniformly, so you may need to accept a single cover for a multi part release to ensure consistent display in Onion OS menus.

When images flicker or vanish after updates, stale caches or playlist inconsistencies are common culprits. Rebuild the specific system’s cache after verifying that playlist entries reference the same clean basenames used by your images. Avoid deleting global caches unless necessary. If crashes or broader instability accompany artwork issues, stabilize the platform first using a calm, end to end workflow like the clear checklists for crashes and updates. Once the base is reliable, revisit the artwork steps. This order prevents confusing symptoms caused by unrelated faults, such as storage errors or partial updates during previous maintenance.

If you discover that ROMs are detected but art remains missing for specific platforms, focus on content hygiene. Ensuring BIOS and ROM structure is clean helps scanners work predictably and avoids false negatives. Frequently asked questions

Why do some games show thumbnails while others stay blank?

Mixed results usually come from naming mismatches or a wrong platform choice for specific titles. Standardize filenames and confirm the correct system in your scraper, then rebuild only that system’s cache and check again.

Do I need to rescrape the entire library to fix missing art?

No. Work on a small pilot set first. If that succeeds, scale in batches. Rebuild only the affected system’s cache to avoid unnecessary rescans and keep working artwork intact elsewhere.

Why does artwork disappear after a reboot?

This points to a stale cache or inconsistent playlist entries. Verify that playlist names match your cleaned basenames, then rebuild the specific system’s thumbnails so references align and survive restarts.

Can I keep region tags in filenames?

You can, but tags often break database matches. If you keep them, ensure your scraper recognizes the convention. Safer is using a clean title for matching and storing details in a separate metadata file.

Where should artwork files live for best results?

Use a single, consistent location per system. Centralizing thumbnails reduces duplicates and makes cache rebuilds predictable. Mixing sidecar images and thumbnail folders often causes partial results and confusion.
