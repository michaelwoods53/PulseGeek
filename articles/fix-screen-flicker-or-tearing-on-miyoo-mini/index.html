Fix Screen Flicker or Tearing on Miyoo Mini

By Jeremy Crawford • Published March 9, 2026

Screen flicker or tearing on the Miyoo Mini usually traces to timing mismatches between rendering and refresh, unstable SD reads, or aggressive shaders. This how to aims to restore smooth video by combining safe RetroArch options, clean power, and file integrity checks. The guide assumes Onion OS or stock firmware with RetroArch available, a computer for SD maintenance, and basic familiarity with copying files. You will plan the fix, prepare your environment, execute precise changes, and validate results with simple tests that reveal tearing lines under motion. If a step does not change symptoms, you will learn what it rules out so your next move remains efficient.

Key takeaways

  • Start by aligning video sync and drivers before chasing rare hardware faults.
  • Confirm SD health to eliminate stutter and flicker from bad reads.
  • Validate with scrolling tests and capture repeatable before and after evidence.
  • Keep one change at a time to isolate the true cause of tearing.
  • Roll back shaders and filters that raise latency or introduce artifacts.

Plan the work

Begin by narrowing the symptom, because “flicker” and “tearing” indicate different timing failures. Tearing presents as a horizontal seam that shifts during motion, whereas flicker looks like periodic brightness or rapid frame instability. Test with a fast scrolling title screen or a menu that moves continuously, then note whether the line stays fixed or travels. This distinction guides options such as vertical sync for tearing or shader reduction for flicker. Also document which cores show issues and whether the problem appears only after waking from sleep. The why matters, because targeted fixes avoid side effects like input lag or reduced battery life caused by heavy synchronization settings that are unnecessary for certain cores.

Set boundaries that keep saves and firmware safe before you touch settings. Make a current backup of your ROMs and save files to your computer, then snapshot any .cfg you plan to adjust. That preserves a clear rollback path if an option unexpectedly worsens ghosting or desyncs audio. Safe boundaries also include avoiding concurrent changes to multiple axes like power, core settings, and shaders in one pass. Changing a single variable per test cycle is slower, but it isolates cause and effect. The tradeoff is more iterations, yet the process prevents chasing false positives that come from paired tweaks masking each other.

Plan test cases you will repeat after each change so comparisons are honest. Pick two or three scenarios that stress timing, such as a 2D platformer with parallax, a racing game with high-speed signage, and a menu with smooth cursor animations. Run each for the same duration and observe in similar lighting to reduce perceived flicker caused by environment. If you depend on RetroArch overlays, temporarily disable them during tests, because extra UI layers can interfere with performance. The goal is consistent evaluation that confirms a fix rather than a temporary improvement caused by luck or a warmer device.

Prepare environment

Preparation reduces time spent undoing changes. Back up the SD card to your computer, then verify the copy. Next, run a non destructive file system check using your OS to catch directory errors that cause stutter and perceived flicker. If you suspect media faults, test with an SD verification tool that reads the full capacity end to end. Intermittent reads can deliver missed frames that mimic tearing under load. Finally, ensure the device has sufficient charge or keep a stable USB power source attached. Low battery voltage may introduce oscillating brightness that is easy to misdiagnose as a software problem.

Stage your configuration access so changes are reversible. Locate RetroArch retroarch.cfg on the SD, and note any core overrides in config/ paths. Onion OS users should confirm whether global settings or per core overrides are active to avoid thinking a change worked when a hidden override later resurrects the issue. Prepare a clean slate by disabling shaders and overlays temporarily. The tradeoff is losing cosmetic effects during testing, but you gain clarity about timing stability before reintroducing optional features that may add latency.

Gather reference materials for setup ordering and safe defaults. If you are new to this handheld, review a start-to-finish setup guide covering safe settings and SD prep so your base configuration is predictable. Predictability matters because flicker fixes sometimes depend on firmware build and RetroArch version. When documentation is uncertain for a specific core driver, prefer conservative options that favor sync and audio lock, then test performance margins later. That sequencing avoids overshooting with aggressive drivers that increase stress on the small display controller.

Execute steps

Start with global RetroArch video options that fix tearing without invasive changes. Enabling vertical sync and hard sync can eliminate the traveling seam that appears during scrolling. On the Miyoo Mini, these settings are accessible in RetroArch menus and via the configuration file. When you edit the config directly, you avoid accidental overrides from layered menus and can commit exact lines. Place these changes in the main retroarch.cfg first, then only use per core overrides if a single emulator requires exceptions. This approach keeps behavior consistent and reduces the chance of conflicting instructions that reintroduce flicker later.

If you prefer precise control, modify the configuration file to set vsync, hard sync, and a stable video driver. The example below shows typical lines that remove tearing and reduce jitter while keeping compatibility high. Expect smoother vertical scrolling and fewer horizontal seams immediately after restarting RetroArch. If a core stutters with hard sync enabled, test with it disabled while leaving vsync on. That toggling helps you balance latency and stability one variable at a time across cores with different timing characteristics.

After applying timing fixes, check power and media influences. Reboot the device to clear any wake related flicker, then test with and without USB power connected. If artifacts disappear on wall power, you may be seeing voltage related brightness oscillation rather than frame tearing. Next, validate the SD with sequential reads by launching a large ROM and watching for hiccups during loads. Replace the SD if integrity tools report write or read mismatches, since media errors can create stutter patterns that resemble periodic flicker during demanding scenes.

Validate results

Validation must be consistent so small improvements are not misread as solved. Recreate your planned tests in the same order and lighting, watching for a moving seam during vertical or horizontal scroll. If vsync eliminated the seam but introduced slight input lag, evaluate whether the tradeoff is acceptable for game types you play most. Platformers and shmups may feel different with hard sync on, so try brief sessions. Objective confirmation includes watching lines on backgrounds with repeating patterns where tearing is easier to see compared to complex scenes that hide subtle artifacts.

Use simple metrics to track progress without special tools. Count how many seconds until a flicker cycle repeats on a static menu or how often a particular seam appears during a looped demo. A reduction in frequency indicates stabilization even if not fully solved. If behavior changes after sleep, test cold starts and wake cycles separately. Sleep related irregularities often point to driver state, which suggests keeping sync enabled but avoiding additional filters after waking. Consistent observations guide whether to tune per core overrides or continue with global settings.

Document what changed so you can revert or reapply quickly. Keep a text note with the exact lines you edited and any per core exceptions. If a core still tears with vsync on, try removing hard sync just for that emulator while leaving global vsync intact. That approach preserves the broad fix while isolating sensitive cores. When the display is stable across most titles but a few remain problematic, consider lighter shaders only after confirming no timing regressions. The why is simple. Cosmetic layers can mask symptoms and make future troubleshooting harder.

Troubleshoot and optimize

When tearing persists after vsync, suspect driver or core specifics. Some cores behave better with fewer buffering stages, so try reducing the swap chain image count or disabling hard sync on that core. If flicker appears primarily after long sleep, power cycle to reset the display controller and retest. Persistent brightness pulsing that correlates with battery level points to power rather than rendering. In that case, verify charging hardware and consider a battery calibration session, performed carefully, to realign reporting. Optimizing means distinguishing graphics timing from electrical behavior so fixes target the true constraint.

Consider SD replacement when integrity tests report mismatches. Migrating to a known good card with correct formatting often resolves micro stutters that mimic flicker under scrolling loads. If migration is necessary, clone with a verified tool and preserve your save directories, then retest before layering shaders back. For owners seeing other symptoms alongside display issues, like freezes during boot, consult recovery oriented guidance to ensure the base system is sound before advanced tuning. Stability at the storage and OS level prevents chasing video settings for a storage fault.

If visual instability returns only after crashes or corruption, repair the software state first. Rebuilding configuration files or reinstalling the OS can clear conflicts introduced by partial writes. Always preserve save data before destructive steps. Once the platform is healthy, reapply minimal timing changes and confirm stability. Only then add optional enhancers in small increments. This progressive approach creates a durable baseline, and future tweaks become safer because you know how to backtrack. The time you spend establishing a clean core pays off when troubleshooting becomes faster and more predictable.

Frequently asked questions

Is screen tearing a hardware problem on the Miyoo Mini?

Usually no. Tearing typically comes from frames not aligning with refresh. Enabling vertical sync and adjusting timing options in RetroArch fixes it for most users without hardware repair.

Why does flicker appear only after waking from sleep?

Sleep can leave the display driver in a less stable state. Power cycling or restarting RetroArch refreshes timing. If it recurs, prefer global vsync and avoid changing shaders immediately after wake.

Do shaders cause flicker or just lower performance?

Shaders increase processing and can amplify timing jitter, which may look like flicker. Disable them while diagnosing. After fixing tearing, reintroduce light shaders carefully and retest for stability.

Should I change the video driver if vsync fails?

Try stable defaults first. If a specific core still tears, test reducing hard sync or swap images. Switching drivers is a later step and should be done per core after confirming regressions.

Could the SD card cause visual stutter?

Yes. Corrupt or slow reads create micro stutters that resemble flicker during motion. Run integrity checks and replace the card if errors appear, then re test with the same scenes.
