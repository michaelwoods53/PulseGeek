Fungus Unity Workflow for Dialogue and Quests

By Lauren Mitchell • Published December 29, 2025

We will build a dependable path that links Fungus and Unity so dialogue choices can start and resolve quests. You will plan IDs and variables, configure Flowcharts, and connect events to gameplay without brittle glue code. The instructions assume a recent Unity LTS release, the free Fungus package from the Asset Store, and a clean sample project. If you already prototype branching dialogue, this guide gives you a workflow you can ship with. Each step emphasizes testable state, readable names, and traceable outcomes to help designers and programmers collaborate smoothly across edits.

Key takeaways

  • Define dialogue and quest variables once and reuse consistent IDs everywhere.
  • Drive gameplay with Fungus messages and Flowchart variables, not hardcoded calls.
  • Validate branches using seed saves and logs tied to quest state changes.
  • Prefer deterministic triggers over timers to ensure repeatable Unity behavior.
  • Version Flowcharts with mergeable exports and stable variable naming in Unity.

Plan the work

Start with a narrow slice that proves your workflow, such as one dialogue that unlocks a starter quest with two outcomes. Constraining scope keeps variables and Flowcharts legible and exposes gaps early. Write a brief contract for each state variable with allowed values and when they change. For example, a quest state might allow NotStarted, Accepted, Completed, and Failed. List who can change each state and why that change is safe. This clarity prevents hidden transitions that confuse debugging. The tradeoff is initial overhead, yet the payoff is faster iteration because both writers and engineers speak the same state language.

Create a naming scheme before assets multiply, since Fungus Flowcharts, Blocks, and Variables will be referenced by scripts and other tools. Use a prefix like Q_GatherHerbs for quest data and D_VillagerIntro for dialogue. Keep names stable after localization begins, because renaming breaks spreadsheets and audio mappings. Decide on a single ID column in your narrative sheets and mirror that in Flowchart variables. A small constraint is that names may feel longer, but the benefit is that logs and automated tests can locate states without guesswork, even after large refactors.

Choose where the boundary between Fungus and core gameplay will sit, because this decides which side owns logic. A practical split lets Fungus own presentation and decision flow while Unity components own inventory, combat, and save data. Pass messages across the boundary using Fungus messages or variable reads and writes. This separation keeps narrative blocks readable to designers and leaves systemic rules in code where performance and unit tests are stronger. The drawback is two places to coordinate, but a clear interface, such as predefined messages like QuestAccepted or QuestCompleted, reduces friction and regression risk.

Prepare environment

Install Fungus from the Unity Asset Store and verify example scenes open without console errors. Consistency starts with a single Unity LTS version across the team, since version drift complicates serialization and scene merges. Create a dedicated folder layout under Assets/Narrative for Flowcharts, portraits, and audio, and another under Assets/Systems for quest scripts. This structure reduces accidental cross-dependencies. Add a baseline Flowchart in a sandbox scene and ensure it runs in Play Mode. The tradeoff is up-front organization effort, but the reward is faster onboarding and fewer merge collisions when multiple writers and engineers collaborate.

Configure project settings that affect dialogue and quests determinism. Set fixed timestep to a value that keeps message timing consistent and avoid relying on frame-based timing in Blocks. Enable development build logging flags in your local editor for richer runtime traces. Add a Script Define Symbol like NARRATIVE_DEV to gate verbose logs without shipping them. Deterministic settings help QA reproduce issues precisely, though they may increase log volume. Counter that by grouping logs under a tag like [Narrative] and ensuring each log includes the stable IDs you planned earlier.

Establish a minimal variable schema in a starter Flowchart to prove read and write paths. Add a Boolean QuestAccepted, a String CurrentObjective, and an Integer Reputation. These will be manipulated by both Blocks and C# scripts. Keep initial defaults simple, such as false, "TalkToNPC", and zero. Next, create placeholder Blocks named Intro, OfferQuest, Accept, Decline, and Complete. Even if they only log messages at first, this scaffolding shows the full handshake. The compromise is temporary duplication, but the visibility helps stakeholders verify the workflow before you write rich dialogue content or hook up inventory systems.

Execute steps

Translate your plan into a working sequence that proves dialogue choices control quests. Start by building the conversation flow inside a Flowchart using Say and Menu commands to present options. Bind Menu choices to Blocks that set QuestAccepted and update CurrentObjective. This keeps the designer in control of branching without touching code. Next, attach a small MonoBehaviour that listens for Fungus messages and talks to gameplay systems. That bridge should set or query Flowchart variables rather than hardcoding dialogue. The advantage is modularity and clear tests, though it needs careful naming to avoid mismatches between Blocks and script fields.

Wire up outcomes that modify Unity systems through a single integration point. For example, on Acceptance, send a message that a quest started, then have the quest manager register tasks and subscribe to updates. Use Flowchart.ExecuteBlock for re-entry into narrative when objectives complete. This approach keeps both sides loosely coupled, since narrative signals intent and gameplay executes details such as checkpoints and inventory adjustments. The limitation is that overusing messages can hide ordering bugs, so prefer immediate ExecuteBlock for sequences that must happen together and reserve BroadcastFungusMessage for decoupled notifications.

Add lightweight telemetry to confirm branches behave as expected under different paths. Before changing a variable, log the previous value, the incoming event, and the next value. Use a consistent prefix and include the stable IDs from planning. Consider a simple ScriptableObject for shared constants such as message names, which reduces typos across scenes. Telemetry cannot replace proper tests, but it shortens time to root cause when QA reports a misfire. Keep the volume controlled by gating under NARRATIVE_DEV and by sampling less critical chatter. If you notice repeated noisy logs, elevate them to assertions with actionable messages.

Validate results

Treat validation as a first class step, not a final checkbox. Build seed saves that place the player before key decisions so QA can replay branches quickly. For dialogue, assert that a choice sets the expected Flowchart variables and only those. Then assert that the quest manager receives exactly one notification and registers objectives. A repeatable test path might read QuestAccepted then check CurrentObjective equals the planned ID. The tradeoff is time spent making seeds, but they expose regression quickly when rewriting scenes or renaming variables. Additionally, keep a lightweight checklist for each branch covering state, notifications, and UI feedback.

Instrument logs to confirm order of operations around handoffs. For example, verify that Accept fires variable writes before broadcasting messages to prevent listeners from reading stale state. When timing matters, prefer synchronous ExecuteBlock calls over messages triggered by delayed events. Capture a small timeline by timestamping logs and including the stable IDs. This is especially useful when two Flowcharts interact and both may respond to the same message. The cost is slightly noisier logs, but the payoff is faster triage when a branch appears to jump or stall between dialogue and quest handoffs.

Automate basic checks so your workflow scales. Add Play Mode tests that load a sandbox scene, execute the Intro Block, accept the quest, and assert variable and message outcomes. Store constants for block and variable names in one file to avoid string drift across tests. Consider nightly runs that execute sampled branches to catch regressions during localization or content spikes. Automation cannot judge narrative quality, but it protects wiring reliability. If tests are flaky, isolate frame based dependencies and shift them to deterministic calls, or buffer events until variables confirm the expected state has been committed in the Flowchart.

Troubleshoot and optimize

When dialogue appears to ignore a choice, first check variable scope and casing in the Flowchart, then confirm the Block name matches exactly in ExecuteBlock calls. A typical pitfall is a renamed Block left referenced in code or Menu options that bypass variable assignments. Reproduce with a seed save and step through logs to pinpoint the first divergence. If multiple Flowcharts listen to the same message, confirm only the intended one acts on it by guarding with a variable precondition. The constraint is extra checks, but they prevent duplicate quest creation or missed completions that are expensive to unwind mid production.

For performance hiccups during heavy conversations, profile UI updates and image loads rather than Fungus logic first. Large portrait atlases and audio clips can stall rendering when swapped rapidly between lines. Preload critical assets in a lightweight scene bootstrap and reuse them during sessions. If memory pressure rises, lower texture import settings for portraits or switch to addressable assets for streaming. Fungus itself is generally light, so you will often find wins in UI and content packing. The tradeoff may be slightly longer initial load, yet smoother per line transitions enhance perceived responsiveness during branching exchanges.

Optimize maintainability by extracting repeated dialogue patterns into reusable Blocks called by parameters or context variables. For example, a standard Accept flow can set shared variables, play a tone, and return to the caller. This ensures consistent quest transitions across scenes and reduces bugs from copy paste. Keep a changelog for message names and variable contracts so dependent systems update deliberately. Finally, schedule periodic audits where writers and engineers review Flowcharts against gameplay needs. The overhead is real, but alignment meetings save rework when scope expands and help retire obsolete messages safely without silent breakage.

Quick start checklist

  1. Create a sandbox scene: add a Flowchart and placeholder Blocks for key beats.
  2. Define variables early: add QuestAccepted, CurrentObjective, and Reputation with defaults.
  3. Build choice menus: wire Menu options to Blocks that set variables predictably.
  4. Add a bridge script: execute Blocks and broadcast messages from one integration point.
  5. Tag narrative logs: include stable IDs and timestamps for each state transition.
  6. Prepare seed saves: position near choices to replay branches during validation.

Frequently asked questions

Should I use BroadcastFungusMessage or ExecuteBlock for quest starts?

Use ExecuteBlock when the next narrative step must occur immediately in order. Use BroadcastFungusMessage for decoupled notifications where multiple listeners may respond independently.

How do I prevent duplicate quest activation from multiple Flowcharts?

Guard activation with a shared Flowchart variable and a quest manager check. Ensure only one listener changes state after verifying the variable is not already set.

Why do my Menu choices not update variables?

Confirm the option links to a Block that sets variables before branching. Check for typos in variable names and ensure the Flowchart is the correct instance at runtime.

What causes timing bugs between variable writes and listeners?

Listeners can read stale state if messages fire before writes complete. Write variables first, then signal, or use synchronous Block execution for tightly ordered sequences.
