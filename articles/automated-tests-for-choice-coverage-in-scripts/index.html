Automated Tests for Choice Coverage in Scripts

By Lauren Mitchell • Published December 26, 2025

Our goal is to design automated tests that measure choice coverage in narrative scripts and reveal unreachable nodes before they become production ghosts. We assume scripts are authored in tools like Ink or Twine and exported as JSON or plain text, with test execution running in Python or a comparable harness. The approach applies whether your engine is Unity or Unreal, because the traversal logic lives outside the runtime. By the end, you will craft repeatable tests, define stable seeds for randomness, and emit reports that inform design and QA. Expect to balance thorough exploration with execution time, and to handle variable gates carefully so tests do not lie about coverage.

Key takeaways

  • Model narrative as a graph and traverse choices deterministically.
  • Track visited edges and nodes to quantify choice coverage.
  • Seed randomness and stub variables to prevent flaky outcomes.
  • Emit unreachable node lists with path hints for quick fixes.
  • Integrate coverage gates into CI to stop regressions early.

Plan the work

Start with a clear coverage definition so your automated tests measure the right thing and guide fixes instead of creating noise. For branching narratives, distinguish node coverage from choice coverage, where nodes are dialogue or state points and choices are directed edges between them. A practical rule is to consider a path exercised when the transition fires under specific variable conditions. For example, selecting Accept Mission while having reputation above a threshold should register a unique edge. The tradeoff is explosion of combinations, so pick a baseline like edge coverage with bounded variable partitions. This keeps reports actionable while avoiding exponential runtimes that stall CI and frustrate the team.

Agree on input formats and IDs so the graph can be parsed and traced reliably across exports and refactors. Use stable identifiers for passages, knots, or nodes, and store choice metadata including conditions and side effects. For tools that export JSON, define a consistent schema capturing source node, target node, label, and guards. If the export is text based, establish conventions for markers that can be parsed into a graph. The reason is simple: tests cannot assert coverage if edges are ambiguous or anonymous. The main edge case is localization changes shifting text but not structure, so your parser must key off IDs rather than lines.

Decide where tests run and who owns their outcomes, because responsibility shapes design. If tests run in CI on every commit, keep them deterministic and under a few minutes using a fixed random seed and limited partitions. If they run nightly, allow deeper exploration and additional validation like variable invariant checks. Assign ownership to narrative design or tools engineering, but include QA in triage so unreachable nodes do not accumulate. The limitation to accept is that automatic traversal cannot judge tone or pacing, so its focus should be structural integrity and coverage quantification. That keeps human reviews on craft while machines guard the logic graph.

Prepare environment

Set up a repeatable environment that loads exports and executes traversals without surprises. Use a language with strong testing libraries like Python with pytest or JavaScript with Jest, since fixtures and parametrization simplify variable partitions. Store exports in version control, and add a pre-commit or CI step that regenerates the JSON graph from your authoring tool to avoid stale inputs. To manage randomness, use a seeded generator so Monte Carlo paths can be reproduced. A realistic example is seeding Python’s random with a specific integer and recording it in the report. The tradeoff is less exploration per run, but determinism is essential for debugging a failing path and correlating it with design changes.

Create a small adapter layer between the export and your traversal so changes in tools do not break tests. The adapter maps raw data to a normalized structure with nodes, choices, conditions, and effects. For example, convert Ink’s divert and conditional lines to edges with predicate functions, while Twine’s passage links become edges annotated with tags. Keep predicates pure so they depend only on a provided variable context, not ambient state. This isolation makes stubbing easy during tests. The primary limitation is that some side effects are complex, like inventory changes or timers, so represent them as simple state transitions in this layer rather than engine-specific calls.

Decide what variable partitions are meaningful and encode them as fixtures. Instead of enumerating every combination, choose representative buckets like low reputation, neutral, and high, or flags on and off for critical story gates. Parametrize tests across these fixtures to multiply coverage without exploding cases. A rule of thumb is three to five partitions per variable across a handful of key variables. The tradeoff is that certain rare interactions may not be exercised, but reports will still reveal unreachable edges across chosen partitions. When that happens, designers can add a targeted test with a custom fixture to investigate the suspicious branch without bloating the standard suite.

Execute steps

Implement traversal that visits nodes and records choice coverage while respecting guards. A depth first search works for most graphs if you track visited edges per variable fixture to prevent infinite loops and still measure distinct outcomes. Represent each edge as a tuple of source, label, target, and predicate that inspects the current state. When the predicate passes, push the target with updated state and mark the edge visited. Include a depth limit or cycle breaker keyed by sequence and state hash to avoid runaway recursion. The tradeoff is potentially missing long-running timers or probabilistic events, but it keeps execution bounded and the report focused on structural reachability rather than simulation length.

After traversal, compute metrics that matter to designers and QA, not just raw counts. Report percent of edges visited overall, list unreachable edges with their source nodes, and include minimal path hints for reproducibility. For Monte Carlo variants, log the seed and number of samples per start node. Emit output as both human readable text and machine readable JSON so dashboards or CI gates can consume it. Surface a threshold like fail if edge coverage drops below an agreed baseline. The limitation is that percent values can mask critical misses, so always include a sorted list of never visited edges to direct immediate fixes without digging into the raw graph.

Validate results

Treat the first run as a calibration step to verify parsing and traversal assumptions before you trust coverage numbers. Start with a small script you understand well, then compare the list of unreachable edges against your expectations. If an obviously reachable choice appears unreachable, inspect the predicate and the fixture values to catch mismatches between exported conditions and your adapter logic. A helpful practice is to print a shortest path hint for each unreachable edge by reverse searching from targets to sources. The tradeoff is extra compute, but on small graphs it reveals mistaken guards quickly and builds confidence that the harness reflects the writer’s intent rather than a parser error.

Translate raw metrics into actionable insights using clear thresholds and stable baselines. For example, establish that edge coverage must not drop relative to the previous milestone by more than a small tolerance, and separately enforce that zero new unreachable edges may be introduced. This dual rule prevents superficial percentage games while spotlighting specific misses. Share the report in your team’s channel and archive JSON outputs so dashboards can chart trends. Remember that a high percentage can hide critical misses when the script grows, so sort unreachable items by narrative priority or entry frequency to ensure scarce QA time goes to high impact paths first.

When interpreting reports, consider how they relate to broader narrative design patterns like branch depth and pacing, because long chains can distort traversal time and mask poor coverage near the end. Using that perspective, decide whether to isolate late branches into separate fixtures or apply targeted tests for deep paths. The limitation is that structural coverage does not judge rhythm or emotion, so it should be paired with human read-throughs for final quality.

Troubleshoot and optimize

Handle unreachable edges by grouping root causes so fixes flow to the right owners. Common causes include broken IDs after export changes, predicates referencing variables not in fixtures, and genuine design dead ends. Reproduce one case using the recorded seed and print the guard conditions alongside fixture values to expose mismatches. When IDs changed, update the adapter or enforce stable naming conventions. For missing variables, extend fixtures or provide default stubs with safe values. True dead ends should be logged as design tasks with suggested entry paths. The limitation is time pressure during sprints, so triage by narrative impact and unblock high frequency entry points before deep optional branches.

Stabilize flaky paths by isolating randomness and time based effects that make results inconsistent across runs. Replace time checks with deterministic ticks in the adapter, and convert random outcomes into seeded draws recorded in the report for replay. For probabilistic branches, run a bounded number of samples per fixture and record confidence ranges so results are comparable week to week. The tradeoff is that rare edges might remain unvisited in a small sample, so create a targeted test for those cases instead of inflating all runs. This keeps CI fast while ensuring sensitive paths still get explicit attention when they matter.

As suites grow, optimize execution by pruning redundant paths and caching subgraph results. Memoize coverage from identical state signatures at the same node so DFS does not revisit equivalent contexts repeatedly. Split large narratives by entry points, then schedule them in parallel on CI workers to keep wall time short. Archive JSON reports and diff them to spot regressions quickly without reprocessing every artifact. Looking ahead

Expand beyond baseline edge coverage by layering semantic checks that confirm state invariants, like reputation never dropping below zero or quest flags staying mutually exclusive. Add format validators that ensure localization context accompanies each line so downstream audio and translation workflows stay aligned. Consider publishing a dashboard that shows coverage by episode or quest, updated on each export. The tradeoff is maintenance, so keep the core traversal simple and isolate extensions as optional plugins. Over time, these guardrails become an unobtrusive soundtrack under your narrative, letting designers experiment while the harness listens for dissonance and nudges the flow back toward reliable, player centered experiences.

Quick start checklist

  1. Export a small script: generate JSON with stable node and choice IDs.

Frequently asked questions

What is the difference between node and choice coverage?

Node coverage counts visited dialogue or state points, while choice coverage counts the directed transitions between nodes. Choice coverage better reveals unreachable options behind conditions.

How do I avoid infinite loops during traversal?

Track visited edges keyed by node, label, destination, and predicate, and add a depth limit or state signature to break cycles cleanly without missing distinct guarded paths.

How many variable combinations should I test?

Use partitions instead of exhaustive combinations. Pick three to five representative buckets for important variables and add targeted cases for rare interactions that reports flag as suspicious.

What causes flaky coverage results?

Unseeded randomness and time based guards often cause instability. Seed the random generator, replace real time with ticks, and record seeds to reproduce failing paths consistently.

Should coverage thresholds be absolute or relative?

Use both. Enforce a minimum baseline to prevent regressions and separately fail builds that introduce new unreachable edges, which focuses fixes on the latest changes.
