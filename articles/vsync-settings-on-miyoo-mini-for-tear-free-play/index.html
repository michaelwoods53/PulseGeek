VSync Settings on Miyoo Mini for Tear-Free Play

By Austin Price • Published January 15, 2026

Our goal is to eliminate tearing with careful VSync settings on Miyoo Mini while preserving audio sync and low input delay. You need a working RetroArch build on the device and basic familiarity with configuration screens or the config file. We assume stock clocks and a 60 hertz display, since tear-free timing depends on matching frame and refresh cadence. This guide prioritizes reversible changes, so you can test one adjustment at a time and back out safely if it causes jitter. If your setup already includes custom shaders or overlays, be prepared to disable them temporarily, because they can amplify timing variance and hide the effect of sync changes during testing.

Key takeaways

  • Enable VSync first to align frames with the display refresh.
  • Match core frame rate to refresh to prevent paced jitter.
  • Keep audio sync on to avoid drift under steady VSync.
  • Use FPS limit only when the core output is unstable.
  • Disable overlays if frame timing still shows tearing.

Plan the work

Start by defining what success looks like, because a tear-free result requires more than toggling VSync. The target is steady 60 frames per second with no torn seams and audio that neither crackles nor drifts over multi-minute play. As a concrete example, a NES core rendering at 60 should present each frame on the next vertical retrace without queuing spikes. The tradeoff is latency, since strict synchronization can add a small delay. That is acceptable if it remains consistent and does not introduce stutter. The plan anchors to safe toggles first, then moves to rate matching, and only later to optional features that may trim latency at the cost of stability.

Map constraints before touching settings, because mismatched timing between core, frontend, and display creates the common tearing patterns. On Miyoo Mini, assume a 60 hertz panel and avoid speculative refresh overrides unless you can verify them. For instance, setting a video refresh target that slightly disagrees with the panel can force periodic dropped or duplicate frames. A practical rule is to leave refresh detection automatic unless your core’s native rate is well known and stable. The limitation is that some classic systems render at rates near but not exactly 60. In those cases, prioritize smoothness and audio lock over perfect numeric matching, then validate for drifting artifacts.

Choose a small change budget per test pass to keep cause and effect visible. Plan an order like: enable VSync, verify, then set an FPS limiter only if the core fluctuates. A scenario worth anticipating is shader load causing frame time spikes, which look like stutter even with VSync on. The plan should include a temporary clean visual path with shaders and overlays disabled to isolate timing. Accept that a few cores may require different per-core settings, so record changes per content type. This methodical approach prevents chasing phantom issues created by multiple simultaneous tweaks that mask the true source of tearing.

Prepare environment

Establish a clean baseline, because environmental noise often mimics tearing. Disable shaders, bezels, and heavy overlays, then set a simple integer scale if possible to avoid fractional scaling costs. A concrete pattern to watch is microstutter triggered by overlay alpha blending, which can cause intermittent frame time spikes. The tradeoff is aesthetics, since the game may look plain during testing, but a neutral baseline makes it easier to spot real sync improvements. Also ensure your SD card performs reliably, because streaming hiccups from storage can masquerade as video issues. This does not mean upgrading hardware, only eliminating avoidable I/O stalls while you measure timing behavior under VSync.

Lock down audio before video changes to prevent two moving targets. Turn on audio sync and pick a moderate buffer that avoids crackle under load. For example, a midrange buffer reduces underruns but keeps latency predictable, which helps you judge video smoothness. The edge case is content that outputs slightly off from 60 hertz, where audio or video must compromise. In that case, keep audio stable and let the video limiter follow the core’s cadence. This reduces the audible artifacts that players perceive more strongly than tiny visual cadence shifts. You can revise audio tuning later after video pacing is proven stable.

When you plan to edit configuration files, capture a snapshot first so reversions are immediate. RetroArch stores options in a config file that you can back up, then adjust with a text editor. The benefit is deterministic reproduction across sessions and per-core overrides when needed. The limitation is that some platform builds may not expose every option. In those cases, apply the equivalent toggles from the UI path and save overrides. This redundancy ensures you can verify whether the effective state matches the intended settings by comparing file values across reboots and content loads, which is vital when diagnosing intermittent tearing.

Execute steps

Apply changes in a fixed order to keep feedback clear and measurable. First, confirm the display target is 60 hertz and enable VSync so frames present on retrace. Then observe a simple scrolling scene for 60 to 120 seconds, which is long enough to expose periodic cadence faults. The tradeoff here is that VSync can mask minor jitter by delaying presentation, so you should still monitor frame time overlays for spikes. If spikes persist, temporarily disable overlays and shaders, then retest. This sequence removes common confounders before you touch rate controls or frame limiters, which keeps the intervention path short and reversible.

Only add an FPS limiter when the core produces a stable but slightly high or low rate relative to the display. For example, if a core drifts around 59.8 to 60.2, a limit at 60 can reduce queuing jitter without overconstraining the pipeline. The edge case is a core with native 50 hertz content, where a 60 hertz limit causes frequent duplicates. In that scenario, prefer letting VSync present evenly while audio sync manages drift. Why this works is simple: you are aligning intent, not forcing equality, and allowing the audio lock to handle small discrepancies while the video thread keeps presentation steady.

If tearing persists despite VSync, suspect a mismatch introduced by performance overlays or non-integer scaling. Try integer scaling and disable heavy post-processing to remove GPU load spikes. A practical test is to switch to a simple core and ROM known for light load and smooth scrolling, then repeat your checks. If that fixes tearing, reintroduce visual features gradually. The limitation is that some combinations remain borderline, where even small cost pushes frame time above budget. In those cases, retain the essential features and accept a minimalistic overlay set so VSync can maintain consistent pacing under all scenes.

Validate results

Validate with multiple lenses to avoid false positives. Use the built-in FPS display to confirm a steady number, then watch a long horizontal pan for any diagonal tearing artifacts. A good scenario is a level with uniform parallax where seams would be obvious. The tradeoff is that a constant FPS does not guarantee even frame pacing, so pair the test with subjective motion checks. Why this works is that both metrics complement each other: numbers expose drift while eyes reveal cadence irregularities. Extend tests to at least two different cores to ensure your settings generalize and are not narrowly tuned to one emulator’s behavior.

Include audio in your verification loop, because VSync interacts with timing queues. Listen for crackle while the FPS overlay holds steady. If you hear pops, the audio buffer may be too small or timing skew too aggressive. Increase the buffer slightly and retest the same scene. The limitation here is that larger buffers add latency, which you can accept temporarily during testing. Once stutter and tearing are gone, you can walk the buffer down to the smallest value that stays clean. This gradual approach prevents mistaking audio underruns for video faults and ensures the final settings are durable across content.

Document your test pass and outcomes, including which visual features you disabled and later restored. A concise log like date, core, content, VSync state, FPS limiter, and audio buffer helps you spot patterns across attempts. The benefit is faster rollback when a later change reintroduces tearing. You can compare logs and revert just the outlier. The limitation is time spent on notes, but it pays back when settings interact in unexpected ways. Troubleshoot and optimize

When you still see tearing with VSync enabled, treat overlays and filters as prime suspects. Disable bezels, HUD elements, and shader passes, then verify again. A concrete fix is to remove alpha-heavy or scaling-intensive effects that push frame time over budget intermittently. The tradeoff is cosmetic loss, but the gain is reliable pacing. If removal yields improvement, restore features one at a time to find the threshold. This isolates the combination that undermines synchronization and lets you keep essentials without sacrificing smoothness. When a feature is borderline, prefer a lighter preset that costs fewer milliseconds per frame.

Address timing mismatches between core output and display by tuning limits rather than forcing equality. If a PAL title renders at 50 hertz, do not clamp it to 60 with an aggressive limiter. Let VSync present consistently and keep audio sync stable, accepting occasional duplicates where necessary. For content near 60, a precise 60 limiter can guard against drift that causes periodic stutter. The limitation is that some cores expose different timing models, so settings may live in per-core overrides. Keep the global baseline simple, then set exceptions only where needed, which reduces the risk of reintroducing tearing in other titles.

If audio crackle appears after visual stability improves, focus on buffer size and resampler settings. Increase the buffer incrementally until pops disappear, then evaluate input feel to ensure latency stays acceptable. A typical improvement is audible cleanliness without any change in frame rate. If the buffer must grow large, revisit visual load to free headroom for audio, because both share time budgets. Frequently asked questions

Should I use adaptive VSync on Miyoo Mini?

If available, adaptive VSync can reduce judder when frame rate dips, but it may reintroduce tearing during drops. Start with standard VSync. Use adaptive only if you see brief hitching that normal VSync cannot smooth.

Why do I still see tearing with VSync on?

Overlays, heavy shaders, or non-integer scaling can cause intermittent frame time spikes that defeat synchronization. Disable extras, try integer scaling, and retest in a long scrolling scene to isolate the real cause.

Do I need a 60 FPS limiter with VSync?

Only add a limiter when the core rate hovers around 60 and causes queuing jitter. For native 50 hertz content, avoid a 60 cap. Let VSync present consistently while audio sync handles minor cadence differences.

Will audio sync increase input latency?

Audio sync with a moderate buffer adds some latency, but it prevents pops and drift. After video is stable, reduce the buffer stepwise until crackle appears, then back off to the smallest clean value.

Is threaded video required for smooth VSync?

Threaded video often helps maintain consistent pacing under load, but behavior varies by build. Enable it if single-threaded rendering stutters. If it adds jitter, revert and reduce visual load to keep frames on budget.
