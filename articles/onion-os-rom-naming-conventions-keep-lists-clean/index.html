Onion OS ROM Naming Conventions: Keep Lists Clean

By Jordan Kelly • Published February 9, 2026

Clean ROM naming is the backbone of reliable libraries in Onion OS and avoids mismatched entries during scraping. This article defines practical naming conventions, shows when to keep region tags, and explains multi disc handling with m3u playlists. You will learn decision rules that balance accuracy with simplicity, so your list remains readable on handheld screens and scrapers match the intended games. We will also note exceptions, like hacks or translations, and how to label them without breaking search or metadata. By the end, you can set a standard once, then scale it safely across systems without constant renames.

Key takeaways

  • Use clear ROM naming with region and revision only when needed.
  • Adopt m3u playlists for multi disc sets to prevent duplicates.
  • Keep tags predictable so scrapers align art and metadata reliably.
  • Prefer one canonical version per game to reduce list clutter.
  • Document edge cases like hacks and translations in short tags.

Concepts and definitions

Good naming in Onion OS anchors three outcomes: clean menus, consistent scraping, and predictable saves. A practical filename pattern keeps the base title, then adds short tags for region in brackets and version info in parentheses, for example Sonic the Hedgehog [USA] (Rev 1). This structure helps scrapers match databases that track region and revision, yet it stays short enough for small screens. The tradeoff is verbosity when many variants exist, which can overwhelm a handheld list. A common rule of thumb is pick one default per title and archive the rest off device, which preserves fidelity while maintaining a quick browse experience.

Region tags exist to distinguish database entries that share a title but differ in content or language, where [USA], [EUR], [JPN], or [World] are typical. Use [World] only when the dump truly matches that designation, and prefer the region you play most when duplicates appear. For language clarity, a compact tag like [En] or [En+Fr] can supplement region when releases vary widely. Over tagging creates clutter and may mislead scrapers if the tag is non standard or reordered. Keeping a predictable tag position and format stabilizes matching across multiple scraping passes and reduces manual fixes later.

Version and revision markers signal bug fixes, revisions, or enhancements, commonly formatted like (Rev 1), (v1.1), or (Beta). Keep only one canonical version in the visible list unless gameplay differences are meaningful. For example, if v1.1 fixes crashes on a core, prefer that as the primary entry and move the older revision to an off device archive. Hacks, translations, and widescreen patches warrant short, specific tags such as (FanTL En) or (Widescreen). However, such builds sometimes break achievements or expected save behavior, so isolate them in separate subfolders when testing. This keeps your main list stable and avoids confusing duplicate names.

Frameworks and decision lenses

A practical decision path starts by selecting a primary release per game based on stability, language, and availability, then documenting a fallback. First choose the region you play most, second choose the latest stable revision, and third apply concise language tags only when ambiguous. This hierarchy prevents runaway tags and reduces visual noise during browsing. Edge cases emerge when a translation patch is superior to official text or when achievements only work on a specific hash. In those cases, prefer the functional variant, then add a short tag that explains the choice. The reasoning keeps future audits simpler and repeatable.

Naming also intersects with folder layout, since folders determine where scrapers look and how platforms render. Before refining file names, confirm your directories match the expected system layout so games appear correctly. If your system structure is uncertain, reference a clear walkthrough that explains where each platform expects its content and why that mapping matters for scanning speed and visibility. When base paths are wrong, even perfect names will not populate lists or metadata. Fixing layout first prevents misdiagnosing problems as naming issues and saves time during large library refreshes.

Multi disc games deserve a dedicated pattern that avoids duplicate entries and streamlines disc switching. The simplest approach stores the discs in a subfolder and references them through a single m3u playlist file named after the game, for example Final Fantasy IX.m3u. Each line points to a disc file with a clear Disc number tag, keeping only the m3u visible in your menu. The tradeoff is an extra playlist file to maintain, but you gain cleaner lists and seamless swapping in compatible cores. When discs are named inconsistently, scrapers may show mismatched art, so normalize disc labels before building playlists.

Looking ahead

The most durable naming standards evolve alongside your library and tools, not in isolation. Begin by documenting a short pattern with two or three examples, then apply it to a small platform first. After scanning, check if scrapers consistently match art and whether your list remains understandable without excessive scrolling. If misalignments occur, adjust tag order or shorten language markers, then re scan to validate improvements. Iterating on a single system limits risk before scaling across consoles. This approach keeps entropy low as you grow and ensures every change has a clear outcome tied to browse speed and metadata accuracy.

When expanding to more complex sets, like disc heavy libraries or mixed regions, build a few m3u playlists and verify that cores switch discs reliably and retain save integrity. Some cores read playlists differently, so test on one or two representative titles before batching. If a core fails to parse your playlist, revisit filename spacing and disc number patterns, as tiny mismatches can break parsing. Only after a stable pattern emerges should you generate playlists in bulk. This cautious cadence protects existing progress, reduces duplicate entries, and prevents later renaming that can orphan saves or artwork.

Finally, maintain a small reference checklist for common exceptions so you do not reinvent rules midstream. Include brief notes on hacks, translations, and regional alternates you keep visible, and record why each remains in the list. A living note helps you resolve future conflicts systematically rather than by memory. If you also manage folders, a structured overview can prevent confusion between BIOS placements, ROM locations, and saves, which often masquerade as naming problems. For those aligning layout and names together, a tidy structure guide can serve as the next checkpoint before large updates or scrapes.

Frequently asked questions

Do I need region tags if I only keep one version?

No. If you keep a single version for a game and your scraper matches reliably, you can omit region tags. Add them only when duplicates exist or when the database distinguishes variants that affect matching or language.

What is the best way to handle multi disc games?

Use a single m3u file with disc paths listed inside and keep individual disc images in a subfolder. Show only the m3u in your game list to avoid duplicates and enable seamless disc switching in compatible cores.

Should I keep betas, prototypes, or hacks visible?

Only if they serve a purpose, such as testing, unique content, or community interest. Tag them clearly and consider separating them into a dedicated subfolder so they do not crowd the main playable list.

How short should language tags be?

Keep language tags compact, such as [En] or [En+Fr]. Use them only when the region does not imply language or when multiple language builds exist and affect readability or scraping in your library.

Can I rely on archives like zip or 7z for names?

You can, but ensure the internal filename follows your standard. Some cores read inside archives while others prefer extracted files. Consistent internal names prevent mismatches during scraping and playlist creation.
