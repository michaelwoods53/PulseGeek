Backup and Restore Onion OS SD Cards

By Jordan Kelly • Published February 16, 2026

Backing up and restoring Onion OS SD cards protects saves, configurations, and hours of setup. This guide targets one goal: create a clean backup image and restore it safely when needed. We assume you can access a Windows, macOS, or Linux computer with an SD reader and enough free space for a full card image. You will learn when to image the entire device versus copying files, how to verify with checksums, and how to validate the restored card. Along the way, we will preview fixes for common write errors so you can recover quickly if something misbehaves.

Key takeaways

  • Prefer full device images to capture boot data and hidden partitions.
  • Verify every image with a checksum before storage or restore.
  • Validate the restored SD by mounting and spot testing content.
  • Keep backups versioned with dates and card capacity in filenames.
  • Use write blockers or read-only toggles to avoid accidental changes.

Plan the work

Start by deciding whether you need a full device image or just folder copies, because the choice defines reliability and time. A device image captures the boot sector, partition table, and Onion OS data in one file, which preserves structure when restoring to the same or larger card. Folder copies are faster for small updates like BIOS packs or themes, but they miss hidden data that the bootloader expects. If you are safeguarding saves and system settings for recovery after experiments, choose a full image. If you are syncing art or ROM folders between cards, targeted copies can be enough, with the tradeoff that boot issues will not be fixable from those copies.

Estimate resources before you start, because bottlenecks often appear as space or time shortages. A 128 GB SD card imaged byte for byte needs roughly that size available on your computer, plus room for checksums and optional compression. Plan an uninterrupted window matching your slowest link, often the SD reader speed, which can range widely across laptops and USB adapters. For risk control, schedule backups after a clean shutdown of the handheld to avoid filesystem inconsistencies. The small delay prevents issues that inode repairs might only partially fix later, especially on ext-like metadata layers inside the image.

Create a naming and versioning scheme that you will actually keep, because retrieval matters as much as creation. Use a pattern like YYYY-MM-DD-device-capacity-onionos-version.img to indicate date, card size, and OS snapshot. This prevents confusion when you juggle multiple cards or test beta firmware. Include a short note when saves are time critical, such as after finishing a long RPG. The tradeoff is a few extra seconds per backup, but you reduce restore risk by choosing the exact point-in-time image you trust. For multi-card setups, add an identifier tied to the handheld to avoid cross-restoring by mistake.

Prepare environment

Select tools that match your operating system and comfort level, because reliability beats novelty with disk imaging. On Windows, GUI utilities can image whole devices with a few clicks, while PowerShell can hash files for verification. On macOS, Disk Utility identifies the correct disk, and Terminal commands create images predictably. On Linux, command-line imaging is standard and easy to script. Whichever route you choose, confirm you can run checksums like SHA256 or BLAKE3 to prove integrity. Favor tools with clear device selection screens or explicit disk paths, since mis-targeting is the fastest way to overwrite the wrong drive.

Before plugging in the SD card, set the adapter’s write-protect switch to the locked position if available, because it reduces accidental writes during reads. Some readers ignore the switch, so treat it as a soft safeguard, not a guarantee. Close any file managers that might auto-index the SD, and disable background sync tools that could open files. On macOS, confirm Spotlight is not actively scanning the card. Eject and remount if the OS flags inconsistencies, then let a filesystem check complete. These small steps lower the chances of read errors or corrupted snapshots caused by concurrent access or unflushed buffers.

Document the disk identifier you will image, because precision avoids data loss. On macOS, run diskutil list to find the removable device like /dev/disk3 and prefer the raw path /dev/rdisk3 for speed. On Linux, lsblk shows devices such as /dev/sdb with partition names like sdb1. On Windows, use Disk Management to note the physical device number and confirm capacity matches your SD. Cross-check by temporarily ejecting the card and seeing which identifier disappears. This extra verification step costs seconds but prevents the severe failure of targeting your system drive accidentally, which is a common and costly mistake.

Execute steps

Create the image with a clean, read-focused command to capture the entire device, because full images are most portable across same-size or larger cards. On Linux and macOS, dd is dependable when used with read-only source paths and appropriate block sizes. Add a progress indicator using tools like pv if installed, or use built-in status flags for visibility. Save the image to a fast local disk to reduce read stalls. After the copy, compute a checksum and store it in a .txt file alongside the image. This lets you confirm integrity later and detect silent corruption introduced by flaky USB readers or transfers.

When restoring, write the image back to a same-size or larger SD card, because shrinking an image onto a smaller card often fails due to capacity variance between manufacturers. Use dd with the image as input and the SD device as output, again confirming the path before pressing Enter. If the target card is larger, you can expand the data partition afterward using standard partition tools so the extra space is not wasted. Always verify the write by computing a checksum directly on the device block or by reimaging the card to a temporary file and comparing hashes, which trades time for confidence.

After the restore completes, safely eject, reinsert the card, and mount both the boot and data partitions to check structure, because early detection saves boot attempts on the handheld. Confirm expected folders exist and spot test a few files that matter most to you, like recent saves or BIOS sets. If anything is missing, revisit the original image and logs to see whether read errors occurred during backup. Consider keeping a second image created with a different reader to mitigate flaky hardware. This redundancy adds storage cost but reduces the likelihood of a bad backup escaping notice until you urgently need it.

Validate results

Validation starts with reproducible hashing, because a checksum is the simplest proof that your image is unchanged. Run SHA256 or BLAKE3 on the .img file immediately after creation and again before restoring. The digests must match the saved value in your .sha256 or .blake3 file. If they differ, discard the suspect image and redo the backup with a different card reader. This discipline prevents the subtle error where a corrupted backup looks fine until a restore silently fails. For long-term storage, keep the image and hash together in a read-only archive to avoid accidental edits or partial transfers.

Functional validation matters just as much as hashes, because a byte-perfect copy can still fail to boot if your target hardware behaves differently. After writing the image, insert the SD card into the handheld and power on to reach the Onion OS menu. Browse a few systems and open a small game to confirm filesystem responsiveness. Load a recent save to ensure memory card and save directories are intact. If your device supports LED or log indicators during startup, watch for pauses that imply filesystem checks. This practical test surfaces compatibility issues that a purely offline verification cannot reveal.

Finish by confirming capacity and alignment so future updates apply cleanly. On a larger target card, expand the data partition using built-in utilities until the filesystem fills the card. Then create a fresh image and checksum from this expanded state to serve as your new baseline. This forward snapshot reduces friction when you add artwork or ROMs later. Note that expanding partitions carries a small risk of interruption, so perform it on stable power and avoid moving the reader. If the restore is mission critical, pause expansion until after you have at least one boot-verified baseline image stored safely.

Troubleshoot and optimize

When dd reports input or output errors, treat them as a signal to isolate hardware first, because failing readers and cables are frequent culprits. Swap the USB adapter and cable, and try a different port away from hubs. Re-run the image with conv=noerror,sync to pad unreadable sectors so the process completes, then check the log for the error count. If errors persist, copy critical folders separately as a fallback. You can also attempt a second image at a lower block size like bs=1m, which may tolerate flaky sectors better. These steps trade speed for resilience while you preserve as much data as possible.

For write-speed stalls or timeouts, compress the imaging path by writing to a fast internal SSD and avoiding network drives, because latency exacerbates timeouts. On macOS, prefer the raw device path /dev/rdiskN for better throughput. On Linux, consider dcfldd for progress and hashing during write if you want integrated checks. To reduce future risk, maintain two alternating images and rotate them after major changes, because redundancy counters single-bad-file scenarios. Store copies on separate physical devices and optionally a cloud vault with client-side encryption. Periodically run a quick read test of the SD card using a non-destructive tool to catch early media failure.   1. Confirm capacity: ensure your computer has free space equal to the SD size.
  2. Lock the reader: set the adapter to read-only before imaging the card.
  3. Find the device: list disks and note the exact removable path.
  4. Create the image: run a full-device read into a dated .img file.
  5. Hash and store: compute SHA256 and archive both files together.
  6. Restore with care: write only to equal or larger SD cards.

A light routine after major tweaks keeps the image fresh and saves time during restores, because fewer changes mean smaller differentials and faster validation. Frequently asked questions

Can I restore a larger image to a smaller SD card?

Usually no. Even same labeled capacities vary slightly, and dd will fail. Create a fresh image from a smaller card or shrink the filesystem and partitions first with care if your tools support safe reduction.

Is copying files enough instead of imaging the device?

Copying folders protects ROMs and artwork but misses boot sectors and hidden structures. For recovery from full failures, a whole device image is safer. Use folder copies only for quick sync of non-boot data.

How often should I back up my Onion OS SD card?

Back up after meaningful changes like firmware updates, new BIOS sets, or major save progress. A monthly cadence works for most users. Keep at least two alternating images to avoid a single point of failure.

What if verification hashes do not match later?

Assume corruption. Discard the mismatched image, reimage the SD with a different reader or cable, and compute a new checksum. Do not restore from a file that fails verification.

Do I need to expand partitions after restoring to a bigger card?

Yes if you want to use all available space. After writing the image, use partition tools to extend the data partition to fill the card, then create a new baseline image and checksum.
