DuckStation Multi-Emulator Save Compatibility List

By Eric Morgan • Published February 7, 2026

Here is a practical multi emulator save compatibility list focused on DuckStation. Each item explains what works, what needs conversion, and where naming or region rules matter. I selected emulators and formats that most users encounter when moving saves, then validated workflows by mechanism rather than unreliable anecdotes. The goal is predictable steps that protect progress and allow reversible changes. Expect concrete examples and tradeoffs for memory card files and save states, with guidance to verify results before retiring old setups.

Key takeaways

  • Memory card saves travel better than save states between emulators.
  • Back up originals before any rename or conversion to avoid loss.
  • Region mismatches break saves even when file extensions appear correct.
  • DuckStation accepts several formats after proper naming and size checks.
  • Use a rollback workflow to test imports without risking corruption.

1) DuckStation core formats and what portability means

DuckStation reads standard PlayStation memory card images that conform to expected sizes and directory structures, which drives most compatibility outcomes. A typical example is a 128 KB card image with valid save directory entries that another emulator also understands under a different extension. When the data layout is consistent, portability is often a matter of naming and placement rather than conversion. The advantage is speed and low risk, since no block data changes. The tradeoff is that some emulators write metadata or headers that DuckStation ignores or rejects, so a file may look right but still fail. Portability always improves when you verify card size, make a backup copy, and test on a single title before migrating everything.

To ground this, consider a card created in another emulator that uses a different extension yet stores the same 128 KB structure. Renaming to the preferred extension and placing it in DuckStation’s memory card folder often loads saves without further edits. This works because the underlying save directory records are unchanged, and DuckStation only needs consistent geometry and filenames. The benefit is a quick win for shared formats. The drawback appears with emulators that prepend headers or use container formats. In those cases, direct renames fail, and you must extract or convert the content. Always confirm by booting a game known to have a save on that card and checking the save browser.

Section highlights

  • Portability hinges on matching card size and internal directory layout.
  • Test with one known save before migrating an entire card image.

2) ePSXe and .mcr imports, when simple renames work

ePSXe uses .mcr files that are often raw 128 KB images, which DuckStation can usually read if you name and place them correctly. A concrete scenario is taking ePSXe’s memcards/card1.mcr, renaming it to a descriptive filename, and assigning it as Memory Card A in DuckStation’s settings. If the file is truly a raw image, saves appear in-game immediately. This route is simple and reversible. The risk is that some users mix region saves or use split per game cards without realizing it, so entries seem missing. Another risk is accidental format drift if tools wrote headers to the file. If a rename does not work, stop and convert using a known-safe method rather than repeated experiments that might corrupt directory entries.

When renaming alone fails, use a conservative conversion workflow that preserves a backup and validates the outcome. One dependable pattern is to extract the individual save blocks from the .mcr into a fresh 128 KB card, then reimport into DuckStation. That isolates any header or alignment issues from ePSXe and recreates a consistent directory table. The upside is high success rates with stubborn cards. The downside is time spent on extraction and the small chance of losing icon or title metadata if a tool strips nonessential fields. If you are new to this path, lean on a walkthrough and confirm with a low stakes title before touching a long RPG playthrough. Section highlights

  • ePSXe .mcr often loads after a careful rename and placement.
  • Use extraction to a clean 128 KB card when renames fail.

3) RetroArch PS1 core saves and name mapping

RetroArch’s PS1 cores typically store memory cards in a global save directory where naming patterns and playlist mapping control which card a game uses. A practical example is assigning per game memory cards named after content or playlist entries, then telling DuckStation to point to the same files or to a synchronized copy. This reduces confusion and keeps saves portable across cores. The benefit is tidy organization: one card per title reduces cross game conflicts and makes migration auditable. The tradeoff is overhead, because you must keep names and folders aligned between applications. If you misspell a filename or keep different folder structures, games create new cards that appear empty, which looks like lost progress until you fix the mapping.

To normalize names at scale, a short, cautious batch rename can align extensions without touching underlying data. The goal is to keep a backup and only transform files that match the raw 128 KB size. This approach avoids conversion and eases imports into DuckStation while staying reversible. The drawback is platform differences in tools and the risk of renaming a non raw container, so add a size check and always keep originals.

Section highlights

  • Keep per game cards and align names across RetroArch and DuckStation.
  • Normalize extensions with a size check and preserve a backup copy.

4) Mednafen cross usage and when conversion is required

Mednafen can use raw memory card images but sometimes expects specific naming or structure that trips up direct sharing with DuckStation. A common case is a raw 128 KB file that opens in both, yet appears empty in one emulator due to region or slot mapping differences. If you verify the size and still see nothing, extracting save blocks into a fresh card image offers a safer bridge. The benefit is that most save data can move without redoing progress. The tradeoff is that containerized or headered Mednafen formats will not travel by renaming. You must strip non raw wrappers before DuckStation accepts the file. That extra step adds time but prevents subtle directory corruption that otherwise shows up weeks later.

Another consideration is region metadata. Many games encode region in save headers, meaning a PAL save will not load on a NTSC build even if the card file itself is valid. The symptom is a save icon that looks right but refuses to load, or no save shown at all. The quick check is to confirm that the game disc region matches the save’s origin. If they differ, use the same region disc or recreate progress to the save point in the correct region. Converters rarely rewrite region identifiers reliably, so manual fixes are error prone. Section highlights

  • Mednafen shares raw cards but rejects headered or container formats.
  • Match game region to save origin before assuming a broken import.

5) PS3 and PSP virtual cards, VME or VMP, and extraction

PS3 and PSP use virtual memory card containers like VME or VMP that bundle PS1 save blocks with metadata, which DuckStation does not directly treat as a raw card. A realistic path is to extract the PS1 save from the container into a standard 128 KB image, then assign it in DuckStation. The draw is that you can preserve long running saves from original hardware or official platforms. The downside is that tool support varies, and incorrect extraction can drop icons or title strings. Always keep the original VME or VMP file untouched and run a verification load in DuckStation before cleaning up. If you are juggling multiple games per container, log which slot you extracted so you can reassemble changes if you return to the console.

Because containers are not raw images, renaming is not a valid shortcut. Attempting to rename a VME to a memory card extension does not make it readable, and repeated attempts risk accidental edits. Instead, follow a predictable workflow that produces a clean card and preserves your original. The upside is clarity and repeatability. The tradeoff is one-time overhead to learn the extraction tool and the discipline to test with a single game first. If you plan to move saves in the other direction later, keep a changelog so you can reconcile differences when reinjecting into the original container. Section highlights

  • Extract PS1 saves from VME or VMP into a standard 128 KB card.
  • Keep original containers untouched and track which slots you moved.

6) PCSX ReARMed to DuckStation, what survives unchanged

PCSX ReARMed often uses raw memory card images that DuckStation can read after straightforward naming and placement, which keeps most saves intact. A representative workflow is copying the card image from PCSX ReARMed’s save directory, confirming it is 128 KB, then assigning it to DuckStation’s Card A for testing with one game. If the size and structure are raw, your save appears and loads. The benefit is quick migration with little risk. The tradeoff is that some builds or frontends wrap cards or expect different default paths, and mixing regions causes false negatives. If your test game fails to find a save, reassess the region, confirm file size, and consider extracting saves into a fresh card to eliminate wrapper issues altogether.

When moving many titles, pace the migration to avoid confusing fresh cards with old images. Move one card, test, then rotate it out only after confirming in-game load and save operations. This incremental pattern catches write permission or path issues early. The upside is a cleaner audit trail, especially when frontends generate default cards silently. The downside is time. You spend extra minutes per title, but you avoid sweeping mistakes that scramble directories. Section highlights

  • Raw 128 KB cards usually import after verifying size and region.
  • Migrate one title at a time to catch path or write issues.

7) Save states are not portable, choose card saves instead

Save states embed emulator specific snapshots of CPU, GPU, and RAM, so they almost never load across different emulators or even different versions. A typical example is a DuckStation save state that another emulator cannot parse, even though both run the same game. The fix is not conversion. Instead, reload the game in DuckStation and create an in game memory card save, which uses the console’s native format and travels across implementations. The advantage is wide compatibility and longer shelf life. The tradeoff is that you must reach a save point again, which takes time in titles without quick saves. Keep save states for temporary safety but treat memory card saves as the canonical archive that survives emulator changes.

There is one nuance worth planning for. If a game supports multiple save slots, write a fresh in game save alongside your old one so you can compare behavior between emulators. Then power cycle and verify that the new save persists and loads after assigning the card in DuckStation. This two slot approach provides a rollback point if something goes wrong later. It costs a few extra minutes now but prevents ambiguous failures. Section highlights

  • Use native memory card saves for long term cross emulator portability.
  • Write a second slot to create a rollback point before migrating.

Frequently asked questions

Why does my save not appear after renaming the file?

Renaming only works for raw 128 KB memory card images. If the file has a header or is a container, DuckStation will not see it. Verify size, confirm region matches the game, and extract or convert into a clean card if needed.

Can I mix saves from different regions on one card?

You can store them, but a game will only load a save that matches its region. A PAL save will not load on a NTSC build. Keep region consistent per title, or maintain separate cards for each region to avoid confusion.

Is it safe to convert .mcr files directly to DuckStation format?

Often yes if the .mcr is a raw 128 KB card. Copy a backup first, then test with one game. If it fails, extract saves into a fresh card rather than forcing repeated conversions that could damage directory entries.

Do I need per game memory cards in DuckStation?

No, but per game cards reduce cross game conflicts and make migrations predictable. They also simplify mapping from RetroArch or other emulators. The tradeoff is slightly more files to manage and name consistently.

Looking ahead

  • Adopt a rollback routine with backups to protect long playthroughs.
  • Confirm disc region matches the save to avoid silent failures.
  • Favor memory card saves over states for durable compatibility.
