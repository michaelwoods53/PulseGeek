Linux Udev Permissions for Controllers in DuckStation

By Joshua Bennett • Published March 8, 2026

Controllers failing to register in DuckStation on Linux usually trace back to udev permissions not granting access to input devices. This how to explains how to choose a udev approach that fits your environment, create a rule, and reload it safely. We assume a standard desktop distribution with systemd and that you have sudo access. If you use Flatpak or non standard packaging, sandboxing can change device visibility, which we will address later. Focus on one change at a time and test after each adjustment so you can pinpoint the exact fix. By the end, your controller should consistently appear in DuckStation and standard input tools.

Key takeaways

  • Prefer uaccess for per user access on logind managed desktops.
  • Use group ownership only when shared multi user access is required.
  • Reload udev and replug devices to apply new permissions cleanly.
  • Validate with evtest or SDL tools before testing inside DuckStation.
  • Flatpak builds may need device permissions or portal adjustments.

Plan the work

The first decision is selecting a permission model that fits your session manager and sharing needs. On most systemd desktops, the uaccess tag grants device access to the active seat, which aligns with single user gaming. For shared labs or multi seat setups, a dedicated group like input or plugdev can offer predictable ownership, although it demands user group membership and careful auditing. Map your constraints before touching rules. For example, if two users hot swap without logging out, uaccess may briefly pass control depending on seat changes. Choosing now avoids rework later. Document the default permissions you observe with ls -l on /dev/input to establish a baseline and confirm which attributes change after your rule.

A clear problem statement guides the sequence of actions, keeps risks visible, and simplifies rollback if results regress. Define the symptom precisely such as DuckStation shows no controllers while evtest lists input but permission is denied. List acceptable outcomes and a fallback. For instance, success may mean non root DuckStation reads inputs with no extra prompts, while failure keeps current behavior without breaking unrelated devices. Set a small time box for each attempt, usually ten minutes per change, to avoid compounding mistakes. This planning step lets you reason about whether a targeted udev rule is sufficient or if packaging and sandbox boundaries are the real bottleneck.

Gather supporting evidence so you can correlate every change with system behavior and avoid guessing. Use journalctl -b for recent kernel input logs and track udev events with udevadm monitor to ensure your rule even triggers. If dmesg shows the controller enumerating as a generic HID while your rule filters by joystick attributes, the match will never apply. Conversely, overbroad matches risk changing unrelated keyboards or mice, which introduces new issues. Capture device properties with udevadm info --attribute-walk so your rule keys on stable identifiers like ID_INPUT_JOYSTICK or USB vendor and product IDs. Precise matches reduce surprises when firmware or kernel versions evolve.

Prepare environment

Preparation starts by confirming basic visibility of the controller and the current permission state. Run lsusb or cat /proc/bus/input/devices to ensure the kernel enumerates your hardware as an input device. Then check ls -l /dev/input for event and js nodes, noting owner, group, and mode. If you already belong to the group owning the device and DuckStation still lacks access, the obstacle may be sandboxing rather than filesystem permissions. Installing evtest and a minimal SDL gamepad tool gives you neutral benchmarks independent of DuckStation. These utilities help isolate if input fails system wide or only within the application runtime.

Next, locate trustworthy attributes for building udev matches so the rule applies only to intended controllers. udevadm info --attribute-walk --name=/dev/input/eventX reveals properties like ID_INPUT_JOYSTICK, ID_VENDOR_ID, and ID_MODEL_ID. A safe rule typically matches SUBSYSTEM "input" and checks ENV values that are set by existing udev helpers. Avoid relying on ephemeral device node numbers that can change across boots or hotplugs. When in doubt, prefer capability flags such as ENV{ID_INPUT_JOYSTICK} "1" to capture any compliant gamepad regardless of vendor. This keeps maintenance low while avoiding accidental matches on keyboards or pointing devices.

Before editing, decide between uaccess and group based ownership, because each approach changes who can open the device node and how seats interact. uaccess grants ACLs to the active graphical session via logind, which is convenient on standard desktops and avoids static MODE changes. Group ownership works on lean servers or non logind systems but requires user group membership and potentially broader access than necessary. The table below summarizes tradeoffs so you can choose confidently. Whichever you select, plan to replug the controller after reloading rules so new ACLs or modes get set.

uaccess tagSingle user desktops with systemd logindDepends on active seat and session state
Group ownershipShared hosts or non logind environmentsRequires user group membership and auditing

Execute steps

Implementation focuses on creating a minimal udev rule that targets joystick class devices, applies your chosen access model, and reloads cleanly. A common pattern matches SUBSYSTEM "input" and ENV ID_INPUT_JOYSTICK "1" so it captures both USB and Bluetooth gamepads through the same pathway. Using TAG "uaccess" delegates per user ACLs to logind, which is safe for a single seat desktop. If you prefer a group, set GROUP "input" and optionally MODE "0660" while ensuring your user belongs to that group. After writing the rule into /etc/udev/rules.d, reload udev and replug devices. This order avoids stale permissions and makes testing deterministic.

It uses ID_INPUT_JOYSTICK to avoid impacting keyboards or mice and relies on uaccess for seat aware permissions. If your desktop does not use logind, swap the tag for a group based approach and add your user to that group. Expect to replug the controller because ACLs are applied during device add events. If you rely on Bluetooth, toggling power or reconnecting the device also retriggers udev processing and applies the new rule.

Validate results

Validation begins outside DuckStation to separate device access from application settings. Run evtest against the correct event node and confirm button presses register without permission errors. If evtest fails with EACCES, your rule did not apply or sandboxing blocked the device. When evtest passes, try a simple SDL gamepad tester to confirm higher level mapping behaves as expected. Only after both tools succeed should you open DuckStation input settings. This staged approach narrows issues quickly and prevents misattributing configuration problems to udev when the real cause is a mapping profile or dead zone configuration.

Inside DuckStation, verify that the controller appears by its expected name and that buttons map without warnings. Try binding a few actions and confirm the emulator persists the layout after a restart. If multiple devices are connected, temporarily unplug extras during testing to prevent conflicts where two nodes expose similar capabilities. Watch for duplicate events that indicate the device is presenting both XInput and HID paths, which can confuse bindings. In those cases, prefer the event node that shows consistent button numbering. Document the working path so you can reapply it if a future update resets preferences.

Finally, watch for platform specific behavior that can mask permission success. For example, Flatpak or sandboxed builds can enumerate the controller but still block reads without granted device interfaces. Likewise, Wayland sessions may defer device handoff during lock screens, briefly hiding inputs until focus returns. If your external tools succeed but DuckStation alone fails, inspect packaging and runtime options next. A system package or AppImage usually sees host devices directly, while sandboxed packages may require additional permissions. Keeping these distinctions in mind helps avoid reopening udev files when the boundary is actually the application container.

Troubleshoot and optimize

If rules reload without effect, confirm matching logic and event timing with udevadm monitor to see if your device hits the rule. A missing ENV property or mismatched subsystem prevents assignment silently. Narrow the match and test again. When evtest still shows EACCES, check competing distribution rules in /lib/udev/rules.d that may override your file by name ordering. Choosing a filename later in sort order, like 60 local override, ensures your assignment wins. If device names change between ports, leverage persistent attributes such as USB vendor and product IDs to target a stable identifier. Precision avoids unintentional changes to keyboards.

Looking ahead

Sustaining reliable controller access means treating your udev rules as living configuration that evolves with hardware and distribution updates. When you add devices, capture their attributes and compare them to your existing matches, refining rules to stay precise. Maintain a small changelog inside your rules directory that records the date, reason, and outcome of adjustments. This habit shortens future debugging by showing which decisions worked and which created regressions. Periodically retest after kernel updates because input properties can change, especially around Bluetooth stacks and HID quirks that shift how devices identify themselves.

As your environment diversifies, consider segmenting rules by device family so each file serves one clear purpose. For instance, keep a general joystick rule and a separate override file for a specialty adapter that requires a group. This structure reduces side effects and makes ownership responsibilities clear to collaborators. If you maintain shared systems, document group membership procedures and implement periodic audits to retire unused accounts. Clear boundaries maintain security while preserving the convenience that makes gamepads straightforward to use across emulator applications and native games alike.

Finally, revisit packaging choices when you change how DuckStation runs, since containers and sandboxes alter device visibility. If you switch to Flatpak or run through a compatibility layer, reassess permissions and portals rather than editing working udev files. Keep a small checklist that starts with external validation through evtest, then checks sandbox flags, and only then returns to udev. This steady diagnostic order protects stability and helps you deliver repeatable results for yourself and anyone who follows your documented process later.

Frequently asked questions

My rule loaded but evtest still shows permission denied. What next?

Check that the rule actually matched by running udevadm info and inspecting properties. Then replug the device and confirm no earlier rule overrides ownership. Finally verify sandbox settings if using Flatpak or other containers.

Should I use uaccess or a dedicated group for controllers?

Use uaccess on single user desktops managed by systemd logind because it grants access to the active seat automatically. Choose a group on shared or non logind systems and add required users to that group with least privilege.

How do I apply udev changes without rebooting?

Run sudo udevadm control --reload to reload rules, then unplug and reconnect the controller or toggle Bluetooth so the device add event reapplies permissions and ACLs. A simple trigger without replug sometimes misses dependent subsystems.

DuckStation sees the device name but inputs do nothing. Why?

If evtest works, the issue is likely in bindings or packaging. Recreate the input profile, ensure no duplicate device paths are mapped, and confirm that your build can access host devices if running inside a sandboxed package.
