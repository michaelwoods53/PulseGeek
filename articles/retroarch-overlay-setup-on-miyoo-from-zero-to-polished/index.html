RetroArch Overlay Setup on Miyoo: From Zero to Polished

By Jared Butler • Published January 14, 2026

You are about to configure RetroArch overlays on a Miyoo handheld so the screen looks tidy without slowing gameplay. We assume stock or Onion OS, basic RetroArch familiarity, and file transfer via USB or SD card reader. The goal is a polished overlay setup with clean alignment, safe opacity, and minimal overhead. By the end, your overlay selection, folder structure, and per core decisions will feel deliberate instead of improvised, and you will know how to reverse changes. If you are also tuning input behavior, you can reference a related guide on mastering controls and clean UI tweaks for hotkeys and remaps when you want to go deeper after overlays.

Key takeaways

  • Use a stable folder layout so overlays and assets stay portable.
  • Prefer lightweight PNG overlays and keep opacity between 35 and 55 percent.
  • Enable overlays per core when controls differ across systems.
  • Validate alignment with integer scaling before changing overlay scale.
  • Disable heavy shaders if overlays cause latency or tearing.

Plan the work

Start by defining the visual goal and technical limits so decisions remain consistent across systems. Choose whether you want system themed bezels or a single neutral overlay for everything, and decide how much screen real estate to sacrifice for art. On Miyoo Mini and Mini Plus, safe targets are 320 by 240 output with integer scaling for 240p systems, which keeps pixels crisp. This baseline means your overlay should not force non integer scaling to fill the frame. Accept that Game Boy and vertical arcade titles may demand unique borders. By setting a shared baseline and exceptions list now, you reduce later thrash when testing opacity or border thickness, and you can document rules like always prefer integer scale first, then nudge overlay scale only when alignment fails.

Next, plan a folder layout that future you can navigate quickly during updates or SD swaps. Place overlays in a predictable path such as /roms/overlays/ or /retroarch/overlays/ depending on your build, and keep system specific subfolders like gb, snes, and arcade. Pair each .png with its .cfg so moving assets does not break references. This organization minimizes broken paths when you update Onion OS or migrate to a fresh card. The tradeoff is a little upfront time, but it pays back whenever you switch cores or try alternative packs. If you routinely test different looks, create a _sandbox subfolder to keep experimentation separate from stable overlays.

Finally, choose performance friendly assets so overlays do not become a bottleneck. Prefer single layer PNGs over multi layered transparency effects, and keep image resolution near the handheld display to avoid needless scaling. On a Miyoo, heavy shader stacks combined with overlays can introduce latency or small stutters, especially on 16 bit systems. A practical rule is choose overlays first, then add gentle CRT looks only if performance remains smooth. If you need shader advice later, consult a guide that curates lightweight options that preserve frame pacing. This approach keeps your baseline strong and avoids chasing problems caused by conflicting visual tweaks rather than overlay configuration itself.

Prepare environment

Begin by setting a clean directory structure and confirming write access so RetroArch can find overlays reliably. Verify the SD card has a dedicated overlays folder and that RetroArch’s Settings to Directory paths point to it. If the overlays path is unset, RetroArch may save references in the root config, which complicates per core overrides later. Place a small starter set like a neutral handheld bezel and a few system themed PNGs with matching .cfg files. To keep things reversible, back up retroarch.cfg before enabling overlays. This prep lets you test a single overlay on one core first. If something breaks, you can restore defaults quickly rather than hunting through multiple configuration layers.

Next, confirm scaling and aspect defaults to reduce overlay misalignment during first runs. Enable integer scaling in Settings then Video when working with 240p systems, and set aspect to Core Provided or 4 by 3 depending on the core’s accuracy. Locking these basics makes overlay borders line up with the active viewport without warping. The tradeoff is some black space on the sides if a bezel expects a slightly different crop. That is acceptable because you can later nudge overlay scale or opacity without losing pixel integrity. If you prefer black frame insertion or other latency features, leave them disabled until overlays prove stable, then reintroduce one change at a time.

Finally, gather reliable references so you know which settings move which part of the frame. Keep a tiny cheat sheet for keys like overlay_opacity for transparency, overlay_scale for artwork size, and overlay0_rect when a pack defines touch zones or interactive areas. While Miyoo does not use touch, some packs include regions for UI elements that still affect placement. Having this glossary next to your files shortens iteration time. Execute steps

Apply overlays in a tight loop so each change has a clear cause and effect. Start by enabling a neutral overlay globally to prove the path works, then move to per core overrides using core config files. This sequencing prevents confusion where a core or game level override masks the global change. A safe pattern is test on SNES first, because 4 by 3 titles with 240p output expose alignment issues quickly. Expect minor gaps around the viewport while using integer scaling. If gaps distract more than they help, you can experiment with overlay scale in small increments, but keep a note of each nudge so you can revert. The aim is repeatable steps that work the same way across systems.

Next, tune opacity with a narrow starting range to maintain readability and reduce eyestrain. Many players settle between 35 and 55 percent because the artwork feels present without pulling focus from the game. You can move lower for busy overlays or higher for minimal frames, but test in motion on a scrolling background to catch flicker or distracting edges. If you run a CRT shader, choose a lighter overlay to avoid compounded darkness. The limitation here is that each core renders slightly differently, so what looks perfect on Genesis may feel heavy on NES. Document a default per system and note exceptions you accept.

Finally, handle per core overrides where control labels or button icons differ. Create or edit a core specific .cfg that points to the right overlay and includes any scale or opacity overrides. Store it alongside the overlay art so moving the folder keeps references intact. If a pack includes multi region art with different label text, confirm your language choice early so screenshots and muscle memory match. The tradeoff is a small increase in maintenance when you switch cores, but it prevents a global overlay from confusing button prompts. This approach is cleaner than per game overrides for most libraries and lands a tidy balance between precision and simplicity.

Validate results

Validation begins with alignment checks that respect integer scaling so you do not mask pixel rounding errors with art. Load a title with sharp edges or scrolling test patterns and look for consistent margins between the game viewport and overlay bezel lines. If you see uneven spacing, confirm aspect ratio first before touching overlay scale. As a rule, fix video and core settings before editing art parameters, because overlays should frame the rendered image rather than force it to fit. Accept that some titles have off by one pixel quirks when cores reproduce original hardware behavior. You can still preserve visual balance by favoring consistent borders over perfect symmetry when the game’s internal resolution shifts mid scene.

Next, assess readability and visual comfort under realistic play. Test font legibility on the overlay, button icon clarity, and whether borders distract during rapid motion. If the overlay includes decorative noise or vignettes, move opacity lower until HUD elements and sprites stand out without competing edges. Play for ten minutes on a mix of backgrounds to surface subtler issues like eye fatigue or perceived dimness. When paired with a CRT shader, ensure combined darkness does not obscure UI cues. If you detect artifacts like shimmering, disable the shader first and retest. This isolates the overlay contribution from other effects and streamlines corrective steps.

Finally, confirm performance by measuring feel rather than chasing small numeric deltas that are difficult to access on Miyoo. Trust your inputs during high action scenes to catch latency or micro stutter. If the overlay coincides with inconsistent pacing, remove heavy shaders and try a lighter bezel as a quick A and B test. You can also switch to a simpler core if a system offers alternatives with different overhead. Record what you changed and the perceived result, then keep the variant that preserved responsiveness. The aim is a stable baseline that you can maintain across firmware updates without redoing the whole evaluation every time.

Troubleshoot and optimize

When overlays do not align, verify configuration layers in order to avoid chasing the wrong file. Check global retroarch.cfg, then core overrides, then any game specific config that could supersede the others. A common pitfall is assuming a core override loaded when the path is wrong due to a moved folder. If you moved overlays, update every reference or revert to the backed up path. Another subtle issue is a pack that encodes margins expecting non integer scaling. In that case, try a variant bezel from the same pack designed for integer scaling. If you need a refresher on quick menu actions that speed iteration, a primer on essential in game tweaks can help streamline testing mid session.

If you see flicker or darkened visuals, treat shaders and overlays as separate sources and reduce them independently. Disable shaders entirely, set overlay opacity lower, then re enable the shader with its lightest preset if needed. Many users find that a clean overlay plus no shader looks balanced on Miyoo’s small screen. If you want decorative frames, consider installing bezel packs purpose built for the handheld to avoid mismatched resolutions. That keeps file sizes modest and artwork crisp. Packs with heavy bloom or thick textures can produce banding artifacts on 240p content that overlay opacity cannot erase, so replace them rather than over tweak settings.

For broader stability, adopt a stable settings routine that favors predictable cores and conservative features. Keep save states outside test runs so you are not biasing results with quick loads that mask slowdowns. If overlays seem fine until you remap buttons per system, verify that remaps are saved per core to avoid confusing prompts that make overlays feel wrong. Frequently asked questions

My overlay looks offset on one core but not others. Why?

Core overrides or aspect settings likely differ. Confirm integer scaling and aspect first. Then check the per core config for a different overlay_scale or a mismatched overlay path that overrides the global setting.

Do overlays slow down Miyoo Mini or Mini Plus?

Simple PNG overlays rarely hurt performance, but heavy shaders combined with overlays can add latency or stutters. Test overlays alone first. If smooth, add a very light shader and retest during motion to confirm pacing.

Should I use per game overlay overrides?

Prefer per core overrides for consistency. Use per game only when a title has unusual resolution or HUD that needs special framing. Per game configs increase maintenance and are harder to track across SD card changes.

What opacity is best for visibility without distraction?

Start around 0.45 and adjust between 0.35 and 0.55. Test in a scrolling scene to detect dimming or edge distractions. Heavier art might need lower opacity, while minimal frames can handle slightly higher values.

Where should I store overlay art and configs?

Keep PNG and CFG pairs together in a dedicated overlays folder with per system subfolders. Set RetroArch’s overlay directory to that path. This keeps references portable and prevents broken links during updates.
