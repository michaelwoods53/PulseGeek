Enable Per-Game Memory Cards in DuckStation

By Eric Morgan • Published February 25, 2026

Our goal is to enable per-game memory cards in DuckStation and keep saves organized without surprises. You will plan a storage location, switch the setting, then confirm that each game creates and uses its own memory card file. This walkthrough assumes you already have DuckStation installed and can launch a game that allows saving early. If not, pick a title with a quick save point, such as an intro menu that offers a save or options write. The process is reversible, so you can test safely before committing. We will focus on practical guardrails, including folder structure, naming patterns, and quick checks that reveal whether per-game behavior is active. Expect clear steps, sensible defaults, and a few fallback tactics if something behaves differently on your system.

Key takeaways

  • Per-game memory cards reduce cross-game conflicts and accidental overwrites.
  • Choose a stable folder path before enabling the setting in DuckStation.
  • Verify in-game that a new card file appears per launched title.
  • Keep one backup rule: export cards before changing any layout.
  • Mixed workflows work if you document which games stay shared.

Plan the work

Start by deciding why per-game memory cards help your library and where files will live. The main benefit is isolation: each game writes to its own card, preventing accidental overwrites when save blocks share names or icons. A good rule is to keep a single directory under your Documents or the emulator’s user path, with write access and consistent backups. For example, create a memorycards-pergame folder and plan filenames that match game titles or IDs. This forethought reduces later friction when you search for a specific save or restore from backup. The tradeoff is slightly more files to manage, but the payoff is predictable recovery. Planning now also clarifies whether some titles should remain on a shared card for convenience, such as quick-testing ROM hacks.

Define a naming convention before flipping any setting so audit and restore steps remain simple. A practical pattern uses a short game identifier plus region and disc indicator, like GAMEID_US_disc1.mcd. If you do not know the identifier, use a human-readable short name that stays consistent across discs. The point is not a perfect scheme, but one you can repeat without thinking. A clear convention allows quick diffs, avoids collisions, and makes cloud backups easier to scan. The limitation is that long names can be cumbersome in file explorers, so keep names concise. By deciding this now, you reduce the chance of creating ambiguous files that slow you down during troubleshooting or migration.

Choose a safety net by defining backups and a fallback path in case behavior is unexpected. Make a dated copy of your current shared memory cards and store it outside the emulator directory. If a save does not appear after switching modes, you can restore with confidence. Set a restore point such as a ZIP of the memory card folder, then test per-game on one title first. The downside is a few extra minutes up front, yet it prevents hours of recovery work later. This safety net is essential when experimenting with settings and paths, since different operating systems can change default directories or permissions in ways that surprise you.

Prepare environment

Verify your storage location and ensure DuckStation can write new files there before enabling per-game behavior. On many systems, using the application’s user directory avoids permission hassles, while custom folders near your ROMs help portability. Test by creating and deleting a dummy text file in the target directory to confirm write access. If you use a syncing service like cloud backup, confirm it does not lock files during synchronization, which can cause transient save errors. The minor cost of this check is a minute of setup time, but it prevents confusing save failures that look like emulator bugs. Setting permissions right now keeps later troubleshooting focused on configuration rather than the filesystem.

Map where DuckStation currently stores memory cards and confirm existing save integrity. Open the current memory card directory and note the file extensions, such as .mcd, which represent PlayStation memory card images. Create a quick backup copy of each file so you can revert if needed. Check file sizes to ensure they are not zero bytes, a common sign of an interrupted write or a previous crash. This quick review provides confidence that your baseline is clean. If anything looks wrong, postpone the per-game switch and address the health of the shared cards first, since migrating from a corrupted baseline invites subtle data loss later.

Document the games you will test and the expected save points for each. Pick one title with a fast save opportunity, like reaching an options menu that writes settings, and another that uses a manual save screen. This variety helps confirm that per-game cards behave consistently across save types. Write down the steps needed to produce these saves, including when to return to the DuckStation file directory and check for new .mcd files. The tradeoff is a few minutes of note-taking, but it anchors your validation process. With a clear plan, you can distinguish configuration errors from normal game behavior, reducing false alarms when a title saves less frequently than expected.

Execute steps

Begin by enabling per-game memory card behavior, then generate a controlled test save. The mechanism routes each game to its own card file, typically created on first save attempt. Before toggling the option, close any running game so settings apply cleanly. After enabling, launch your fastest test title and perform a save action, then watch the memory card directory for a new .mcd file. The benefit is instant feedback that confirms both directory and naming are working. If the emulator names files for you, note the pattern it uses to keep your manual names consistent. The only tradeoff is that you may create an extra test file you later delete, which is harmless.

Validate that per-game files do not overwrite or reuse the prior shared card. Check timestamps on both the existing shared .mcd and the newly created per-game file. You should see the shared card untouched while a distinct file appears for the current title. Open the in-game memory card manager when available to verify that only the current game’s blocks show on the new card. This check guards against misrouted saves caused by a lingering shared setting. The limitation is that not all games expose a card manager, so rely on filesystem evidence if the UI is sparse. This dual confirmation reduces doubt and prevents accidental cross-contamination.

Establish a repeatable pattern for multi-disc titles and special cases that span discs. When switching discs, confirm that the same per-game card remains attached, either automatically through the emulator’s rules or by your chosen naming. If the emulator derives names from a game identifier that is shared across discs, you are covered. If not, maintain a consistent manual filename suffix so each disc can locate the right card. The goal is continuity across the playthrough without manual reattachment every session. The drawback is a little setup for the first multi-disc test, but after confirming behavior you can trust the process and focus on playing.

Validate results

Use both filesystem checks and in-game menus to confirm per-game isolation is active. After saving in two different titles, you should see two .mcd files in your chosen directory with distinct names and timestamps. Launch each game again and verify that the correct file updates when you save, which proves attachment is consistent across sessions. If available, open any in-game memory card manager and confirm only the current title’s blocks appear on its dedicated card. This multi-angle verification eliminates reliance on a single signal that could be misleading. The tradeoff is a few extra launches, but it buys confidence that your saves will not collide in future sessions.

Test edge cases that often reveal misconfiguration, such as auto-save features and options writes. Some games save configuration on exit rather than during gameplay. Perform an options change and leave the game to provoke a write, then check whether the correct per-game file updates. This covers the scenario where a user thinks saving worked but only the options wrote to disk. If timestamps do not change, revisit the setting and path. The limitation here is that behavior varies between titles, so look for consistent file updates rather than relying on a single save screen as proof.

Document your final directory and naming pattern so future maintenance stays straightforward. Capture a short note in a README file inside the memory card folder describing your convention and backup cadence. This tiny artifact prevents confusion when you return months later or migrate systems. It also helps if a friend or a future you needs to recover saves after a reinstall. The only cost is seconds of typing, and the benefit is avoiding guesswork during a stressful recovery. With documentation in place, you can confidently move on to optimizing performance and handling exceptional titles that might prefer a shared card for convenience.

  2. Pick a save directory: choose a writable folder dedicated to per-game files.
  3. Turn on per-game mode: enable the setting in DuckStation and restart.
  4. Make a test save: save in a game that writes quickly, then check timestamps.
  5. Verify isolation: repeat with another title and confirm a second file appears.
  6. Note your convention: record naming and backup rules in a simple README.

Troubleshoot and optimize

When a new .mcd does not appear, verify three suspects in order: permissions, paths, and the setting state. First, confirm the target directory allows writes by creating a test file. Second, ensure DuckStation points to the intended folder and is not using a default user path. Third, double-check that per-game behavior is still enabled after a restart. If the problem persists, try a different directory to isolate whether the filesystem is at fault. The tradeoff is moving files temporarily, but it quickly distinguishes configuration from environment issues. This sequence resolves most cases without touching your existing saves, which helps maintain confidence during experimentation.

If a game cannot find prior progress after switching modes, attach the old shared card for that title then migrate cleanly. Load the game with the shared card, save once on the new per-game card by copying blocks in the in-game manager when available, then retire the shared file for that title. This reduces risk because you avoid manually editing memory card images, which can corrupt files if mishandled. The limitation is that not every game exposes a copy function, so you may need to temporarily switch back to shared mode, save, then return to per-game with a fresh start for that title.

Optimize by deciding when per-game is not the best fit. For quick testing sessions or cheat experiments, a temporary shared card can be faster. Create a short-lived shared file and delete it after the session while keeping your main library on per-game cards. For large libraries, add a weekly backup task that zips the entire per-game directory, ensuring a quick restore point. This routine lowers the chance of losing progress to unexpected power loss or file sync conflicts. Frequently asked questions

Why did my game not create a new .mcd file after saving?

Check write permissions on the target folder, confirm the configured path, and verify that per-game mode remained enabled after a restart. Try saving again after closing and relaunching both the emulator and the game.

Can I move an existing save from a shared card to per-game?

Often yes, by loading the shared card, copying the save in the game’s memory card manager, and then saving again so the per-game card contains the data. If copying is unavailable, consider replaying to a nearby save point.

Do multi-disc games require separate per-game files?

Usually no, because identifiers or naming rules keep continuity across discs. If your setup creates separate files, standardize filenames or reattach the same card so the second disc can access the original save blocks.

Is per-game mode slower than using one shared card?

Performance is typically similar, since memory card images are small and writes are brief. Any differences usually come from storage or sync processes, so avoid locking files with cloud tools during active play sessions.

What backup schedule should I use for per-game cards?

A simple weekly ZIP of the per-game directory works for most players. Increase frequency if you play daily or rely on long sessions. Keep at least one older archive so you can recover from incidental changes or corruption.
