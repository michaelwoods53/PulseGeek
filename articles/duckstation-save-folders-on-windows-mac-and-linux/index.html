DuckStation Save Folders on Windows, Mac, and Linux

By Eric Morgan • Published January 23, 2026

Finding DuckStation save folders on Windows, Mac, and Linux is the first step toward consistent backups and seamless device switching. This list focuses on where saves live by default, how to set custom directories, and when portable mode is the right fit. Each item was chosen because it removes a common failure point, like overwriting memory cards or scattering save states across drives. You will see concrete directory patterns, a couple of safe defaults, and tradeoffs that matter when cloud sync enters the picture. If you already manage backups, you will still benefit from path hygiene that reduces conflicts when restoring or moving to a new machine.

Key takeaways

  • Know the default DuckStation save paths before changing any directories.
  • Use portable mode for self contained setups on external or cloud folders.
  • Separate memory cards and save states to avoid accidental overwrites.
  • Adopt clear names with dates to simplify recovery and version rollbacks.
  • Test restores with staged copies to validate backup integrity and paths.

1) Find default save locations by OS

Start by confirming where DuckStation writes memory cards and save states on your operating system, because accurate paths make backups and restores predictable. On Windows, DuckStation often uses %USERPROFILE%\Documents\DuckStation unless configured otherwise. On macOS with a standard install, look under ~/Library/Application Support/DuckStation. On Linux following XDG conventions, check ~/.local/share/duckstation for data and ~/.config/duckstation for configs. Verifying these base folders lets you copy the correct files before reformatting a drive or moving machines. The tradeoff is variability from portable builds or custom installations that redirect data. Because of that, always open DuckStation’s Settings and note the actual directories reported there instead of guessing based on typical layouts.

Once you know default locations, snapshot them with a simple read‑only pass so you can catch subtle differences like per‑game memory cards or multiple save state subfolders. For example, some setups place memcards and savestates under a single DuckStation folder, while others split them alongside bios and covers. Keeping a small inventory helps when you enable scheduled backups later, and it reduces the risk of missing a subdirectory during a restore. The limitation is that defaults can change after updates or when switching builds, so repeat this check whenever you reinstall. 2) Set a custom save directory or portable mode

Switching to custom directories centralizes data and simplifies sync, while portable mode keeps everything self contained next to the executable. Use custom paths when you want saves in a dedicated folder, like D:\Emu\DuckStationData or ~/Emu/DuckStationData, where backup tools and cloud clients run reliably. Portable mode is better when you need a single movable folder for USB drives or a cloud directory. The tradeoff is that portable setups can increase sync churn if large files change frequently, and some cloud clients do not handle rapid state updates smoothly. If you sync between desktops, review this step‑by‑step article that explains save types and migration so changes do not break paths: complete memory card setup and migration guidance.

After you redirect paths, test behavior with a small scenario. Create a new save state and a fresh memory card slot in a test game, then confirm the files land inside your chosen directory. On macOS and Linux, also check permissions so tools can read and write without prompting. If you placed DuckStation inside a cloud‑synced folder, pause sync during gameplay to prevent conflicts, then resume afterward so versioning can capture a clean snapshot. The limitation is operational overhead, because pausing and resuming requires habit. If you prefer automation, consider a straightforward approach to scheduled copies described here on automating DuckStation save backups with simple tasks.

3) Structure folders for memory cards and save states

Separating memory cards and save states into distinct subfolders reduces accidental overwrites and makes restores faster. A simple pattern is DuckStationData/memcards for .mcd files and DuckStationData/savestates for state snapshots, with optional per‑game subfolders that use a consistent naming rule like GAMEID_Title_YYYY‑MM‑DD. This structure helps you roll back only what changed during a test, rather than replacing an entire directory. The tradeoff is a bit more housekeeping, because per‑game folders multiply over time. A light naming convention keeps them readable, and it plays well with cloud history. If you want a complete walk through of creating per‑game cards and migration choices, review this clear explainer on creating consistent DuckStation save file names with IDs and dates.

When syncing or backing up, exclude ephemeral files that do not matter, and include at least memory cards, save states, and configuration relevant to paths. On Linux, retain both ~/.local/share/duckstation and ~/.config/duckstation if you rely on global settings. On Windows and macOS, ensure the data directory travels with your cards. The tradeoff is slightly larger backups, but restores become straightforward because paths and content match. To avoid sync conflicts across devices, create a staging copy before swapping in live files. 4) Make sync safe with cloud friendly settings

Cloud sync works well for DuckStation if you minimize conflicts and large file churn. Favor selective sync so only your DuckStationData folder travels, and disable aggressive real‑time watching during gameplay. One approach is to pause the client while playing and resume afterward, letting version history capture discrete saves. Some services offer file versioning that can rescue recent changes if a state becomes corrupted, which pairs nicely with per‑game subfolders. The tradeoff is extra steps and the risk of forgetting to resume. If you are a OneDrive user, see this detailed setup that covers conflict‑free settings and recovery tactics for multiple PCs: set up OneDrive to sync DuckStation saves across devices. Dropbox and Google Drive can follow the same principles with selective folders and cautious merges.

Test sync safety by creating a throwaway save on device A, waiting for the client to finish, then opening the same game on device B and confirming timestamps match. If a conflict file appears, do not delete it immediately. Instead, copy both versions into a local staging folder and load each in isolation to see which is correct. This extra step prevents irreversible data loss from a hasty cleanup. The limitation is added time during troubleshooting, but it is cheaper than rerunning hours of progress. If you prefer a non‑cloud approach, scheduled local backups to a secondary drive provide quick rollbacks and avoid network dependency, though they do not handle cross‑device play.

Section highlights

  • Use selective sync and pause clients during gameplay to prevent conflicts.
  • Validate with cross device tests and preserve conflict copies for review.

Frequently asked questions

Does DuckStation support portable mode on all platforms?

Yes. Portable mode keeps data next to the executable across platforms. Behavior depends on how the build is packaged, so verify in Settings after enabling to confirm directories moved as expected.

Which folders should I always back up for DuckStation?

Back up memory cards and save states at minimum. If you changed directories or rely on per game cards, include configuration files that reference those paths so restores do not break.

Are cloud sync conflicts common with save states?

Conflicts happen when two devices modify the same state before sync finishes. Reduce risk by pausing sync during play, resuming afterward, and testing with a small file before trusting cross device changes.

Can I move saves between Windows, macOS, and Linux?

Yes, provided file paths and formats match. Use a consistent directory structure and verify BIOS and memory card files load correctly on the target system before committing changes.
