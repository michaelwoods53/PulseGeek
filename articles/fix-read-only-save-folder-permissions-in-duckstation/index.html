Fix Read-Only Save Folder Permissions in DuckStation

By Eric Morgan • Published March 6, 2026

Read only save folder errors in DuckStation usually point to blocked write permissions, not broken saves. This guide explains what read only means at the file system level, why the save directory matters, and how Windows, macOS, and Linux enforce access rules differently. We will test where DuckStation stores its save files, confirm whether the folder and parent directories allow writing, and correct misconfigurations carefully. The aim is reliable saves without loosening security more than necessary. Along the way, you will see examples of inherited attributes and user account control that mimic read only states, plus reversible fixes that protect progress while you experiment.

Key takeaways

  • Confirm the actual save folder path before changing permissions.
  • Test write access with a small file to isolate the blocker.
  • Adjust only needed rights, preserving inheritance when possible.
  • Fix ownership mismatches that silently force a read only state.
  • Keep backups and versioned copies to protect existing saved data.

Concepts and definitions

Read only, in this context, means the operating system denies write operations to DuckStation’s save directory, not that the emulator refuses to save by design. A quick way to verify is attempting to create a zero byte test file in the target folder and watching for an access error. On Windows, the folder Read only checkbox often signals custom attributes rather than a hard block, while NTFS Access Control Lists actually decide writes. On macOS and Linux, ownership and mode bits or Access Control Lists set the effective rules. The key is identifying whether the emulator’s configured save path points to a location that the current user and process can modify consistently.

Save locations differ by setup, so first learn where DuckStation writes memory card files and save states. Many users keep them under a user profile directory that normally inherits writable permissions, yet portable installs may place them beside the executable, which can land under Program Files on Windows and block writes. If the emulator runs in a sandboxed context, such as a flatpak on Linux or a restricted folder on macOS, the presented path might be remapped with scoped permissions. Mapping the effective path to a real directory ensures you test the right place and do not chase unrelated folder attributes that are harmless.

Ownership determines who controls the folder, and mismatches often explain stubborn read only behavior. For example, if a folder was created by an administrator account, a standard user might read contents but fail to write new files even though the parent seems permissive. Conversely, overly broad Everyone write access can mask the real owner and complicate inheritance. A reliable baseline is a folder owned by your active user with modify rights and inherited permissions from a trusted parent directory. When ownership or inheritance looks unusual, plan to correct them with the least invasive change that still enables predictable writes for DuckStation.

  • Prioritize correct ownership and minimal rights over broad access.

Frameworks and decision lenses

A simple three question lens reduces guesswork and avoids risky permission changes. First, does the configured save path match a writable user directory, such as Documents or a dedicated games folder, rather than a protected system location. Second, can your current account create, modify, and delete a small file there without elevation. Third, do parent folders inherit predictable rules so new subfolders stay writable. If any answer is no, adjust just enough to flip it to yes. For Windows, avoid toggling the Read only box and instead review NTFS entries for your user, Administrators, and SYSTEM. For macOS and Linux, check owner and group, then confirm mode bits or ACL entries grant write access to your account.

When the emulator is portable or installed in a guarded directory, the safest fix is moving saves to a user controlled location and pointing DuckStation to that folder. This avoids fighting system policy and respects updates that reapply defaults. You can then grant modify rights only to your user, leaving wider groups untouched. If the move is not possible because a shared machine requires centralized storage, create a dedicated subfolder with clear ownership, and document its parent path. For long term reliability, schedule periodic backups so one mistaken permission tweak cannot cascade into lost progress across multiple games.

If you work across macOS and Linux, build parallel habits that translate the Windows approach to ownership and inheritance into their tools. On macOS, confirm that your user owns the save directory and that permissions show Read and Write in Finder’s Get Info panel, then verify with a quick touch command. On Linux, ensure the directory is owned by your user with chown and writable via mode bits like 750 or 770, depending on group needs. In both cases, avoid granting world write unless absolutely required by a shared environment, and prefer targeted group membership for collaborative scenarios.
