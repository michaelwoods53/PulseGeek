Backup and Restore Saves on Miyoo Mini

By Jeremy Crawford • Published March 3, 2026

Backing up and restoring saves on a Miyoo Mini keeps progress safe across updates and SD swaps. This tutorial focuses on a repeatable backup strategy using a card reader and simple commands, with optional tools from Onion OS or RetroArch when needed. You only need a computer that can read the SD card and basic file navigation. We will favor methods that minimize write operations on the card to reduce wear and lower corruption risk. If your device currently boots, you can capture a snapshot before making changes. If it does not boot, you can still pull files directly from the card to recover saves.

Key takeaways

  • Back up the entire Saves directory, not individual emulator folders.
  • Use rsync archive and checksum flags to preserve metadata safely.
  • Verify restores with hashes and small sample loads before overwriting.
  • Keep at least two rotating copies on separate physical devices.
  • Diagnose SD faults before writing by checking read-only and SMART status.

Plan the work

A reliable plan starts by defining the scope of what to protect and when to run backups. For Miyoo Mini, prioritize the Saves folder and configuration that maps button profiles and core settings. A weekly snapshot is sensible for casual play, while daily copies suit active runs or testing new Onion OS builds. Decide whether you want versioned history or a single rotating backup and note the storage impact. For example, a month of daily snapshots may fit easily on a 16 GB USB drive if you compress older sets. Tradeoffs include time spent and restore complexity, so aim for a routine you will actually keep.

Clarifying source paths avoids missed files and inconsistent restores later. Typical Onion OS layouts store save states and SRAM under /Roms or /Saves with emulator subfolders, while RetroArch places states in configured directories that can vary. Confirm exact locations by opening RetroArch settings to view the paths for saves and states. If you are unsure, search the SD card for file extensions like .srm, .sav, and .state to locate all sources. The risk of partial backups is high when paths change between updates, so capture the parent directories instead of cherry picking files.

Risk controls reduce chances of corruption during copying and restoration. Only back up from a cleanly unmounted SD card to prevent half written entries and use a USB 3.0 reader with a steady connection. Consider read first workflows that copy to the computer before you test any new firmware. Keep at least two copies on separate devices to avoid a single point of failure, such as one on a NAS and another on an external drive. The main limitation is discipline and storage space, so set reminders and prune old versions with clear rules to stay consistent over time.

Prepare environment

Preparation begins with confirming that your SD card and reader are healthy before copying data. Inspect the adapter for wobble and test read speed with a small file to catch intermittent dropouts. If your computer supports it, check the SD card’s error counters or run a non destructive read test to spot weak sectors. Set the SD switch to unlocked and avoid writing until you complete a backup. If you recently experienced crashes, consider making a raw image with a disk utility as a safety net. The downside is time, yet an image can rescue files if the directory tree deteriorates later.

Next, align tools so file attributes and directory structure survive the transfer. On macOS and Linux, prefer rsync with archive mode to preserve timestamps and permissions. On Windows, use WSL or a portable rsync build, or fall back to a careful copy that preserves folder names and hidden files. Disable any antivirus real time scanning for the SD card while copying to prevent lock delays or skipped files. Keep the destination path short and simple to avoid issues with long paths during restores. These measures ensure the restored files behave identically to their originals.

Documenting your SD layout now simplifies future restores and questions. Capture a screenshot of the Saves directory tree and note paths for RetroArch content, states, and SRAM in a small text file stored with your backups. If you plan to update Onion OS soon, record your current release tag and any core overrides that affect save file placement. A simple README that lists where you copied from and the rsync flags used can prevent mistakes later. This light documentation adds minutes today and saves hours when troubleshooting after a change or a device failure.

Execute steps

Execution focuses on safe transfers that retain metadata and structure. Use rsync with archive mode to copy the Saves directory to your computer, then create a second copy on another drive. For restores, reverse the direction while protecting newer files with checksum comparisons. If your unit boots, close any running games to flush save writes before removing the SD card. If it does not boot, copy from the card directly and prioritize preserving data before attempting any fixes. The main tradeoff is speed versus certainty, so choose flags that balance thorough verification with practical runtime for your library size.

Flags matter because they dictate what gets copied and how differences are detected. Archive mode bundles recursion and metadata preservation, while -H protects hard links created by some tools. The --delete option prunes files removed from your source so the backup mirrors reality, which is helpful for cleanup but risky if the source is already damaged. Adding -c forces checksum comparisons to avoid overwriting a newer destination file in rare timestamp drift cases. As a rule, use -aH for backups and -aHc for restores when you want to preserve newer data on the SD card and still align the rest.

When a graphical method is preferred, you can still apply the same principles using a file manager. Copy the entire Saves directory to two destinations and avoid selective copying of individual emulator folders. Sort by modified time to confirm recent files moved, then spot check by opening a couple of SRAM files with a hex viewer to ensure nonzero content. Before a restore, rename the existing Saves on the SD to Saves.bak so you can roll back if anything goes wrong. This extra step costs space temporarily but provides a safe fallback with minimal effort.

Validate results

Validation proves your backup and restore process worked before you trust it in emergencies. Start by comparing directory sizes and file counts between the SD and your primary backup, then run rsync with --dry-run to confirm no unexpected changes remain. Generate hashes for a random sample of files and verify they match across copies. A quick sanity check is to load one game after restoring and ensure the latest save state appears with the expected timestamp. These checks cost minutes and identify silent failures like partial transfers or blocked hidden files that often do not throw clear errors.

Play testing is a practical way to catch emulator specific quirks that a checksum cannot reveal. Some cores rebuild companion files on first load, which can change timestamps without indicating data loss. Load a state, make a minor in game change, save again, and confirm the update propagates to the backup on the next sync. If any emulator moves its save path after a configuration change, update your documentation and adjust future backups. The limitation is time spent across multiple systems, so prioritize consoles you use most and rotate through the rest over several sessions.

Record evidence of successful validation so you can audit later. Keep a text log with the date, rsync output summary, and notes from your play test like titles and save slots. Store this alongside the backup folders so context travels with the data. If you use a NAS, enable snapshots on the backup share to capture history without copying gigabytes repeatedly. The tradeoff is additional storage for snapshots, but it enables point in time recovery if a future script or mistake deletes valid saves. Clear records make troubleshooting faster when something feels off months later.

Troubleshoot and optimize

When backups fail or restores misbehave, isolate the weakest link before retrying. If copying halts, check the SD’s write protect tab and test with a different reader to rule out intermittent contacts. For filesystem errors, mount the card read only and copy what you can before attempting repairs. If Onion OS will not boot, prioritize extracting the Saves directory first to preserve progress. After recovery, consider replacing the SD if errors repeat. Optimization focuses on reducing manual steps and preventing drift between devices. Schedule a periodic job on your computer that syncs the primary backup to a secondary drive, then trigger a manual sync after play sessions that matter. Keep your RetroArch save and state directories stable across updates to avoid moving targets. Before major changes like Onion OS updates, create a fresh backup and label it with the date and version to anchor future comparisons. Some failures trace to hardware rather than software. If restores seem correct but games still show missing progress, test the SD with another system to rule out slot issues. Consider proactive replacement when random write errors appear, and choose reputable cards from known vendors. Maintain adequate battery during heavy file operations to prevent brownouts that corrupt writes. Separating hardware and software variables speeds resolution.

Frequently asked questions

Where are Miyoo Mini save files stored by default?

Most builds keep saves under a top level Saves directory with emulator subfolders. RetroArch can override paths, so check its settings for save and state locations before copying. When in doubt, search for file extensions like .srm, .sav, and .state.

Can I restore saves between Onion OS versions safely?

Yes, if the directory structure and core names remain the same. Back up the entire Saves folder, then restore and test a few titles. If a core changed its path, update configuration or move the affected subfolder to the new location.

Should I include RetroArch config files in backups?

Include core overrides and custom paths if you rely on them. These files do not hold progress but affect where saves live. Back up configs alongside Saves to avoid confusion after updates that reset or relocate directories.

What if the SD card shows read errors during copy?

Stop writing to the card and retry with a different reader. Mount read only if possible and copy what you can. Create a raw image for recovery, then replace the card if errors persist to avoid repeating corruption.

Is cloud storage a good place for backups?

It works if sync is reliable and you keep an offline copy. Use a folder that does not rename paths and verify uploads by comparing hashes on a small sample. Maintain one additional local backup for fast restores without bandwidth limits.
