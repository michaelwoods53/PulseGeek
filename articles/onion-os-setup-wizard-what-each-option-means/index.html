Onion OS Setup Wizard: What Each Option Means

By Jeremy Crawford • Published January 27, 2026

The Onion OS setup wizard introduces core choices that shape how your Miyoo Mini boots, saves, and organizes content. Understanding setup wizard options upfront prevents confusing behavior later, like unexpected resume states or missing thumbnails. This article explains each screen, clarifies what the options actually change, and provides decision criteria for common goals such as safe save handling, snappy menus, and battery-friendly defaults. I will also point to deeper resources when you want to install Onion OS cleanly or adjust firmware. By reading once and setting sane defaults, you avoid trial and error while keeping save files intact. The guidance focuses on practical tradeoffs and how the wizard writes configuration files that affect launchers and RetroArch behavior across systems and cores.

Key takeaways

  • Wizard choices map to config files that control boot, saves, and menus.
  • Prefer safe save handling over speed when unsure about resume states.
  • Use trimmed art scraping and later bulk updates to save time.
  • Leave advanced toggles off until a need appears in testing.
  • Document initial options to spot regressions after future updates.

Concepts and definitions

The best way to approach the Onion OS setup wizard is to treat each screen as a contract that writes specific settings into configuration files and folders. For example, toggles related to resume or autosave often translate to RetroArch’s savestate_auto_load and menu scripts that affect launch behavior. A concrete case is enabling quick resume globally, which speeds return to play but can create stale states after core updates. The tradeoff is convenience versus reproducibility if you switch cores or update assets. Knowing the why helps: the wizard sets defaults designed for new users, but your library size, preferred systems, and power habits may warrant different choices that reduce write cycles or avoid surprises when swapping SD cards.

A second concept is scope. Some wizard options are global across Onion OS layers, while others apply only to RetroArch cores or the front-end theme. A screen that offers thumbnail generation affects the media cache and can be reversed without touching save data, while a setting for autosave on exit changes how games write SRAM on suspend. Consider a scenario where you often open and close short arcade sessions. Global autosave reduces manual steps, yet it can introduce unwanted save churn on systems that rely on SRAM rather than states. The limitation is that not every core interprets these settings identically, so consistency improves when you pair the wizard’s defaults with per-core checks inside RetroArch if you notice irregular behavior.

The third definition worth pinning down is what persists across updates. Many first-time installers worry that a later Onion OS update will reset wizard choices and erase preferences. Typically, user data folders preserve key files like RetroArch configs, playlists, and BIOS references, while the OS layer refreshes scripts and themes. An example is keeping your hotkey combo intact after an upgrade because the user override file remains. The tradeoff is that inherited mismatches can occur if a new version assumes different defaults than your older overrides. Understanding persistence explains why a careful initial setup, paired with simple documentation of your chosen options, leads to less friction during upgrades and fewer mysteries about changed behavior.

Frameworks and decision lenses

A reliable framework is goals, risks, and reversibility. Start by naming your top priority, such as fast boot, resilient saves, or consistent art. Then select wizard options that support the goal while keeping risks manageable. For example, prioritize resilient saves by choosing manual exit saves and turning off global quick resume to avoid stale states after core changes. The tradeoff is an extra button sequence on exit, which is minor compared to losing progress. Reversibility matters because some choices are easy to change later, like theme and art scraping, while others imprint habits that are hard to unwind. This lens explains why conservative save settings and modest UI features often suit a mixed library.

A second decision lens is workload versus battery. Wizard screens that offer frequent scraping, aggressive animations, or rapid resume behaviors can increase SD writes and power draw. A tangible example is enabling artwork generation for the entire library during first boot, which can lock the device in long indexing cycles and drain battery if you have thousands of ROMs. The alternative is scraping only favorites and letting idle-time jobs handle the rest while charging. The limitation appears when you want instant completeness. In that case, schedule bulk tasks while connected to power and verify SD card health to reduce the chance of corruption while many small files are written in quick succession.

Use a small decision table to apply the lenses quickly. Match common goals to recommended defaults and note potential tradeoffs so you can adjust with intention rather than guesswork. This format keeps choices consistent across future reinstalls or SD migrations, especially when sharing devices with family. The idea is not rigid rules but a starting position you can audit after a week of play. If your experience contradicts the table, change one variable at a time and retest, which prevents confusing cross effects where multiple toggles hide the true cause of a problem.

Examples and short scenarios

Consider a handheld shared with kids where progress loss is the main concern. Choose manual SRAM saves on exit and keep quick resume off for systems that struggle with state compatibility, like certain 16-bit cores. Add a simple theme, limited animations, and focused scraping for a small favorites list. This setup reduces write bursts and keeps behavior predictable when someone switches games abruptly. The tradeoff is that resuming play takes a moment longer and artwork may appear incomplete for lesser used titles. This approach works because it aligns with real usage, accepts minor friction, and avoids hidden dependencies that emerge when multiple users suspend and resume across many cores without consistent exit habits.

Now imagine a solo player with a large library who values speed over meticulous preservation. Enable per-system quick resume for handheld consoles where savestates are stable, keep a light theme for responsiveness, and schedule batch art downloads overnight while charging. This configuration shines when you dip into many titles rapidly and want instant continuity. The limitation is potential state breakage after core updates or when switching between different emulators for the same system. Mitigate that risk by archiving critical progress with in-game saves before big updates and by limiting quick resume on platforms known to have finicky savestates so a single toggle does not compromise progress across the board.

Finally, consider a traveler who plays in short bursts and worries about battery life more than visuals. Disable heavy transitions, keep screen brightness modest, and limit background indexing. Favor manual saves and avoid full library scraping on the go. This profile may benefit from postponing artwork jobs until connected to power, while a small favorites playlist keeps menus tidy. The cost is a less glamorous interface and occasional manual steps when leaving games. The payoff is longer sessions between charges and fewer incidents where the device is busy writing while you close the lid hurriedly. The how is simple: map settings to travel constraints and review them after the trip to restore your home profile.

Frequently asked questions

Can I change Onion OS wizard choices after setup?

Yes. Most options can be adjusted later through settings, themes, and RetroArch. Save behavior is editable, but recheck per-core settings if states were created under different defaults.

Does quick resume risk corrupting my saves?

Quick resume itself does not corrupt saves, but stale savestates can conflict after core changes. Mitigate by using in-game saves for key progress and limiting quick resume on finicky systems.

Should I scrape artwork for the full library at first boot?

Usually no. Scrape favorites first to reduce time and battery use, then run bulk updates while charging to avoid heavy writes during normal play.

Will an Onion OS update reset my wizard settings?

User data and overrides typically persist, so most preferences remain. After updates, verify save and resume behavior because new defaults can interact with older overrides.

Do different RetroArch cores respect the same save settings?

Not always. Global options set defaults, but some cores behave differently. If results vary, tune per-core settings and test with a single game before applying widely.
