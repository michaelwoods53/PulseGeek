RADSEC Configuration Guide: RADIUS over TLS

By Thomas Phillips • Published January 23, 2026

Use this how to configure RADSEC so RADIUS traffic travels through TLS with certificate based trust. We assume you operate enterprise Wi‑Fi authentication with 802.1X and need encrypted transport between proxies and servers. The environment covers a RADSEC proxy, a RADIUS server, and firewalls under your control, with access to a private certificate authority or a publicly trusted option.

Key takeaways

  • Pin certificate trust and hostnames before enabling RADIUS over TLS.
  • Use a proxy that supports TCP 2083 and strict server name checks.
  • Segment UDP RADIUS from TLS transports to isolate failure domains.
  • Log TLS handshakes and OCSP status to speed incident triage.
  • Stage with permissive policies, then tighten cipher and client auth.

Quick start checklist

  1. Choose trust model: decide on private CA or public CA and hostname policy.
  2. Generate certificates: issue server and client certs with proper EKUs and SANs.
  3. Open firewall ports: allow TCP 2083 between proxy and server with egress rules.
  4. Configure proxy: set RADSEC listener, upstreams, and server name verification.
  5. Test connectivity: verify TLS handshake with openssl and probe auth with radtest.
  6. Enable OCSP: validate revocation and monitor stapling or responder reachability.

Plan the work for RADSEC

Start by defining why RADSEC fits your network and what risk it reduces. Encrypting RADIUS over TLS prevents credential leakage and simplifies traversing untrusted links, such as provider backbones or inter‑site paths. A practical model sets RADSEC between site proxies and central RADIUS, while local 802.1X remains UDP. The tradeoff is added TLS complexity and stateful behavior over TCP, which can increase retries if buffers fill. Map which devices originate RADIUS, which proxy terminates UDP, and which upstream servers accept TLS. This mapping clarifies certificate subjects and firewall rules. The goal is fewer ambiguous flows when you later test failures with simulated link drops or certificate revocations.

Choose a certificate authority strategy before generating any keys, because subject names and key usages must align with TLS verification. Private CAs give control over issuance speed and custom names, which helps when servers sit on non‑public DNS. Public CAs reduce trust distribution work, but you must route verification and prove domain control. For client authentication, decide whether mutual TLS is mandatory on day one or staged. Staging with server‑only TLS allows phasing, but leaves risk if a proxy is impersonated. Record decisions in a short runbook so the team can reproduce enrollment reliably.

Define SLOs for authentication latency and success rates so you can judge success after cutover. A common target keeps median EAP‑TLS authentication under a few hundred milliseconds across the proxy hop, but ensure peaks remain acceptable during rekeys. Document expected volumes per site and per server, because TCP head‑of‑line blocking can surface when bursts align with RADIUS retransmits. Plan capacity with a simple rule of thumb: keep average concurrent RADSEC sessions below half of the proxy’s tested limit to preserve headroom. Note dependencies such as OCSP responders and internal DNS. By setting thresholds in advance, you know whether to add instances or tune keepalive intervals during pilots.

  • Pick CA and mutual TLS stance early to avoid reissuing certs.
  • Set latency and success SLOs to judge pilot readiness.

Prepare environment for RADIUS over TLS

Prepare a naming scheme that anchors TLS verification with predictable hostnames. Use subject alternative names for each RADSEC endpoint, and ensure internal DNS returns stable A or AAAA records. For proxies that front many sites, prefer a unique hostname per instance to simplify logging. Generate private keys with adequate length, such as 2048 or 3072 bit RSA, or ECDSA if both sides support it, and mark Extended Key Usage for serverAuth and clientAuth when mutual TLS is required. The tradeoff is compatibility, since some legacy stacks only validate serverAuth explicitly. Store keys in a restricted directory with least privilege. Document each certificate’s expiry to avoid synchronized rollovers that cause TLS failures during peak hours.

Harden your CA chain distribution and trust stores before any cutover. If you run a private CA, distribute the root and intermediates to proxies and RADIUS servers using your standard configuration management. Validate trust anchors with a script that checks file hashes and openssl verify output. When using a public CA, confirm that your RADSEC software trusts the system store and does not require a separate bundle. Enable OCSP or CRL fetching paths and test reachability from each site. Revocation calls often cross restricted egress, so define explicit allowlists for responder hosts. Failure to pull revocation data can surface as intermittent handshakes that succeed in the lab but fail in production.

Align firewall and routing policies to permit TCP 2083 between proxies and upstream servers. Document any NAT, because server name indication and certificate hostname checks rely on DNS names, not translated addresses. Permit management access for troubleshooting, including ICMP and TCP 2083 from a jump host to validate handshakes. Keep UDP 1812 and 1813 paths intact for local supplicants to reach the proxy. Consider a temporary maintenance window where keepalive intervals are shortened to detect stale connections quickly. This helps reveal asymmetric routing or stateful firewall timeouts that would otherwise appear as random latency spikes. By clearing these hurdles early, your execution phase becomes a predictable set of changes rather than a guesswork exercise.

Execute steps for RADSEC setup

Configure your RADSEC proxy to listen for local UDP RADIUS and forward to upstream servers over TLS with strict verification. The example below shows a minimal radsecproxy style configuration that binds a local UDP listener, defines an upstream RADSEC server on TCP 2083, verifies the server name against the certificate, and presents a client certificate for mutual authentication. Expect the proxy to maintain persistent TLS sessions to reduce handshake overhead. The tradeoff is longer-lived state, so tune keepalive or TLS session resumption to match your failure detection goals. After applying the configuration, reload the service rather than restarting to preserve existing sessions where possible.

After configuration, apply ordered steps to transition traffic without disrupting active users. First, enable the proxy listener while keeping upstream in a disabled state, then direct a single test NAS to the proxy. Validate authentication and accounting to confirm routing. Next, enable upstream TLS forwarding and pin server name checks, then move a small site segment. Finally, expand gradually and monitor counters for TLS session reuse and handshake failures. This phased approach contains blast radius and gives time to adjust cipher suites. Validate results over TLS

Validation starts with proving the TLS channel authenticates the expected peer and presents the right chain. Use openssl to connect to the upstream and ensure the certificate subject and SAN match the configured hostname. Check that the negotiated protocol meets your policy, such as TLS 1.2 or 1.3, and that preferred ciphers are selected. Then run a negative test by changing the expected name to a non‑matching hostname and confirm the proxy rejects the session. This verifies that you would not accept a man‑in‑the‑middle position with a different certificate. Capture logs showing OCSP status and store them alongside change records for audit evidence.

Next, prove end‑to‑end authentication works through the proxy by generating a standard RADIUS request. Tools such as radtest can submit a PAP or EAP test to the proxy’s UDP listener while the proxy forwards over TLS. Expect accounting to follow the same path if enabled. Compare response times against baseline UDP only flows. If latency grows significantly, investigate TLS session reuse stats or TCP retransmissions that hint at MTU or path issues. To ground these checks in operations practice, consult comprehensive operational best practices for lifecycle and assurance at enterprise WLAN operations guidance and align verification steps with existing processes.

Finally, validate resilience by simulating failures and observing behavior. Drop the upstream link to confirm the proxy retries correctly and respects backoff. Expire a certificate in a test environment to verify alerts trigger before production expiries. Throttle OCSP to ensure stapling fallbacks operate or alarms escalate quickly if responders become unreachable. Measure recovery time after restoring links and compare to your SLOs. A useful rule is to treat validation as a forecast for production: if behavior under stress matches expectations, proceed. If not, adjust idle timeouts or retry logic before a broader rollout to avoid widespread session churn when conditions degrade.

Troubleshoot and optimize RADSEC

When authentication fails after enabling RADSEC, isolate whether TLS or RADIUS logic broke by testing each layer independently. First, run openssl s_client from the proxy to the upstream to confirm the handshake and name verification succeed. If this fails, review trust chains, server CN or SAN, and OCSP reachability. If TLS passes, send a radtest request directly to the proxy and observe logs for routing to the upstream. Look for message authenticator failures that indicate shared secret mismatches on the UDP side. The tradeoff is time, so script these checks to avoid manual drift. Structured logs that include SNI, cipher, and realm help correlate failures to specific tenants or sites.

Optimize performance by tuning connection reuse and timeouts. RADSEC benefits from persistent TLS sessions to amortize handshake cost across many authentications. Increase session cache sizes and enable session tickets when both sides support them, while monitoring for any regulatory constraints that disallow tickets. Adjust TCP keepalive and application level health checks so idle links do not flap during quiet periods. If you observe head‑of‑line blocking, consider sharding upstream connections per realm or per site to distribute bursts. Also audit MTU along the path, because TLS records over TCP can suffer from fragmentation that looks like random latency variance during busy hours.

Plan future maintenance to prevent surprise outages. Stagger certificate renewals so no two critical endpoints expire on the same day, and add automated reminders at least thirty days out. Keep a rollback plan that toggles endpoints back to UDP RADIUS for a subset of sites if TLS dependencies fail, such as OCSP responder outages. Finally, update your security policy documents to reflect transport changes. If you maintain an enterprise Wi‑Fi security policy template with sections for authentication, segmentation, and logging, ensure RADSEC transport and monitoring requirements are explicitly recorded so audits remain predictable and repeatable over time.

Looking ahead

With RADSEC running, scale operations by codifying changes and monitoring into versioned configuration management. Treat every new site as a repeatable pattern that enrolls certificates, verifies name checks, and proves end‑to‑end authentication before production. As you expand, evaluate whether a managed cloud RADIUS or NAC platform fits your governance model, focusing on exportable logs and strong TLS posture. Maintain a single source of truth for endpoints and certificate expiries so ownership is clear. Finally, plan tabletop exercises for OCSP outages and link failures to ensure operational readiness. These rehearsals convert rare incidents into well‑understood drills that preserve user experience during real events.

Key terms

  • Automatic Repeat Request — A protocol that requests retransmission of failed frames.
  • Extensible Authentication Protocol — Framework for network access authentication used in enterprise Wi‑Fi.
  • Maximum Transmission Unit — The largest packet size that can be sent on a network path.
  • Network Address Translation — The process of mapping private addresses to public ones.
  • Remote Authentication Dial‑In User Service — Authentication, authorization, and accounting protocol.
  • Transmission Control Protocol — A reliable, connection-oriented transport protocol.
  • Virtual Local Area Network — Layer‑2 segmentation technique used to isolate traffic.
  • Wi-Fi Protected Access 3 — The current Wi-Fi security standard for encryption and auth.

Frequently asked questions

What port does RADSEC use and should I close UDP RADIUS?

RADSEC typically uses TCP 2083 between proxy and server. Keep local UDP 1812 or 1813 open for supplicants that reach the proxy. Closing UDP on the proxy would break local authentication flows, so restrict it to trusted subnets instead.

Do I need mutual TLS client certificates on day one?

Mutual TLS improves assurance by authenticating the proxy to the server. Many teams stage with server-only TLS first to reduce variables. If you stage, define a short window and plan to enable client certificates once basic flow stability is proven.

How do I validate certificate revocation in production?

Enable OCSP or CRL checks on both sides and verify responder reachability from each site. Log status for each handshake and alert on failures. Test quarterly by revoking a noncritical certificate in a lab and confirming alarms fire as expected.

Why did latency increase after switching to RADSEC?

TLS handshakes and TCP behavior add overhead compared to UDP. Enable session reuse and tickets to reduce handshakes, check MTU for fragmentation, and tune keepalives. Persistent connections and healthy reuse metrics usually bring latency back in line.
