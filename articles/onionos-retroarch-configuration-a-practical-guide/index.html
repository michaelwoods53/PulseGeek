OnionOS RetroArch Configuration: A Practical Guide

By Jared Butler • Published February 22, 2026

Great OnionOS setups start with clear RetroArch configuration goals. This guide picks settings that favor stability, predictable inputs, and consistent save behavior across cores. Items were chosen through hands-on testing and common pain points like BIOS placement, hotkey ergonomics, and scanner accuracy. Each section explains why a setting matters, shows a concrete example, and notes the inevitable tradeoff you should consider. If you are starting fresh, pair this with an end-to-end reference for a smooth first session, then layer tweaks only when the benefit outweighs complexity.

Key takeaways

  • Favor stable RetroArch defaults, then add overrides only when needed.
  • Place BIOS in the system folder and verify core detection signals.
  • Choose cores that fit OnionOS hardware limits and latency targets.
  • Use curated playlists over blind scans to reduce bad matches.
  • Protect saves with autosave rules and verified directory paths.

1) Set stable global defaults first in RetroArch on OnionOS

Start by locking in global defaults that make every core predictable. A practical baseline is integer scaling on, bilinear filtering off, and video sync enabled for consistent frame pacing. For example, enabling integer scale avoids shimmering on pixel art at the cost of black borders on certain aspect ratios, which is usually preferable to soft scaling. Turning on autosave for SRAM and a short savestate slot list offers quick recovery when a handheld sleeps unexpectedly, but it also increases write frequency which can age an SD card earlier. The principle is to pick defaults that reduce surprises across cores, then override only where a specific system benefits. Keep the baseline lean so changes are trackable and reversions are easy.

A concise config is easier to audit and migrate, so choose explicit values rather than relying on defaults that vary by build. For instance, set menu driver to ozone if you prefer clear text lists and stable navigation on small screens, while acknowledging that xmb offers thumbnail flair but heavier rendering. Explicitly define the system directory for BIOS, saves, and states to keep content portable when you swap SD cards. This improves reproducibility yet reduces flexibility if you like per-core storage separation. Document your chosen options in a small text note so you can restore them after updates. That discipline prevents debugging sessions where you cannot recall which tweak caused a latency spike.

2) Map comfortable hotkeys and reliable menu access

Ergonomic hotkeys reduce friction and mistakes during play, especially on compact Miyoo buttons. A strong pattern is Select plus another face button for quick actions and Select plus Start for the RetroArch menu, keeping the combination unlikely to trigger during normal gameplay. As an example, map Select plus Y to toggle fast forward for grind-heavy RPGs, accepting that accidental triggers are still possible during frantic mashing. Assign a safe quit combo that writes SRAM before returning to the launcher to prevent progress loss. The tradeoff is longer chorded inputs that take time to learn. The benefit is consistency across cores so muscle memory transfers. Confirm each mapping inside a couple of different systems to catch conflicts like the same chord used for in-game features.

Decide early whether hotkeys live globally or per-core, because mixing both leads to surprises. If you bind a global rewind toggle but a fast Genesis core struggles with rewind buffers, that single shortcut can tank performance. A better approach is to keep global chords for pause, menu, screenshot, and save state next, then enable rewind only on 8-bit cores that tolerate it. Test your RetroArch menu access in a random game session to ensure the chord is recognized while the core is under load. If input latency rises, consider disabling overlays or vibration feedback. This preserves responsiveness while sacrificing a bit of visual flair or haptic confirmation.

3) Place BIOS files correctly and verify detection

Correct BIOS placement determines whether cores boot at all or use high accuracy modes. On OnionOS, point RetroArch’s system directory to a single folder and drop required BIOS files there with exact filenames. For instance, the PlayStation core expects the correct region BIOS name and checksum, or it may fall back to slower HLE behavior with incompatibilities. The upside of a unified system folder is easier backups and fewer path mistakes. The downside is less separation if you test alternate BIOS variants. After copying files, open core information and look for a green status that each BIOS is present. If a file is not detected, check case sensitivity and hidden extensions that some OS tools add by default.

Verification beats guesswork, so test with a known title that requires a BIOS call. A small boot test confirms both filename and CRC assumptions without committing to a long play session. If you are unsure which consoles need firmware, consult a focused checklist on BIOS requirements and folder placement to avoid confusion, then re-scan core info. A practical cross-check is comparing the system directory tree to a simple map that explains where cores, system, saves, and states live so you do not misplace a file by one level. The tradeoff to all this diligence is a few extra minutes upfront, but it prevents repeated errors that cause black screens or muted audio later.

4) Select cores tuned for handheld performance limits

Core choice often matters more than any individual setting. Favor cores that are proven stable on Miyoo-level hardware over feature-packed builds that need headroom. As a rule, pick lighter cores for 16-bit and older systems and test latency with run-ahead disabled first. For example, a core with modest accuracy but fast audio sync may deliver a steadier 60 fps and clearer sound on OnionOS. The tradeoff is missing fringe features like cycle-accurate timing or shader chains. When you need run-ahead, try a single frame and measure whether input feels snappier without audio crackle. If you notice dips, prefer core-level latency controls or prefetch options rather than global changes that impact every system.

Document per-system winners so future installs are faster and more consistent. Keep notes on which cores resume cleanly from sleep and which struggle with savestates after long idle periods. A stable set might prioritize minimal overlays and integer scaling while reserving shader experiments for docked play. When exploring alternatives, make changes one at a time. That makes it obvious whether the core or the configuration caused the improvement. 5) Organize directories, playlists, and scanner rules

A deliberate directory layout makes playlists reliable and scanning predictable. Keep ROMs under a short path name and disable recursive scanning where possible to avoid picking up hacks or duplicates. As an example, use a top-level platform folder with clean file names, then build playlists from known-good databases rather than letting the scanner guess everything. The cost is a little manual effort up front, but you reduce false matches. For large libraries, favor curated playlists and manual additions where naming conventions differ from the database. When thumbnails matter, sync only small box art sets to conserve space on the SD card. If storage is tight, skip snapshots entirely and rely on text lists for fast navigation.

When a scan is unavoidable, use specific content directories and whitelist extensions that you actually use. This prevents RetroArch from trawling through saves or states by accident, which can stall the handheld. If a game fails to appear, check whether the core supports the file format or if the database recognizes your region’s naming. 6) Configure saves, states, and autosave to protect progress

Protecting progress starts with explicit save directories and conservative autosave behavior. Enable SRAM autosave on exit so progress persists even if you forget to save in-game, but avoid aggressive autosave intervals that flood writes during long sessions. For example, set autosave on content close with a short delay, then confirm that the handheld completes writes before power-off. The tradeoff is a slightly longer exit time after big sessions. Keep a limited number of savestate slots and rotate them to prevent corruption from repeating across multiple files. If you test shaders or run-ahead features, create a temporary profile so experiments do not contaminate your everyday save folder layout.

Regular backups are insurance against SD failures and update errors. Copy the saves, states, configs, and remaps folders before making major changes, and verify the backup on another device. To move progress to a larger card, use a migration guide focused on safe storage moves to ensure timestamps and directories remain intact. Consider disabling rewind for platforms where the buffer becomes large and causes sound stutter when the device sleeps. The small compromise in convenience prevents subtle desyncs that break savestates. After changing save paths, test with a small game to confirm in-game saves and a manual state both write to expected locations.

7) Create per-core overrides and game remaps cleanly

Overrides let you keep a clean global baseline while tailoring specifics where they matter. For instance, apply a fast shader only to a core that benefits and leave the global shader off. Save a core override when the improvement is universal across that system, and a content override when a single game needs special timing or aspect ratio. The tradeoff is more files to track, so label overrides clearly and avoid overlapping settings that fight each other. Before saving, reset to default in the submenu to ensure you are only recording the intended changes. This prevents surprise interactions like a global latency setting sticking to an override and producing stutter later.

Remaps are powerful for games with unusual control schemes. Build a per-game remap when the original layout clashes with your hotkeys, then store it alongside content for clarity. As an example, swap shoulder buttons for a racer that expects analog triggers, acknowledging that some cores will not translate every axis perfectly. Keep remaps minimal and document the reason in a short filename tag like racer-swap-shoulders. When going deeper, you can edit a compact config snippet to pin options that the UI hides. Frequently asked questions

Do I need shaders on OnionOS for good results?

No. Start with no shaders and integer scaling for clarity and performance. Add a lightweight shader per core only if you confirm steady frame pacing and readable text. Heavy chains can hurt battery life and responsiveness.

How can I tell if a BIOS file is recognized?

Open the core information screen and check the BIOS status list. A present file shows as detected by name. If it does not appear, confirm the exact filename, location in the system folder, and that the file is not incorrectly capitalized.

Why are my playlists missing some games?

The database may not match your region or file names. Try manual playlist entries for outliers and whitelist only the extensions you use when scanning. Confirm the core supports the file format before troubleshooting RetroArch.

Is rewind safe to enable on every core?

Not always. Rewind buffers increase memory and write activity which can cause audio stutter or slow menus on limited hardware. Enable it per core where performance remains stable and keep the buffer length small.

What should I back up before updating RetroArch?

Back up configs, remaps, overlays, saves, states, and playlists. Verify the backup by opening a save on another device. This protects your setup from update errors or SD card issues without relying on rollback features.
