Update Miyoo Firmware Without Losing Settings

By Austin Price • Published January 30, 2026

Goal focused updates prevent lost settings, broken inputs, and corrupted saves. This guide shows how to update Miyoo firmware while protecting configuration files, RetroArch profiles, and userdata through verifiable backups and clean restores. We assume a Windows, macOS, or Linux host with SD card access, plus a Miyoo device running Onion OS or MinUI. You will see why each step exists, where it can fail, and how to verify success before the first boot. By sequencing backup, firmware write, and validation, you reduce risk and preserve feel. The plan favors reversible actions and uses clear checkpoints so any misstep can be corrected without guesswork.

Key takeaways

  • Back up configs and saves with timestamps preserved before any update.
  • Verify firmware files with checksums to avoid silent corruption issues.
  • Restore only needed settings to prevent legacy conflicts after upgrades.
  • Boot once stock, then reintroduce tweaks incrementally with tests.
  • Create a rollback SD image when results deviate from expected behavior.

Plan the work

A deliberate plan cuts risk by isolating the settings you must keep from those you can safely rebuild. Start by listing exact directories to preserve, such as RetroArch configs, controller mappings, shader presets, BIOS files you legally own, and per game saves. On many setups that means backing up /Roms/, /Saves/, and OS specific config folders, while leaving system binaries to the new firmware. The tradeoff is that restoring too broadly can reintroduce stale files that cause crashes. Scoping the backup to user data and portable profiles strikes balance. Document where each file lives so you can verify placement after the update. This inventory becomes your checklist and prevents partial restores that feel fine initially but break later.

Check compatibility notes for the target firmware version and your current OS flavor. While Onion OS and MinUI share RetroArch underpinnings, they may change directory names, default cores, or content path rules between releases. When such shifts happen, blind restoration of old paths can make content invisible or produce missing core errors. Reading maintainers’ release notes and migration guidance reveals specific rename patterns or deprecated options. If details are unclear, default to restoring only saves and bios, then re apply non critical settings later. That sequencing ensures gameplay remains intact while you evaluate whether legacy options still map cleanly to the new structure.

Define checkpoints with objective pass or fail criteria before touching the SD. A useful sequence is pre image hash verification of the installer, post write file system integrity check, first boot without customizations, and a smoke test of three representative titles. Choose one light 8 bit, one mid 16 bit, and one heavier 32 bit game to cover varying core behavior. If any title exhibits audio crackle or inconsistent frame pacing, stop and validate restores rather than chasing symptoms. This gatekeeping limits scope creep when debugging and prevents compounding issues. Write the checkpoints down so you can quickly roll back to the last known good state if results deviate.

Prepare environment

Backups must preserve timestamps and permissions to keep profiles and saves predictable. A plain drag and drop sometimes drops dotfiles or modifies modified times, which complicates sync direction later. Using a tool like rsync or a verified disk imager protects metadata and lets you compare source and destination. The choice depends on your platform and need for full images versus file level control. Images are faster to revert but consume more space and take longer to validate. File syncs are granular and excellent for selective restores, but require careful include rules. For mixed workflows, capture one full image plus a targeted file backup for configs and saves.

Before writing new firmware to the SD card, verify the integrity of the downloaded archive. Many maintainers publish checksums you can validate locally. A mismatched hash indicates a damaged or tampered file, and installing it risks filesystem corruption or odd boot loops. If checksums are not available, perform a local hash before and after transfer to detect accidental truncation. Additionally, run a filesystem check on the SD card to catch latent errors that would otherwise surface post update. It is easier to replace a failing card now than to troubleshoot intermittent read errors after restoring data and settings.

Execute steps

Execution begins only after backups and integrity checks pass. Write the firmware to the SD using the maintainer’s recommended method, which often involves flashing an image or copying an OS folder to a fresh card. A fresh card reduces cross contamination from prior system files and makes rollback trivial by swapping cards. After writing, mount the card and confirm expected directory structure appears. If paths differ from your previous layout, note the changes. This observation informs selective restores and prevents copying settings into obsolete locations that the new firmware will ignore or that could cause boot errors.

Restore in layers to limit variables. First boot stock without any customizations to ensure the base firmware is stable. Navigate the UI, check battery reporting, test input mapping screens, and confirm sleep wake behavior. If anything misbehaves now, the issue lies in the firmware write or card health rather than your settings. Next, add only core user data: saves and BIOS files you legally own. Boot again and test two or three games to confirm performance is unchanged. Only then bring in configuration directories for RetroArch and OS tweaks. This progressive approach isolates problems and accelerates troubleshooting.

When restoring settings, prefer known good subsets over wholesale overwrites. For RetroArch, that could mean copying retroarch.cfg plus input profiles, but leaving global video drivers to the new defaults. For OS tunables, adopt small changes like animation toggles and power settings first. If you use Onion OS or MinUI, reapply their recommended defaults before layering personal tweaks. This keeps restores aligned with tested baselines.

Validate results

Validation should measure feel and correctness, not just boot success. Start with frame pacing and audio sync in titles you know well. A quick heuristic is to listen for steady audio under scrolling and watch for consistent sprite motion without micro stutter. If you observe anomalies, toggle the video sync setting inside RetroArch or switch audio latency by a small increment to compare. The goal is to confirm that the new firmware and restored settings produce equal or improved stability. If a change fixes one game but worsens another, capture that note and consider per content overrides instead of global toggles.

Confirm storage integrity to prevent slow creeping issues. Run a hash comparison on several large save files between your backup and restored copies. Differences without gameplay explainers suggest copy issues. Next, check free space and wear indicators if your card reader provides them. Low headroom increases fragmentation and can degrade load times. If space is tight, archive seldom played systems off card. For Onion OS or MinUI users, verify that curated directories appear in the UI and that content scans find expected titles. Missing entries often trace back to path changes or hidden characters introduced during extraction.

Cross check OS level toggles and UI performance. Disable heavy wallpapers and motion effects to remove overhead during testing. If menu responsiveness improves, keep visuals minimal and retest gameplay for any change. For a systematic rundown on balancing presentation with speed, see guidance on tuning Onion OS and MinUI for safe speed, which explains per game overrides and power options. While visual trims rarely affect in game performance directly, they do improve navigation and reduce CPU spikes during browsing. Keeping the interface lean shortens the observation loop when diagnosing other bottlenecks.

Troubleshoot and optimize

When issues surface, narrow the source by toggling one variable at a time. If a core crashes only after restoring configs, move the config aside and boot with defaults to see whether stability returns. If it does, reapply settings in small groups to identify the offender. Pay attention to video driver choices and threaded options, which can drift across versions. For handhelds with limited resources, threaded video might help menus but introduce timing noise in gameplay. That tradeoff is acceptable if you assign it to the menu only and keep gameplay paths clean through per content overrides.

Use a short decision table to resolve ambiguous flag behavior during backup and restore. For example, rsync --delete keeps destinations tidy by removing files absent from the source, but using it during the first restore may erase firmware created defaults you want to keep. In that case, skip deletion on the first pass and add it later when you are certain about directory mapping. Similarly, the archive flag preserves extended attributes that some hosts ignore. When attributes are not meaningful on your host filesystem, prioritizing timestamps is enough. The table below summarizes common choices and their preferred moments.

Keep optimizations reversible. When enabling performance modes or trimming background tasks, document the original values and test after each change. If battery life becomes erratic or sleep resumes inconsistently, roll back the latest tweak and retest. Quick start checklist

  1. Inventory what to keep: list saves, BIOS, and config folders to preserve.
  2. Verify the archive: compare checksums and re download if hashes disagree.
  3. Image a fresh card: write firmware to new media to simplify rollback.
  4. Backup with metadata: use rsync or imaging to keep timestamps intact.
  5. Boot stock once: test UI, sleep, and inputs before restoring anything.
  6. Restore in layers: add saves first, then configs, with tests after each stage.

Looking ahead

Sustained stability comes from habits that make future updates routine. Keep a dated backup after every major change so you can return to a known good state in minutes. Maintain a short change log of tweaks applied, firmware versions, and any anomalies observed during validation. That record speeds troubleshooting and informs whether to wait for a minor release before adopting new builds. As you refine your baseline, consider saving a pristine SD image that includes stock firmware plus your cleanest settings. Treat it as a golden master you can clone for experiments, then discard imperfect branches without hesitation. This rhythm keeps the handheld fast, predictable, and easy to recover.

Frequently asked questions

Will updating firmware erase my saves?

No. Saves are stored in user data folders. If you back up and restore those directories as directed, your save files remain intact. Always test a few titles after restoration to confirm paths match the new firmware layout.

Do I need to reconfigure RetroArch after the update?

Often only partially. Start with input profiles and essential options, leaving video and audio drivers at defaults until you validate stability. If behavior stays consistent, reapply remaining preferences gradually.

Is a full SD image better than file backups?

Each has benefits. A full image enables instant rollback by cloning, while file backups allow selective restores and smaller storage. Many users keep one image plus targeted copies of saves, BIOS, and configs.

What if the device boot loops after flashing?

First, reverify the firmware checksum and rewrite the card. Then try a different SD card or reader. If a stock boot fails, do not restore settings yet. Resolve the base issue before adding user data.

Can Onion OS or MinUI settings cause crashes after upgrading?

Yes. Legacy options or renamed paths can conflict with newer builds. Restore saves first, then reapply settings in small groups. If a specific option reintroduces issues, keep the new default or use per-game overrides.
