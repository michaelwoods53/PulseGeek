Toggle FPS Counter and Performance Overlay

By Jordan Kelly • Published January 14, 2026

Goal-oriented players benefit from an FPS counter and a lightweight performance overlay when tuning Onion OS. This guide shows how to reveal FPS, surface basic performance data, and verify changes without adding distraction or delay. Assumptions are a handheld running Onion OS with RetroArch-based cores available and at least one game loaded for testing. We focus on safe menu paths and reversible configuration so experiments never risk saves or core stability. You will toggle the overlay, confirm accurate FPS reporting, and record a baseline before making changes elsewhere. Along the way, you will learn simple checks that reveal whether FPS and performance indicators reflect real loads. By the end, you can enable the overlay quickly, understand what it is telling you, and disable it cleanly when you want a distraction-free session.

Key takeaways

  • Use RetroArch’s on-screen display to enable FPS with minimal noise.
  • Validate FPS by comparing steady scenes against known frame targets.
  • Keep overlays lightweight to avoid input lag and visual clutter.
  • Store changes in per-core configs to prevent unintended global shifts.
  • Toggle overlays off during long play to preserve battery life.

Plan the work

Start by defining what the FPS counter and performance overlay should answer for you. The overlay’s role is to reveal whether a scene maintains its target frame rate and how settings affect headroom. Pick two short test scenes per system, such as a static menu and a busy level intro, to bracket typical loads. Keep your goal practical, like confirming 60 or 50 FPS on supported systems, or stable 30 FPS on heavier ports. Decide whether you need only FPS or also CPU load indicators where available. Simpler is often better because extra metrics can distract and may not be comparable across cores. Finally, set a rule to capture a quick baseline before changing graphics or latency settings, which keeps retrofits measurable and reversible when results surprise you.

Establish a scope that aligns with Onion OS realities and the cores you use most. RetroArch-based cores expose a consistent Show Framerate setting, while standalone emulators may not present identical overlays. That means your plan should account for per-core differences and avoid assuming one menu path fits every system. When possible, prefer RetroArch cores for their predictable on-screen display, then note exceptions in your test list. This scoping reduces false troubleshooting later, like hunting for a missing overlay in a core that never supported it. Decide in advance whether to store settings globally or per core. Per-core storage keeps console-accurate expectations intact, while global toggles are faster when you benchmark multiple systems in one session.

Define your safety and accuracy checks to prevent misreads. An FPS counter can underreport during fast-forward, overstate during menu pauses, or lag if notification timing is throttled. Plan to verify FPS in normal runtime without fast-forward or rewind active, then repeat with fast-forward intentionally to understand how the overlay behaves. Note that high shader complexity and aggressive scaling tend to reduce headroom and can introduce stutter that the overlay might not sample perfectly. Your safety checklist should include confirming VSync state and ensuring no runahead changes were left enabled. These checks isolate the overlay’s report from confounders, so decisions about visuals or latency lean on trustworthy numbers rather than coincidences caused by background features.

Prepare environment

Begin with a clean state so toggles persist and do not corrupt other preferences. Back up your RetroArch configuration files and any per-core overrides to a safe folder before you touch display options. Onion OS uses RetroArch for many systems, so retaining a copy of retroarch.cfg and related overrides lets you roll back if OSD notifications become noisy. Perform a quick firmware and package update if your device supports it. Newer builds often fix OSD visibility bugs or menu path inconsistencies. Finally, ensure you have a save state free slot for your test game so you can resume scenes quickly. This preparation takes a few minutes yet prevents time-consuming rebuilds if a setting sticks globally or a core persists a noisy overlay you only wanted temporarily.

Next, create a repeatable test route that opens a title, reaches a stable scene, and then transitions into an action-heavy moment. Save states or in-game saves make this loop efficient for validation. Capture a simple log of what you changed in each pass, including whether VSync and shaders were active, because these change how the overlay reads. Consistency ensures that you attribute newfound stability or dips to the correct option rather than random load differences. If you rely on hotkeys, confirm that your input device maps do not assign conflicting shortcuts to the OSD or statistics toggles. Mis-mapped hotkeys can make overlays flicker or disappear, draining confidence in your checks and masking whether the FPS counter itself is functioning correctly.

Finally, confirm your RetroArch menus open inside content and that core options are accessible. Many OSD toggles are only visible when content is loaded, so testing them on an empty menu can be misleading. If you use standalone cores for some systems, note whether they provide their own FPS indicator and how it is enabled. When a standalone core lacks an overlay, plan to rely on RetroArch equivalents for comparable systems or test by proxy using similar loads. As a cross-check, verify the built-in notification visibility setting is enabled so FPS text can render. Without this, the FPS option is on but invisible, leading to confusing results where you think the feature is broken when it is simply hidden by a visibility rule.

Execute steps

Enable the FPS counter first, then layer minimal performance details to avoid clutter. In RetroArch, the Show Framerate option sits under Onscreen Display categories, and it requires notification visibility to be active. Toggle Show Framerate while content is running so you can see the result immediately. Keep font size modest for readability without obscuring HUD elements. If a core supports additional statistics, enable just one extra metric, such as frame time, so you can correlate dips with a clear signal. Overlays that show CPU percentages or thread load vary across cores and are not always equivalent. Limiting indicators makes it easier to compare results between systems, and it reduces the risk that the overlay itself affects responsiveness or introduces flicker in sprite-heavy scenes.

Store your toggle choice at the right scope to maintain predictable behavior. If your goal is benchmarking multiple consoles quickly, set Show Framerate globally and then apply a temporary per-core override to turn it off where it blocks UI elements. If you mostly play one system, save the FPS counter within that core’s override so other systems remain uncluttered. This separation prevents a common pitfall where enabling an overlay for one test leads to every game opening with persistent text. It also helps when troubleshooting because you can disable the override file to revert behavior instantly. Document where you saved the setting so you can repeat the path later without guessing whether a conflicting profile is modifying your choice.

When available, confirm the hotkey that quickly toggles notifications so you can hide or show the overlay mid-scene. This is useful for screenshots, visual comparisons, and sensitivity checks during latency tuning. Keep in mind that hotkeys vary by device mapping and may be disabled in handheld profiles. Test the shortcut in both the static scene and the action scene to ensure it functions consistently. If the toggle appears delayed, check for notification throttling and make sure fast-forward is off, because some builds deprioritize stats drawing during time scaling. Record the working hotkey in your notes along with the menu path, as this speeds future experiments and lets you switch the overlay quickly when teaching others or capturing before and after footage.

Validate results

Validation starts with a steady scene check that matches a known target for the system. For example, many classic consoles aim for 60 or 50 frames per second, while some titles lock to 30. Pause in a static menu and note whether the FPS counter holds constant for several seconds. Then transition to a busy moment and watch for dips or erratic swings. If numbers fluctuate without visible hitching, you may be reading notification refresh timing rather than true rendering cadence. Repeat with shaders off to see if the overlay stabilizes. This two-scene approach reveals whether the counter is meaningful and whether visual effects mask changes. A reliable overlay should correlate with what you feel on the controls during action.

Next, check whether the overlay introduces visual clutter or latency that could bias results. Large fonts, multiple metrics, or lower contrast backgrounds can cause readability issues that reduce the usefulness of quick checks. To test latency effects, perform a simple input timing routine such as jumping repeatedly and noting whether inputs feel delayed compared to overlay-off runs. While an FPS counter alone is lightweight, combined notifications and high shader loads can push weaker devices near limits. If input feels sticky when the overlay is on but fine when off, reduce the overlay to FPS only and simplify shader stacks. The aim is a diagnostic tool that remains invisible to the feel of play.

Finally, capture evidence so future tuning sessions begin with confidence. Take two short recordings or screenshots showing the FPS value in both test scenes, and store them alongside a text note describing shaders, scaling, and VSync state. This material gives you a baseline for future comparisons after you tweak cores, audio latency, or scaling methods. If you share profiles, it also lets others reproduce your setup. Aligning your overlay tests with good hygiene prevents mysterious regressions when you revisit the device later.

Troubleshoot and optimize

When the FPS display does not appear, check notification visibility first, then confirm you toggled Show Framerate inside running content. If text flashes briefly and vanishes, your hotkey mapping may be colliding with other shortcuts. Simplify the input profile or temporarily remove conflicting bindings, then retry. If the overlay appears but reads strangely during fast-forward, that is expected because stats often deprioritize under time scaling. Perform measurements at normal speed for accuracy. For standalone cores without overlays, rely on RetroArch equivalents for comparable systems or test with similar workloads to approximate behavior. If you suspect a build-specific quirk, update to a recent Onion OS release that includes RetroArch fixes for OSD refresh.

Reduce overlay noise by keeping only FPS visible and choosing a subtle position that avoids UI elements. Drop font size one notch and avoid bright colors that collide with game palettes. If shader stacks or scaling drive dips, you will find more headroom by choosing simpler filters. For a structured path to performance and visuals with stable controls, consult a guide detailing cores, controls, and visual tuning like the emulator settings overview for Onion OS. There you will see how per-core options, controller mappings, and scaling choices interact with responsiveness, which places your FPS overlay readings in a coherent context rather than isolated guesswork.

When you optimize for feel, latency and VSync matter as much as raw frames. If the overlay shows stable FPS yet inputs feel slow, investigate latency-oriented settings before pushing resolution or shaders. A concise list of hotkeys can help you toggle features quickly mid-test, so consider reviewing a reference like the essential Onion OS hotkeys and shortcuts to speed experiments. As you refine, remember to disable overlays for long sessions to conserve battery and reduce distraction. Keep one per-core profile with the overlay ready for diagnostics so you can switch into test mode quickly, then revert to a clean presentation when the device is tuned to your preference.

Key terms

  • Controller Layout — A mapping of inputs for a specific game.
  • Emulator Core — The component that emulates a specific system.
  • Frame Rate Cap — A set limit on frames per second to control performance and power.

Frequently asked questions

The FPS counter is enabled but I do not see numbers. What should I check?

Confirm Notification Visibility is on and test inside running content. If text still does not appear, reduce shaders and verify font color and size are readable against the game background.

Why does FPS fluctuate even in a static menu?

Minor drift can come from notification refresh timing or background tasks. Disable fast-forward, simplify shaders, and test again. If the value stabilizes during gameplay, the counter is working as expected.

Does the overlay affect input lag?

An FPS-only overlay is lightweight, but stacked notifications with heavy shaders can add delay. Compare jump timing with the overlay on and off. If input feels slower, trim to FPS only.

Should I save FPS settings globally or per core?

Use global for quick benchmarking across systems and per-core overrides where the overlay conflicts with UI. Per-core storage keeps other consoles clean during normal play.

How do I quickly hide the overlay during screenshots?

Assign and test a hotkey to toggle notification visibility. Ensure it does not conflict with other shortcuts. Verify it works consistently in both static and action scenes.
