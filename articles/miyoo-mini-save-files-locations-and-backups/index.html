Miyoo Mini Save Files: Locations and Backups

By Jeremy Crawford • Published February 24, 2026

Save files on the Miyoo Mini are straightforward once you understand where emulators write data, which formats matter, and how backups protect progress. This guide explains locations for common cores, how states differ from SRAM saves, and a simple approach to safe backups. Whether you use stock UI or Onion OS, you will find practical patterns that reduce confusion and prevent accidental loss.

Key takeaways

  • SRAM saves are smaller and safer to back up regularly.
  • Savestates are larger and version sensitive across emulator updates.
  • Onion OS keeps saves in tidy per-system folders for clarity.
  • Automate backups to off-device storage to prevent data loss.

Concepts and definitions

Save files fall into two main types on the Miyoo Mini: SRAM saves and savestates, and knowing the difference guides how you back them up. An SRAM save mirrors the original cartridge memory, typically with extensions like .sav or .srm, and the emulator writes it when you reach an in-game save point or exit cleanly. A savestate captures a full emulator snapshot, often .state, which restores exact execution, sound, and video timing. Savestates are larger and can break after emulator updates, so they are riskier as your only record. Favor SRAM saves for durability, use states for convenience, and back up both if storage allows. This division matters because recovery from firmware changes often succeeds with SRAM while a mismatched state might refuse to load.

Locations vary by firmware layout, but the pattern is consistent: each emulator core stores saves inside a system-specific directory that mirrors your ROM organization. On Onion OS, you typically see a Saves or SaveStates directory under each platform, while stock UI keeps related files near emulator data folders that align with system names. When browsing an SD card on a computer, follow your ROM path and look for associated save directories or similarly named subfolders. If you keep ROMs and saves on separate partitions, ensure the emulator is configured to point to the correct path. Mixing locations can cause progress to appear missing until the reference is fixed, which is confusing but easily reversible.

File extensions provide strong hints about what you can back up safely and what may be rebuilt. SRAM files like .sav or .srm are compact and portable between compatible cores, making them ideal for routine copies. Savestates such as .state or .st0 contain emulator RAM and device state, which can change format when a core updates, creating compatibility gaps. Some systems add memory-card style files like .mcr for PlayStation or .eep for certain Nintendo titles, which behave like SRAM and travel well between builds. A good rule is to keep all save formats, but treat SRAM-like files as your canonical records. That approach reduces surprises when switching cores or upgrading firmware later.

Stock UI and Onion OS store metadata differently, which affects how you search for saves and organize backups. Onion OS emphasizes clean separation with per-system directories that echo your ROM tree, simplifying routine backups and selective restores. Stock UI can be just as reliable, but paths may be less uniform across cores, which means taking a moment to note where each emulator writes is worth the effort. If you maintain playlists or favorites, remember these are metadata and not actual progress files, so they belong in your broader SD backup but do not replace saves. Keeping notes on paths for a few systems you play most reduces hunting and helps during SD migrations.

Frameworks and decision lenses

A simple framework balances safety, storage use, and time by classifying files as critical, convenience, or rebuildable. Critical includes SRAM and memory card files because they carry irreversible progress and remain small enough for daily copies. Convenience covers savestates, which you might keep weekly or for milestones to avoid ballooning storage. Rebuildable includes thumbnails and cache, which you can regenerate if lost, so they belong in periodic full-card images. This lens reduces indecision when space is tight or transfers are slow. By grouping files, you decide what to back up daily, what to rotate, and what to image less often. The result is a routine that survives firmware updates without hoarding every byte.

Path strategy is the next lens, because consistent directories make backups predictable and prevent partial restores. Keep ROMs and saves under a mirrored structure, ideally with per-system folders that match your library naming. On Onion OS this is usually the default arrangement, so your backup job can glob by system and capture both SRAM and states reliably. On stock UI, confirm where each core writes and align paths where possible to reduce exceptions. When upgrading SD size or migrating content, preserving this structure lets you copy or verify a subset like Game Boy only. That precision speeds transfers and reduces the risk of missing a save folder hidden elsewhere.

Automation closes the loop, and even a lightweight command offers better protection than manual copying. Use a tool that supports verification, timestamps, and incremental writes so unchanged files do not churn. On Windows, macOS, or Linux, choose platform-native options that you already trust rather than experimental utilities. A daily job for SRAM and a weekly job for savestates achieves a good balance for most players. If you frequently update firmware or switch cores, increase the savestate cadence to avoid version gaps. Always keep one off-device copy, such as a cloud folder or external drive, to isolate against SD corruption or accidental deletion.

You can use a minimal rsync example to copy only new or changed save files with verification. This pattern reads your SD card, writes to a dated folder, and preserves timestamps so later checks are faster. Expect it to skip identical files, reducing unnecessary wear on the card.

Looking ahead

Create a short note listing directory patterns like platform names, SRAM extensions, and where states live, then test a restore on one title. That dry run exposes path mistakes before you rely on the process. As your library grows, consider a monthly full SD image stored off-device for disaster recovery, while your daily or weekly job keeps day-to-day progress safe. This layered approach is resilient to firmware updates and SD replacements because it combines quick restores with an occasional complete snapshot.

Frequently asked questions

Where do Miyoo Mini SRAM saves usually live?

They are stored in per-system save folders that mirror your ROM organization. On Onion OS, look for Saves under each platform. On stock UI, paths vary by core, so note the directory the emulator uses.

Are savestates safe across emulator updates?

Not always. Savestates capture full runtime and can become incompatible after core updates. Keep them, but treat SRAM or memory card files as your reliable progress record.

What should I back up daily versus weekly?

Back up SRAM and memory card files daily because they are small and durable. Copy savestates weekly or at milestones to limit growth while keeping convenient resumes.

Do I need to back up thumbnails and playlists?

They are helpful but rebuildable. Include them in occasional full SD images, but prioritize saves for frequent backups to protect actual progress.

How do I verify a backup worked?

Use a tool with checksums or file size and timestamp verification, then test restoring one game’s save to confirm the path and format are recognized by the emulator.
