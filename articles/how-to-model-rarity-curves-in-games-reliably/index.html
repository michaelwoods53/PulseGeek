How to Model Rarity Curves in Games Reliably

By Ryan Turner • Published January 10, 2026

Modeling rarity curves in games is about translating intent into probabilities that behave under real play. You will define rarity tiers, shape curves, and verify supply over time so the model stays reliable under load. This guide assumes a spreadsheet or scripting environment and access to your loot table schema. We will frame goals first, then prepare parameters, execute simulations, and validate outcomes with clear criteria. Along the way we will surface tradeoffs between player motivation and economy health, so you can tune with confidence.

Key takeaways

  • Set explicit targets for supply, pacing, and rarity tier proportions.
  • Choose distributions that match desired progression shape and volatility.
  • Simulate sessions to check variance, pity effects, and expected value.
  • Validate economy impact with sinks, caps, and trade constraints.
  • Iterate using small parameter deltas and monitor player-facing metrics.

Plan the work

Start by declaring measurable goals so your rarity curve has a target to hit. Define tier proportions, session-level expected value, and acceptable variance bands for each rarity. For example, you might aim for epics to appear for 2 to 3 percent of loot events while mythics sit below 0.2 percent with a pity safeguard. Tie these to progression beats, like first epic by 6 to 10 hours for typical players. The tradeoff is clarity versus flexibility: tighter targets simplify validation but reduce room for live balance. Formal goals also allow you to detect drift when content scales or events change player behavior.

Capture constraints that shape what is feasible before choosing any distribution. Constraints include daily playtime ranges, currency sinks, item binding rules, and duplication handling. If items bind on pickup, you reduce secondary market pressure, which means more latitude on higher drop rates. If tradeable, you must control inflation through sinks or rotating availability. Edge cases like event-limited content spike demand and should be modeled separately with seasonal caps. Write constraints into a short spec so decisions later can reference why a parameter cannot exceed a threshold.

Map dependencies that affect curve stability over time, then set monitoring hooks for them. Dependencies include new content cadence, reward sources outside the table, and pity systems that adjust odds over streaks of attempts. A useful rule of thumb is to enumerate all sources and sinks that touch each rarity tier and estimate their throughput ranges. The tradeoff is modeling complexity versus operational clarity: adding every dependency makes simulations heavier, but missing a big faucet can invalidate results. Plan to review dependencies monthly and before major events to keep the curve aligned with reality.

Prepare environment

Choose tools that are easy to iterate in and auditable by design peers. A spreadsheet works for deterministic calculations and quick charts, while a short script in Python or JavaScript handles Monte Carlo simulation and pity counters. Set up version control for parameters in a simple text format like CSV or JSON so changes can be reviewed. The tradeoff is accessibility versus power: spreadsheets are approachable but brittle at scale, while scripts require discipline but enable reproducibility. Whichever you choose, lock a seed for random simulations to compare runs deterministically when tuning.

Define your rarity tiers, base probabilities, and any modifiers as explicit parameters. Include multipliers for streak protection, event bonuses, and player status where applicable. For clarity, keep all probabilities in one table and compute derived values like cumulative odds and expected attempts separately. A good practice is to store per-tier pity step size and cap so you can turn a dial rather than rewrite logic. Edge cases include mutually exclusive rewards or guaranteed pity thresholds that reset drop sequences; capture those rules as switch-like parameters to avoid hidden logic.

Compare candidate curve shapes before committing to one implementation, using a simple summary table. Exponential decay emphasizes long tails, while piecewise linear grants predictable progress. Logit transforms allow easy parameterization around mid probabilities without extreme tails. The key tradeoff is excitement spikes versus predictability. For cosmetics, bigger tails can sustain prestige, but for progression-critical items, smoother curves reduce frustration. Pick a default shape and keep one alternative ready for A and B testing so you can course correct without rewriting systems.

Execute steps

Implement your curve as a function that maps attempts to probabilities and supports modifiers. A practical approach is to compute a base probability per tier, then apply pity increments after each non-hit until a cap. For multi-tier tables, run a hierarchical selection: roll for the highest tier first, then descend, ensuring probabilities do not exceed 1. As a concrete scenario, set epic base at 0.025 with a pity increment of 0.002 per miss capped at 0.08. The tradeoff is code simplicity versus tuning granularity; a single pity layer is easy to reason about, while tier-specific adjustments add control at the cost of complexity. Prepare to log every roll with seed and parameters for repeatability.

Before the code, note the outcome you want from a simulation: distribution of drops per session, attempts to first hit, and long-run supply per active user. You will run Monte Carlo across session lengths that reflect typical and heavy play. Expect variance to be wide for top tiers; therefore compute percentiles and not just means. You will also test extreme cases like a week-long event bonus. The goal is to observe whether the curve respects constraints under realistic and boosted conditions, which prevents surprises during promotions or seasonal content.

Validate results

Interpret outputs against the goals you set, focusing on percentile behavior rather than averages alone. If average attempts to first epic meet target but the ninetieth percentile exceeds your frustration threshold, increase pity increments or introduce soft guarantees after N attempts. Validate per-user supply against expected sinks, like upgrade fusion or crafting inputs, to avoid inventory bloat. A limitation here is that simulated play patterns may not capture session clustering after updates; counter this by running a heavier burst scenario and observing whether the economy still drains surplus over a week.

Cross-check whether the curve maintains perceived value over time by measuring how often duplicates appear and whether they convert into sinks. If duplicates are common, ensure conversion yields meaningful progress rather than dust that accumulates without purpose. For tradeable items, examine whether your supply targets could provoke inflation or hoarding. Troubleshoot and optimize

When players report droughts, investigate variance before raising base rates. Inspect the distribution of attempts to first hit and compare to your ninetieth percentile goal. If the tail is too long, first increase pity increments or lower the guarantee threshold, then re-simulate. The benefit is targeted relief without inflating overall supply. A risk is creating timing exploitation where players sequence pulls to maximize pity. Mitigate by resetting pity on hit and capping the bonus tightly. Document the change with seed-reproducible runs to show the impact is within constraints.

When economy inflation appears, hunt for silent faucets and adjust sinks before nerfing drops. Review event bonuses, achievements, and unlisted sources that may bypass your main table. If needed, add a temporary sink such as a limited-time upgrade path that consumes duplicates. That context helps you choose whether to tighten caps, rotate availability, or shift items to bind on pickup to stabilize prices without eroding fun.

If frustration comes from streak volatility rather than scarcity, consider switching curve family. Piecewise linear with gentle pity creates smoother session experiences at the cost of less dramatic highs. Conversely, if prestige is fading, tilt toward an exponential top tail and limit guaranteed thresholds. Edge cases include event-limited items where forcing high prestige is part of the appeal; in those cases, separate their tables with strict caps and keep everyday rewards steady to avoid collateral churn. Always pair curve changes with messaging that explains intent to preserve player trust.

Looking ahead

Treat your rarity model as a living artifact with scheduled reviews tied to content releases. Establish a rhythm of pre-release simulations, post-release telemetry checks, and mid-season parameter nudges that stay within published bounds. A practical cadence is to revalidate after major updates and seasonal events, then compare percentile pacing to baselines. The tradeoff is operational overhead for stability; without proactive checks, small content shifts can compound into noticeable drift that players feel as unfairness. Put the monitoring dashboard in front of both design and economy owners to sustain shared accountability.

Develop lightweight experiments to test alternate shapes without destabilizing the live game. A and B test distributions behind the scenes where both variants respect the same constraints and rewards. Use near-indistinguishable rewards or cosmetic-only items to learn about player sentiment toward variance and pity. Keep sample sizes sufficient to detect meaningful differences, and predefine stop conditions to avoid experiment creep. The key is learning with minimal risk: experiments should illuminate sensitivity to parameters you intend to adjust, not explore speculative changes that would require systemic rewrites.

Codify your insights into a single source of truth so new team members ramp quickly. Store parameter histories, seed values used for validation runs, and links to telemetry views alongside a brief decision log. Each entry should capture the what, the why, and expected side effects, which forms a playbook for future tuning. When you add new tiers or bind rules, update the model and its documentation in the same commit to preserve traceability. Over time, this discipline reduces incidents and shortens recovery after missteps, keeping the rarity curve aligned with player expectations and economy goals.

Quick start checklist

  1. Set targets: define tier proportions, pacing goals, and variance limits.

  4. Check percentiles: compare first-hit P90 and long-run supply to goals.
  5. Probe events: test boosted scenarios to confirm constraints still hold.
  6. Tune safely: adjust pity before base odds and re-validate results.

Frequently asked questions

How do I pick between exponential and linear curves?

Choose exponential for prestige and scarcity, and piecewise linear for predictable progression. If volatility drives complaints, prefer linear with pity. If prestige feels diluted, lean exponential with caps and stricter guarantees.

What if pity makes items too common over time?

Lower the pity increment, reduce the cap, or reset pity more often. Validate with simulations focused on first-hit percentiles and per-user supply to confirm pacing stays within targets.

How many users should I simulate?

Use enough trials to stabilize tail estimates. Ten thousand user simulations often produce stable P90 metrics, but confirm by rerunning with different seeds and ensuring variance in outputs is acceptably small.

How do events with boosted odds affect balance?

Boosts raise short-term supply and can inflate markets. Model event windows separately with higher multipliers, then ensure sinks or cooldowns reclaim surplus within a defined period after the event ends.
