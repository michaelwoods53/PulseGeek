RetroArch Directories: Miyoo SD Card Structure Map

By Jared Butler • Published February 24, 2026

The fastest way to stabilize RetroArch on a Miyoo handheld is to understand how its directories map onto the SD card. Knowing where configs, cores, and BIOS files live prevents guesswork and protects saves when you experiment. This article untangles the SD card structure that RetroArch expects, explains why some paths change across OnionOS or MinUI, and shows practical verification steps. We focus on repeatable patterns, not firmware trivia, so you can adapt when directory names shift. Along the way, you will see how playlists relate to content folders and what defaults secure performance. If you are migrating from another device, the same principles apply, though paths differ. With a clear map, you avoid broken detection, misplaced assets, and slow rescans of large libraries.

Key takeaways

  • RetroArch relies on predictable SD card paths for configs and cores.
  • Place BIOS in the system directory and verify per core needs.
  • Keep playlists relative to content to avoid broken lookups later.
  • Use one writable config root to protect remaps and overlays.
  • Confirm path casing and slashes to prevent silent loading failures.

Concepts and definitions

Start with a clear model of RetroArch directories on the SD card because terminology drives decisions later. The config root holds global settings, core options, overlays, and remaps, which RetroArch reads on boot then writes during gameplay. A separate system folder stores BIOS files that some cores require to boot or to provide full functionality. Cores themselves are shared libraries in a dedicated folder that must match your device architecture. Finally, playlists describe where games reside and which core to open for each entry. Treat each path as a contract and you gain predictable saves and faster loading. If the model blurs, symptoms appear as missing thumbnails, disabled achievements, or unexpected core fallbacks. Consistency across these directories reduces scanning time and keeps content portable.

Think in terms of path stability across Miyoo variants because OS flavors introduce small but impactful changes. OnionOS and MinUI often keep RetroArch’s high level structure but may store the config root and system folders under different top level directories. That means an upgrade or SD migration can silently break references when the expected path changes. Use a principle of relative addressing for playlists and thumbnails so content follows its directory without rewriting entries. When a path must be absolute, place it under a known writable location that persists across updates. This separation between stable content and movable configuration makes rolling back safer. If your handheld supports multiple environments, keep separate config roots to avoid cross pollution, and label them clearly.

Define content adjacency early to protect performance and storage hygiene. Content adjacency means placing ROMs, thumbnails, and playlists in a coherent structure where each playlist references nearby files rather than scattering assets across the SD card. For example, storing platform folders under a unified content parent cuts traversal time and keeps scanning predictable. The tradeoff is that large thumbnail sets can inflate that same area, so consider splitting thumbnails to a dedicated cache folder if your OS allows. Always ensure the content parent resides on a partition with enough space for growth, since resizing SD partitions later risks data. Adjacency also aids backup by letting you copy one directory tree and recreate the library on a new card with minimal edits.

Frameworks and decision lenses

Use a stability first lens when deciding where RetroArch writes and reads on a Miyoo SD card. Prioritize one writable config root that survives OS updates, then place cores in a directory the frontend never rewrites. This reduces churn and prevents option files from reverting. Next, treat the system directory for BIOS as read only once populated to avoid accidental edits. For playlists and thumbnails, favor relative paths anchored to the content parent to keep portability. A counterexample is placing playlists inside a volatile theme directory, which risks deletion during updates. Finally, impose a simple naming scheme across platforms to minimize typos. The stability first lens makes updates predictable while preserving flexibility for OnionOS or MinUI path conventions.

Adopt a verification lens that asks how you will prove every directory works before loading your full library. Create a small test set per platform, scan with known good core mappings, then inspect generated files under the config root. Check that BIOS are detected by opening a core information screen and verifying firmware status. If a core still fails, the issue is often casing differences or trailing spaces in filenames. An additional check is using a different skin or theme to confirm overlay and shader paths resolve as expected. The tradeoff is time spent on test runs, but this prevents mass rescans and broken playlists. Verification becomes your safety net whenever you upgrade or move to a new SD card.

Choose a portability lens when planning for future SD migrations or OS swaps. Keep content and playlists in a self contained subtree that you can move without touching RetroArch’s core configs. Store core specific options under the config root so they travel together during backup. When an OS enforces a different top level, retain the same substructure beneath it so relative references still align. This design avoids fragile absolute paths and eases restores. If you later switch to OnionOS configuration, the content subtree can remain unchanged. Pitfalls, limitations, and edge cases

One frequent failure is placing BIOS outside the system directory then assuming the core will search multiple locations. Many cores only check the configured system path and require exact filenames that match internal lookups. A practical safeguard is to keep a per core checklist naming required firmware files and to verify status under core information before full scans. If a BIOS is optional, the game may boot with degraded features, masking the issue until later. Another trap is mixing region variants that require different BIOS revisions. Keep a regional tag in filenames and document the mapping. When in doubt, laboratory test a small sample first to isolate missing firmware from content mismatches.

Case sensitivity and path separators cause silent breaks when moving between environments. Some Miyoo builds treat the filesystem as case sensitive, so playlists that reference Tetris.GB will not match tetris.gb. Standardize on lowercase filenames for content, BIOS, and playlist entries, then enforce with a bulk rename pass. Similarly, inserting stray spaces or unusual Unicode characters in directory names can block detection even when the file exists. A safe rule is limiting names to letters, numbers, underscores, and hyphens. The tradeoff is losing decorative naming, but you gain reliable scanning and fewer surprises. When problems persist, inspect a failing playlist entry’s full path and compare it character by character to the real file.

Migrating to a new SD card often breaks saves and states because the config root moves while content paths remain absolute. To reduce this risk, commit to relative paths in playlists and verify save directories under the config root are writable. Back up config, remaps, and overlays together to preserve controller tweaks. When you update RetroArch itself, avoid overwriting cores blindly because mismatched versions can change required BIOS names. Always test with a small set before reimporting the full library.

Frequently asked questions

Where should BIOS files go on a Miyoo SD card?

Place BIOS in the RetroArch system directory and ensure filenames match each core’s expected names. Confirm detection in the core information screen before scanning a full library.

Do playlists need absolute paths or relative paths?

Use relative paths anchored to your content parent so playlists survive SD moves and OS layout changes. Absolute paths are brittle and often break after updates or migrations.

Why are some ROMs not detected even though files exist?

Common causes are filename casing differences, stray spaces, or unsupported formats for the scanner. Standardize lowercase names and check scanner compatibility for each platform before large imports.

Which folders should I back up before updating RetroArch?

Back up the config directory, the system BIOS folder, and all playlists. Include remaps and overlays to preserve controller tweaks and visual settings across updates.

Can I share one config root across OnionOS and MinUI?

It is safer to keep separate config roots for each environment to prevent conflicts. Label them clearly and maintain the same content subtree so playlists remain portable.
