Fix Frame Pacing on Miyoo Mini RetroArch

By Austin Price • Updated January 4, 2026

Stutter and crackle rarely come from one setting, so the fix mixes frame pacing, vsync behavior, and audio sync inside RetroArch on Miyoo Mini. This guide shows how to connect decisions across video timing and buffering so you can fix frame pacing without chasing myths. You will map symptoms to root causes, then run short tests that confirm improvements before you lock changes in place.

Key takeaways

  • Match video refresh, vsync mode, and audio timing to prevent jitter.
  • Prefer stable sync first, then trim latency with small frame delay.
  • Use audio buffering ranges that avoid crackle during load spikes.
  • Test one change at a time and confirm with repeatable scenes.
  • Disable features that add latency before enabling runahead carefully.

Foundations

Reliable pacing starts with understanding how frame time, vsync, and audio sync interact on the Miyoo Mini within RetroArch. A consistent frame time means each frame arrives near the target interval, like 16.67 ms for 60 Hz systems, which stabilizes input feel and scrolling. Vsync aligns presentation with the display’s refresh, preventing tearing while adding a small queue that can raise latency. Audio sync locks the mixer to video timing, avoiding drift but exposing slow frames as crackle if buffers are too small. The tradeoff is predictable: prioritizing perfect visual sync can surface audio issues when a core occasionally misses deadlines, while larger buffers hide variation but dull input response. The goal is to establish a baseline where visual cadence and audio playback remain coherent under minor load changes.

Choosing a timing authority is the next decision. When the core reliably meets the target rate, allowing vsync to drive presentation yields smoothness without aggressive buffering. If the core varies, audio as a soft anchor can mask small jitter, but pushing audio to dominate will amplify delay and may desynchronize cues. On Miyoo hardware, most 8 and 16 bit cores meet 60 fps comfortably, so a video led approach with modest audio buffers works well. For heavier cores or shaders, you may prefer conservative audio settings while trimming visual overhead. The key is avoiding dueling clocks where video chases one cadence and audio another. Align both toward the same nominal refresh, then allow only minimal elasticity to absorb short stalls.

Decision criteria should be explicit to avoid guesswork. First, lock display refresh expectations to the core’s native rate, commonly 60 or 50 Hz, to reduce resampling and phase errors. Second, confirm that frame delivery variance remains under a threshold you can tolerate, typically within a couple of milliseconds on average scenes. Third, size audio buffering so a single late frame does not cause pops, yet does not create a perceptible input echo. Finally, audit any latency features like runahead and frame delay in isolation before combining them, since their interaction can turn minor jitter into obvious stutter. Using these steps creates a repeatable baseline and ensures any tuning has a measurable purpose rather than cosmetic change.

Core practices

Start with safe defaults that privilege stability, then reduce latency incrementally. Enable vsync to prevent tearing and set a conservative audio buffer that avoids crackle during brief load spikes. With that baseline, introduce a small frame delay to trim latency without courting missed frames, typically stepping in tiny increments while watching for judder. Avoid large frame delay values unless you are certain the core has headroom across heavy scenes. Keep shaders minimal or use presets known not to introduce stalls, since their cost comes in bursts that defeat steady pacing. This method front loads smoothness, confirms health with a test scene, then cautiously reclaims responsiveness so you do not trade one artifact for another.

When determining sync options, match the core’s native rate and keep FPS limiting consistent with vsync. If you cap frames at a value different from display refresh, you risk beat frequency patterns that show as periodic stutter. A good pattern is to let vsync govern presentation and use the FPS limiter only to prevent runaway rendering in menus or when a core runs faster than real time. Pair that with audio timing that follows video, not the other way around, to avoid dueling control loops. If you encounter slight drift, gentle resampling settings can maintain alignment, but heavy resampling taxes CPU and can introduce its own rhythm errors, which undermines the goal.

Latency features require restraint. Runahead can improve button feel by predicting one or more frames, yet it raises CPU demand and can expose stutter if performance is marginal. Frame delay defers work within a frame to reduce total latency but narrows the margin for error under bursts. A practical rule is to test these independently, then combine at low values only if the core holds 60 fps under worst case effects and sprite loads. If you notice inputs feel great but scrolling hiccups occasionally, dial back frame delay first before reducing runahead, since slicing the safety margin often triggers visible pacing faults sooner than prediction does. Keep measurements grounded in the same test scene to preserve comparability.

Pitfalls and edge cases

Mismatched limits create rhythmic stutter that no single setting can hide. If FPS limiting and display refresh differ, you will see periodic hitching even with vsync enabled. Likewise, using an aggressive frame delay on a core that barely meets 60 fps guarantees dropped frames during particle effects or parallax scenes. The mitigation is to align caps with refresh and back off delay until your worst case scene holds steady. Another subtle issue arises when audio resampling is set to a heavy mode that oscillates CPU use, producing cycle to cycle variance that turns into visible jitter. Choose moderate resampling and verify consistency with a busy soundtrack that overlaps action.

Feature interactions often explain puzzling behavior. Runahead can feel excellent in static tests but fall apart when combined with rewind or frequent autosaves because extra memory and I/O increase variance. Overlays and heavy shaders introduce intermittent work that defeats even perfect vsync, since bursts land at frame boundaries and cause late presents. If you suspect either factor, test with overlays off and use minimal shader presets, then restore features one at a time. For more detail on keeping visuals sleek without hiccups, review which aesthetics are safe using the advice on picking shaders that run well and the notes on overlay performance impact.

Audio crackle that appears only during loading is not always a pure audio problem. Storage stalls can momentarily starve both the video and audio paths, surfacing as pops followed by a hitch. Increasing the audio buffer slightly may hide the symptom, but it can also mask a deeper I/O issue. Clean your storage, keep cores and assets on faster media when possible, and avoid frequent autosaves during high action. Frequently asked questions

Should FPS limiter be used with vsync on Miyoo Mini?

Yes, but align the limit with the display refresh so it does not fight vsync. Use it to prevent runaway frames in menus, not to set a different cadence than the screen.

Why does audio crackle even when the frame rate shows 60?

Short stalls from storage or CPU spikes can starve the audio path while the average frame rate stays near 60. Increase audio buffer slightly and reduce costly features that cause bursty work.

Is runahead safe on all RetroArch cores?

No. It depends on headroom and the core. Start with one frame, verify stability in heavy scenes, and avoid combining with rewind or frequent autosaves that add variance.

What is a good starting value for frame delay?

Begin at a very low value and step up one notch at a time. Stop increasing when you notice a hitch in a demanding scroll scene, then back off to the previous stable setting.

Do shaders always cause stutter on Miyoo Mini?

No, but heavier presets can introduce bursty work that breaks pacing. Favor lightweight options and recheck scrolling stability whenever you apply visual effects.
