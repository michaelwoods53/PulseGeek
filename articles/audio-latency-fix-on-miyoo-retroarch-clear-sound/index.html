Audio Latency Fix on Miyoo RetroArch: Clear Sound

By Jared Butler • Published February 2, 2026

Here is a focused path to fix audio latency on Miyoo RetroArch without trading stability. The goal is responsive sound that matches input and video timing across common 8 and 16 bit cores. You will adjust audio buffering, verify sync behavior, and test repeatable scenarios so changes stick across sessions. This guide assumes a stock Miyoo handheld running RetroArch with write access to configuration files and the on device menu. If you use per core overrides, we will call that out when the behavior differs. Expect to weigh small latency reductions against potential crackle when hardware limits are reached, then choose the setting that keeps sound clear during real gameplay.

Key takeaways

  • Start with audio buffer changes before touching advanced sync options.
  • Lower buffers gradually, watching for crackle during real gameplay.
  • Match video sync choices to core speed to avoid drift.
  • Validate with repeatable actions and short A B comparisons.
  • Save per core overrides when one system behaves differently.

Plan the work

Begin with a clear target: reduce audio delay until button presses feel immediate while keeping sound free of artifacts. Define a measurable test like jumping in a platformer while listening for attack sounds that align with the sprite movement. Plan to change one variable at a time because buffers, sync, and runahead can interact. Use a notebook or a notes app to capture starting values and outcomes so you can revert quickly. A good rule is to compare three settings at most in one pass to prevent decision fatigue. Expect some cores to require per core overrides due to different mixing pipelines, so document which systems respond best to the same baseline.

Document constraints up front to avoid chasing impossible targets on limited hardware. The Miyoo CPU and audio path can handle modest buffers, but extremely low values often cause pops during busy scenes. Treat audio latency as a continuum rather than on or off: shaving 10 to 20 milliseconds often feels meaningful without risking crackle. Plan for tradeoffs with features like rewind or heavy shaders because they consume headroom that audio relies on. The plan should favor stability first, then iterate downward on buffering until artifacts appear, finally backing off slightly to lock a safe setting for daily play.

Define your measurement method so results are comparable across sessions. Use in game cues that repeat predictably, such as menu blips or a character landing sound. Record short video clips with the handheld mic if possible, then compare frame by frame to see relative shifts after each change. When testing, keep the same core and ROM to control variables. If you do explore broader tuning like VSync timing later, schedule it after you finish audio buffer work to avoid confounding. This methodical approach helps you return to a known good configuration even if a later change introduces drift or delay.

Prepare environment

Create a safety net before changing anything so you can revert instantly if audio degrades. Back up your global RetroArch config and any per core overrides by copying the configuration directory to a separate folder on the SD card. Inside RetroArch, confirm that autosave and rewind are disabled during testing because both can exaggerate audio stutter when CPU load spikes. Set a sensible baseline buffer to start, aiming for a middle value that avoids obvious delay without inviting pops. This baseline becomes your control for comparisons later. If you use overlays or filters, temporarily disable them so audio results reflect buffer changes rather than GPU load interactions.

Verify that your firmware and RetroArch build are consistent with known stable behavior. While we avoid version claims, matching your setup to commonly referenced defaults helps reduce surprises. Ensure audio driver is set to the platform recommended option within RetroArch because switching drivers can change latency behavior and break comparisons. Check that audio rate matches core expectations to prevent resampling overhead that can cause subtle delay. If you rely on runahead to reduce input feel, note its current value but leave it unchanged until the buffer passes are complete. This keeps your experiments focused on one audio path variable at a time.

Execute steps

Start from your baseline and reduce the audio buffer until minor artifacts appear during fast scenes, then step back to the last clean value. Next, confirm that audio sync remains enabled so the mixer follows the main timing reference rather than drifting under load. If you still hear lag, evaluate whether frame delay or video sync choices are over constraining timing. Each change should be followed by the same jump or menu click test to keep your comparisons valid. Save the working value globally, then consider overrides for specific cores that tolerated lower buffers.

Integrate video timing checks when audio tuning alone cannot remove a lingering offset. If the core runs slightly under full speed, forcing tight sync often exposes stutter and crackle because audio cannot keep up. In that case, increase the buffer modestly and relieve pressure by avoiding heavy overlays or extra effects. When sound is clean but still feels late, try decreasing frame delay in small increments to free up headroom for audio scheduling. The goal is a workable balance where audio arrives promptly without periodic pops during scrolling or heavy sprite layers. Keep your notes detailed to avoid returning to ineffective combinations later.

If the improvement is minor, prefer the simpler path with runahead disabled to reduce maintenance across games. Validate results

The better configuration should feel consistently snappier without producing random ticks. If you hear intermittent issues at the lower buffer, treat that as a fail and keep the safer value.

It helps to define simple thresholds that guide decisions without stopwatch precision. For example, if the lower buffer introduces even rare pops during scrolling, prefer the next size up that stays silent in all tested scenes. Record the exact values you settle on and whether they are global or per core so you can reproduce them after updates. Disable them temporarily and retest the same scene. If noise vanishes, re introduce features one at a time until the culprit appears. For cores that run slightly under speed, tightening sync usually worsens stutter, so relax timing or increase the buffer a notch. If gameplay remains clean but feels late, consider small decreases to frame delay or a one frame runahead trade, always verifying stability with your repeatable test.

Address drift or gradual desync by aligning video timing with what the core can reliably deliver. If you notice audio sliding out of step during long sessions, the mixer may be compensating for sustained timing differences. In such cases, a modest buffer increase stabilizes playback, and avoiding heavy visual features prevents oscillation between catch up and slow down. Frequently asked questions

How low can I set the audio buffer before risking crackle?

There is no universal safe number. Lower gradually and test a busy scene. If pops appear, raise the buffer to the last clean setting and keep it for that core.

Should I turn off audio sync to reduce delay?

No. Disabling audio sync can cause drift or periodic stutter. Keep audio sync on and adjust buffer size or frame delay for safer latency improvements.

Why does audio crackle only during scrolling or heavy sprites?

Those scenes increase CPU and timing pressure. The buffer becomes too small under load. Raise it slightly or disable features like overlays that add overhead.

Do per core overrides help with inconsistent results?

Yes. Different cores mix audio differently. Save stable values per core when a system needs a higher buffer or different frame delay than your global default.

Can runahead cause audio artifacts at otherwise clean settings?

It can. One extra frame may be fine while two causes pops in heavy scenes. If crackle appears, reduce runahead or increase the buffer slightly and retest.
