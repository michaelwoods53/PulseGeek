Overlays and Bezels Setup for Onion OS: Retro Style

By Jordan Kelly • Published January 12, 2026

Authentic overlays and bezels in Onion OS add retro personality while preserving clarity. This guide targets handheld users who want a tasteful style without introducing artifacts or dropped frames. We assume RetroArch-based emulation on Onion OS, a microSD with typical folder layout, and basic familiarity with copying files. You will plan bezel sources, prepare directory paths, execute per-core or per-game configuration, and validate the viewport against your screen. Along the way, you will learn how to check performance impact and resolve common conflicts between overlays and shaders. If you need a broader setup refresher, see the end-to-end playbook later linked in context.

Key takeaways

  • Use per-game overlay configs to avoid global scaling conflicts.
  • Keep overlay PNGs and CFGs in short, stable folder paths.
  • Match aspect ratio and viewport to bezel art dimensions.
  • Test performance with frame pacing, not only average FPS.
  • Prefer light shaders when combined with detailed bezels.

Plan the work

Start by defining the visual goal, because overlays and bezels should support playability first. Decide whether you want system-themed frames, subtle mats, or full cabinet borders. A light bezel that leaves a generous viewport often keeps text readable on small screens, while ornate frames can shrink the playable area. As a rule of thumb, target a viewport that is at least 85 percent of the screen height on Game Boy and 70 to 80 percent on systems with wider aspect ratios. Consider battery impact if you stack shaders with high resolution artwork. Your plan should note which cores will use shared art and which titles demand bespoke frames.

Select trustworthy sources for bezel packs, because inconsistent naming and scaling cause wasted effort. When curating art, prefer PNG files that match the handheld’s resolution or exactly double, since the GPU scales cleanly from those ratios. For example, a 640 by 480 bezel scales predictably to 320 by 240 or 960 by 720 viewports. Avoid artwork that includes embedded transparency gradients heavier than necessary, because they can trigger color banding on lower quality panels. Confirm license terms if sharing screenshots. Lastly, collect a small set first and pilot on three systems before expanding the library to avoid refactoring later.

Decide where settings will live before copying anything, since Onion OS merges RetroArch configs with its own file structure. Use a simple folder map with short names to minimize path errors. Keep core-wide overlays in a shared directory and game-specific items in per-title subfolders. Document a naming scheme like console_title_variant to keep lookup predictable. This plan simplifies future updates or rollbacks when a bezel conflicts with shaders. Also note whether your goal requires integer scaling, because that choice affects viewport math and frame spacing. With a clear plan, the remaining steps become mechanical rather than exploratory guesswork.

Prepare environment

Create a clean directory structure, because predictable paths make overlays load reliably. On your Onion OS microSD, establish an overlays root with subfolders for systems and games, keeping names short like gb, snes, and psx. Place PNG artwork and matching CFG files together to avoid relative path ambiguity. Test a small batch by browsing with RetroArch’s file picker to ensure the files are visible and names are readable on device. If your firmware supports both SD1 and SD2, note which card holds assets, since cross-card references often fail when cards are remounted. Keep a backup copy of the overlays folder on a computer for quick recovery.

Confirm prerequisites inside RetroArch, because overlays require specific toggles. In Settings, ensure Onscreen Overlay is enabled and the Overlay Opacity is set to 1.0 for fully opaque art or a slightly lower value if you want translucent mats. Check that Display is set to the device’s native aspect ratio and that integer scaling is either on or off intentionally. As a rule, turn integer scaling on for pixel-perfect handheld systems and off for 3D consoles with odd ratios. Capture a configuration snapshot using Save Current Configuration so you can revert if changes create conflicts later.

Document essential paths and labels in a simple table, because short references prevent typos during step execution. The table should capture the overlays root, a core-wide directory, and a sample game path that you will test. Verify on the device that these paths match the actual folder tree. When multiple variants exist, prefer the one with fewer segments. This deliberate preparation reduces trial-and-error when you switch cores or replicate settings for another handheld. If you update Onion OS later, recheck that the mount points and folder names remain consistent, since firmware updates sometimes alter default paths subtly.

Execute steps

Apply overlays in a controlled sequence, because changing multiple variables hides the cause of visual issues. Start with a per-core configuration that sets a neutral bezel, then override specific games that benefit from tailored art. This hierarchy keeps global behavior predictable. Use core overrides when a whole system shares the same bezel geometry and reserve game overrides for special cases like vertical shooters. Maintain opacity and scale defaults on the core level, then modify viewport at the game level if artwork requires different margins. This approach keeps troubleshooting simple when a future shader update or driver change nudges how RetroArch interprets scaling.

Use a minimal configuration file to bind an image overlay and tune its position, because explicit keys reduce surprises. The essential directives include overlay path, full-screen flag, and overlay opacity. For games that need tighter control, provide viewport settings that match the art’s inner frame. Place the CFG next to the PNG so the path remains short and portable across cards. Expect minor differences between cores regarding how they respect integer scale and viewport coordinates. When a core ignores a specific option, favor RetroArch’s global Display settings for the generic behavior and keep the per-game file focused on art selection.

Before saving, preview with the fast load workflow to confirm naming and alignment. Open the game, load the overlay through the Quick Menu, and verify that button labels or art edges do not encroach on the active display. If text appears clipped, gently reduce bezel thickness by choosing a variant or adjusting the viewport. If performance seems jittery during scrolling scenes, temporarily disable heavy shaders and confirm frame pacing improves. This preview step saves time before writing configs to disk. After validation, save the core override or game override so the overlay persists the next time you launch the title.

Validate results

Verify visual fit first, because an accurate viewport makes gameplay readable. Load a test title with text at the edges, like a JRPG menu or platformer HUD, and confirm nothing is clipped by the bezel. Inspect corners for any misaligned transparency that would distract during motion. A quick rule is that the inner frame should sit at least 4 pixels outside active text in all four corners on low resolution screens. If the handheld supports integer scaling, switch it on and recheck, since integer math can nudge the viewport. Document any exceptions where the art’s geometry forces a different margin.

Assess performance with frame pacing, not just average frame rate, since overlays reveal micro-stutter. Use RetroArch’s built-in statistics overlay or frame time graph if available. Walk through a scrolling scene and watch for consistent frame intervals without spikes. If stutter appears with heavy shaders, pause the shader or swap to a lighter preset while keeping the bezel in place. On many handhelds, a simple LCD or CRT mask paired with a bezel maintains smooth motion. Note that large PNGs increase memory use during transitions between games, so stagger testing rather than quickly cycling through dozens of titles.

Confirm persistence across launches, because a configuration that only works once cannot be trusted. Close the game, return to the menu, and relaunch several times. Power cycle the device to catch any mount timing issues that break file paths. If the bezel fails to load on the second launch, examine whether the override was saved at the game level or unintentionally saved globally. Save a backup of the working CFG, then replicate the steps on a second system to ensure the process is repeatable. This discipline prevents regressions when you later add new art or update Onion OS.

Troubleshoot and optimize

Diagnose load failures by isolating the weakest link, because multiple moving parts can hide the cause. If an overlay does not appear, first set a known-good PNG in the same folder to confirm the path. Next, remove viewport keys from the CFG to test a simpler baseline, since some cores ignore custom viewport fields. Finally, check character encoding for file names if you used special characters. A short name without spaces often resolves unexpected parse errors. When nothing loads, temporarily move the overlay folder to a shallower path and retest to rule out length limits in the filesystem.

Mitigate performance issues by prioritizing what matters for the system in question. On 8 and 16 bit consoles, integer scaling plus a bezel typically produces crisp pixels with minimal overhead. On 32 bit and early 3D systems, choose lighter shaders or none, because texture effects combined with high resolution bezels can strain handheld GPUs. If the screen flickers when toggling overlays, disable threaded video as a test and re-evaluate frame pacing. When battery life dips quickly, compare overlay plus light shader versus overlay alone and pick the option that keeps your play session length within your comfort range.

Streamline management for the long term by aligning overlays with other settings you maintain. If you keep per-core controller mappings, consider using the same folder structure and naming scheme for overlays to reduce mental overhead. Maintain a small change log noting which titles use custom viewports. When updating Onion OS, retest a handful of representative games to catch regressions early.
