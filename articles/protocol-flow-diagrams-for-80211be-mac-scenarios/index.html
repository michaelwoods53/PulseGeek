Protocol Flow Diagrams for 802.11be MAC

By Allison Grant • Published January 9, 2026

These scenarios focus on protocol flow diagrams that engineers can implement without guesswork. Each sequence highlights 802.11be MAC behaviors that shape latency, reliability, and airtime fairness. We selected flows that recur in production designs and interoperability events, emphasizing message order, state variables, and timing windows that affect outcomes.

Key takeaways

  • Draw flows around state changes, not just message order or labels.
  • Time windows and backoffs dominate reliability in dense deployments.
  • MLO coordination shifts decisions from per link to per station.
  • Use explicit fallbacks when puncturing or HARQ edge cases appear.
  • Annotate RU choices with buffer and channel observations for clarity.

1) MLO association and setup

Start with the claim that Multi Link Operation association works best when the flow treats per link authentication and capability exchange as one coordinated station state machine. In practice, the non-AP MLD discovers one or more AP links, chooses a primary link for initial authentication, then advertises its multi-link capabilities alongside per link parameters. An effective diagram shows Probe, Authentication, and Association frames with EHT capability elements, then a follow up exchange that binds secondary links under the same MLD. For example, the STA might complete association on 5 GHz, then add a 6 GHz link using the announced profiles. The tradeoff is complexity in timer handling, because retries on one link should not collapse progress on another unless the policy defines a station-wide failure.

Flow clarity improves when you annotate which timers are link local and which are MLD wide, because 802.11be introduces decisions that cross link boundaries at the MAC. A helpful depiction flags association response waits, capability negotiation windows, and when security key material becomes usable across links after successful exchange. Consider a scenario where the AP advertises different channel widths per link, prompting the STA to select a narrower secondary based on observed occupancy. The benefit is flexible throughput, yet the cost is additional state to track per link QoS and aggregation limits. Edge cases include secondary link setup lagging the primary, where your diagram should show buffered frames waiting for multi-link acknowledgement policies to activate.

Section highlights

  • Model link local and MLD wide timers to avoid hidden deadlocks.
  • Show secondary link add flows when primary completes capability exchange.

2) EMLSR link switching with buffers

EMLSR, or Enhanced Multi Link Single Radio, hinges on the claim that switching policy must align with buffered data and observed channel access, not only beacon schedules. A practical diagram starts with a STA that has a single RF chain and two potential links, one busy and one lightly loaded. It shows the STA evaluating backoff counters, queued ACs, and expected TWT opportunities, then executing a timed switch to the alternate link to transmit a burst. For example, the STA might finish a short transmit opportunity on Link A, then switch to Link B for higher priority voice frames. The tradeoff is switch latency that can erode gains if bursts are too small, so the flow should mark minimum dwell times and conditions that cancel a planned switch.

Annotate buffer thresholds and AC priorities to explain how the MAC decides that a switch will improve service. A good rule is to require a predicted airtime benefit exceeding the cost of switch time plus recontention, which your diagram can express as a decision gate. Consider a case where simultaneous interference reduces the clear channel assessment pass rate on both links, making a switch ineffective. Your flow should show the fallback to holding traffic for the next scheduled opportunity or aggregating frames for better efficiency. The limitation is that EMLSR cannot transmit on both links at once, so your depiction must show the radio’s busy periods and how they interact with per link NAV.

Section highlights

  • Gate switches on airtime benefit exceeding switch and contention cost.
  • Mark radio busy windows and per link NAV to bound concurrency.

3) HARQ feedback cycle and retry

The central claim is that Hybrid ARQ in 802.11be demands tight feedback windows that your diagram must render explicitly, because timing governs whether to send a new transmission or an incremental redundancy block. A concrete example shows a data PPDU followed by a short interframe space, then HARQ feedback with a bitmap that maps to data units. The transmitter either proceeds with fresh data on success or schedules a coded retransmission on failure, possibly on another link if policy allows. The tradeoff is contention overhead versus recovery speed, so the flow should include a branch where the sender waits for a clearer slot to avoid repeated collisions, balanced against stalling upper layer queues if the pause is too long.

Annotate sequence numbers, HARQ process identifiers, and the lifetime of soft combining buffers at the receiver, since those state variables drive correctness. Consider a case where the receiver’s soft buffer is near capacity due to multiple failing units, which forces the sender to limit simultaneous HARQ processes or switch to a simpler ARQ to free memory. The limitation is hardware budget, because extensive soft combining requires more memory and energy. A useful flow adds a timer that bounds feedback wait and a condition that triggers fall back to classic block acknowledgment when the environment is unstable. This clarity helps reconcile throughput targets with predictable latency.

4) OFDMA and multi‑RU scheduling

The claim is that accurate OFDMA flows must reflect how the AP allocates multiple Resource Units based on buffer status reports, channel sounding, and fairness constraints. A useful diagram begins with trigger frame transmission, followed by per STA RU grants that may combine noncontiguous blocks to fit diverse queue lengths. For example, one STA with bursty video could receive two small RUs while a latency sensitive voice STA gets a single narrow RU soonest. The tradeoff is fragmentation complexity against aggregate efficiency, so the flow should show when the AP coalesces grants to reduce overhead and when it splits them to meet deadlines. Include a branch for grant rejection if the STA reports limits that would make multi RU inefficient.

Show how the AP updates its scheduling state after receiving UL data, including acknowledgments and any buffer status feedback used to refine the next trigger. A practical rule is to annotate RU choices with observed PER and recent CQI-like measures from sounding, highlighting when the AP avoids assigning fragile widths on noisy channels. Consider a scenario where one STA repeatedly fails on a wide RU, prompting a narrower RU on the next trigger to stabilize throughput. The drawback is reduced peak capacity for that STA. Your diagram should indicate where fairness metrics apply to prevent a single device from monopolizing contiguous RUs across intervals.

Section highlights

  • Tie RU grants to buffers, sounding data, and fairness constraints.
  • Depict adaptive width changes following repeated error patterns.

5) TWT negotiation for latency

The claim is that Target Wake Time flows are most effective when the STA states latency and duty cycle needs as negotiable parameters, not fixed intervals. A concrete flow shows the STA proposing a wake schedule with tolerances, the AP responding with an adjusted plan that aligns multiple STAs to reduce contention, and both parties confirming the schedule. For instance, a headset might request 10 ms wake opportunities with a small jitter allowance to protect audio. The tradeoff is that tighter windows reduce energy flexibility and increase coordination cost. Your diagram should mark how deviations are handled, including a recovery path where missed wake opportunities trigger a resync exchange without discarding the overall plan.

Include annotations for coexistence with MLO, because a multi link STA could prefer waking on a link with better reliability at that moment. A realistic example is a device that pins TWT to the 5 GHz link during busy hours, then shifts to 6 GHz when occupancy drops. The benefit is predictable latency, yet the cost is the need to synchronize across links to avoid overlapping commitments that exceed the device’s radio capabilities. Edge cases include clock drift accumulating between schedule confirmations, which your flow should capture with a guard that bounds tolerated skew and initiates a light weight correction before the next window.

Section highlights

  • Negotiate windows with tolerances and resync when drift exceeds bounds.
  • Coordinate TWT with MLO to respect single radio constraints.

6) Channel puncturing and fallback

The claim is that diagrams for punctured transmissions must present the decision path from channel observation to mask selection, because incorrect assumptions about usable subchannels produce avoidable retries. A practical flow begins with sensing, then generates a puncture bitmap that avoids busy portions while keeping aggregation sizes efficient. For example, the AP could prefer a 160 MHz channel with one puncture over dropping to 80 MHz, provided impairments are localized. The tradeoff is between maintaining large aggregates and risking collisions on partially busy spectrum. Your diagram should show when the MAC reduces MCS or drops channel width entirely, and how that decision interacts with ongoing HARQ processes or pending QoS traffic across links.

Include a branch for multi link awareness, where one link cannot support the desired puncture pattern but another can, prompting a quick policy decision to move traffic to the healthier link. A helpful example is a burst that shifts to the secondary link with a cleaner 80 MHz path rather than persisting with a problematic wide channel. The limitation is switching overhead and potential misalignment with TWT windows. Also note regulatory constraints on allowable puncture patterns, which the flow should model as a pre condition that filters candidate masks before selection. This structure keeps the diagram honest and reduces undefined behaviors in edge cases.

Frequently asked questions

Do I need exact timers in my protocol flow diagrams?

Include timers when behavior changes at a boundary such as feedback windows, backoff limits, or resynchronization points. Omit low level constants if your goal is logic clarity and annotate ranges instead to avoid misleading precision.

How should I show multi link decisions with a single radio?

Depict radio busy intervals and per link NAV, then add a decision gate that checks whether a switch yields net airtime gain after accounting for switch latency and recontention. This clarifies why some switches do not happen.

What is the best way to visualize HARQ feedback?

Use a compact sequence that marks data PPDUs, feedback bitmaps, and the branch between new data and incremental redundancy. Add labels for process identifiers and buffer lifetimes to ground retransmission choices in visible state.

When should I diagram puncturing versus width fallback?

Show puncturing when sensing indicates localized interference and the policy tolerates fragmentation. Prefer width fallback when errors repeat or when regulatory masks disallow useful patterns. Add a guard that caps repeated failures.
