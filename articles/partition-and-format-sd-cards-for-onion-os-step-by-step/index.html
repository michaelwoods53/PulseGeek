Partition and Format SD Cards for Onion OS

By Jordan Kelly • Published February 23, 2026

You will partition and format SD cards for Onion OS in a repeatable way that avoids data loss. The workflow covers partition selection, filesystem format, and verification with common tools across Windows, macOS, and Linux. We assume you have administrator rights, a card reader, and a working backup of any existing data. If you are unsure about card quality, start with authenticity tests to avoid counterfeit media issues. When the plan is clear, format the card using FAT32 or exFAT based on device support, then validate with a read back check. Along the way, we will note recovery branches if something deviates, so you can correct safely without guessing.

Key takeaways

  • Choose FAT32 for widest device compatibility and reliable small file handling.
  • Use exFAT when large ROM files are required and the device supports it.
  • Confirm partition alignment and capacity to prevent performance penalties.
  • Validate formats with read back checks before loading Onion OS content.
  • Keep one primary partition and avoid hidden leftovers from old layouts.

Plan the work

Start by defining the goal and constraints so partition and format choices match Onion OS behavior and device limits. Write down capacity needs, expected ROM sizes, and whether the handheld prefers FAT32 or exFAT. As a rule of thumb, FAT32 offers broad compatibility and stable small file handling, while exFAT supports files larger than 4 GB. Consider backup windows and recovery needs, since a validated image saves time if a later step fails. A quick risk review catches common problems like counterfeit cards that report fake capacity, mismatched alignment, or hidden partitions from prior uses. By clarifying these boundary conditions, you select tooling and a sequence that reduces surprises and speeds validation.

Next, inventory your tools and confirm administrative access on the workstation used to prepare the SD card. On Windows, Disk Management and a minimal PowerShell are often sufficient, though third party formatters help with large FAT32 volumes. On macOS, Disk Utility and diskutil provide reliable control, while Linux users can rely on lsblk, parted, and mkfs utilities. Test the card reader, since flaky adapters cause intermittent write failures that look like filesystem errors. Plan checkpoints after major actions such as partition creation and format. Each checkpoint should include a mount, a tiny copy test, and a safe eject to surface errors early. This reduces downstream troubleshooting time meaningfully.

Finally, decide on partition layout and naming before touching the disk. Most Onion OS setups work best with a single primary partition labeled clearly, which simplifies mounting and directory mapping. Multi partition layouts add complexity and seldom improve performance on handheld devices. If you anticipate expanding later, prioritize reliable cloning and resizing techniques over pre carving multiple partitions. Establish a consistent volume label, for example ONIONOS, to make selection unambiguous on any host OS. Define a rollback strategy that includes reinitializing the partition table and reformatting from scratch if verification fails. This blueprint makes the upcoming steps mechanical instead of exploratory.

Prepare environment

Confirm the SD card is genuine and healthy before partitioning, because formatting cannot fix counterfeit capacity. Use write and verify utilities that detect over reported size by cycling through the full card. On Windows, H2testw is a common option, while Linux and macOS users can use F3 write and F3 read. Expect this to take time proportional to capacity, and ensure your reader stays cool to avoid throttling. If errors appear, do not proceed, since Onion OS will inherit corruption. When the card passes, gather OS native tools for partition management. This upfront validation prevents chasing phantom filesystem issues caused by defective media.

Map the device identifier carefully, since selecting the wrong disk wipes unrelated data. On Windows, verify the removable disk number in Disk Management and cross check with size. On macOS, run diskutil list to identify the disk like disk2 based on capacity and media name, then unmount partitions. On Linux, run lsblk or sudo fdisk -l to confirm the target device path such as /dev/sdb. Create a note with the exact identifier and keep it visible. As a safety rule, disconnect external drives that are not part of this operation to reduce selection risk. This identification step is the most effective damage prevention move you can make.

Decide the filesystem now so you install only what you need. For FAT32 on large cards, Windows built in formatting can be limited, prompting use of a trusted formatter that supports volumes above 32 GB. macOS and Linux can create FAT32 at large sizes via diskutil and mkfs.vfat respectively. If exFAT is acceptable for your device, modern Windows and macOS can format natively, and Linux can use mkfs.exfat after installing exfatprogs. Keep capitalization and labels consistent, since Onion OS directory mapping can be sensitive to expected folder names. Prepare an empty folder to stage test files used during validation to catch early write errors.

Execute steps

Follow a precise sequence to create one primary partition and format it for Onion OS. The single primary partition reduces mount ambiguity and supports predictable directory structures. Start by reinitializing the partition table only if you intend to wipe the card completely, since this removes hidden leftovers from other uses. Next, create a partition aligned to megabyte boundaries, which most modern tools do by default to maintain performance. Choose the filesystem based on earlier planning, then apply a stable volume label. After formatting, mount the volume and confirm the label appears as expected. Small write tests and an immediate safe eject surface issues early, avoiding corrupted first loads.

Windows, macOS, and Linux each expose similar operations with different commands and dialogs. Windows Disk Management lets you delete existing volumes, create a new simple volume, and format it with allocation unit sizes left at defaults unless workload requires change. macOS Disk Utility provides Erase and Partition tabs that map cleanly to the same outcome when you select GUID or MBR as needed. On Linux, parted or fdisk works with mkfs utilities for final formatting. If a step contradicts earlier planning or yields an error, stop and validate the device path again before proceeding. That pause prevents accidental modification to unrelated storage.

If your build requires larger ROM files, exFAT can be the right choice when your device supports it. Otherwise, FAT32 remains a safe baseline that reduces compatibility issues across firmware versions. Allocation unit size can influence performance with many small files, yet extreme values risk wasted space or compatibility trouble. Default cluster sizes usually provide balanced results for Onion OS libraries. After formatting, create the expected folder scaffolding and verify names match case and spelling guidelines established by the platform. Keep a short log of each action taken with timestamps. This narrows diagnostics later if performance or mounting behaves unexpectedly.

Validate results

Validation confirms the partition and format are correct and that writes persist without silent errors. Begin by remounting the card and checking the volume label and available capacity match expectations within a small tolerance. Create a test folder and copy a handful of files representing typical ROM sizes, then unmount and remount to ensure persistence. Run an optional read back verification tool to catch bit errors that a casual copy would miss. If a mismatch appears, rerun checks on the card reader and try a different USB port to exclude host issues. This disciplined confirmation avoids discovering corruption only after loading large libraries.

Next, verify directory names and case sensitivity where relevant, since Onion OS expects specific folder structures for content and artwork. On Windows and macOS default setups, case is generally insensitive at the filesystem level, but naming consistency still matters for portability. Linux environments can enforce case sensitivity that may reveal subtle errors in folder naming. Place a small text file that records the formatting choices and date in the root of the card, which aids future maintenance. If a device fails to recognize the volume, check whether the handheld expects MBR versus GPT and adjust accordingly, as some devices favor MBR for external SDs.

Finally, perform a quick throughput check to ensure the card and reader combination meets reasonable performance for your workload. Copy a set of medium sized files and time the transfer to estimate write speed. While absolute numbers vary by brand and class, you mainly care about consistency and absence of retries. If the speed is erratic, suspect the reader or a background process on the host. Swap adapters to isolate hardware problems before blaming the card itself. This pragmatic performance sanity check protects you from slowdowns that appear only after the library grows and indexing becomes more demanding.

Troubleshoot and optimize

When validation fails, narrow the issue by separating media, reader, and host causes. If files disappear after remounting, suspect a fake capacity card that wraps writes, and rerun authenticity tests immediately. If the card mounts read only unexpectedly, check the physical lock switch and examine the system log for filesystem errors. Recreate the partition table, then format again if metadata looks inconsistent. Always re verify the device path before destructive actions. Keep recovery attempts logged, including exact commands and timestamps, to maintain a clear audit trail. This structure prevents compounding mistakes and shortens the path to a clean, reliable Onion OS volume.

Some devices require specific partition schemes or filesystem variants for stable operation. If your handheld shows the card but will not read content, try switching from GPT to MBR to satisfy legacy expectations. Conversely, if resizing or very large capacities are involved, GPT can be safer for metadata integrity. For filesystem choice, stay with FAT32 when compatibility problems appear with exFAT drivers. If the device supports exFAT and you need large files, confirm the firmware version and update notes before adopting it. These targeted adjustments balance reliability with feature needs without resorting to unnecessary complexity.

Frequently asked questions

Should I use FAT32 or exFAT for Onion OS?

Use FAT32 for widest compatibility and predictable behavior with many small files. Choose exFAT only if you need files larger than 4 GB and your device firmware supports it reliably.

Why does my SD card show the wrong capacity after formatting?

Hidden or leftover partitions can misreport space. Recreate the partition table, then create a single primary partition and format. If the issue persists, test for counterfeit capacity with a full write and verify pass.

My card mounts read only. What should I check first?

Check the physical lock switch on the SD adapter, verify filesystem integrity with host tools, and inspect system logs. If errors persist, back up what you can, recreate the partition table, and reformat.

Do I need MBR or GPT for handheld devices?

Many handhelds prefer MBR for removable media. If your device does not recognize the card with GPT, reinitialize as MBR and format again. Use GPT when capacities are very large and the device supports it.

What allocation unit size should I pick?

Defaults are typically balanced for Onion OS. Larger clusters can help with large sequential files, but may waste space. If you are unsure, leave the default and validate performance with a small copy test.
