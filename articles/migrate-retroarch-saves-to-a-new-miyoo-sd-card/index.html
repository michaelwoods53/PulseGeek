Migrate RetroArch Saves to a New Miyoo SD Card

By Jared Butler • Published February 18, 2026

Moving RetroArch saves to a new Miyoo SD card succeeds when you identify paths, copy data with integrity, and validate on-device. This how-to assumes a working Miyoo Mini or Mini Plus, a formatted replacement microSD, and either a PC or Mac with card reader access. The process focuses on migrating save files, save states, and core options while preserving directory structure. We will compare copy methods, show practical verification, and cover pitfalls like mismatched cores or system folder paths. If you already installed RetroArch fresh on the new card, these steps still apply and simply overlay your existing structure. By the end, your games should load the same progress with consistent cores and options.

Key takeaways

  • Identify RetroArch save, state, and system paths before copying anything.
  • Copy with verification to preserve timestamps and avoid corrupted saves.
  • Keep core versions aligned so save states remain compatible across cards.
  • Validate in-game progress and thumbnails after the transfer completes.
  • Back up the old SD card first to hedge against copy errors.

Plan the work

Start by defining the exact scope of your migration, because RetroArch stores progress across several directories that behave differently. Saves are the canonical battery-backed files, often with .srm or core-specific formats, and live under a configured savefile path. Save states are snapshots tied to a core version and sit under a savestate path. The system directory may include BIOS files required for certain cores to boot. A good rule is to migrate all three to avoid hidden mismatches. The tradeoff is storage usage on the new card, but these folders are usually small compared to ROMs. Mapping paths up front prevents partial transfers that load a game but fail when states or BIOS are missing.

Document current directory paths on the old card before you remove it, since Miyoo setups vary across OnionOS, MinUI, or stock environments. RetroArch typically nests under /RetroArch/ with subfolders like /saves, /states, and /system. Some builds consolidate content under /AppData/RetroArch/ or redirect in retroarch.cfg via the savefile_directory and savestate_directory keys. Record these values to prevent guessing later. If any custom overrides exist, such as per-core options or remaps, include those folders in your plan. The downside to copying extra config files is potential preference drift, but it is safer than losing mappings you rely on.

Choose copy tooling that can preserve filenames, timestamps, and hierarchy, because saves must align with ROM names. GUI drag-and-drop works, but it rarely verifies integrity. Tools like rsync or verified copy utilities give confidence by rechecking bytes and can retry transient read errors. The tradeoff is a slight learning curve and a need to watch flags. If you only have a single card reader, plan a staging folder on your computer to hold the transfer between cards. This adds one more step, yet it ensures you do not accidentally mix old and new SD structures during the move.

Prepare environment

Create a clean baseline by backing up the old SD card in full, then test the new card for reliability. Backups hedge against accidental deletions or partial copies, which are easy to miss with similarly named files. Card health matters because write errors can corrupt states in silent ways. Many users format to FAT32 for compatibility and use a reasonable allocation size to balance performance. As you stage folders on your desktop, mirror the RetroArch structure exactly, including case-sensitive names where applicable. This avoids future path confusion when you place the data on the new card. The small cost is a few extra minutes now, but it saves hours of debugging later.

Confirm RetroArch paths and set expectations for file counts before copying so you can spot anomalies. On your old card, note the number of files in /RetroArch/saves and /RetroArch/states, and whether /RetroArch/system has BIOS files you rely on. If your setup uses an alternative path through retroarch.cfg, read those keys in a text editor to verify directories. Consider copying per-core option files under /RetroArch/config/ because mismatched options can affect controller behavior and video timing. The tradeoff is copying preferences you no longer use, but you can prune safely after validation. If you are migrating between OnionOS and MinUI, verify where each expects RetroArch content directories to live.

If you have a Unix-like shell on your PC or Mac, a verified transfer reduces risk by preserving attributes while reporting progress. The following example uses rsync to copy staged folders from the desktop to the mounted new card. It keeps permissions, timestamps, and directory structure. Adjust paths to match your environment and ensure the destination mount point is correct to avoid overwriting unrelated data.

Execute steps

Execute the migration in a controlled sequence that minimizes surprise outcomes and preserves working states. Always copy saves first, then states, then the system folder. This order ensures that the most stable progress files are present even if you pause mid-transfer. When using drag-and-drop, copy one directory at a time and confirm the file count afterward. If you use command-line tools, run a dry run if available to preview changes. The tradeoff with single directory copies is extra time, but it is easier to pinpoint errors. As an added safeguard, keep the old card untouched until you boot the new one and verify progress loads correctly.

Choose between direct card-to-card transfers or staging through your computer based on available hardware and risk tolerance. Direct transfers are faster when you have two readers, but errors on one card can propagate to the other without you noticing. Staging to the desktop gives you a clean inspection point where you can compare file counts and look at timestamps. Verification matters more than speed because corrupted save states often only fail when a core loads them. If you expect significant data, verify free space on the new card to avoid partial copies, as full cards can produce incomplete folders that appear normal at a glance.

Validate results

Validation begins with in-game checks because a copied file that never loads is not a success. Boot the Miyoo with the new card, start RetroArch, and open a title with a known save point. If the game uses battery saves, confirm the checkpoint appears as expected. For state-based progress, load at least one recent save state and confirm the scene, audio, and inputs feel normal. A good heuristic is to test one title per system you care about. The small time investment ensures any core-specific subtlety is caught early. If anything fails to load, back out rather than overwriting files with new saves that mask the original issue.

Next, verify core alignment because save states are tightly coupled to the core and sometimes its version. If you changed cores during the move, states may refuse to load or crash. Check which core the content uses in the RetroArch menu, then open the same core on the new card. If cores differ, consider updating the old card’s core to match first, then recopy states. The alternative is to intentionally abandon incompatible states and rely on battery saves, but that sacrifices recent progress. Keeping core versions synchronized avoids this tradeoff.

Finally, review metadata and peripherals that hint at successful migration. Thumbnails loading in playlists, achievements systems toggled as before, and controller remaps that still apply are strong indicators your config folders made the trip. If thumbnails are missing, the issue is usually path configuration rather than data loss. Check RetroArch settings for thumbnails_directory and ensure it matches your new structure. While not essential to gameplay, these details confirm that your environment is consistent. Investigating small mismatches now prevents confusion later when a feature quietly fails.

Troubleshoot and optimize

When saves are missing in-game, the most common cause is a path mismatch between your new card and RetroArch settings. Inspect savefile_directory and savestate_directory in retroarch.cfg to confirm they point to the expected folders. If they are blank, RetroArch may default to content directories. A quick test is to create a new save in-game and then search the card for the newest file to locate where it wrote. The downside is that this generates fresh data, so do not overwrite existing files. Once you find the path, move your migrated files there or update the configuration to the structure you prefer.

Crashing when loading a state usually indicates a core or option incompatibility. Check that the core installed on the new card matches the one used previously, including any major version differences. Some cores change state formats across versions. If the new card shipped with different defaults, reinstall matching cores or update the old card first, then remigrate the states. As a contingency, rely on battery saves for titles where states are unstable. This avoids repeated crashes but may cost some recent progress, which is a reasonable tradeoff for stability.

To optimize for future moves, standardize directory layouts and keep a small text file listing your core versions, key options, and path settings. This snapshot helps you reproduce a known-good environment on new storage quickly. Periodic backups of /RetroArch plus a short test plan reduce anxiety when hardware fails. Looking ahead

Building a repeatable migration habit keeps RetroArch dependable across storage changes. The same steps that protected your progress today will serve when you expand capacity or move between OnionOS and MinUI. Keep a backup routine, track paths, and confirm core versions before copying states. Those three habits reduce risk more than any single tool. If you standardize directory names and avoid ad hoc overrides, your environment remains predictable. Consistency matters because it lets you diagnose failures quickly and restore from known-good folders without hunting for hidden settings.

As you refine your setup, save a minimal checklist with file counts for saves, states, and the system folder, plus notes on which titles rely on states versus battery-backed progress. This small inventory helps you prioritize validation and detect missing items early. If you plan to reorganize ROMs or playlists, stage that work after migration so you isolate changes. The tradeoff is a second pass of housekeeping, but it prevents conflating file moves with path configuration issues. Keeping changes separate simplifies troubleshooting and makes the next migration straightforward.
