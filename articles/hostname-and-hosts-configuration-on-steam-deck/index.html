Hostname and Hosts Configuration on Steam Deck

By Brittany Coleman • Published March 11, 2026

Hostname choices shape how your Steam Deck introduces itself on networks, while entries in hosts determine quick name lookups without DNS. These two tools feel simple, yet they influence SSH trust, file sharing, and scripts that expect stable names. By understanding hostnamectl, /etc/hostname, and /etc/hosts together, you will avoid nagging prompts and brittle shortcuts that fail at the worst moment. I will guide you through the concepts, offer decision lenses for safe changes, and share scenarios that echo what you hear from your fans and see on your router. The goal is confidence, so your Deck responds with a steady name and neighbors resolve it predictably.

Key takeaways

  • Use hostnamectl to set a persistent system hostname on Steam Deck.
  • Keep /etc/hosts minimal, mapping 127.0.0.1 to the primary name.
  • Avoid frequent renames that trigger SSH host key change warnings.
  • Pick a lowercase short hostname; prefer hyphens over spaces or dots.
  • Add local aliases only when a tool cannot query DNS reliably.

Concepts and definitions

Hostname is the system’s personal name, and Steam Deck sets it persistently through systemd hostnamed with a value stored in /etc/hostname. This label shows in prompts, SSH banners, and router client lists, making it a key identity marker. Hosts, by contrast, is a static map where IP addresses resolve to names without touching DNS, usually binding 127.0.0.1 to your primary hostname and localhost. On Steam Deck, hostnamectl updates the persistent name and signals running services, while hosts provides quick overrides for lookups. The distinction matters because one defines identity and the other fakes resolution. Overusing hosts can mask real DNS issues, while ignoring hostname stability invites SSH trust churn and confusing log entries.

Fully qualified domain name, or FQDN, combines a hostname with a domain, such as deck01.lan, and differs from the short label like deck01. Steam Deck does not require an FQDN to operate, yet some services present prettier logs or self URLs when one exists. If your home router advertises mDNS, the Deck will often answer as deck01.local without editing hosts. However, relying on an FQDN you do not control can break when routers reboot or firmware changes behavior. Prefer a stable short name and let DNS or mDNS fill in the rest when available. Use hosts entries only to paper over a specific tool that cannot resolve local names reliably.

System identity leaks into daily touchpoints like your Konsole prompt, SSH fingerprints, and SCP paths. A good hostname reads easily, survives reimages, and matches labels in Desktop Mode so confusion does not creep in during quick fixes. In that spirit, choose lowercase, avoid spaces, and use hyphens for readability. Mapping the chosen name in hosts to 127.0.0.1 keeps local services honest about who they contacted. Overly clever names tend to age poorly, and renames ripple outward. If you need to work across profiles or backups, keep the same base hostname and only vary a suffix for clarity. This pattern limits unexpected SSH host key changes and reduces retries.

Frameworks and decision lenses

Start with the stability lens: if a change will alter SSH prompts or router records, default to keeping the current hostname. On Steam Deck, hostnamectl writes a persistent name, so frequent tweaks force clients to reconcile fingerprints again. A solid rule of thumb is to change identity only when hardware meaningfully shifts or your naming scheme evolves. When you must rename, schedule it before new automation or backups so fingerprints align with the first connection. The tradeoff is living briefly with an outdated label, which is harmless compared to scattered host key warnings. Stability first prevents status noise that hides real faults.

Use the resolution lens for hosts edits: add entries only to fix a concrete lookup that fails repeatedly and cannot be corrected upstream. For example, a tool that does not speak mDNS might stumble over deck01.local, so adding a static map for the Steam Deck’s own short name helps that workflow. The risk is staleness, since IPs shift on DHCP networks and static hosts lines do not follow changes. To reduce breakage, limit entries to loopback mappings and avoid embedding dynamic LAN addresses. When you need local reachability, prefer DHCP reservations on your router to lock the IP, then let DNS or mDNS advertise the name consistently.

Choose formatting with the clarity lens: pick a short hostname like deck-play or steamdeck-01 and avoid dots unless you own the domain. Dots imply an FQDN, and some tools treat the first dot as domain separation, which can mislead logging and scripts. Hyphens improve readability and survive shell completion gracefully. On the hosts side, keep one line that maps 127.0.0.1 to the chosen hostname and localhost, and optionally 127.0.1.1 to the hostname when older utilities expect it. The tradeoff is redundancy, but it preserves compatibility without complex DNS setups. Clarity pays off every time you open Konsole and spot the prompt at a glance.

Pitfalls, limitations, and edge cases

Rapid renames create SSH host key warnings that look like security problems even when expected. Each time the Deck’s hostname changes, clients may store a new key under the updated label and compare it against the old entry. This mismatch triggers rekey prompts that users learn to ignore, which dulls real alarms. Limit renames, and when necessary, plan a controlled first connection to update known hosts safely. If you truly rotated keys, remove the old entry with ssh-keygen -R hostname. The cost is a brief setup task, but it preserves the trust model. Treat quiet, predictable hostnames as part of your security hygiene rather than a cosmetic tweak.

Overfilling hosts with LAN devices invites staleness. DHCP moves addresses, guest networks isolate segments, and routers swap firmware behavior without notice. A notebook entry of static lines might work today but fail silently next week. Use hosts for loopback mappings and a few genuine exceptions where you cannot influence upstream resolution. When you must pin addresses, configure a DHCP reservation on the router and let local name services advertise the mapping. The tradeoff is walking through a router menu once, which sidesteps hours of chasing intermittent lookups later. Remember that hosts has no awareness of interfaces or connectivity and cannot adapt to roaming networks.

Mixing FQDNs in hosts with short hostnames can confuse tools that parse dots as domain boundaries. If you add steamdeck-01.mynetwork to loopback while scripts expect steamdeck-01, some programs will display only the prefix, splitting logs across two identities. Prefer a single canonical short name for local identity and let domain services layer on FQDN when appropriate. If a service insists on an FQDN, ensure you control the domain or at least understand how your router handles .local or search domains. The compromise is readability against strictness, but keeping one canonical label reduces ambiguity. Clarity beats cleverness when identity slips into logs, prompts, and cache keys.

Frequently asked questions

Do I need an FQDN on Steam Deck?

No. A short hostname is sufficient. Use an FQDN only if a service requires it and you control the domain or understand how your router advertises local names.

Is editing /etc/hosts required after hostnamectl?

Usually you only add a minimal loopback mapping. Map 127.0.0.1 to the chosen hostname and localhost to keep local services consistent without touching LAN addresses.

Why did SSH warn about a changed host key after renaming?

Clients store the server key under its name. When the hostname changes, the stored entry no longer matches, so SSH presents a warning. Confirm the change and update known hosts.

Should I put other devices in my Deck’s hosts file?

Avoid it. Static lines go stale when DHCP changes addresses. Prefer DHCP reservations and rely on DNS or mDNS to advertise names across the network.

Can I use spaces or uppercase in a hostname?

No. Use lowercase letters, numbers, and hyphens. Spaces and uppercase cause parsing issues and may confuse tools that expect simple labels.
