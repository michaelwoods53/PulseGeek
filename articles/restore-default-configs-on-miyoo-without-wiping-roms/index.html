Restore Default Configs on Miyoo Without Wiping ROMs

By Austin Price • Published January 29, 2026

Resetting configuration on a Miyoo device should not endanger ROMs or saves. This guide shows how to restore default configs while preserving libraries, using file backups and targeted resets that avoid data loss. You will prepare a clean backup, reset only configuration paths, then verify system behavior before resuming play. The process assumes a Miyoo Mini or Mini Plus with an SD card, a computer with an SD reader, and basic familiarity with RetroArch. If you use Onion OS or MinUI, the steps call out differences and provide reversible touch points. By the end, you can revert misapplied tweaks, return to sensible defaults, and keep progress intact.

Key takeaways

  • Back up configuration directories separately from ROMs and saves.
  • Reset only config files to preserve libraries and achievements.
  • Verify defaults by checking RetroArch settings and input behavior.
  • Use versioned backups to quickly roll back mistaken changes.
  • Pair a clean reset with measured Miyoo performance tuning later.

Plan the work

Start by defining what a reset touches and what it must not. Configuration includes RetroArch configs, emulator front end settings, and UI preferences. It should not include ROM directories or save data like SRM and state files. A practical boundary is to treat /mnt/SDCARD/RetroArch and UI folders as reset candidates while isolating /mnt/SDCARD/Roms and /mnt/SDCARD/Saves as protected. This separation ensures library metadata and progress remain intact. Edge cases exist when themes or overlays live near ROM paths, so confirm actual locations before proceeding. The general rule is to enumerate directories rather than assume defaults. That planning prevents accidental deletions and shortens recovery if you need to restore.

Choose the reset depth appropriate for your issue, because deeper changes trade convenience for certainty. A soft reset replaces only top level config files like retroarch.cfg and front end settings, which fixes most misconfigurations without redoing inputs. A broader reset deletes per core overrides and shader presets to eliminate stubborn visual or audio problems. Avoid full device reimages unless core corruption or file system errors persist, since that requires rebuilding indexes and can consume hours. The right choice depends on symptoms like broken hotkeys, stutter from bad shaders, or mismatched aspect ratios. Selecting scope carefully saves time while reducing risk to your data.

Document your current state before you touch anything, since notes help diagnose root causes and confirm improvements. Capture a quick list of affected cores, active shaders, and system version. Screenshots of RetroArch settings for Video, Audio, and Input make reapplication straightforward if you choose to reintroduce specific tweaks. If your setup uses Onion OS or MinUI, write down their versions and any optional packages. This context lets you compare behavior after the reset and attribute outcomes to a single change. Without documentation, you can improve one area but regress in another, and you may not notice immediately. Written context converts guesswork into predictable, repeatable changes.

Prepare environment

Back up before any reset, because backups are your safety net if a step misfires. Create a versioned snapshot of configuration directories and saves to a computer. Keep ROMs out of the reset path by backing them up to a separate folder so you can validate their integrity independently. On the SD card, the common structure includes /mnt/SDCARD/Roms for libraries and /mnt/SDCARD/Saves or per core save locations. Copy these to distinct folders with timestamps like backup-2026-01-05-config and backup-2026-01-05-saves. The separation makes restores faster and avoids overwriting good data with newly created defaults. If disk space is tight, prioritize saves and configs, since ROMs rarely change.

Verify the SD card and file system health, because a reset cannot fix underlying corruption. Safely eject the card from the Miyoo and use a reliable reader. On Windows, run chkdsk on the volume and check for errors. On macOS or Linux, use fsck or disk utility equivalents and confirm the volume mounts cleanly. If errors exist, repair them before touching configuration folders. Corrupted directories can fail mid copy and leave partial files that complicate resets. Also check free space to ensure defaults can be recreated. A good rule is to leave several hundred megabytes free, which reduces fragmentation and avoids unexpected write failures during the reset.

Note your operating environment to avoid path confusion and permission issues. Onion OS and MinUI place configs in predictable but different directories, and some themes add optional assets nearby. Record the exact paths by browsing the SD card rather than relying on memory. Confirm whether saves are global or per core, since RetroArch can be configured both ways. If you use content directory overrides, list where they live so you do not mistake them for ROM folders. These small checks reduce the chance of deleting the wrong folder. They also make your verification step faster because you know where the defaults should appear after the reset.

Execute steps

Use a targeted copy and remove sequence so defaults regenerate without touching libraries. The idea is to back up configuration folders, delete only those folders, then boot the device to let the system recreate pristine files. This approach helps when a broken shader chain or misplaced input file causes crashes. The example shows typical Onion OS style paths, but the pattern is the same for MinUI with directory names adjusted. The script copies configs and saves to dated folders, excludes Roms, and removes config files only. After running it, the next boot builds clean defaults while all ROMs remain. If you need to revert, restore from the backup directories you created earlier.

If you prefer a manual approach, the same outcome is achievable via file explorer. Copy RetroArch, Emu, and Saves to your computer, then delete only retroarch.cfg and the config subfolders from the SD card. Leave Roms and any artwork directories untouched. On next boot, RetroArch spawns a fresh retroarch.cfg and recreates missing directories using safe defaults. A limitation is that some overlays or custom shaders will be gone until you reapply them. That is by design, because the goal is to eliminate problematic overrides. If you want to keep specific assets, stash them separately before deletion and reintroduce them one by one after testing stability.

Validate results

Confirm that defaults actually loaded, because a partial reset can leave hidden overrides active. In RetroArch, check if Video uses the default driver and no shader preset is active. Inspect Input for neutral hotkeys and confirm your gamepad is detected without custom binds. Look in the config directory and ensure new files have recent timestamps that match your reboot. Run a short session with a representative 8-bit and 16-bit core to test audio sync and frame pacing. If performance improves and stutters disappear, the reset succeeded. If an issue persists, it likely points to a core specific setting or an external asset like a shader or overlay.

Verify that ROMs and saves remain unmodified, because the goal is preservation. Browse /mnt/SDCARD/Roms and spot check a few titles. Open their save files or continue from a known checkpoint to confirm progress is retained. If you used content directory overrides earlier, check that per folder configs did not reappear automatically. They should only exist if you restore them explicitly. If any artwork is missing, that reflects the reset removing custom assets rather than data loss. Reintroduce artwork later if desired. Keeping this distinction clear prevents chasing ghosts when assets and configs disappear by design, while core content stays intact as required.

Collect a quick benchmark of responsiveness to establish a new baseline. Measure menu navigation speed subjectively and note how long RetroArch takes to open. Watch for audio crackle or desync at scene transitions, which typically relate to mistuned audio latency settings. If you plan to retune performance, use that baseline to decide which adjustments are worth reapplying. For example, if a shader preset costs frames, avoid it until you confirm your device can handle it comfortably. Linking your reset to measured feel turns anecdote into signal. Troubleshoot and optimize

If the device fails to boot after removal, the usual cause is an unexpected dependency or a damaged SD card. Reinsert the card, run a file system check on a computer, and restore the config backup you created. If only RetroArch crashes, move its freshly created retroarch.cfg aside and let it generate another on next launch, since a partial write can corrupt the file. As a last resort, copy back the entire RetroArch folder from your backup. These steps restore operational status while preserving ROMs, because you never touch the library directories. Keeping the backup nearby shortens recovery to minutes rather than a full rebuild.

When a specific core still misbehaves, isolate it by testing with clean per core configs. Delete only that core’s override under RetroArch/config and relaunch the content. If the issue vanishes, reapply desired options one at a time, such as integer scaling or audio latency, and test after each change. This method narrows the responsible setting without destabilizing other cores. Be wary of cumulative shader stacks, because layering effects can consume performance budget quickly. Avoid mixing global and per core overlays unless you prefer the maintenance cost. Focus on one variable at a time so you can attribute each improvement or regression accurately.

After stability returns, reintroduce helpful optimizations with intention rather than habit. Start with basics like consistent frame pacing, audio sync, and storage hygiene. Favor reversible tweaks so you can revert without repeating the entire reset. Keep a change log with dates and brief notes so patterns reveal themselves over time. If you use Onion OS or MinUI, apply UI trims and safe defaults before cosmetic changes. Pair measured tuning with periodic backups so you can iterate safely. This approach delivers smoother play without raising clocks and keeps your environment maintainable when future updates change defaults or introduce new options.

Frequently asked questions

Will resetting configs delete my ROMs or saves?

No. If you only remove configuration files and avoid Roms and Saves directories, your libraries and progress remain intact.

Do I need to rebind my controls after a reset?

Usually yes for RetroArch. Defaults restore neutral hotkeys and input, so you may need to map buttons again once to fit your device.

What if RetroArch still crashes after restoring defaults?

Move the new retroarch.cfg aside and relaunch to regenerate it again. If crashes persist, restore your backup RetroArch folder and test per core.

Is a full SD reimage ever required?

Only if the file system is corrupted or the device will not boot. Try repairing the card first, then consider reimaging as a last resort.

Can I keep specific overlays or shaders?

Yes. Back them up separately before the reset. Reintroduce them one at a time after validation to confirm they do not reintroduce problems.
