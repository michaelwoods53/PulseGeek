How to Log FPS on Miyoo for Testing

By Austin Price • Published March 9, 2026

Accurate FPS logging on Miyoo helps separate real performance issues from perception. You will enable an FPS counter, run repeatable scenes, and document readings for testing. The workflow minimizes risk by relying on RetroArch options and core-level counters, not overclocking or unstable tweaks.

Key takeaways

  • Use RetroArch OSD and core counters to observe consistent FPS.
  • Test the same scene for thirty to sixty seconds per run.
  • Log min, max, and typical FPS with timestamps and settings.
  • Prefer safe toggles like sync and buffering before deep changes.
  • Validate results twice to confirm repeatability and stable FPS.

Plan the work

Start with a clear test goal because vague objectives produce noisy data. Decide whether you are measuring average FPS, frame pacing stability, or the impact of a specific setting like audio sync. For example, plan to test one game scene for sixty seconds with the same save state. That scene might be a scrolling segment or a busy battle where slowdowns are likely. Limiting scope reduces hidden variables, especially on handhelds where thermals and power modes can shift behavior. The tradeoff is narrower coverage, but the benefit is high confidence comparisons. A precise scope also guides which counters to enable and what notes to collect during each run.

Choose a fixed scene to minimize variability because different rooms or maps load different assets. A reliable approach is to create a save state immediately before a repeatable moment, like entering a town and walking along a fixed route. Use the same input pattern each run to keep CPU and I/O demand comparable. If the scene still varies, increase run time to sixty seconds to smooth spikes. This consistency lets you compare RetroArch OSD readings with core-level counters fairly. The limitation is that some games randomize elements, but longer samples offset that randomness without demanding extra tools.

Define what success means so you can stop tuning at the right moment. A practical rule is targeting steady 60 FPS for 8 and 16 bit cores or 50 FPS for PAL content, with frame time swings small enough that the OSD counter does not flicker wildly. Set acceptable ranges like plus or minus 2 FPS during the run. If readings fall outside that boundary, you will capture settings and try one controlled change. Without a defined finish line, you risk endless tweaking that muddies results. A success criterion also makes your notes actionable when comparing across OnionOS and MinUI or different cores later.

Prepare environment

Enable visibility first, since you cannot optimize what you cannot see. In RetroArch, turn on the on screen display counter to show frame rate during gameplay. Many cores also include their own “Show FPS” toggle inside core options, which can be more accurate for that emulator’s timing. Use both when available to cross check. Prepare a simple notes template that logs date, game, core, scene, and settings. The tradeoff is extra setup time, but the payoff is data you can compare later. If the counter is distracting, reduce its size or opacity rather than switching it off mid test.

Set paths and logging carefully because file access can fail on marginal SD cards. Configure a log directory and enable logging to a file so configuration changes and core messages are captured. While most builds do not record FPS values to logs, having timestamps around pauses, fast forward, or core reloads helps explain weird dips. Keep at least 200 MB free space on the card to avoid fragmentation during saves and screenshots. If you suspect storage issues, run a separate health check using the guide on diagnosing SD bottlenecks for Miyoo to prevent data skew from slow I/O.

When menu navigation is limited, editing the RetroArch config directly can be faster. You can toggle the FPS overlay and logging by updating the configuration file. After saving, reboot the device or fully quit RetroArch to apply changes. This method avoids inconsistent menu states if an unexpected shutdown occurred previously. The limitation is that some frontends or OS layers can overwrite settings on update. Keep a backup of your config so you can quickly restore known good defaults if things drift. Execute steps

Run the test sequence in a consistent order so changes map cleanly to results. Begin with default safe settings, record a baseline, then adjust one variable. For example, test with audio sync on, VSync on, and frameskip off before experimenting. This mirrors stable performance guidance that emphasizes pacing over raw speed. If you suspect stutter not related to FPS, compare readings while walking and while idling to isolate rendering from input spikes. A tight sequence also prevents temperature drift from masking improvements. Keep rest times similar between runs to reduce thermal variance during back to back measurements.

Use notes that separate readings from interpretations to keep bias out of logs. Record start time, scene description, counter values at 10 second intervals, and any visible skips. If the OSD counter fluctuates between two values, write the lower one as the floor and the modal value as typical. When core and RetroArch counters disagree, prioritize the counter that aligns with on screen feel. Some cores round differently or include frameskip in their display. Flag those cases for follow up. This structure yields comparable snapshots that explain whether a tweak affected performance or just changed timing.

Include screenshots sparingly to document overlay values, but avoid video capture during testing because it can alter performance on low power devices. Capture one screenshot near the start and another near the end of the run. If a device hotkey triggers both screenshot and fast forward by accident, remap temporarily. Screenshots should confirm what your notes already contain, not replace them. If storage is borderline, delete unneeded images after transcribing values. Validate results

Validate by repeating the baseline at the end of your session to check for drift. If the repeated baseline differs by more than two FPS, temperature or background processes likely shifted. In that case, allow a cooldown and retest. Next, compare RetroArch OSD with the core’s counter. Agreement suggests the reading reflects real timing, while a discrepancy hints that one counter is rounded or delayed. For example, some cores update their display once per second, which can hide rapid swings. Validation protects you from misattributing gains to a setting that only changed how numbers are reported.

Use a simple comparison table to decide which counter to trust in common cases. If counters match and the game feels smooth, keep using the simpler overlay. If they diverge and you feel judder, prioritize the counter that aligns with perception. When both counters fluctuate but the feel is stable, you might be hitting exact divisors like 59.7 that round inconsistently. In those cases, extend the sample time. This approach keeps decisions tied to playability rather than chasing numerical noise. Store the decision in your notes so future tests remain consistent across sessions and games.

Cross check controls that influence pacing because changes outside graphics can affect feel. Audio buffering and sync settings alter CPU scheduling and may introduce micro stutter without reducing average FPS. If stabilizing audio removes skips while the counter stays steady, you fixed pacing rather than raw throughput, which is a win. Troubleshoot and optimize

When FPS is unstable, fix pacing before speed. Turn off frameskip, keep VSync on, and ensure audio sync is enabled. If the counter still swings, raise audio buffer slightly to give the CPU breathing room. Many handheld issues trace to storage latency or thermal throttling, not the emulator itself. If you see sporadic dips during loads, test another SD card or reformat with a reliable cluster size according to official guidance. Thermal shifts often appear after several minutes of play. If symptoms point to heat, pause testing and allow a cooldown so numbers reflect software changes rather than hardware limits.

Quick start checklist

  1. Enable OSD counter: turn on the RetroArch FPS overlay for quick visibility.
  2. Pick a repeatable scene: create a save state and fixed route for testing.
  3. Log a baseline: run sixty seconds with VSync and audio sync enabled.
  4. Change one setting: adjust a single toggle, then retest the identical scene.
  5. Record observations: note floor, typical FPS, and any visible stutter.
  6. Recheck baseline: repeat the first run to confirm no drift after changes.

Key terms

  • Emulator Core — The component that emulates a specific system.
  • Frame Rate Cap — A set limit on frames per second to control performance and power.
  • Frames Per Second — The number of images shown each second in a game.
  • I/O Bottleneck — A slowdown caused by limited read/write speed.

Frequently asked questions

Does RetroArch log FPS to a file on Miyoo?

Most builds do not write per frame FPS to logs. Enable the on screen counter and record values manually. Logging to a file is still useful for timestamps and core messages that explain dips.

Which counter is more accurate, RetroArch OSD or core FPS?

They often agree, but cores can reflect emulator timing more closely. Trust the one that aligns with perceived smoothness, and document which you chose for consistent comparisons.

Will screenshots affect performance during tests?

Capturing a single screenshot has minimal impact on most scenes. Avoid continuous video recording during tests because it can change performance on low power devices.

How long should each test run be?

Thirty to sixty seconds balances stability with time. Use longer runs if scenes are variable or counters fluctuate, and keep the duration consistent across tests.

Is frameskip a good way to raise FPS?

Frameskip can inflate FPS numbers while harming feel. Leave it off when measuring. Use it only as a last resort for playability, and note it clearly in your logs.
