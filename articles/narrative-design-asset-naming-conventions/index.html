Narrative Design Asset Naming Conventions

By Lauren Mitchell • Published January 1, 2026

Clear narrative design naming conventions turn messy folders into a readable soundscape. This guide curates patterns that keep asset names human friendly and machine parsable across writing tools, exports, and builds. I selected each item for its repeatable benefit, then tested the tradeoffs on real tasks like localization prep and QA filtering. Expect concrete examples you can paste into your pipeline and small rules that protect big deadlines. As we move, listen for the cadence of prefixes, separators, and IDs settling into place, so a quest step or a line of VO can be found by feel as well as by filter.

Key takeaways

  • Use short, unambiguous prefixes to group narrative asset families.
  • Balance readability with machine parsing using consistent separators.
  • Add stable IDs for localization and cross-tool synchronization.
  • Place version and locale markers in predictable positions.
  • Automate validation with lightweight regex linters in CI.

1) Prefixes that encode purpose

Adopt concise prefixes to convey asset purpose at a glance, because the first token is what filters and folders sort by. Use two to four letters like CHR for character portraits, VO for voice lines, DLG for dialogue text, and QST for quest states. For example, VO_NPC_Baker_line045_tk02.wav sorts beside other voice takes and separates cleanly from DLG_Baker_line045_en-US.txt. This speeds batch operations such as exporting all VO for a region or muting dialogue during a test build. The tradeoff is acronym ambiguity if teams invent similar prefixes, so publish a short glossary and keep the list tight. Choose brevity over cleverness, avoid overlapping meanings, and reserve new prefixes for genuinely new asset families, not for one-off experiments.

Prefixes also reduce the need for deep nested folders, because the category meaning travels with the file. In a mixed content drop, QA can grab VO_* items, while integrators import DLG_* into a dialogue database. For instance, a build script can locate QST_* to rebuild quest state enums without scanning unrelated textures. The risk is prefix expansion over time, where teams extend meanings to cover edge cases like barks versus conversations. Handle this by pairing the prefix with a second fixed token when necessary, such as VO_BARK and VO_SCENE, and deprecate rarely used tags during retros. Consistency beats exhaustiveness, and retiring unused tokens keeps search results predictable.

Section highlights

  • Short prefixes speed filtering and keep mixed folders navigable.
  • Publish a glossary and retire ambiguous or unused tokens.

2) Scope and granularity in the name

Include scope markers that show where an asset belongs within the project timeline, because finding “which scene” often matters more than “which character.” A practical pattern is PRJxx for project, SCyy for scene or location, and SEGzz for segment, yielding names like DLG_PRJ01_SC05_SEG12_GuardGreeting_en-US.txt. This lets producers ask for all content from scene 5 without loading a tool, and empowers engineers to build scene-specific bundles. The tradeoff is longer names, which can flirt with path length limits on some systems. Mitigate by abbreviating predictable tokens and relying on folder paths to encode the most stable scope, leaving the filename to carry volatile details like segment and line numbers. Document which scopes live in folders versus names to avoid duplication.

Granularity markers help isolate deltas during reviews. If an editor changes only segment 12, version control diffs can focus on SEG12-tagged files. A clear example is quest steps: QST_PRJ01_SC02_STEP03_ObjectiveText_en-US.json makes it obvious which objective was updated. However, overeager granularity creates brittle names that change often and break links during export. Use a rule of thumb: encode the highest level likely to be filtered by non-technical teammates, and keep lower levels inside the file’s internal IDs. That way a localization partner can batch grab SC02 content, while integrators still map inner line IDs reliably after import.

Section highlights

  • Scope markers reveal project and scene context without opening tools.
  • Favor stable scopes in folders and volatile details in filenames.

3) Human readable and machine parsable

Choose separators and casing that parse cleanly in scripts while remaining readable in reviews. Kebab case or snake case are resilient choices, such as dlg-town-square-greeting_en-US_v002.txt, because hyphens and underscores split reliably across tools. Avoid spaces that complicate shell operations and exotic characters that break cross-platform paths. In practice, this means fixed token order, lowercase for general tokens, and TitleCase only for proper names that must remain recognizable. The tradeoff is style enforcement friction during crunch. Solve this by setting formatters or export templates in your writing tools, so authors do not hand-type every token. Machine parsing shines when teams automate beyond file naming. If your build system needs to collect all greetings, the consistent token greeting lets scripts sweep up assets with a single rule instead of fragile wildcards. For example, localization can script a pass that finds *_en-US_* for source extraction and *_fr-FR_* for quality checks. The limitation is English-centric token bias creeping into names, causing confusion for non-English teammates. Keep the core tokens in a shared lingua franca but preserve the original language in text content, not in structural tokens. Section highlights

  • Use kebab or snake case with fixed token order for easy parsing.
  • Automate formatting at export to avoid manual typing errors.

4) Stable IDs for lines and strings

Create stable, opaque IDs for dialogue lines and quest strings so references survive rewrites. A compact scheme like DLG.00123 or STR.QST.Step03.0045 can live inside the file header and the exported text table. For instance, DLG.00123 should map to a row in your localization spreadsheet and to a node in your editor, allowing imports from both directions. The upside is durable links across Twine, Ink, or a custom tool. The tradeoff is discoverability because opaque IDs are not self-descriptive. Counterbalance with a companion human label in comments or metadata while keeping the ID immutable. For more on export mapping and validation strategies between authoring tools and engines, review our guide to export strategies for narrative data and versioning.

Stable IDs also cut noise during QA, where testers can file bugs against a single symbol instead of a paragraph quote. A report that names DLG.00123 is easier to grep across text sources and engine logs than “the guard’s second line.” The cost appears when IDs get recycled after deletions, which can corrupt references. Establish a one-way policy: retired IDs never return, and new content burns new numbers. Store the counter in version control and gate changes behind review. When toolchains permit, add checks that flag duplicated IDs at export. This prevention is cheaper than untangling mismatched dialogue during a localization sprint.

Section highlights

  • Use immutable, opaque IDs to anchor strings across tools.
  • Retire IDs permanently and automate duplicate detection.

5) Version and variant markers

Append version and variant markers in predictable positions to control workflow churn. A common pattern is _v### after the base tokens and before the extension, like DLG_TownGreeting_en-US_v003.txt. For voiced lines, include take numbers as _tk## or cut numbers as _cut##. This makes it simple to archive, diff, and roll back without asking which file is current. The tradeoff is noise when variants proliferate, such as mood alternates or conditional reads. Prevent bloat by routing experimental passes to a _WIP suffix and promoting only approved versions to numbered series. Place locale between content tokens and version so that files sort by language first, then by drafts, which mirrors localization workflows.

Variants should encode the decision axis that matters for integration. If performance tone affects lip sync, VO_Hero_Line120_tone-angry_tk02.wav helps mixers track timing differences. If gameplay system is the axis, use _combat versus _stealth to keep bundles coherent. However, more axes compound exponentially. Limit to one or two axes per family and push the rest into metadata inside companion JSON or spreadsheets keyed by the stable ID. Define the canonical sort order of suffixes and teach scripts to expect it, so name_locale_variant_v###.ext never flips unpredictably. This predictability removes a surprising amount of friction from nightly builds.

Section highlights

  • Keep version and take markers consistent for simple diffs and rollbacks.
  • Limit variant axes and fix suffix order across asset families.

6) Audio and VO taxonomy

Standardize a taxonomy for voice assets that distinguishes delivery type, speaker, and line identity. A dependable pattern is VO_{SCOPE}_{SPEAKER}_{LINEID}_tk##.wav, as in VO_SC05_NPCBaker_0045_tk02.wav. Add BARK, SCENE, or SYSTEM as a secondary token to group quick reactions versus scripted scenes. This taxonomy lets audio teams filter takes, and allows localization to pair text and audio by ID without manual relabeling. The tradeoff is long names for ensemble scenes, where multiple speakers share a beat. Handle these with per-speaker files that share the same LINEID and differ by _Speaker, or maintain a short multi-speaker code in metadata only. For guidance on preparing dialogue pipelines with IDs and context, see our article on localization-ready dialogue pipelines.

Sorting behavior matters in DAWs and file browsers. Keep numeric parts zero-padded, such as _0045_ and _tk02, so chronological and lexical orders align. Include a channel or mix token only when it affects integration, for example _mono versus _stereo, or target platform constraints like _48k. The risk is inventing too many optional tags that users apply inconsistently. Constrain optional tokens to a small whitelist and publish examples that cover 90 percent of use, pushing corner cases into a notes field in the tracking sheet. Taxonomies work when they are memorably boring, not when they encode every sonic nuance in the filename.

Section highlights

  • Use a fixed pattern for VO with padded numbers and take markers.
  • Whitelist optional tags and move details into metadata.

7) Validation and linting

Automate checks that enforce naming rules before assets reach the build, because conventions drift without guardrails. A minimal validator can scan a folder and report files that fail your pattern, such as a regex for dialogue lines like ^DLG_[A-Za-z0-9-]+_[a-z]{2}-[A-Z]{2}_v\\d{3}\\.(txt|json)$. 8) Cross-tool mapping and exports

Plan naming so exports from authoring tools map predictably into engine structures. Treat the filename as a transport label and the inside IDs as the contract. For Twine, Ink, or Articy, ensure node or knot names are not relied upon for identity, and use stable IDs to join with engine tables. A workable example is exporting a CSV where StableID, Locale, and Text travel together, while filenames follow DLG_{Scope}_{ReadableLabel}_{Locale}_v###.txt purely for organization. The tradeoff is duplication of labels that exist both in files and rows. Accept this redundancy to shield engine imports from accidental renames. When moving between tools and engines, compare how collaboration and data structures differ in our piece on collaboration and production-ready pipelines.

Exports are fragile without versioning and validation on both sides. Add a checksum of the text payload to the export row so build scripts can detect unintended changes even when names remain stable. If integration relies on Unreal data tables or Unity ScriptableObjects, generate assets using the stable ID as the primary key and keep the human label as a field. This design decouples editor-facing labels from the build identity. For workflow glue across teams, our guide on mapping content pipelines from ideation to engine shows where names hand off to IDs and where automation should catch drift.

Section highlights

  • Use filenames for transport and stable IDs for integration.
  • Add checksums and primary keys to harden exports and imports.

9) Folders versus filenames

Let folders carry slow-changing context and reserve filenames for frequently filtered details. If your project already nests by episode and scene, such as /PRJ01/SC05/, repeating PRJ01_SC05 in every name wastes characters and risks path-length issues. Instead, prefer DLG_ShopGreeting_en-US_v002.txt inside the scene folder. This separation avoids double edits when a scene moves. The tradeoff is reduced portability when files are emailed or moved out of context. Counter that by exporting shareable zips that preserve folder paths, or by embedding a minimal header inside files with Project and Scene fields. This file-to-folder contract should be written down so refactors do not shuffle meaning between path and name unexpectedly.

Folder-first structure also simplifies access control and build steps. Grant localization vendors access to /DLG and /VO trees without exposing concept art or tools, then let scripts aggregate by locale suffixes within. The limitation is that some tools flatten imports and only read filenames. For those, design filenames that can stand alone, but keep duplication intentional and minimal. If you plan extensive QA on branching dialogue, review approaches to coverage, seed saves, and automation so your structure supports fast traversal. Balance remains the theme: let the folder whisper the setting while the name hums the line’s identity.

  • Place stable context in folders and volatile details in filenames.
  • Design names that travel when tools flatten directory paths.

Looking ahead

Write down the chosen naming rules, seed examples into templates, and wire a validator into your exports. Start with two or three families like dialogue, VO, and quest text, then expand once the team feels the rhythm. Plan a short calibration review after the first milestone to prune confusing tokens and retire overlap. If the structure supports readable browsing and reliable parsing, you will spend more time listening to scenes and less time fixing labels. Keep a change log so newcomers learn the cadence quickly and your naming stays steady under pressure.

Section highlights

  • Document the convention and add validators to exports and CI.
  • Review after a milestone and simplify confusing or redundant tokens.

Frequently asked questions

How long should narrative asset names be?

Keep names concise but informative. Aim for 40 to 80 characters including tokens for category, scope, locale, and version. Use folders for stable context to avoid hitting path length limits on some systems.

Should locale codes be in the filename or folder?

Place locale in filenames for tools that flatten paths and in folders for bulk operations. Many teams do both. Use consistent BCP 47 style tags like en-US or fr-FR and keep their position fixed.

Do I need stable IDs if filenames are unique?

Yes. Filenames change during rewrites and refactors. Stable IDs give imports, localization, and QA a durable key that survives renames and file moves across tools and builds.

What separator is best for parsing?

Hyphens or underscores are safe across platforms and tools. Pick one consistently. Avoid spaces and special characters that complicate shells or script parsing, especially in automated pipelines.

When should I increment version numbers?

Increment when content meaning changes or a take is selected for review. Skip bumps for harmless metadata edits. Keep a predictable pattern like _v003 and only promote approved versions from WIP labels.
