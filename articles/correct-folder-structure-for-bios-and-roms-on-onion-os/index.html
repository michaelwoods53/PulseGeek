Correct Folder Structure for BIOS and ROMs on Onion OS

By Sarah Carter • Published January 6, 2026

Getting the folder structure right for BIOS and ROMs in Onion OS prevents missed scans, core errors, and artwork gaps. This list focuses on practical path conventions, consistent names, and asset alignment that keep your library stable. Each item explains a rule, shows a concrete setup, and notes a tradeoff to watch. If a scan still fails after reorganizing, start with a brief pass through the steady, end-to-end troubleshooting pillar and then return here to refine structure.

Key takeaways

  • Consistent folder names and BIOS paths prevent Onion OS scan failures.
  • Use supported archives and avoid nested zips to reduce parsing errors.
  • Match ROM names to playlists and artwork to keep thumbnails stable.
  • Place BIOS in the system folder expected by each emulator core.
  • Normalize case and special characters to improve cross-platform reliability.

1) Group ROMs by system: one folder per platform

The most reliable pattern is one platform per folder, because Onion OS scanners and many cores infer system context from steady directory names. For example, create top-level folders like ROMS/nes, ROMS/snes, ROMS/psx, and ROMS/gba, then place only that system’s games inside. This makes filters, playlists, and artwork lookups predictable, since paths remain stable across rebuilds. The tradeoff is flexibility when you own regional sets or hacks, because subfolders like ROMS/nes/usa or ROMS/nes/hacks can complicate scanning if your tool does not recurse. A safe rule is one extra level at most, with subfolders named by simple lowercase tokens. When you need more depth, test with a small sample before reorganizing your full card to confirm scan behavior is consistent.

Consistent folder naming also reduces false mismatches during metadata scraping, because parsers often pair a ROM’s filename with its immediate parent directory to make educated guesses. For instance, ROMS/psx containing only PlayStation titles avoids cross-system confusion with similarly named files that exist for Sega or Nintendo. The upside is fewer manual corrections and faster lists after initial scans. The limitation is when you prefer mixed collections like favorite-games across systems, which can scatter assets and generate duplicate artwork entries. A practical compromise is to keep curated mixes inside a separate PLAYLISTS folder while preserving platform-pure directories for scanning. If a mixed set must exist under ROMS, ensure your scraper can target only that folder to prevent unintended metadata edits.

Section highlights

  • Use one folder per platform with minimal subfolders to stabilize scans.
  • Keep mixed collections separate or target-only to avoid mismatched metadata.

2) Put BIOS in the exact system directory cores expect

BIOS files must live in the path each core checks by default, because many emulators refuse to boot if hashes or locations do not match. On Onion OS, a common target is the RetroArch system directory such as /retroarch/system, where files like scph5501.bin or gba_bios.bin belong. The benefit is plug-and-play boot checks across multiple cores without per-core overrides. The tradeoff is that some cores use customized subpaths or require specific filenames, so you must confirm the expected location per system. When troubleshooting, verify integrity with checksums and place only verified files to avoid silent failures. If you are unsure which systems need BIOS, review a concise explainer on adding required BIOS files safely before moving or renaming anything that already boots.

Centralizing BIOS in one predictable location simplifies backups and SD card swaps, since you can copy the system directory as a single unit. For example, keeping all PlayStation BIOS variants in /retroarch/system while ensuring filenames match the core’s documented expectations reduces confusion across updates. The downside is when an alternative emulator expects a different folder or a different case pattern on a case-sensitive file system. In that situation, maintain a small mapping note near the BIOS directory that lists each core and its exact filename requirement. 3) Standardize ROM filenames and avoid noisy characters

Uniform filenames scan faster and map to artwork more accurately, because scrapers tend to strip known tags but can trip on punctuation or unsupported symbols. A practical naming baseline is Title (Region).ext with only spaces, parentheses, and hyphens, avoiding brackets, ampersands, and unicode symbols. For example, keep Super Mario World (USA).sfc rather than adding dump tags or scene notes. The benefit is fewer false positives and less manual relabeling later. The tradeoff shows up when you want to preserve romset provenance for auditing. In that case, store detailed tags in a companion text file per folder while keeping the actual ROM filename clean. If artwork still fails to attach, consider a short pass through guidance on restoring missing thumbnails with cache rebuilds and strict naming.

Consistent naming also influences playlist stability, since many generators match entries by exact filename. If you change The Legend of Zelda - Link to the Past.sfc to a variant later, a previously built playlist may reference the old name and produce a broken link. A safe approach is to lock naming after your first good scan, then batch rename carefully with a tool that updates playlists in tandem. The limitation is that not all generators support automatic relinking. When they do not, rebuild the playlist right after renaming to keep references fresh. If you face recurring mismatches, a short troubleshooting sequence that covers end-to-end checks for assets, updates, and recovery can help isolate whether the issue is naming or cache state.

  • Use simple filenames with region tags to improve scraping and artwork.
  • Lock names after a clean scan or rebuild playlists immediately after.

4) Use supported archives and avoid nested compression

Choose archive formats that Onion OS scanners and cores can parse quickly, because unusual or nested compression adds latency and errors. For many systems, single-level .zip or uncompressed files provide the most predictable results, while nested archives like .zip inside .7z often fail. As an example, store Genesis titles as ROMS/genesis/Game Title.zip with one ROM inside. The upside is smaller storage for large sets and straightforward index building. The tradeoff is a small load-time penalty compared to raw files, and certain cores may prefer uncompressed images for disc-based systems. A rule of thumb is uncompressed or .chd for large discs, and single-level .zip for small carts. If a game will not appear, verify the archive is not multilevel and that the internal filename matches your naming rules.

Compression choice also affects artwork workflows, because some scrapers scan filenames while others inspect file headers. A consistent extension per system reduces accidental type mismatches. For example, store SNES games uniformly as .sfc or .smc across the folder, not a mix, so metadata jobs do not treat two formats as different titles. The downside is converting legacy sets takes time and CPU, which is inconvenient on slower machines. Schedule conversions in batches and confirm the first batch scans clean before committing the entire library. When conversions are complete, rebuild the thumbnails cache to sync artwork with the updated filenames and extensions so UI galleries do not show stale or missing imagery after the migration.

Section highlights

  • Prefer single-level zips for carts and uncompressed or CHD for discs.
  • Keep extensions consistent per system and rebuild artwork caches post-move.

5) Align playlists and artwork directories with ROM locations

Playlists should reference stable, final ROM paths and names, because any later move or rename breaks artwork and recent-play entries. Keep your playlists under a predictable directory and build them only after your ROM folders and naming are settled. As an example, finalize ROMS/psx and ROMS/psp first, then generate their lists and scrape images. The benefit is a one-time scrape with minimal rework. The tradeoff is upfront planning, which can feel slower than ad hoc scanning. If images appear during the session but disappear later, investigate why scraped images vanish and how to make them stick, then confirm that the artwork folder mirrors the playlist’s system identifiers. Finally, after any reorg, trigger a targeted cache rebuild so thumbnails reflect the new layout without a full rescan.

Artwork packs and live scraping both depend on coherent structure to place images in the correct asset tree. If your folder layout uses ROMS/nes and ROMS/snes, configure your scraper or pack installer to deposit images into matching system-named subfolders. For instance, thumbs/nes and thumbs/snes keep galleries tidy and predictable. The upside is speed when reloading the UI and less duplication across themes. The limitation appears when you mix assets from different sources that disagree on naming conventions. Before importing a second pack, compare its folder scheme to your current one and rename in advance so images land where the UI expects them. If visibility or art still looks fragmented, review a focused piece on restoring missing artwork thumbnails with naming and cache checks.

6) Normalize case and special characters to prevent cross-device issues

Normalization reduces invisible path problems, because some file systems treat Case and case as different names while others do not. Standardize on lowercase for folders and filenames across ROMS and BIOS directories. For example, use roms/psx/ and scph5501.bin to avoid surprise mismatches after moving to a device with a case-sensitive format. The benefit is fewer hard-to-trace failures when a playlist refers to one case and the filesystem stores another. The tradeoff is a one-time rename pass that can ripple through playlists and artwork caches. To mitigate, apply batch renamers that preserve extensions and spaces, then immediately rebuild any dependent lists. If after normalization items vanish or crash, follow a calm, checklist-driven troubleshooting path that covers index recovery and cache clearing before rolling back changes.

Special characters can also derail parsers, so keep a small allowed set and remove accents or symbols that your tools do not handle. As a rule, stick to letters, numbers, spaces, hyphens, and parentheses. For example, rename Pokémon to Pokemon when a scraper lacks unicode support, and avoid ampersands in both filenames and folder names. The upside is more portable backups and easier scripting for batch tasks. The limitation is losing typographic detail in titles, which may matter for collectors. Keep a separate manifest file to store original, display-friendly names if you want to restore typography in frontends that support it. When your library grows, consistent ASCII names also make command-line filters and playlist generators more predictable and repeatable.

Section highlights

  • Use lowercase and simple characters to avoid cross-filesystem mismatches.
  • Batch rename safely, then rebuild playlists and caches to relink items.

7) Plan SD card layout, path depth, and free space

Stable storage layout prevents subtle failures that look like missing BIOS or ROMs but are really path or space constraints. Keep ROMS near the root of the SD card with short folder names to avoid exceeding path length limits in tools. For example, prefer /roms/psx/Game.cue over a deep hierarchy with multiple descriptive folders. Leave adequate free space for thumbnails and cache files, since artwork jobs can create thousands of small images. The tradeoff is less descriptive directory nesting, but you gain predictable scanning and faster UI loads. Make periodic integrity checks on the card to detect corruption early. If you still see content not appearing after a clean layout and adequate space, consult a reliable overview that walks through boot loops, crashes, updates, and recovery in a calm sequence.

Separating large disc-based systems onto a second card or partition can improve performance and reduce fragmentation, provided you mirror the same top-level folder names. For instance, placing ROMS/psx on a larger card while keeping ROMS/nes and ROMS/snes on the primary card still works if playlists reference absolute or consistent relative paths. The benefit is faster backups and easier upgrades by swapping only the heavy libraries. The limitation is the need to update path references when changing mount points or device letters. Keep a small notes file documenting where each system lives and the expected mount label. When reattaching storage, verify a couple of sample games and thumbnails before assuming the entire library linked correctly to the new location.

Frequently asked questions

Do BIOS filenames need to match exactly?

Yes. Many cores check exact filenames and hashes. Use the core’s documented name and place the file in its expected system directory to avoid silent failures.

Can I keep ROMs in multiple subfolders per system?

One level of subfolders usually works if your scanner recurses. Keep names simple and test with a small sample before applying the pattern across your full library.

Should I use zip or keep ROMs uncompressed?

For carts, single-level zip or uncompressed both work. For disc images, uncompressed or CHD is safer. Avoid nested archives since scanners often miss them.

Why did artwork disappear after renaming files?

Playlists and caches still point to old filenames. Rebuild the playlist and refresh the thumbnails cache so artwork paths match the new names and extensions.

Are special characters like ampersands a problem?

They can be. Stick to letters, numbers, spaces, hyphens, and parentheses. Remove accents and symbols that scrapers or filesystems may not handle consistently.

After reorganizing, run a small verification loop: launch one BIOS-dependent title, scan one platform folder, and refresh thumbnails. This log shortens future migrations and helps you spot drift quickly. When you introduce new systems or artwork packs, trial them in a sandbox directory first, confirm scans and thumbnails, then promote the pattern to your main library. Iterating in small, measured steps preserves momentum and prevents large rollbacks.
