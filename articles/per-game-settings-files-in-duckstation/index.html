Per-Game Settings Files in DuckStation

By Brian Rogers • Published January 15, 2026

Per-game settings in DuckStation let you tailor behavior for specific titles without upsetting your global configuration. These files capture targeted options like renderer tweaks or memory card assignments so a finicky game plays smoothly while others remain unaffected. The approach is valuable when one release needs a workaround that would harm performance if applied systemwide. Treat these overrides as precise tools, not defaults in disguise. Use them where a repeatable issue appears, test results against a baseline, and document why the change exists. This discipline makes future audits easier when emulator updates shift compatibility. If the goal is consistent behavior across hundreds of games, start with clean global settings, then introduce per-game files only where measurable benefits outweigh maintenance overhead and potential conflicts.

Key takeaways

  • Use per-game settings only when a title needs targeted overrides.
  • Prefer global defaults, then layer narrow changes with clear notes.
  • Keep names consistent with serials to avoid duplicate configurations.
  • Audit overrides after emulator updates to retire unnecessary tweaks.
  • Separate performance, controller, and memory choices to isolate risk.

Concepts and definitions

Per-game settings files capture overrides for a single title so DuckStation can apply special handling only when that game launches. The core idea is scope control, where global defaults establish baseline behavior and per-game files change a small subset like renderer, texture filtering, or input mapping. This separation prevents a fix for one title from slowing or breaking others. A practical example is enabling a software renderer for a single game that displays artifacts under hardware rendering, while leaving hardware mode elsewhere for speed. The tradeoff is added complexity, since more files mean more moving parts to audit. Keep the why documented in comments or a separate note so you remember what problem the override solves and when it can be removed safely.

Override precedence matters because DuckStation reads settings in a predictable order, typically applying base defaults first and then merging more specific layers. Think of it as a cascade where the most specific scope wins. When a per-game file turns on a compatibility option, that change should supersede the same flag set in the global profile. The benefit is deterministic behavior that resists surprise regressions from global tweaks. The limitation is that conflicting directives can hide upstream problems, making debugging harder if you forget an override exists. A simple rule of thumb helps: set the minimal value at the narrowest scope that solves the issue, and avoid duplicating the same option across scopes unless you intend to replace the broader value.

Naming discipline reduces confusion and accidental duplicates. Many users align per-game filenames to the PS1 serial identifier like SCUS, SLUS, or SLES codes so a single title maps to one file regardless of region naming quirks. That consistency makes audits and migrations easier when you move libraries or rebuild indexes. For example, keeping Resident Evil 2 Leon and Claire discs tied to a unified identifier prevents divergent options that drift over time. The tradeoff is that multi-disc or revision variants may share a serial yet need tiny differences, so create a documented exception only when necessary. The goal is traceability, not rigid perfection. Use consistent patterns first, then branch with a clear note when the gameplay experience truly diverges.

Frameworks and decision lenses

A practical decision lens starts with baselines. First, establish clean global settings that play well with most PS1 games, then verify a problem title under those defaults. If the issue persists and a targeted change resolves it without harming performance, consider a per-game override. For instance, toggling texture correction or adjusting resolution scaling may fix shimmering in a single title while your library remains fast. The cost is maintenance, so require a reason statement stored alongside the override. Periodically review that list after DuckStation updates, because the emulator may fix the underlying issue. Favor reversible changes and avoid broad flags that influence multiple systems when a narrower option exists to minimize unintended side effects.

Think in scopes to avoid conflict: global, systemwide categories like controller defaults, then per-game overrides. Rank choices by impact and risk. Visual correctness fixes usually deserve high priority because artifacts harm experience, while cosmetic improvements might wait. Audio desync and timing issues can justify overrides, but confirm the change does not create input lag or save incompatibility. Performance tweaks should be localized, since aggressive settings risk inconsistent frame pacing when reused elsewhere. A simple matrix helps: correctness before speed, speed before polish. If two options fix the same issue, prefer the one with the smallest blast radius, such as a per-title renderer toggle instead of rewriting global GPU behavior or altering timing that other games rely on.

Documentation and rollback are part of the framework. Keep a short changelog of game, reason, and options changed so you can undo failing experiments quickly. This is crucial when migrating to a new machine or comparing behavior across versions. For backup strategy, treat these files like source of truth for that title and store them with other configuration assets. If your library spans multiple platforms, note OS-specific dependencies. When in doubt, test with a fresh profile to ensure the override, not cached data, drives improvement. If you need fundamentals first, follow a full environment setup to confirm BIOS and paths are correct before chasing game-specific tuning, using a guide that covers install and configuration from a clean slate.

Examples and short scenarios

Renderer differences illustrate a classic use case. Suppose a 3D title shows geometry flicker under hardware rendering but displays correctly in software mode. Create a per-game setting that forces software rendering for that serial while leaving hardware mode globally for speed. Test movement-heavy scenes and UI overlays to ensure stability. The tradeoff is higher CPU demand, so if your device struggles, try reducing scaling only for that title instead. For organization, name the file by serial and store a short note that mentions the affected areas, like battle scenes or menus. Revisit this override after DuckStation updates to verify if hardware mode now behaves, then retire the temporary change to regain performance.

Input quirks often affect specific games, such as titles expecting an analog controller only during certain scenes. A per-game file can assign a DualShock profile for that title while your global config remains digital to match most classics. The benefit is predictable button mapping across the library with targeted exceptions. The limitation is fragmentation if multiple similar overrides accumulate. Consolidate by defining a sensible global controller layout and reserving per-game profiles only for required modes, like analog-only menus or vibration tests. When you manage saves, ensure memory card selection remains consistent so switching controller type does not incidentally point to a different card, which could confuse save discovery between discs or regional variants.

File organization matters for maintenance and portability. Keep per-game settings in a dedicated folder mirrored by serial names and region tags, and back them up with memory cards and save states before moving to a new PC. This discipline helps avoid orphaned overrides that no longer match your library structure. When adding many new titles, scan and organize the game library first so overrides align with correct file names and Redump-compliant cues. If you need to revisit foundational pieces like BIOS validation, follow a focused setup reference that covers legal acquisition and folder paths to ensure compatibility. After that, per-title files become smaller, safer touches rather than attempts to compensate for unstable global environments.

Looking ahead

Plan periodic audits so per-game settings remain lean and justified. After major DuckStation releases, re-test a shortlist of historically problematic titles, measure frame timing and visual correctness, and remove overrides that no longer help. Keep a living document that records what changed and why so your library becomes easier to maintain over time. When you add new games, try them under global defaults first to discover if the environment is already good enough. Only then consider selective overrides, maintaining your goal of minimal, high-value changes that reduce risk while preserving performance and consistency across platforms and operating systems.

As your collection grows, invest in repeatable structure. Store overrides in version control or routine backups alongside memory cards to enable clean migrations and recovery. Use clear branches or folders for test configurations so experiments never pollute your stable profile. When hardware changes, such as moving from laptop to desktop or Steam Deck, verify that any machine-specific settings are documented separately from game-specific ones. This separation avoids confusing differences where a per-game tweak attempts to mask a device limitation. Building these habits yields faster onboarding for new devices and easier collaboration if you share settings with friends who mirror your library layout.

Finally, align per-game overrides with upstream hygiene. Validate BIOS files and emulator directories once, then focus on organizing games with consistent formats for fewer surprises. When you face multi-disc titles or odd CUE arrangements, solve those library issues before writing overrides that treat symptoms. If the base is sound, per-title configuration becomes a precise tool that nudges compatibility rather than a crutch. Over time, you will create a small, well-labeled set of exceptions that enhance difficult titles while the majority run happily on global defaults, keeping maintenance predictable and your play sessions uninterrupted by configuration churn.

Frequently asked questions

Do per-game settings change my global configuration?

No. They override selected options when that title launches, leaving your global defaults intact for other games.

When should I prefer a global option over a per-game file?

Use a global option when the change improves most titles without harm. Reserve per-game files for fixes or requirements unique to specific games.

Can per-game overrides cause conflicts?

Yes. Conflicts arise when the same option exists at multiple scopes. Keep overrides minimal and document intent to avoid confusion.

How do I keep per-game settings organized?

Use serial-based filenames, store notes about the reason for each change, and back them up with your memory cards and saves.
