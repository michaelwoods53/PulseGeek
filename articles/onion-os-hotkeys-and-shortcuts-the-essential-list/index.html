Onion OS Hotkeys and Shortcuts: The Essential List

By Jordan Kelly • Published January 9, 2026

Here is a focused list of Onion OS hotkeys and shortcuts chosen for reliability, not novelty. Each entry explains what the shortcut does, where it lives in RetroArch or the frontend, and how to avoid unintended side effects. We tested common scenarios like swapping save states during a session, toggling overlays mid-battle, or cutting input lag while keeping visuals smooth, so you can apply the right shortcut without guessing.

Key takeaways

  • Use a dedicated hotkey enable button to prevent accidental triggers.
  • Favor per-core overrides when systems need unique shortcut behavior.
  • Fast forward and rewind trade responsiveness for battery and stability.
  • Overlay toggles help tune performance, then disable during gameplay.
  • Back up global configs before experimenting with shortcut remaps.

01) Global menu and safe exit

The core claim is that a reliable menu combo prevents progress loss and crashes when exiting Onion OS or returning to RetroArch. A common pattern is holding a Hotkey Enable button then pressing Start to open the Quick Menu, or Hotkey Enable plus Select to exit cleanly after saving. For example, on many handhelds the Hotkey Enable is mapped to the Menu or Function key, so Hold Hotkey then Start opens the in-game menu without affecting gameplay state. The tradeoff is that if Hotkey Enable is remapped or disabled, the same presses could trigger unintended system actions. That is why you should verify the Hotkey Enable mapping under Settings then Input in RetroArch and test it on a non-critical game before trusting it mid-session.

Another safe exit approach is using the frontend’s quit shortcut after creating a save state to guard against core-specific shutdown bugs. For instance, create Save State with Hotkey plus R2, confirm a brief stutter which signals the write, then use Hotkey plus Select to return to Onion OS. This sequence minimizes the chance of losing the last minutes of play if a core hangs during exit. The downside is slightly longer exit time and more steps, which can feel slow when hopping between titles. Accepting that small delay buys consistency across systems like SNES and PSX, where cores behave differently when interrupted, especially if shaders or run-ahead are active.

Section highlights

  • Confirm the Hotkey Enable mapping before trusting menu or exit combos.
  • Save state first, then quit, to avoid hangs during shutdown.

02) Save state create and load

Save states give fast checkpoints, but using clear hotkeys avoids overwriting progress. A typical setup maps Hotkey plus R2 to Save State and Hotkey plus L2 to Load State, so the triggers mirror chronology. For example, save at the start of a boss with Hotkey plus R2, then test the load with Hotkey plus L2 to confirm the slot works. The tradeoff is that save states are not cross-core safe, and some games need SRAM writes too. To reduce risk, pair quick saves with periodic in-game saves, and reserve Slot 0 as a throwaway while keeping Slot 1 as a stable anchor. This prevents accidental loads from erasing a long play session when muscle memory kicks in.

Organizing slots amplifies reliability. Map Increment State Slot to Hotkey plus D-pad Right and Decrement to Hotkey plus D-pad Left, so you can cycle without opening the menu. Say you maintain Slot 1 for stable progression, Slot 2 for experiments, and Slot 3 for speed practice. Cycling lets you set context on the fly, then Save State to the intended target. The tradeoff is increased complexity that can distract during action-heavy scenes. To manage that, rehearse slot changes during quiet moments, and enable on-screen notifications in RetroArch to show the active slot and confirm saves. When notifications briefly stutter, that is a healthy sign the write completed.

Section highlights

  • Map save and load to mirrored triggers for clear muscle memory.
  • Use slot cycling and notifications to prevent accidental overwrites.

03) Fast forward and slow motion

Fast forward helps skip grind, while slow motion aids tight inputs, and both map cleanly to hotkeys. A common pattern is Hotkey plus B to toggle fast forward and Hotkey plus Y to toggle slow motion, with a separate Hotkey plus D-pad Up to hold turbo temporarily. For example, speed through random encounters with the fast forward toggle, then snap back to normal when a boss appears. The tradeoff is higher CPU use and possible audio crackle while fast forwarding, especially on cores under heavy shaders. That is why you should combine this with a lighter shader preset for sessions that involve frequent speeding. Slow motion can introduce input delay, so use short bursts during practice rather than leaving it enabled throughout a level.

Another tactic is using a hold-to-boost mapping instead of a toggle for fast forward so accidental presses do not linger. Map Hold Fast Forward to Hotkey plus R1, which only accelerates while pressed. In a platformer, that makes rush sections easy to boost while preserving normal timing for jumps. The downside is hand fatigue if you hold the button for long stretches. If that becomes an issue, switch back to a toggle during long JRPG grinds and keep the hold mapping for action games. Balance depends on the system load and your play style, so test both in a consistent scene with an FPS overlay to observe frame pacing changes.

Section highlights

  • Use toggle or hold fast forward based on game pacing needs.
  • Pair speed changes with lighter shaders to avoid audio artifacts.

04) Rewind toggle and hold

Rewind is powerful for practice, but it stresses the device by recording recent frames, so map it deliberately. Many users map Hotkey plus X to Toggle Rewind and Hotkey plus L1 to Hold Rewind for short corrections. For example, when learning a tricky Mega Man jump, hold rewind to retake only the last second, then release and continue. The tradeoff is memory and battery cost, since cores buffer frames in the background, and some cores disable other latency features while rewinding. A safer approach is using hold-only mapping to minimize frame history when not needed. Also set a modest rewind buffer under Settings then Rewind, since extreme buffers can cause stutter when the device is already shader heavy.

Training mode benefits from pairing rewind with save states so you can step back to a known good setup if the buffer misses your window. Consider this flow: load your stable Slot 1, attempt a section, hold rewind for micro-corrections, then save to Slot 2 when it feels right. That sequence lets you alternate between coarse and fine time control without opening menus. The limitation is that frequent state writes can fragment session flow and slightly increase wear on storage, though modern cards handle this well. To minimize disruption, use on-screen notifications to confirm actions silently, and keep rewind disabled during normal play so the device can devote resources to stable performance.

Section highlights

  • Prefer hold-to-rewind for micro-fixes with lower overhead.
  • Combine rewind with stable save slots for structured practice.

05) Toggle FPS counter and performance overlays

Overlay hotkeys help you measure changes in real time, then get out of the way. Map Hotkey plus Start to open the Quick Menu and Hotkey plus D-pad Down to toggle the FPS counter, so you can flip metrics on and off without digging through submenus. For example, enable FPS before switching shaders or turning on run-ahead, then disable it after confirming steady 60 frames. The tradeoff is visual noise and a small performance hit, since some overlays draw every frame. A safer cadence is to profile for one minute after a change, take a mental note, and return to a clean screen. If you need deeper data, momentarily enable frame time graphs, then disable them for normal play.

When tuning responsiveness, pair overlays with a short test loop like a repeating camera pan in a safe area. Hit Hotkey plus D-pad Down to show FPS, toggle VSync or run-ahead, and watch for smoother frame times or reduced input latency. The limitation is that the FPS number alone cannot capture micro-stutter, so use frame time bars when diagnosing hitching. After finishing a tuning pass, turn overlays off to reclaim headroom and reduce distraction. Section highlights

  • Use overlays briefly to validate changes, then turn them off.
  • Check frame time graphs when FPS hides micro-stutter issues.

06) Screenshot and quick capture

Hotkeys for screenshots and brief recordings preserve moments without derailing play. A common mapping is Hotkey plus A for Screenshot and Hotkey plus R3 for Start Recording where supported. For example, capture a pixel-perfect scene right after you toggle a CRT shader, then compare it to a sharp pixel preset later. The tradeoff is that capture can impact performance or balloon storage, especially at higher resolutions or with filters active. To manage this, store captures on a dedicated folder and keep recordings short. If the device struggles during recording, disable heavy shaders or lower scaling for the duration. Screenshots are usually light, but confirm success with a discreet notification so you do not repeat captures needlessly.

Organizing captures helps you build a repeatable tuning library. Use date-stamped filenames and a subfolder per system so you can revisit settings that looked best on GBA versus SNES. Pair a screenshot taken with the FPS counter enabled to document the performance context, then another without overlays for clean presentation. The limitation is added housekeeping, which can distract during exploration sessions. To keep focus, reserve a few minutes at the end of play to move or rename files, rather than micro-managing mid-run. For tuning comparisons between shader presets and scaling approaches, you might also consult our guide on dialing shaders and scaling for clarity.

Section highlights

  • Keep captures short and use folders to manage storage usage.
  • Pair screenshots with overlays to document performance context.

07) Per-core hotkey overrides

Per-core overrides let you tailor hotkeys to each system so accidental conflicts vanish. The claim is simple: some consoles need different button priorities, so keeping a global Hotkey Enable alongside core-specific bindings avoids surprises. For example, a PSX core may benefit from moving Fast Forward to a shoulder button to prevent overlap with action buttons, while a GBA core can keep the default A and B mappings. The tradeoff is maintenance, since overrides multiply configurations. To control complexity, store notes in a small README inside the config folder and keep a consistent naming scheme for per-core files. If things go sideways, fall back to the global default and reintroduce changes one at a time.

Creating a minimal, readable config is easier than digging through menus repeatedly. The short example below shows input lines you can place in a per-core config to define a Hotkey Enable button and map fast actions predictably. Expectation is that after saving and restarting the core, Hotkey plus the bound button triggers the intended behavior only for that system. The tradeoff is portability, as these bindings may not fit other handheld layouts. Keep backup copies and confirm device-specific button indices before reusing.

Section highlights

  • Use per-core configs to avoid action conflicts on specific systems.
  • Back up bindings and confirm button indices before reusing mappings.

Frequently asked questions

Why do some hotkeys not work in certain cores?

Some cores override or ignore mappings to avoid conflicts with original hardware behavior. Set per-core overrides, verify the Hotkey Enable button, and test in a non-critical scene after saving the core config.

Is rewind safe to leave on all the time?

It works but costs memory and battery and can increase stutter. Use hold-to-rewind for short corrections, keep buffers modest, and disable rewind during normal play for better stability and responsiveness.

How do I prevent accidental save state overwrites?

Use mirrored save and load buttons, assign slot cycling, and reserve Slot 1 as a stable anchor. Enable on-screen notifications so you confirm writes and loads without pausing the game.

Do overlays reduce performance noticeably?

A small overhead is common and frame time graphs can add more. Enable overlays briefly to verify changes, then switch them off to regain headroom and avoid visual distraction during play.

Should I keep a single global mapping or per-core files?

Keep a sane global default for consistency, then add per-core overrides where conflicts appear. Back up configs and reuse a naming scheme so maintenance stays simple across devices.
